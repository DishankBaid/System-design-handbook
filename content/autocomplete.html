Search autocomplete, or typeahead, suggests completions while the user types: after "new y" it offers "new york weather" and "new york times". Each keystroke is a query that must come back in well under 100 ms or the suggestions trail behind the typing and become useless. The work splits cleanly in two: an offline pipeline that turns billions of logged searches into ranked suggestions, and an online path that answers prefix lookups from memory, with as many requests as possible never reaching a server at all.

How to use this case study

Sections follow the order of a real interview. Concepts used here have their own chapters: Search & Inverted Indexes, Caching, CDNs, Batch vs Stream Processing, Sharding.

1. Requirements

Functional

Given a prefix, return the top 5 to 10 completions ranked mostly by popularity. Reflect trending searches within minutes (breaking news). Light personalisation from the user's own recent searches. Never suggest offensive, dangerous or personal-data completions.

Non-functional

Under 100 ms from keystroke to rendered suggestions, so server time must be a few milliseconds at p99. Very high availability: if suggestions fail the search box must still work. Read-heavy at enormous scale; suggestions may be hours stale for the long tail.

Out of scope

Spelling correction, multi-language tokenisation and the search results page itself. Mention spelling correction as a separate "did you mean" service.

The key observation: the answer for a prefix changes slowly, but it is requested constantly. "new y" has the same top suggestions for hours. So precompute the answer for every prefix, keep it in memory, and cache it everywhere between the server and the keyboard.

2. Estimation

Assume 500 million searches per day, about 20 characters typed per search, and a vocabulary of the 100 million most frequent queries over the last few weeks.

Two conclusions. The whole index fits in the memory of a handful of machines, so the online path is pure in-memory lookups and the scaling problem is request volume, which caching attacks directly. And the expensive work, counting and ranking billions of queries, belongs in an offline pipeline that runs on its own schedule.

    { "text": "new york times",   "kind": "popular" },
    { "text": "new year 2027",    "kind": "trending" },
    { "text": "new york knicks",  "kind": "history" }   // only when personalised

Normalise the prefix before anything else (lowercase, collapse whitespace, strip accents where the locale allows) so that "New Y", "new y" and "new y" share one cache entry. The public part of the response is identical for every user with the same prefix and locale, which is what makes CDN and browser caching possible. Personal history is either merged in on the client from local storage or fetched with a separate, uncached call, so it never pollutes shared cache entries.

5. High-level design

  1. Type. The client waits until typing pauses briefly, normalises the prefix, and checks its own cache of recent prefix responses.
  2. Edge. On a miss, the request goes to a CDN edge, which serves popular prefixes such as "new" or "how to" from cache for a few minutes.
  3. Serve. On an edge miss, a suggest server routes the prefix to the trie shard that owns it, reads the precomputed top-k at the prefix's node, merges trending entries from the overlay, applies the blocklist, and responds in a couple of milliseconds.
  4. Learn. Every completed search is logged. The offline pipeline aggregates logs into counts, builds new trie snapshots, and the servers swap them in. A streaming job updates the trending overlay every minute.

6. Deep dive: a trie with top-k at every node

A trie (prefix tree) stores strings character by character, so all queries that start with "new" sit under one node. Finding that node takes as many steps as the prefix has characters. The naive next step, walking the whole subtree to find the most popular completions, is far too slow for a short prefix like "n" whose subtree holds millions of queries. The fix is to precompute and cache the top k completions at every node when the trie is built. A lookup then costs O(len(prefix)) and returns a list that is already sorted.

import heapq

K = 3                                   # suggestions kept per node (5-10 in production)
BLOCKED = {"buy fake passport"}         # filtered at build time, never stored


class Node:
    __slots__ = ("children", "top")

    def __init__(self):
        self.children = {}
        self.top = []                   # [(count, query)], best first


class Trie:
    def __init__(self):
        self.root = Node()

    def add(self, query, count):
        """Insert or update a query; refresh the top-k list on every node of its path."""
        if query in BLOCKED:
            return
        node, path = self.root, [self.root]
        for ch in query:
            node = node.children.setdefault(ch, Node())
            path.append(node)
        for n in path:
            others = [entry for entry in n.top if entry[1] != query]
            n.top = heapq.nlargest(K, others + [(count, query)])

    def suggest(self, prefix):
        node = self.root
        for ch in prefix:               # O(len(prefix)), then the answer is precomputed
            node = node.children.get(ch)
            if node is None:
                return []
        return [q for _, q in node.top]


weekly_counts = {                       # aggregated from query logs
    "netflix": 120_000, "new york weather": 90_000, "news": 80_000,
    "new balance": 60_000, "nearest pharmacy": 45_000, "nest thermostat": 30_000,
    "how to tie a tie": 70_000, "how to screenshot": 65_000, "how tall is mount everest": 20_000,
    "buy fake passport": 5_000,
}
trie = Trie()
for q, c in weekly_counts.items():
    trie.add(q, c)

for prefix in ("ne", "new", "how t", "nes", "buy"):
    print(f"{prefix!r:8} -> {trie.suggest(prefix)}")
# 'ne'     -> ['netflix', 'new york weather', 'news']
# 'new'    -> ['new york weather', 'news', 'new balance']
# 'how t'  -> ['how to tie a tie', 'how to screenshot', 'how tall is mount everest']
# 'nes'    -> ['nest thermostat']
# 'buy'    -> []
trie.add("news", 130_000)               # an election night pushes "news" up
print(f"{'new'!r:8} -> {trie.suggest('new')}")
# 'new'    -> ['news', 'new york weather', 'new balance']
  • Memory. Storing k entries at every node multiplies memory, so nodes store small integer query ids, not strings, and the strings live once in a side table. Character-per-node tries also waste space on long unbranched chains; a radix tree merges them into single edges labelled with whole substrings.
  • Updates only go up. The incremental add above handles a query becoming more popular. It cannot handle one becoming less popular: a node that evicted an entry from its top-k has forgotten it and cannot bring it back. That is one reason the trie is rebuilt from counts on a schedule rather than mutated forever.
  • Alternatives. A flat key-value table from every prefix to its top-k list (500 million keys) is simpler to shard and to serve from a generic KV store, at the cost of more memory. Search engines such as Elasticsearch implement completion suggesters with finite-state transducers, which compress shared prefixes and suffixes far better than a plain trie.

7. Deep dive: building suggestions from query logs

  • Aggregate with decay. A daily batch job counts queries per locale over the last few weeks, weighting recent days more, for example a weight that halves every 7 days. "world cup" fades after the tournament without a hard cutoff. Only queries above a minimum count (say, searched by at least 50 distinct users) qualify, which also keeps one person's private search out of everyone's suggestions.
  • Filter. Remove queries matching the blocklist (slurs, violent and sexual terms, dangerous goods), queries that look like personal data (phone numbers, emails, street addresses), and completions about named people that pair them with harmful claims. Filtering at build time keeps them out of memory; a second check at serve time catches terms added to the blocklist since the last build.
  • Build and validate. Build one trie per shard, write it as an immutable snapshot, and run checks before publishing: size within a few percent of the last build, known canary prefixes ("weather", "facebook") still returning their expected top results, no blocked term present. A bad build is never published.
  • Trending. A stream job counts queries over a sliding one-hour window (a Count-Min sketch plus a small heavy-hitters heap keeps memory bounded) and flags those far above their usual rate for that hour. Only a few thousand trending queries exist at a time, so the overlay is tiny and rebuilt every minute. At serve time, the server merges overlay entries into the trie's top-k with a boost, and the overlay entries pass through the same blocklist.

Why not update the trie in place from the stream? Updating top-k lists along every query's path at tens of thousands of searches per second means constant writes to shared, read-hot structures, and decreasing popularity cannot be handled incrementally anyway. Rebuild-and-swap keeps the serving path read-only, which is simpler and faster.

8. Deep dive: serving, sharding and caching

Sharding by prefix

Hashing the full prefix spreads load evenly and suits the flat prefix → top-k table, because every answer is precomputed offline. It cannot split a trie, though: "new", "new " and "new y" would land on different shards, and each shard would need every node on their path. Range sharding on the first one or two characters keeps every prefix's subtree together. The cost is skew, which is handled by cutting ranges by traffic and by giving hot shards more replicas. At 65 GB in total, each of 4 to 7 shards fits comfortably in RAM.

Fewer requests: debouncing and caching

The cheapest request is the one never sent. Step through someone typing "new york" with a pause after "new ".

  • Debounce on the client: wait 100 to 150 ms after the last keystroke. Also cancel in-flight requests for prefixes that are no longer current, and ignore responses that arrive out of order, so a slow response for "ne" never overwrites suggestions for "new".
  • Browser cache. Responses carry Cache-Control: max-age=300, so backspacing from "new y" to "new" is instant and free. The client can also keep an in-memory map of the last few dozen prefixes.
  • CDN cache. Short, popular prefixes dominate traffic and are identical for every user in a locale, so an edge cache with a few minutes of TTL absorbs a large share of requests. The cache key is the normalised prefix plus locale, nothing else. The TTL bounds how stale trending suggestions can be.
  • Prefetch. When the search box gains focus, fetch suggestions for the empty prefix (trending and recent searches); some products also prefetch the next likely character's list.

Personalisation and filtering at serve time

Personal suggestions are the user's own recent searches that match the prefix, ranked above popular ones. They are merged on the client from local history, or by a separate per-user call that bypasses the CDN, so shared caches only ever hold public answers. Some products also re-rank public suggestions by coarse signals such as location ("weather" completes to the user's city), which means adding that signal, at low resolution, to the cache key. The serve-time blocklist check runs on every merged list, including history and trending entries, and there is a fast path for operators to add a term and have it disappear from suggestions within minutes, without waiting for the next build.

10. Key trade-offs to state

  • Precomputed top-k per node: answers in O(prefix length) with no subtree walk, in exchange for memory and an offline rebuild instead of live updates.
  • Batch plus streaming: stable rankings from complete data, with a small, fast overlay for trends; two pipelines to run.
  • Range sharding by prefix: every lookup hits one shard, in exchange for skewed ranges that must be rebalanced from measured traffic at each build.
  • Aggressive caching: most requests never reach a server, in exchange for suggestions up to a few minutes stale.
  • Public and personal answers kept apart: shared caches stay safe and effective, at the cost of a client-side merge.
Interview angle

What the interviewer is checking

Whether you see that the online path must be precomputed and in memory, can describe a trie with cached top-k and its memory cost, separate the data pipeline from serving, and use the client and the CDN to cut traffic.

Follow-ups to expect

  • How do you get the top 10 completions for "a" without scanning millions of queries?
  • How often do you rebuild, and how does a breaking-news query appear within minutes?
  • The trie does not fit on one machine. How do you split it?
  • How do you stop an offensive suggestion from appearing, and how fast can you remove one?
  • How would you add personalisation without ruining caching?
  • What happens on the client if the user types faster than responses arrive?

Red flags

  • Running LIKE 'prefix%' queries against a database on every keystroke.
  • Walking the trie subtree at request time to rank completions.
  • Updating counts in the serving trie on every search.
  • Caching personalised responses at the CDN.
  • No debouncing or request cancellation on the client.
