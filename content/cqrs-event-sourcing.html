Why it matters

A bank account table with a balance column answers "how much money is in account 42?" and nothing else. It cannot say what the balance was on 3 March, why it dropped by $90 on Tuesday, or whether a bug last month double-charged anyone. Accountants solved this centuries ago: they never overwrite a balance, they append entries to a ledger and derive the balance by adding them up.

Two related patterns bring that idea into software. Event sourcing stores every change to an entity as an immutable event and derives current state by replaying them. CQRS (Command Query Responsibility Segregation) splits the model that handles writes from the models that serve reads, so each can have the shape its job needs. They are often used together, because an event log is a natural way to feed many read models, but each is useful on its own.

Both are powerful and both are expensive. Interviewers bring them up to see whether you know what they buy, what they cost, and when a plain table with an audit log is the better answer.

CQRS: separate models for writing and reading

In a typical CRUD service, one model (one set of tables, one ORM entity) handles both the commands that change data and the queries that read it. That works until the two pull in opposite directions. Writes want normalised data and strict invariants ("a withdrawal may not overdraw the account"). Reads want denormalised, pre-joined data in many shapes: the account page wants balance plus last 20 transactions, the fraud team wants spend per merchant per hour, search wants full-text over payees.

CQRS gives each side its own model:

  • The write model receives commands (Withdraw(acc-42, 9000)), loads the relevant entity, checks business rules, and records the change. In domain-driven design terms, the unit of consistency is an aggregate: one account, one order, one cart. A command touches exactly one aggregate, inside one transaction.
  • One or more read models are built from the changes, each optimised for specific queries and stored wherever fits best: a SQL table, an Elasticsearch index, a Redis hash, a data warehouse.
  • Projections (or projectors) are the code that turns changes into read-model updates: on Withdrawn, subtract from account_summary.balance and insert into recent_transactions.

Read-model lag

Projections run asynchronously, so a read model is always slightly behind the write model: typically tens of milliseconds, seconds under load, and arbitrarily long if a projector is down. The classic bug: a user withdraws $50, the page reloads from account_summary, and the old balance is still there. Ways to handle it:

  • Return the new state from the command. The write side knows the new balance; send it back and let the client render it.
  • Version tokens. The command returns the aggregate version it produced (v1002). The query passes it along, and the query API waits briefly until the projection has processed v1002, or reads from the write side if it has not.
  • Design the UI for it: show the transaction as "pending" until the read model confirms it, as banking apps commonly do.
  • Monitor it. Projection lag (newest event position minus the projector's checkpoint) is the key health metric, exactly like consumer lag in event streaming.

CQRS without event sourcing

CQRS does not require events as the source of truth. A service can write to normalised PostgreSQL tables and maintain read models from them via change data capture, an outbox, or simply a materialised view. Shipping product data from a relational database to Elasticsearch for search is CQRS in everything but name. This lighter form captures most of the benefit (read models shaped for queries, scaled independently) with far less machinery, and it is the version worth proposing first in an interview.

Event sourcing: state as a fold over events

In an event-sourced system the events are the database. The account table does not exist; there is only the stream for acc-42: Opened, Deposited, Withdrawn, and so on. Current state is computed by starting from an empty state and applying each event in order. In functional terms, state is a left fold over the event stream: state = reduce(apply, events, initial).

A command handler follows the same three steps every time: load the aggregate by folding its stream, decide whether the command is allowed given that state, and append the resulting events. The apply function never validates or fails, because the events it applies already happened; all business rules live in the decision step.

The event store

An event store is a database optimised for this access pattern. Its core operations are small:

  • Append to a stream with an expected version. append("acc-42", events, expected_version=1002) fails if another writer appended first. This is optimistic concurrency control: two concurrent withdrawals both read version 1002, the first append succeeds, the second gets a conflict and retries against the new state, so the overdraft check cannot be bypassed by a race.
  • Read a stream in order, from a given version.
  • Subscribe to all events in a global order, from a checkpoint, which is what projectors use.

Purpose-built stores (EventStoreDB, Axon Server) provide these directly. Many teams instead use PostgreSQL with an events table and a unique constraint on (stream_id, version), which gives optimistic concurrency for free, or DynamoDB with a conditional put. Kafka is a poor primary event store: it has no per-entity streams to read efficiently and no way to append conditionally on an entity's version, though it is a fine transport for publishing events onward.

Snapshots

Folding 30 events per load is free. Folding 2 million events for a busy corporate account on every command is not. A snapshot stores the folded state at some version; loading becomes "read the latest snapshot, then fold only the events after it". Snapshots are a cache: they can be deleted and recomputed at any time, and they must be discarded when the apply logic changes in a way that would produce a different state.

Take snapshots only where the numbers demand it. Most aggregates in a well-designed model have short streams (an order rarely exceeds 50 events), and adding snapshots everywhere adds a second representation of state to keep correct.

Versioning events: upcasting

Events are immutable and kept forever, but the code that reads them changes. When Deposited moves from a float in dollars to integer cents, the old events are not rewritten. Instead an upcaster converts old versions to the current shape as they are read, so apply only ever handles the latest version. Rules that keep this manageable: version every event type from day one, make only additive changes where possible, write an upcaster for each breaking change, and keep a test suite of real historical events that must still load. For changes too large to upcast, the last resort is to copy the stream into a new one with transformed events, which is a migration with all the usual risks.

Replays and new read models

This is event sourcing's best feature. A new requirement arrives: "show customers their average monthly spend for the last two years". With a CRUD table, the history needed may not exist. With an event store, you write a new projection, start it at position zero, let it replay years of events into a new table, and switch the query API over when it has caught up. The same mechanism fixes bugs: if a projection had a bug for three weeks, fix the code, wipe the read model, and replay.

Replays have operational cost. Projections must be idempotent and deterministic (no calling external APIs or reading the clock), replays need throughput (see the worked example), and a replay must not re-trigger side effects such as emails. Side-effecting handlers are kept separate from projections and track their own checkpoint so they never run against old events.

Temporal queries

Because every change is recorded with its time, past state is a fold over a prefix of the stream: "what was the balance at the end of day 3?" means folding only the events up to day 3. This answers audit questions ("what did the system believe when it approved this loan?"), supports debugging by replaying the exact sequence that led to a bad state, and enables "as of" reports without designing history tables in advance.

Implementation: an event-sourced account

A complete, minimal event-sourced aggregate: pure apply, an upcaster for a legacy event version, an in-memory store with optimistic concurrency, snapshots, a command handler that enforces "no overdraft", and a temporal query.

from dataclasses import dataclass, replace
from functools import reduce


@dataclass(frozen=True)
class Account:
    id: str = ""
    owner: str = ""
    balance_cents: int = 0
    version: int = 0          # number of events applied: used for optimistic concurrency


def upcast(e: dict) -> dict:
    """v1 events stored dollars as a float; v2 uses integer cents. Old events are never rewritten."""
    if e.get("v", 1) == 1 and e["type"] in ("Deposited", "Withdrawn"):
        e = {**e, "v": 2, "amount_cents": round(e.pop("amount") * 100)}
    return e


def apply(state: Account, e: dict) -> Account:
    """Pure function: state + event -> new state. No validation, no I/O: the event already happened."""
    e = upcast(dict(e))
    if e["type"] == "Opened":
        state = replace(state, id=e["account"], owner=e["owner"])
    elif e["type"] == "Deposited":
        state = replace(state, balance_cents=state.balance_cents + e["amount_cents"])
    elif e["type"] == "Withdrawn":
        state = replace(state, balance_cents=state.balance_cents - e["amount_cents"])
    return replace(state, version=state.version + 1)


class ConcurrencyError(Exception):
    pass


class EventStore:
    def __init__(self):
        self.streams, self.snapshots = {}, {}

    def append(self, stream, events, expected_version):
        log = self.streams.setdefault(stream, [])
        if len(log) != expected_version:          # someone else appended first
            raise ConcurrencyError(f"{stream}: expected v{expected_version}, found v{len(log)}")
        log.extend(events)

    def load(self, stream, use_snapshot=True):
        state, start = Account(), 0
        if use_snapshot and stream in self.snapshots:
            state = self.snapshots[stream]
            start = state.version
        tail = self.streams[stream][start:]
        return reduce(apply, tail, state), len(tail)

    def snapshot(self, stream):
        self.snapshots[stream] = self.load(stream)[0]


def withdraw(store, account_id, cents, day):
    """Command handler: rebuild state, check the invariant, append the new fact."""
    acct, _ = store.load(account_id)
    if cents > acct.balance_cents:
        raise ValueError(f"insufficient funds: {acct.balance_cents} < {cents}")
    store.append(account_id, [{"type": "Withdrawn", "v": 2, "amount_cents": cents, "day": day}],
                 expected_version=acct.version)


store = EventStore()
store.append("acc-42", [{"type": "Opened", "account": "acc-42", "owner": "Ana", "day": 1},
                        {"type": "Deposited", "v": 1, "amount": 120.50, "day": 1}], 0)   # legacy v1
for day in range(2, 1001):                       # 999 days: deposit $100 on odd days, spend $90 on even
    kind, cents = ("Deposited", 10_000) if day % 2 else ("Withdrawn", 9_000)
    store.append("acc-42", [{"type": kind, "v": 2, "amount_cents": cents, "day": day}], day)

state, replayed = store.load("acc-42")
print(f"balance ${state.balance_cents / 100:.2f} at v{state.version}, replayed {replayed} events")
store.snapshot("acc-42")
withdraw(store, "acc-42", 5_000, day=1001)
state, replayed = store.load("acc-42")
print(f"balance ${state.balance_cents / 100:.2f} at v{state.version}, replayed {replayed} after snapshot")

# Temporal query: what was the balance at the end of day 3? Fold only the events up to then.
as_of = reduce(apply, (e for e in store.streams["acc-42"] if e["day"] <= 3), Account())
print(f"balance at end of day 3: ${as_of.balance_cents / 100:.2f}")

# Two concurrent withdrawals both read v1002; the second append is rejected.
stale = store.load("acc-42")[0].version
store.append("acc-42", [{"type": "Withdrawn", "v": 2, "amount_cents": 100, "day": 1002}], stale)
try:
    store.append("acc-42", [{"type": "Withdrawn", "v": 2, "amount_cents": 100, "day": 1002}], stale)
except ConcurrencyError as err:
    print("rejected:", err)

Output:

balance $5020.50 at v1001, replayed 1001 events
balance $4970.50 at v1002, replayed 1 after snapshot
balance at end of day 3: $130.50
rejected: acc-42: expected v1002, found v1003

The first load folds all 1,001 events, including the legacy v1 deposit, which the upcaster converts on the fly. After the snapshot, the next load folds a single event. The temporal query is just a fold with a filter. And the second of two concurrent appends at the same expected version is rejected, which is what makes the overdraft check safe without locks.

Deletion, GDPR and crypto-shredding

An append-only store collides with the right to erasure. A customer asks to be forgotten, and their name, address and email are in hundreds of immutable events, in snapshots, in every read model, and in backups. Options:

ApproachHowTrade-off
Keep personal data out of eventsEvents reference customer_id; the personal data lives in a separate, mutable storeSimplest; erasure is a normal delete. Events lose some self-containment
Crypto-shreddingEncrypt personal fields in each event with a per-customer key held in a key store. To erase, delete the keyEvents stay immutable, the data becomes unreadable everywhere, including backups (as long as key-store backups do not keep the key). Needs key management and a plan for projections that held decrypted copies
Rewrite the streamCopy the stream without the personal data and delete the originalBreaks immutability and audit guarantees; operationally risky

In practice teams combine the first two: personal data is stored separately where possible, and anything that must appear in events is encrypted with a per-subject key. Read models are ordinary mutable stores and must also delete the data, usually by reacting to a CustomerForgotten event.

When not to use them

Most systems should not be event-sourced, and most CQRS benefits are available without it. Warning signs that the patterns will cost more than they return:

  • The domain is CRUD. A product catalogue edited through forms, where nobody asks how a field reached its current value, gains nothing from an event history. An updated_at column and an audit table cover it.
  • Queries need current state across many entities, immediately. "Find all accounts with balance below zero" is easy in a table and needs a projection (with lag) in an event-sourced system.
  • The team is new to it. Upcasting, projections, replays, snapshots, idempotent handlers and eventual consistency are each manageable; learning all of them at once on a deadline is how event-sourced projects fail.
  • Applied to the whole system. Event sourcing is a per-aggregate or per-service decision. Use it where history is the product (ledgers, orders, inventory movements, workflows) and keep everything else as plain tables.
Common mistake

Treating internal event-sourcing events as the integration contract for other services. Internal events are shaped by one aggregate's implementation and change with it. Publish separate, deliberately designed integration events (see Event-Driven Architecture), or every refactoring becomes a cross-team schema migration.

Worked example: a bank ledger

A digital bank has 10 million accounts averaging 50 transactions per month, and wants every balance change auditable for seven years. Each event is about 300 bytes. Ledgers are the textbook fit: history is the product, regulators ask "as of" questions, and the invariant (no unauthorised overdraft) is per account, which matches one aggregate per account.

Events 10M accounts × 50 / month = 500M events/month Write rate 500M / (30 × 86,400 s) ≈ 190 events/s average (peaks of a few thousand on payday) Storage 500M × 300 B = 150 GB/month ≈ 1.8 TB/year, ~12.6 TB for 7 years Typical stream 50 × 12 = 600 events/year → ~4,200 after 7 years; folds in about a millisecond Busy accounts a payroll account: 2M events/year → snapshot every 1,000 events, fold ≤ 1,000 New projection 7 years × 6B = 42B events at 50,000/s ≈ 233 hours single-threaded partitioned by account over 20 workers ≈ 11.7 hours

The design that falls out: PostgreSQL as the event store, partitioned by month, with a unique (account_id, version) constraint for optimistic concurrency; snapshots for any stream above 1,000 events (most accounts within two years), or "closing the books" with one stream per account per year that opens with the carried-forward balance; three projections (balances and recent transactions in PostgreSQL, payee search in Elasticsearch, monthly statements in the warehouse); and a projection framework that can replay in parallel by account, because a projection that takes ten days to rebuild single-threaded is a projection nobody dares to fix. Personal data lives in a customer service; ledger events only carry account ids, so erasure never touches the ledger.

In the real world

  • Banking and accounting ledgers are event-sourced by nature: double-entry bookkeeping appends entries and never edits a posted one. Modern ledger databases and core banking systems keep the same model.
  • EventStoreDB (since renamed KurrentDB) is a database built for event sourcing, with streams, expected-version appends and persistent subscriptions for projections.
  • Axon Framework and Axon Server provide aggregates, command and event buses, sagas and an event store for Java applications.
  • LMAX, a retail foreign-exchange exchange, runs its business logic single-threaded in memory and recovers by replaying its journal of input events; Martin Fowler's write-up describes it handling 6 million orders per second on one thread. It shows event sourcing as a performance tool, not just an audit one.
  • Git is a familiar analogy: commits are immutable events, the working tree is a projection, and checking out an old commit is a temporal query.
Interview angle

When to bring it up

When the problem involves money, inventory, or any domain where "how did we get here?" matters (ledgers, wallets, order lifecycles), or when reads and writes have very different shapes and scale (a write-light system with many read views, a news feed with precomputed timelines). Lead with the light version: "writes go to a normalised store, read models are projections updated asynchronously". Add event sourcing only when audit and history are requirements.

Follow-ups to expect

  • A user updates something and does not see it. Why, and what do you do? (Read-model lag; return state from the command, version tokens, pending UI.)
  • How do two concurrent commands on the same aggregate not violate an invariant? (Expected-version append, retry on conflict.)
  • Loading an aggregate is slow. (Snapshots, or a smaller aggregate boundary.)
  • The event format must change. (Version events, upcast on read, never rewrite history.)
  • A user invokes the right to be forgotten. (Data separation, crypto-shredding, deleting from read models.)

Red flags

  • Event sourcing the whole system, including simple CRUD entities.
  • Using Kafka as the event store for aggregates and loading state by scanning a topic.
  • Projections that send emails or call APIs, so a replay re-sends a year of notifications.
  • Ignoring read-model lag, or claiming CQRS gives strongly consistent reads.
