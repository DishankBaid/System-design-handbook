Why it matters

Replication copies the same data to more machines. That helps reads and availability, but every replica still holds all the data and the leader still takes every write. When the dataset no longer fits on one machine, or the write rate exceeds what one machine can absorb, you have to split the data itself. Sharding (or partitioning) gives each machine a different subset of the rows, so capacity grows with the number of machines.

The usual triggers, with rough numbers for a well-provisioned relational node:

  • Data size. Beyond a few tens of terabytes, backups, restores, index builds and replica rebuilds take many hours, and the working set no longer fits in memory.
  • Write throughput. Tens of thousands of writes per second is where a single primary's WAL, locks and disk start to saturate.
  • Blast radius. One giant database is one giant outage. Eight shards means a bad shard affects an eighth of users.

Sharding is not free. Queries that span shards get slower, transactions across shards need special protocols, and moving data between shards while serving traffic is one of the harder operations in infrastructure. The whole game is choosing a partitioning scheme that keeps the common operations on a single shard. In practice each shard is itself replicated, so the two techniques combine: Replication for copies, sharding for capacity.

Partitioning strategies

Every scheme answers one question: given a key, which shard owns it? The three families differ in whether neighbouring keys stay together.

Range partitioning

Assign contiguous key ranges to shards: a to f on shard 1, g to m on shard 2, and so on, like volumes of an encyclopedia. A router keeps the table of split points. Range scans (WHERE name BETWEEN 'g' AND 'h', "all events for sensor 17 in October") touch only the shards covering the range, often one. Split points can follow the data: when a range grows too big, split it in two. HBase regions, Bigtable tablets, CockroachDB and TiDB ranges, and MongoDB ranged sharding all work this way.

The weakness is skew. If the key increases over time (a timestamp, an auto-increment id), every new write lands in the last range, so one shard takes all inserts while the others idle. The standard fix is to put something with spread in front: key by (sensor_id, timestamp) instead of timestamp, so writes spread across sensors and each sensor's history stays contiguous.

Hash partitioning

Hash the key and partition by the hash: shard = owner_of(hash(key)). A good hash spreads even sequential keys uniformly, so load is balanced as long as no single key is hot. Cassandra (Murmur3 tokens), DynamoDB, Redis Cluster and MongoDB hashed sharding work this way. The cost is that neighbouring keys end up on different shards, so a range query on the key has to ask every shard.

Never use hash(key) % N directly: changing N moves almost every key. Map hashes to a fixed set of slots or tokens instead, as described in Consistent Hashing. A useful hybrid, popularised by Cassandra and DynamoDB, is a compound key: hash the first part to choose the shard, keep rows sorted by the second part within it. PRIMARY KEY ((user_id), created_at) spreads users across the cluster and keeps each user's timeline as one sorted range on one node.

Directory-based partitioning

Keep an explicit lookup table from key (or tenant) to shard, stored in a small, replicated, heavily cached service. It is the most flexible scheme: you can place a large customer on dedicated hardware, move one tenant without touching others, or keep a country's data in its region. The cost is an extra lookup on every request (mitigated by caching), and a critical component that must never be wrong or unavailable. Multi-tenant SaaS systems often use it at the tenant level, with hash partitioning inside each shard.

Choosing a shard key

The shard key (partition key) is the column that decides placement. It is the most consequential and least reversible decision in a sharded design, because changing it means rewriting every row. Judge candidates on four properties:

  1. Cardinality. Many more distinct values than shards, so data can always be split further. country has about 200 values and one of them is the United States; it is a poor shard key on its own.
  2. Even data and load. Not only rows but requests must spread. A key with uniform row counts can still concentrate traffic.
  3. Query isolation. The hottest queries should include the shard key so they run on one shard. A design where the main query fans out to every shard has thrown away most of sharding's benefit.
  4. Locality for transactions. Rows updated together should share a shard key, so the transaction stays on one node. Tenant id in a SaaS product is the classic winner: almost every query and transaction is within one tenant.

Hotspots and celebrity keys

Hashing balances keys, not traffic. A celebrity with 100 million followers, a viral product, or one huge enterprise tenant can send a large fraction of all requests to one key, and therefore one shard. This simulation sends one million requests from 100,000 users with Zipf-like popularity to 16 hash-partitioned shards, then salts the ten hottest keys:

import hashlib
import random
from collections import Counter

SHARDS = 16


def shard_of(key: str) -> int:
    return int.from_bytes(hashlib.md5(key.encode()).digest()[:8], "big") % SHARDS


def load_per_shard(requests, hot_keys=frozenset(), salt_buckets=1, rng=None):
    load = Counter()
    for user in requests:
        key = f"user:{user}"
        if user in hot_keys:                       # spread a hot key over several sub-keys
            key += f"#{rng.randrange(salt_buckets)}"
        load[shard_of(key)] += 1
    return [load[s] for s in range(SHARDS)]


rng = random.Random(42)
users = range(1, 100_001)
weights = [1 / u ** 1.1 for u in users]           # Zipf-like popularity: user 1 is a celebrity
requests = rng.choices(users, weights, k=1_000_000)

plain = load_per_shard(requests)
top = {u for u, _ in Counter(requests).most_common(10)}
salted = load_per_shard(requests, top, salt_buckets=16, rng=rng)

mean = len(requests) / SHARDS
print(f"top user's share of all requests: {Counter(requests)[1] / len(requests):.1%}")
print(f"busiest shard / mean, plain keys:   {max(plain) / mean:.2f}x")
print(f"busiest shard / mean, top 10 salted: {max(salted) / mean:.2f}x")

for fanout in (1, 4, 16, 64):                      # tail-latency amplification of scatter-gather
    print(f"fan-out {fanout:2}: {1 - 0.99 ** fanout:5.1%} of queries wait on at least one shard's p99")
# top user's share of all requests: 13.5%
# busiest shard / mean, plain keys:   2.99x
# busiest shard / mean, top 10 salted: 1.30x
# fan-out  1:  1.0% of queries wait on at least one shard's p99
# fan-out  4:  3.9% of queries wait on at least one shard's p99
# fan-out 16: 14.9% of queries wait on at least one shard's p99
# fan-out 64: 47.4% of queries wait on at least one shard's p99

Ways to deal with a hot key, roughly in order of preference:

  • Cache it. If the hot traffic is reads, a cache in front (or an in-process cache for the top few keys) absorbs it before it reaches the shard. See Caching.
  • Salt it. Append a suffix, user:1#0 to user:1#15, and write to a random one. Writes spread across 16 shards; reads must gather all 16 sub-keys and merge. Good for counters and append-only data, and worth doing only for keys known to be hot, since every read of them now fans out.
  • Isolate it. With a directory or range scheme, give the hot tenant its own shard or hardware.
  • Change the data model. Twitter's answer for celebrity tweets was not to fan them out on write at all, but to merge them at read time. See the news feed case study.

Secondary indexes on sharded data

The shard key answers "where is user 42?". It does not answer "which user has email asha@example.com?". Sharded systems offer two kinds of secondary index, and the difference shapes query cost.

Local (document-partitioned)Global (term-partitioned)
Index livesOn each shard, covering that shard's rowsIn its own shards, partitioned by the indexed value
WriteSame shard, same transactionSecond shard, usually asynchronous
Read by indexed valueAsk every shardOne index shard, then the data shard(s)
FreshnessUpdated with the data on the same shard (Elasticsearch: after a ~1 s refresh)May lag behind writes
ExamplesDynamoDB LSI, MongoDB, Elasticsearch, Cassandra secondary indexesDynamoDB GSI (eventually consistent), CockroachDB and Spanner indexes (transactional)

Distributed SQL databases maintain global indexes transactionally, paying a cross-node commit on writes. Many teams skip built-in secondary indexes and maintain a second table keyed by the lookup value (users_by_email), which is a global index managed by hand.

Cross-shard queries and joins

A query without the shard key becomes scatter-gather: send it to every shard, wait for all of them, merge the results. Two costs grow with the number of shards. Total work grows linearly, since every shard does the work even if most return nothing. And latency is set by the slowest shard: if each shard is slow 1% of the time, the simulation above shows a 64-shard query waits on a slow shard 47% of the time. This is tail latency amplification, and it is why fan-out queries belong off the hot path.

Joins follow the same logic. A join between two tables sharded on the same key, for the same key value, runs locally on one shard: orders and order_items both sharded by user_id join without any network traffic. Citus calls these co-located tables. Small, rarely changing tables (countries, currencies, product categories) are copied to every shard as reference tables so any shard can join against them. Everything else is either denormalized at write time, joined in the application, or sent to an analytics system that is built for big scans. Transactions across shards need two-phase commit or a saga; see Distributed Transactions.

Resharding without downtime

Data grows unevenly, so you will need to move it. The partitioning scheme decides how painful that is.

Fixed number of partitions

Create many more logical partitions than machines at the start, for example 1,024 for a 16-node cluster, and move whole partitions when nodes join. The key-to-partition mapping never changes. Redis Cluster (16,384 slots), Couchbase (1,024 vBuckets) and Elasticsearch (primary shard count set at index creation) work this way. Pick the count for the largest cluster you expect.

Dynamic splitting

Start with one range and split it when it exceeds a size or load threshold, then move halves to balance. The number of partitions tracks the data. HBase, CockroachDB and DynamoDB split automatically (CockroachDB and DynamoDB also split on load for hot ranges); MongoDB balances chunk ranges by data size.

Logical shards on physical hosts

The application-level version of fixed partitions. Instagram mapped thousands of logical PostgreSQL schemas onto a few physical servers; Notion started with 480 logical shards on 32 databases. Moving capacity means moving whole logical shards, never re-hashing rows.

Moving data while it is being written follows the same pattern everywhere: copy a snapshot, stream the changes made since, cut over when the copy is caught up, keep a way back. Vitess, the MySQL sharding system built at YouTube, automates it as a resharding workflow:

Citus (distributed PostgreSQL) does the same with logical replication in its shard rebalancer: move a shard by copying it, replicating changes, then briefly locking it to switch over. The design lesson for interviews is the order of operations: copy, catch up, switch reads, switch writes, keep rollback, and never a big-bang migration with the old system turned off.

Request routing

Someone has to turn a key into a shard address. There are three places to put that logic:

  • Smart client. The client library holds the partition map and connects straight to the right node, saving a hop. Cassandra's token-aware drivers and Redis Cluster clients (which follow MOVED redirects and refresh their slot map) work this way. Every client must be updated when the map changes.
  • Routing proxy. Clients talk to a stateless router that knows the map: Vitess VTGate, MongoDB mongos, Twemproxy, Envoy's Redis proxy. Applications stay simple; the proxy is an extra hop and must be scaled and kept highly available.
  • Any node as coordinator. Clients connect to any node, which forwards the request to the owners. Cassandra coordinators, Elasticsearch nodes and CockroachDB gateways work this way.

In all three, the authoritative partition map lives in a strongly consistent store (ZooKeeper, etcd, MongoDB config servers, Vitess's topology service) or is spread by gossip, and routers cache it. A request that reaches a node that no longer owns the key must be redirected or rejected, never served from stale ownership.

Worked example: sharding an orders table

An e-commerce platform has 2 billion orders, growing by 3 million a day, on 64 shards. The access patterns:

QueryRateShard by user_idShard by order_id
Order detail by id6,000/sNeeds the user id or a lookup (fixable: see below)One shard
"My orders" page4,000/sOne shard, one index rangeAll 64 shards, merge, sort
Place order350/s peakOne shard, local transactionOne shard
Seller's orders300/sAll shardsAll shards
Load balanceSkewed by heavy buyers (B2B accounts)Perfectly even
"My orders" with order_id sharding 64 shard queries per page view 4,000/s × 64 = 256,000 shard queries/s P(slow shard) = 1 - 0.99^64 ≈ 47% of page views hit a p99 "My orders" with user_id sharding 4,000/s × 1 = 4,000 shard queries/s

Shard by user_id. It keeps the busiest read and every write transaction on one shard. Then fix its two weaknesses:

  • Order lookup by id. Embed the shard in the order id itself. Instagram's scheme packs 41 bits of milliseconds, 13 bits of logical shard id and 10 bits of sequence into a 64-bit id, so any service can extract the shard from the id with a bit shift, no lookup needed. See Distributed ID Generation.
  • Seller view. Maintain a second, seller-sharded table (orders_by_seller), fed asynchronously from the order shards by change data capture. Sellers tolerate a second of lag; buyers placing orders never wait for it.
  • Heavy buyers. A B2B account with millions of orders gets a bigger share of one shard. With 1,024 logical shards on 64 hosts, that logical shard can be moved to a less loaded host; if a single account outgrows a host, it gets a dedicated shard through a small directory override.

In the real world

  • Vitess shards MySQL at YouTube, Slack and many others: the application connects to VTGate as if to one MySQL, and vindexes map columns to keyspace ids.
  • Citus distributes PostgreSQL tables by a distribution column, co-locates tables with the same column, and replicates reference tables to every node.
  • DynamoDB hashes the partition key, splits partitions automatically by size and throughput, and applies per-partition throughput limits, which is why a hot partition key is the classic DynamoDB performance problem.
  • Discord partitions messages by (channel_id, time bucket) so that a busy channel's history is split into bounded partitions instead of one ever-growing hot one.
  • Notion sharded PostgreSQL by workspace id in 2021, using 480 logical shards so it could later grow the number of physical databases without re-sharding.
Interview angle

When to bring it up

After estimation shows that data or writes exceed one node, not before. Name the shard key, say why the top queries stay on one shard, and say what fans out: "Shard messages by conversation_id; loading a conversation is one shard; search across conversations goes to a separate search index."

Follow-ups to expect

  • Why that shard key? What query does it make expensive?
  • How do you find an order by id if you shard by user? (Shard bits in the id, or a lookup table.)
  • One customer is 20% of traffic. What happens and what do you do?
  • How do you add shards without downtime? (Fixed logical partitions, or copy, catch up, cut over.)
  • How do you handle a transaction that spans two users on different shards?

Red flags

  • hash(key) % N with no plan for changing N.
  • Sharding by a timestamp or auto-increment id with range partitioning.
  • A shard key under which the main query is scatter-gather.
  • Sharding a 200 GB database "for scale" when one node and replicas would do.
