Why it matters

A checkout service that sends the receipt email inside the request handler inherits every problem of the email provider. When the provider takes 2 seconds, checkout takes 2 seconds. When the provider is down, checkout fails, and a customer who has already been charged sees an error page. Nothing about the email needed to happen before the customer saw "order confirmed".

A message queue fixes this by splitting the work in time. The checkout service writes a small message ({"type": "send_receipt", "order_id": 81723}) to a durable queue and returns in a few milliseconds. A separate pool of workers reads messages and does the slow part at its own pace. The service that produces work is the producer, the service that does it is the consumer, and the queue is a buffer that both trust to hold the message until it is handled.

That buffer gives you three things at once:

Decoupling

The producer does not know how many consumers exist, where they run, or whether they are up right now. Either side can deploy, scale or fail independently.

Load levelling

Bursts are absorbed as queue depth instead of overload. Consumers are sized for the average rate, not the peak.

Retries for free

A message that fails is not lost. It stays in the queue and is delivered again, so transient errors heal themselves without the producer doing anything.

Point-to-point delivery and competing consumers

A classic queue is point-to-point: each message is delivered to exactly one of the consumers reading the queue, and once that consumer confirms it, the message is gone. Add more consumers and they share the work, each taking the next available message. This pattern is called competing consumers, and it is how you scale a queue-backed worker pool: throughput grows roughly linearly with the number of consumers until something downstream (a database, a rate-limited API) becomes the bottleneck.

Contrast this with publish/subscribe, where every subscriber gets its own copy of every message. Queues answer "do this job once"; pub/sub answers "tell everyone who cares that this happened". Log-based systems like Kafka can do both, and are covered in Pub/Sub & Event Streaming. Many brokers combine the two: an SNS topic fanning out to several SQS queues, or a RabbitMQ fanout exchange bound to one queue per consuming service, gives each service its own point-to-point queue of the same events.

Load levelling, drawn to scale

Traffic is rarely flat. A marketing push, a cron job in a partner's system, or the top of the hour produces bursts far above the average. Without a queue you must provision for the peak or reject work during it. With a queue, work that arrives faster than consumers can handle simply waits.

The cost is latency. A message that arrives at the peak waits behind 2,800 others, which at 120/s is about 23 seconds. That is fine for receipts and thumbnails and unacceptable for a payment authorisation the user is staring at. Queues are for work whose result the caller does not need right now. If the caller needs the answer, a queue only hides the overload until the caller's timeout fires.

The useful mental model is that a queue converts a throughput problem into a latency problem. It only works while the average arrival rate stays below the consumers' capacity. If arrivals exceed capacity for long enough, the backlog grows without bound and the age of the oldest message climbs until messages expire or the business notices.

Acknowledgements: how a queue knows work is done

The hard question for any queue is when to forget a message. If it deletes a message the moment a consumer reads it, a consumer that crashes halfway through loses that message forever. So brokers wait for an explicit acknowledgement (ack) from the consumer, sent after the work is finished. Until the ack arrives, the message is in flight: handed out, not yet done. The two dominant designs differ in how they notice that an in-flight message has been abandoned.

Visibility timeout (SQS)

Amazon SQS has no long-lived consumer connections. A consumer calls ReceiveMessage, and SQS returns a message plus a receipt handle, then hides that message from other receivers for the visibility timeout (30 seconds by default, up to 12 hours). If the consumer calls DeleteMessage with the receipt handle before the timer runs out, the message is gone. If not, for any reason at all, the message becomes visible again and the next ReceiveMessage gets it with an incremented receive count.

The broker never needs to know whether the consumer crashed, hung or is just slow. Silence is treated as failure. Step through what happens when a worker dies mid-job:

Choosing the timeout is a real trade-off. Too short, and a job that takes 40 seconds is redelivered at 30 and runs twice in parallel. Too long, and a crash leaves a message stranded for the whole period. The usual answer is a timeout a few times longer than the typical job, plus a heartbeat for long jobs: the worker calls ChangeMessageVisibility every so often to push the deadline out while it is still making progress.

Prefetch and ack (RabbitMQ)

RabbitMQ (AMQP 0-9-1) keeps a TCP connection open to each consumer and pushes messages to it. Each delivery carries a delivery tag. The consumer sends basic.ack with that tag when it is done, basic.nack or basic.reject to give it back. Failure detection is tied to the connection instead of a timer: if the channel or TCP connection closes with messages unacked, the broker requeues them immediately and marks them redelivered. Recent versions also enforce a consumer delivery timeout (30 minutes by default) to catch consumers that are alive but stuck.

Because messages are pushed, the consumer must limit how many it holds at once. The prefetch count (basic.qos) caps unacked deliveries per consumer. With prefetch 1, a consumer gets the next message only after acking the previous one, which is fair but wastes a network round trip per message. With an unlimited prefetch, the first consumer to connect can grab ten thousand messages while the others sit idle, and all of them are redelivered if it dies. A small prefetch (tens) is a sensible starting point; measure and adjust.

At-least-once delivery and duplicates

When the consumer acks decides what can go wrong:

  • Ack before processing (auto-ack, Celery's default early ack): a crash after the ack loses the message. This is at-most-once delivery.
  • Ack after processing: a crash after the work but before the ack causes the work to be done again. This is at-least-once delivery, and it is the default for almost every serious use of a queue.

At-least-once means duplicates are normal, not exceptional. They come from crashes between work and ack, from slow consumers outliving their visibility timeout, from producers retrying a send whose response was lost, and, in SQS standard queues, occasionally from the service itself. A consumer that charges a card or sends an SMS must therefore be idempotent: processing the same message twice must have the same effect as processing it once. The usual tool is a deduplication record keyed by the message id or a business key, written in the same transaction as the side effect (INSERT INTO processed(message_id) ... fails on the second attempt, so the work is skipped). Idempotency & Delivery Semantics covers the patterns in depth.

Common mistake

Claiming "exactly-once delivery" from a queue. Some brokers deduplicate within a window (SQS FIFO drops duplicate sends with the same deduplication id for 5 minutes), but no broker can know whether your consumer's side effect happened before it crashed. Exactly-once processing is something the consumer builds, by combining at-least-once delivery with idempotent handling.

Retries, backoff and dead-letter queues

Redelivery handles crashes. Errors need a policy too. A worker that calls a payment API and gets 503 Service Unavailable should not ack the message, because the work did not happen. It also should not retry instantly in a tight loop, because the API is already struggling and a thousand workers retrying at once keep it down.

  • Exponential backoff with jitter. Wait 1 s, then 2, 4, 8 and so on, each multiplied by a random factor so that retries from many workers spread out instead of arriving in synchronised waves. In SQS, the worker sets the message's visibility timeout to the backoff delay instead of deleting it. In RabbitMQ, the common pattern is a retry queue with a per-message TTL that dead-letters back into the main queue. Sidekiq and Celery do it in the library. Timeouts, Retries & Circuit Breakers explains the maths.
  • A retry limit. Some messages will never succeed. After a fixed number of attempts the message moves to a dead-letter queue (DLQ), a separate queue that nobody consumes automatically. In SQS this is the redrive policy's maxReceiveCount; in RabbitMQ it is a dead-letter exchange plus, on quorum queues, a delivery limit (20 by default since RabbitMQ 4.0; without a dead-letter exchange, messages over the limit are dropped).
  • Operating the DLQ. Alarm on DLQ depth above zero. Someone inspects the messages, fixes the bug or the data, and redrives them back to the main queue. A DLQ that nobody watches is just a slower way to lose data.

Poison messages

A poison message is one that crashes or fails its consumer every time: malformed JSON, a reference to a deleted customer, an input that triggers a bug. Without a retry limit it is redelivered forever. In a FIFO queue it is worse, because it blocks every message behind it in the same group. With a crash (rather than a caught exception) it can take down worker after worker as each one picks it up. Defences:

  • Catch and classify errors. A validation error will never succeed, so send it straight to the DLQ instead of burning four more retries. A timeout might succeed, so retry it.
  • Always configure a retry limit and a DLQ. The default in several brokers is unlimited redelivery, and where a default limit exists (RabbitMQ 4 quorum queues) a missing DLQ means the message is silently dropped.
  • Include enough context in the DLQ (error message, stack trace, attempt count, original queue) that a human can act without reproducing the failure.

Ordering and its throughput cost

A standard queue with competing consumers does not preserve order, even if the broker hands messages out in order. Worker 1 takes m1, worker 2 takes m2, worker 2 finishes first. Add redelivery after a crash and m1 may complete minutes after m5. SQS standard queues go further and only promise best-effort ordering.

Usually the order you need is per entity, not global: the events for cart 17 must apply in order, but cart 17 and cart 42 are independent. FIFO queues express exactly that. In SQS FIFO, each message carries a message group id. The queue delivers messages within a group strictly in order and will not hand out the next message in a group until the previous one is deleted. Different groups proceed in parallel.

The price of ordering is throughput and isolation:

  • Parallelism is capped by the number of active groups. If every message uses the same group id, the queue processes one message at a time no matter how many consumers you run.
  • Lower broker limits. An SQS FIFO queue in its default mode supports 300 API calls per second per action, or 3,000 messages per second with batches of 10; standard queues are effectively unlimited. High-throughput mode raises the FIFO limit by partitioning on group id.
  • Head-of-line blocking. One slow or failing message stalls its whole group until it succeeds or reaches the DLQ.

Before paying that price, check whether the consumer can make order irrelevant. A version number on each update (apply only if newer), a state machine that rejects impossible transitions, or a last-writer-wins timestamp often remove the need for a FIFO queue altogether.

Backpressure and scaling on queue depth

A queue decouples the producer from the consumer's speed, which also means the producer gets no signal when consumers fall behind. Backpressure is any mechanism that pushes that signal back upstream. With a queue in the middle you have three choices when the backlog grows: let it grow (and watch message age), slow producers down (a bounded queue that rejects or blocks sends, like RabbitMQ's max-length with reject-publish or its memory alarms), or add consumers.

The third is the usual answer for stateless workers, and the queue gives you the best possible scaling signal. CPU is a poor signal for I/O-bound workers that spend most of their time waiting on an API. Queue depth measures directly how much work is waiting.

  • Backlog per worker = visible messages / running workers. Pick a target from your latency goal: if one worker handles 66 messages per second and messages may wait 30 seconds, the target is about 2,000 messages per worker. AWS documents exactly this target-tracking setup for SQS, and KEDA does the same on Kubernetes for SQS, RabbitMQ, Kafka and Redis.
  • Age of the oldest message (SQS ApproximateAgeOfOldestMessage) is the best alert. It is what users feel, and it catches stuck consumers that a depth threshold misses when traffic is low.
  • Scale-in slowly. Removing workers when the queue hits zero causes flapping. Use a cooldown and let in-flight messages finish (graceful shutdown) or their visibility timeouts will cause redeliveries.

Scaling consumers only helps until the downstream dependency saturates. If 50 workers already max out the database, 200 workers make it slower. Cap the worker count at what the downstream can take.

Priority and delay queues

Priority queues

A password-reset email should not wait behind 200,000 newsletter emails. Two designs:

  • Broker-level priority. RabbitMQ supports priority queues declared with x-max-priority (2 to 4 levels are recommended, as each level has a cost; quorum queues ignore this argument and support priorities natively). Higher-priority messages are delivered first among those waiting. Priority only applies to messages that are queued, so with a large prefetch, low-priority messages already sitting in a consumer's buffer still go first.
  • Separate queues. SQS has no priorities, so you create emails-high and emails-low. Either give each its own worker pool (simple, isolated, but idle capacity cannot be shared), or have workers poll the high queue first and fall back to the low one. Sidekiq does this with weighted queues so the low queue is never fully starved.

Strict priority starves low-priority work under sustained load. Weighted polling, or a reserved minimum capacity per class, avoids that.

Delay queues and scheduled messages

Some work should happen later: "send a reminder if the cart is still abandoned in 30 minutes", "retry in 5 minutes". SQS supports a per-queue or per-message delay of up to 15 minutes, during which the message is invisible. RabbitMQ needs a plugin or the TTL plus dead-letter trick. Sidekiq and Celery store scheduled jobs in a Redis sorted set keyed by run time and move them to the work queue when due. For delays of hours or days, a database table of due jobs polled by a scheduler is often simpler and easier to inspect than a queue.

Simulating a visibility timeout

The code below models an SQS-style queue: receiving hides a message rather than removing it, deleting needs the latest receipt, and a message received too many times moves to a dead-letter queue. Two workers process three orders. worker-a crashes holding one, and one order contains bad data that fails every time.

import itertools


class Queue:
    """SQS-style queue: a receive hides a message for `visibility` seconds instead of removing it."""

    def __init__(self, visibility=30, max_receives=3):
        self.visibility, self.max_receives = visibility, max_receives
        self.msgs = {}                    # id -> {"body", "visible_at", "receives", "receipt"}
        self.dlq = []
        self.receipts = itertools.count(1)

    def send(self, msg_id, body):
        self.msgs[msg_id] = {"body": body, "visible_at": 0, "receives": 0, "receipt": None}

    def receive(self, now):
        for msg_id, m in list(self.msgs.items()):   # oldest first (best effort in SQS standard)
            if m["visible_at"] > now:
                continue                            # in flight with some consumer
            if m["receives"] == self.max_receives:  # redrive policy: stop retrying
                self.dlq.append(msg_id)
                del self.msgs[msg_id]
                log(now, "queue", f"{msg_id} moved to DLQ after {self.max_receives} receives")
                continue
            m["receives"] += 1
            m["visible_at"] = now + self.visibility
            m["receipt"] = next(self.receipts)
            return msg_id, m["body"], m["receipt"]
        return None

    def delete(self, msg_id, receipt):
        m = self.msgs.get(msg_id)
        if m and m["receipt"] == receipt:          # a stale receipt must not delete a newer delivery
            del self.msgs[msg_id]


def log(t, who, what):
    print(f"t={t:>3}s  {who:<8} {what}")


q = Queue(visibility=30, max_receives=3)
for i, body in enumerate(["charge $42.00", "charge $17.50", "charge $-1 (bad data)"]):
    q.send(f"order-{1001 + i}", body)

jobs = {"worker-a": None, "worker-b": None}   # name -> (msg_id, receipt, finishes_at)
down = {"worker-a": range(3, 10)}             # worker-a crashes at t=3, restarts at t=10

for now in range(100):
    for name in jobs:
        job = jobs[name]
        if now in down.get(name, ()):
            if job:
                log(now, name, f"crashed holding {job[0]}, never deleted it")
                jobs[name] = None
            continue
        if job and job[2] == now:
            msg_id, receipt, _ = job
            if "bad data" in q.msgs[msg_id]["body"]:
                log(now, name, f"{msg_id} raised ValueError, left in queue")
            else:
                q.delete(msg_id, receipt)
                log(now, name, f"{msg_id} processed and deleted")
            jobs[name] = None
        if jobs[name] is None and (got := q.receive(now)):
            msg_id, _, receipt = got
            log(now, name, f"received {msg_id} (receive #{q.msgs[msg_id]['receives']})")
            jobs[name] = (msg_id, receipt, now + 5)  # every job takes 5 s

print("queue:", list(q.msgs), "dlq:", q.dlq)

Three things to notice. Nothing happens between t=10 and t=30: order-1001 is stranded in flight until its timeout expires, which is the cost of crash detection by timer. The poison order is retried every 30 seconds and holds a worker each time until the redrive policy parks it. And the stale-receipt check in delete matters: if worker-a had only been slow, not dead, its late delete must not remove the copy that worker-b is now processing.

Worked example: sizing an email worker fleet

A retailer sends transactional email through a provider API. Peak load is 1.2 million emails per hour during a sale. Each API call takes 150 ms on average. The goal: no email waits more than 60 seconds at peak, and a 10-minute provider outage must not lose anything.

Peak rate 1,200,000 / 3,600 s ≈ 333 msg/s Concurrency 333 msg/s × 0.15 s (Little's law) = 50 calls in flight Per pod 10 threads / 0.15 s ≈ 66 msg/s Pods 333 / 66 ≈ 5, plus 40% headroom → 7 pods Autoscale target 66 msg/s × 30 s acceptable wait ≈ 2,000 visible msgs per pod Outage 333 msg/s × 600 s ≈ 200,000 msgs queued Drain at 14 pods 14 × 66 = 924 msg/s, net 924 - 333 ≈ 591 msg/s Drain time 200,000 / 591 ≈ 5.6 minutes

The outage is where the queue earns its keep. Checkout never noticed. When the provider recovers, the autoscaler sees 200,000 visible messages (about 29,000 per pod against a target of 2,000) and scales out, capped at 14 pods because the provider's rate limit is around 1,000 requests per second. The oldest emails go out about 10 minutes late, which is the outage itself; anything sent after recovery waits at most a few minutes behind the backlog. The business accepted that in advance. Three configuration choices fall out of the numbers: a visibility timeout of 30 seconds (200 times the mean call time, enough for slow tail calls), a maxReceiveCount of 10 with backoff doubling from 1 second (1 + 2 + ... + 512 s, about 17 minutes in total) so a 10-minute outage does not push good messages into the DLQ, and retention well above the longest plausible outage (SQS keeps messages 4 days by default, up to 14).

Retries and outages interact

With a maxReceiveCount of 3 and a 30-second visibility timeout, every message received during a 10-minute outage would hit the DLQ after 90 seconds. Size the retry budget so that its total backoff time covers the outages you expect, or stop consuming entirely while a circuit breaker on the provider is open.

In the real world

  • Amazon SQS: the canonical managed queue. Visibility timeouts, long polling, redrive policies to a DLQ with one-click redrive back, FIFO queues with message groups and deduplication ids. Often paired with SNS for fan-out to several queues.
  • RabbitMQ: an AMQP broker with exchanges that route messages to queues by key or pattern. Quorum queues (Raft-replicated) are the recommended durable queue type; dead-letter exchanges, per-queue TTLs and priorities are built in. Streams, added in 3.9, provide a Kafka-like log alongside classic queues.
  • Celery: the standard Python task queue, on RabbitMQ or Redis. By default it acks a task before running it; setting acks_late switches to at-least-once, which is what you want for idempotent tasks. With the Redis broker it emulates a visibility timeout (one hour by default), so long ETA tasks can be redelivered.
  • Sidekiq: Ruby background jobs on Redis. Failed jobs retry with exponential backoff, 25 times over about three weeks by default, then go to a "dead" set. The open-source version's basic fetch can lose in-flight jobs if a process is killed; Sidekiq Pro's super_fetch keeps them in a per-process list so they can be recovered.
  • Google Cloud Pub/Sub and Azure Service Bus sit between the two worlds: topic-based, but with per-message ack deadlines, dead-letter topics, and ordering keys (Pub/Sub) or sessions (Service Bus) that behave like a managed queue per subscription.
Interview angle

When to bring it up

Whenever a request triggers slow or unreliable work whose result the user does not need immediately: sending email or push notifications, transcoding video, generating thumbnails or reports, calling flaky third parties. Say "the API writes to a queue and returns 202; workers process it with at-least-once delivery and idempotent handlers, failures retry with backoff and land in a DLQ" and you have covered most of what the interviewer wants. It shows up in the notification system, video platform and web crawler cases.

Follow-ups to expect

  • What happens if a worker crashes mid-job? (Visibility timeout or connection loss triggers redelivery; work must be idempotent.)
  • How do you handle a message that always fails? (Retry limit, DLQ, alarm, redrive.)
  • Do you need ordering? Per what key? (Message groups or partitions, and their throughput cost.)
  • How do you scale the workers? (On backlog per worker or oldest message age, capped by downstream capacity.)
  • The queue keeps growing. What do you do? (Find the bottleneck: more workers, a downstream limit, a poison message, or a producer bug; then decide between scaling, shedding and backpressure.)

Red flags

  • Assuming exactly-once delivery, or ignoring duplicates entirely.
  • Putting a queue in front of work the user is waiting on synchronously, and calling it scaling.
  • No retry limit or DLQ, so one bad message loops forever.
  • Requiring global ordering on a high-throughput queue without asking whether per-entity ordering is enough.
