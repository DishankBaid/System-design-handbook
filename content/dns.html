Why it matters

Every request your users send starts with a question your servers never see: what IP address is api.shop.example.com? The Domain Name System answers it, usually in under a millisecond from a cache, sometimes in 200 ms after a walk across three continents. If DNS is slow, every first request is slow. If DNS is down, your perfectly healthy service is unreachable.

DNS is also more than a phone book. Because the answer can differ by who is asking and when, it is the first traffic steering layer in most architectures: it picks the region a user lands in, shifts load during a deploy, and moves everyone away from a failed data center. Each of those uses runs into the same constraint, which is the theme of this chapter: an answer, once handed out, is cached in places you do not control, for at least as long as you said it could be.

How a name gets resolved

DNS is a distributed, hierarchical database. The name api.shop.example.com. is read right to left: the trailing dot is the root, then the top-level domain (TLD) com, then example.com, which someone registered and whose records live on servers they chose. Each level only knows who is responsible for the level below it. That split is what lets the system hold hundreds of millions of domains with no central server holding them all.

The four kinds of server

Stub resolver

The small client library in the operating system (getaddrinfo on Linux, mDNSResponder on macOS). It sends one question to a configured resolver and waits for a final answer. It never walks the hierarchy itself.

Recursive resolver

Does the actual work: walks from the root down, follows referrals, caches everything it learns. Run by your ISP, your cloud VPC, or a public service such as 8.8.8.8 or 1.1.1.1. One resolver serves thousands to millions of users.

Root and TLD servers

The root servers (13 named identities, a to m.root-servers.net, each replicated to many sites) know only who runs each TLD. The com servers know only which name servers each .com domain uses.

Authoritative server

Holds the actual records for a zone and is the source of truth for them. This is what you configure in Route 53, Cloudflare DNS or a BIND zone file. It answers only for its own zones and never recurses.

The stub sends a recursive query ("give me the final answer"). The resolver then sends iterative queries: each server either answers or replies with a referral, "I do not know, but these servers are responsible for the next level down". Step through the four cases below. The first is rare in practice; most lookups end in the third or fourth.

Referrals and glue

A referral contains NS records naming the next servers, for example example.com. NS ns1.example.com.. That creates a chicken-and-egg problem: to find ns1.example.com, you would have to ask the servers for example.com, which is ns1.example.com. The parent zone breaks the loop by including the name server's address in the referral. These extra address records are called glue. When you change DNS providers at your registrar, you are changing the NS records and glue in the TLD zone, which is why that change is slow to take effect: the old NS records are cached for up to two days.

Modern resolvers also use QNAME minimisation (RFC 9156): they ask the root only about com and the TLD only about example.com, instead of sending the full name to every server. It leaks less about what users are looking up and changes nothing about the answer.

UDP, TCP and response size

Queries normally travel over UDP port 53: one packet out, one packet back, no handshake. Classic DNS limited UDP responses to 512 bytes; the EDNS(0) extension lets the client advertise a larger buffer, and since DNS Flag Day 2020 the common default is 1,232 bytes, small enough to avoid IP fragmentation. If an answer does not fit, the server sets the truncated (TC) bit and the client retries over TCP. That matters to you when a name has many records (a round-robin set of 30 IPs, or a long TXT record): responses that silently switch to TCP are slower, and a firewall that blocks TCP 53 turns them into failures. The transport details of UDP and TCP are in TCP, UDP & HTTP.

Caching and TTLs

Without caching, the root servers would receive every lookup on the internet. With it, they see a tiny fraction. Every record carries a TTL (time to live), in seconds, set by the zone owner. Any server that caches the record may reuse it for at most that long, and when it hands the record on it passes the remaining TTL, not the original.

Three consequences shape every DNS decision:

  • Changes are eventually visible, never instantly. After you edit a record, the worst-case time until every well-behaved cache sees it is the old TTL. "DNS propagation" is just caches expiring; nothing is pushed.
  • The resolver is the unit of caching. Ten thousand users behind one ISP resolver generate one query per TTL, not ten thousand. That is why DNS scales, and also why DNS-based decisions are made per resolver, not per user.
  • Not everyone obeys. Some resolvers enforce a minimum TTL (often 30 to 60 seconds) or a maximum (Unbound defaults to one day). Some applications cache on their own terms: a JVM running with a security manager historically cached successful lookups forever. Worse, a long-lived connection never re-resolves at all. An HTTP keep-alive or gRPC connection opened yesterday still points at yesterday's IP.

Negative caching

"This name does not exist" (NXDOMAIN) is cached too, so that typos and bots do not hammer authoritative servers. RFC 2308 sets its lifetime from the zone's SOA record: the smaller of the SOA record's own TTL and its MINIMUM field. The classic trap: a deploy script queries new-api.shop.example.com a few seconds before the record is created, the resolver caches the NXDOMAIN for an hour, and the new service is "missing" for some users long after the record exists. Keep the negative TTL short (a few minutes) on zones where you create names programmatically.

CNAME at the apex, and ALIAS records

A CNAME says "this name is really that other name", so RFC 1034 forbids any other record at a name that has one. The zone apex (the bare example.com) must have SOA and NS records. Therefore example.com cannot be a CNAME, which is awkward when your site lives on a CDN or a load balancer that only gives you a hostname like my-alb-1234.us-east-1.elb.amazonaws.com.

DNS providers solve this with a non-standard ALIAS record (also called ANAME, Route 53 "alias", or Cloudflare "CNAME flattening"). The authoritative server resolves the target itself and returns the resulting A and AAAA records, so to the outside world the apex holds plain addresses. Two caveats are worth naming:

  • It only works inside one provider: the authoritative server must do the lookup at query time, so you cannot use it with a secondary DNS provider that does not support the same feature.
  • The target is resolved from the DNS provider's location, not the user's. If the target is a geo-aware CDN hostname, users may be sent to the PoP nearest the DNS provider unless the provider forwards client location.

The standards-track fix is the HTTPS/SVCB record (RFC 9460), which can alias at the apex and also advertise supported protocols (alpn=h3,h2) so a browser can try HTTP/3 without a first HTTP/2 round trip. Browser support is growing but not universal, so apex ALIAS records remain the common answer.

CNAMEs also cost lookups. www.shop.example.com → shop.cdn-provider.net → edge-7.cdn-provider.net may need a separate resolution for each hop on a cold cache. Keep chains short.

DNS as a load balancer

An authoritative server is free to give different answers to different resolvers. Managed DNS services turn that into routing policies, often called GSLB (global server load balancing). DNS decides which region or cluster a client goes to; a load balancer inside that region then decides which server.

Routing policies

  • Round robin. Publish several A records; the server rotates their order on each response, and most clients use the first. Spreads load roughly evenly across resolvers, with no notion of distance or health.
  • Weighted. Return endpoint A for 90% of queries and B for 10%. Useful for canarying a new region or shifting traffic gradually during a migration.
  • Latency-based. The provider measures latency from resolver networks to each region and answers with the fastest one. Route 53 builds this from its own measurements between networks and AWS regions.
  • Geo DNS. Answer by the resolver's country or continent. Used for data residency ("EU users stay in the EU") as much as for speed.
  • Health-checked failover. The DNS provider probes each endpoint (HTTP every 10 or 30 seconds from several locations) and stops returning endpoints that fail. Combined with any of the above, this is how most multi-region systems fail over a region.

Anycast

Anycast takes a different route to the same goal. Instead of handing out different addresses, many sites announce the same IP prefix over BGP, and the internet's routing delivers each packet to the nearest site in network terms (usually, but not always, the geographically closest). It is how all 13 root server identities are served from well over a thousand machines, how 1.1.1.1 and 8.8.8.8 are fast everywhere, and how most CDNs and large DNS providers run their edges (see Content Delivery Networks).

Anycast suits short, stateless exchanges like a DNS query over UDP, where it does not matter if the next packet lands on a different site. For long TCP connections, a routing change mid-connection would send packets to a site with no state for that connection, so anycast TCP needs stable routing and, at scale, load balancers that share connection state or use consistent hashing (Google's Maglev and Cloudflare's edge both do this). In practice, DNS steering and anycast are combined: anycast gets the DNS query to a nearby DNS server fast, and that server's answer steers the user to a region.

Worked example: failover with TTL 60 s vs 3,600 s

An API at api.shop.example.com runs active-passive across two regions. It serves 10,000 requests per second, arriving through about 5,000 distinct recursive resolvers. The primary region dies at t = 0. The DNS provider health-checks every 10 seconds and marks an endpoint down after 3 consecutive failures, and it takes about 10 more seconds for every authoritative server to return the standby's IP.

Detection 3 checks × 10 s = 30 s Publish all authoritative servers updated = +10 s → fixed at t = 40 s Cache drain copies expire spread over one TTL after t = 40 s (a copy expiring before 40 s re-fetches the dead IP) Mean outage per resolver = 40 + TTL/2 TTL 60 70 s × 10,000 req/s ≈ 0.7M failed, clear at 100 s TTL 3,600 1,840 s × 10,000 req/s ≈ 18.4M failed, clear at ~61 min Query cost 5,000 / 60 s ≈ 83 q/s vs 5,000 / 3,600 s ≈ 1.4 q/s

The simulation below reproduces those numbers to within sampling noise by modelling each resolver's cache expiry, including the subtle case where a cache expires during the detection window and re-fetches the dead IP for another full TTL:

import random

RPS = 10_000                 # requests per second to api.shop.example.com
RESOLVERS = 5_000            # distinct recursive resolvers sending that traffic
CHECK_EVERY, FAILS = 10, 3   # health check every 10 s, 3 misses marks the region down
PUBLISH = 10                 # seconds until every authoritative server returns the new IP


def outage(ttl, seed=7):
    rng = random.Random(seed)
    fixed_at = CHECK_EVERY * FAILS + PUBLISH       # new answer is live at t = 40 s
    recovered = []
    for _ in range(RESOLVERS):
        expiry = rng.uniform(0, ttl)               # cached copy expires somewhere in the next TTL
        while expiry < fixed_at:                   # expired too early: re-fetches the OLD answer
            expiry += ttl                          # ...and caches the dead IP for another full TTL
        recovered.append(expiry)
    failed = sum(recovered) * RPS / RESOLVERS      # each resolver carries an equal share of traffic
    return failed, max(recovered)


for ttl in (60, 300, 3600):
    failed, last = outage(ttl)
    print(f"TTL {ttl:>4}s: {failed / 1e6:5.2f}M failed requests, last resolver recovers at {last:6.0f}s")

# TTL   60s:  0.70M failed requests, last resolver recovers at    100s
# TTL  300s:  1.89M failed requests, last resolver recovers at    340s
# TTL 3600s: 18.24M failed requests, last resolver recovers at   3639s

Three lessons. First, the short TTL is cheap: 83 queries per second is nothing for a managed DNS provider. The real cost of a short TTL is resilience to the DNS provider itself, because a resolver with a 60-second copy runs out of answers 60 seconds into a provider outage. Second, below about 60 seconds the TTL stops being the bottleneck: detection and publishing already take 40 seconds, so tighten health checks before shaving the TTL further. Third, this is the best case. Clients holding keep-alive connections to the dead region, or runtimes caching beyond the TTL, recover only when their connections error out and they re-resolve, which is why clients also need sensible timeouts and retries.

DNS as a dependency and a failure source

DNS sits in front of everything, so its failures look like total outages, and its incidents are some of the best-known on the internet:

  • Dyn, October 2016. The Mirai botnet, built from hacked cameras and home routers, flooded Dyn's authoritative DNS with traffic. Sites that used Dyn as their only DNS provider, including Twitter, GitHub, Netflix and Reddit, were unreachable for many users for hours, although their own servers were fine.
  • Facebook, October 2021. A maintenance command cut Facebook's backbone. Its authoritative DNS servers, detecting they could not reach the data centers, withdrew their BGP anycast routes as designed. With the name servers gone from the internet, facebook.com stopped resolving everywhere for about six hours, and the internal tools engineers needed to fix it depended on the same DNS.
  • AWS us-east-1, October 2025. An automation race left the regional DynamoDB endpoint's DNS record empty. Services that could not resolve the endpoint failed, and the failures cascaded through other AWS services that depend on DynamoDB.

The patterns that reduce the blast radius:

  1. Two authoritative providers. List name servers from two independent providers in your NS set and keep the zones in sync (zone transfers or tooling such as octoDNS). Resolvers retry the other provider if one fails. Provider-specific features like ALIAS and latency routing make this harder, which is the trade-off.
  2. Serve stale. Resolvers that implement RFC 8767 keep answering with expired records when the authoritative servers are unreachable. Enable it on resolvers you run.
  3. Cache close to the app. Run a local caching resolver on each host or node (systemd-resolved, NodeLocal DNSCache in Kubernetes), so a resolver blip does not fail every outbound call.
  4. Keep the control plane independent. The tools you use to fix DNS (consoles, VPN, runbooks) should not depend on the DNS you are fixing.
  5. Watch internal DNS volume. In Kubernetes, pods default to ndots:5 with several search domains, so a lookup for api.stripe.com first tries api.stripe.com.default.svc.cluster.local and two more suffixes before the real name. One outbound call can become four or more lookups, doubled for A and AAAA. Use fully qualified names with a trailing dot, or lower ndots, for hot external calls.

DNSSEC and encrypted DNS

DNSSEC: is this answer authentic?

Plain DNS has no integrity protection. An attacker who can race a resolver with a forged response can poison its cache and send all its users to a fake bank.example.com; Dan Kaminsky's 2008 attack made this practical until resolvers randomised source ports. DNSSEC adds signatures: each zone signs its record sets (RRSIG) with a key published in a DNSKEY record, and the parent zone vouches for that key with a DS record, forming a chain of trust up to the root's key. A validating resolver rejects anything that does not verify.

DNSSEC proves the answer is authentic; it does not encrypt it, and it does not protect the last hop from resolver to stub. It also adds an operational failure mode: an expired signature or a botched key rollover makes your domain fail to resolve for every validating resolver, which is exactly what happened to Slack for many users in September 2021 when an attempted DNSSEC rollout went wrong. Adopt it with automated signing and key rollover, or through a provider that manages both.

DoT and DoH: who can see the question?

Classic queries travel in clear text, so anyone on the path (a cafe Wi-Fi operator, an ISP) can see and alter which names you look up. DNS over TLS (DoT, RFC 7858, port 853) and DNS over HTTPS (DoH, RFC 8484, port 443) encrypt the stub-to-resolver hop. DoH looks like ordinary HTTPS traffic, which makes it hard to block and is why browsers adopted it, sometimes sending queries to a public resolver instead of the one the network configured. For a system designer the consequences are practical: split-horizon DNS (internal names that only the corporate resolver knows) can break when a browser bypasses that resolver, and network-level DNS filtering stops seeing traffic. The resolver itself still sees every query, so encryption moves trust rather than removing it.

In the real world

  • Amazon Route 53 offers simple, weighted, latency, failover, geolocation, geoproximity, IP-based and multivalue routing policies, plus health checks and alias records at the apex. Note its fail-open rule: when every record in a health-checked group is unhealthy, Route 53 treats them all as healthy and returns them anyway, on the theory that some answer beats none.
  • AWS Elastic Load Balancing gives each load balancer a DNS name with a 60-second TTL, because its IPs change as it scales. Clients that cache DNS forever eventually connect to IPs that no longer belong to them.
  • Cloudflare runs both its authoritative DNS and the 1.1.1.1 resolver over anycast from its whole edge network, and pioneered CNAME flattening for apex records.
  • Google Public DNS (8.8.8.8) is anycast, supports DoT and DoH, and sends EDNS Client Subnet to authoritative servers that support it, so CDNs can still map users to nearby PoPs.
  • Kubernetes uses CoreDNS for in-cluster service discovery: orders.shop.svc.cluster.local resolves to a service IP, and headless services return one A record per pod plus SRV records with ports.
  • Netflix runs active-active across AWS regions and evacuates a region by changing DNS so users resolve to the healthy regions, which is why it treats DNS TTLs as part of its failover budget.
Interview angle

When to bring it up

In any multi-region design, and whenever you draw the first box labelled "users". One or two sentences usually suffice: "GeoDNS with health checks and a 60-second TTL sends users to the nearest healthy region; inside the region an L7 load balancer spreads requests." Go deeper if the interviewer asks how failover works or how fast it is.

Follow-ups to expect

  • Walk through what happens when I type the URL. Name stub, recursive, root, TLD and authoritative, and say where caching cuts the walk short.
  • How quickly can you fail over a region with DNS? Detection plus publish plus TTL, and the stragglers that ignore the TTL or hold connections open.
  • Why not set the TTL to 1 second? Resolvers clamp it, query volume rises, and you lose resilience if the DNS provider has an outage.
  • Why can't the apex be a CNAME? RFC 1034 forbids other data next to a CNAME and the apex needs SOA and NS. ALIAS records or HTTPS records solve it.
  • Your DNS provider is DDoSed. What now? Second provider in the NS set, long TTLs on NS records, serve-stale.

Red flags

  • Treating DNS round robin as a real load balancer that knows about server health and load.
  • Promising instant failover through DNS changes, or forgetting that existing connections never re-resolve.
  • A single DNS provider for a system with a 99.99% availability target.
  • Confusing DNSSEC (authenticity) with DoH (privacy).
