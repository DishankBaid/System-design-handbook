Why it matters

At 02:14 the checkout error rate jumps from 0.1% to 4%. Nothing was deployed. CPU is normal on every host. The database dashboard is green. Somewhere across forty services one thing is different, and every minute of searching costs orders. How fast you find it depends almost entirely on the telemetry you decided to emit months earlier.

A distributed system fails in ways nobody predicted: one bad pod behind a load balancer, a payment provider that is slow only for one card network, a retry storm that only starts above a certain request rate. You cannot write a dashboard for every one of these in advance. You need data rich enough to ask questions you did not know you would have.

Monitoring

Collecting predefined signals and alerting when they cross thresholds. It answers questions you thought of in advance: "is the error rate above 1%?" It catches known failure modes.

Observability

How well you can explain the internal state of a system from the data it emits, without shipping new code. It lets you slice by any dimension ("only iOS users on build 8.2 in eu-west-1") to debug failures nobody predicted.

Observability is a property of the system, borrowed from control theory, and monitoring is an activity you perform on top of it. You need both: monitoring tells you that something is wrong, observability lets you find out why. The rest of this chapter covers the raw signals, how to turn them into alerts that page for the right reasons, and the pipeline that carries them.

The three pillars

Telemetry comes in three shapes. Each is cheap for some questions and useless for others, so a production system emits all three and links them together.

LogsMetricsTraces
UnitOne event, with contextA number aggregated over timeOne request's path through services

The usual debugging loop uses them in order: a metric fires an alert, an exemplar trace attached to the slow bucket shows which hop is slow, and the logs for that trace ID show the exact error. The pillars are only as useful as the links between them, which is why every log line should carry the trace ID.

Logs

A log is a timestamped record of a discrete event. Logs are the most detailed signal and the most expensive one to keep.

Structured logging

A free-text line like Payment failed for user 4412 after 2 retries is easy to write and painful to query: every question needs a regular expression, and changing the wording breaks every saved search. Structured logging emits each event as key-value pairs, almost always JSON, so the log store can index fields and filter on them directly.

{"ts": "2026-10-09T02:14:07.412Z", "level": "ERROR", "service": "payment",
 "msg": "charge failed", "order_id": "ord_88213", "user_id": "u_4412",
 "psp": "psp.example", "http_status": 502, "attempt": 3, "duration_ms": 1840,
 "trace_id": "0af7651916cd43dd8448eb211c80319c", "span_id": "b7ad6b7169203331",
 "version": "2026.10.08-3", "pod": "payment-7d9f-x2kq4", "region": "eu-west-1"}

Now "every ERROR from payment where psp is psp.example in the last hour, grouped by version" is one query. Three rules make structured logs pay off:

  • Consistent field names across services. If one team logs userId and another user_id, cross-service queries fail silently. OpenTelemetry's semantic conventions give a shared vocabulary.
  • Always include correlation fields: trace_id, span_id, service, version, and host or pod. They turn a log line into a pointer to everything else.
  • Never log secrets or raw personal data. Passwords, tokens, card numbers and full email addresses end up in a store with weaker access control than your database. Redact in the logging library, and again in the pipeline as a backstop.

Levels and sampling

Log levels (DEBUG, INFO, WARN, ERROR) let you change verbosity without changing code. Production usually runs at INFO, with a way to raise one service or one request to DEBUG at runtime. Reserve ERROR for things a human may need to act on; if a healthy system logs hundreds of errors per minute, nobody reads them, and the real one hides in the noise.

At high volume, log sampling keeps cost bounded: keep every WARN and ERROR, keep 1% of successful request logs, and keep 100% of logs for requests whose trace was sampled, so a kept trace always has its logs. Rate-limit identical messages so one failing dependency cannot produce a million copies of the same line.

What logs cost

Service 2,000 req/s × 5 log lines × 1 KB per line = 10 MB/s Per day 10 MB/s × 86,400 s = 864 GB/day Per month × 30 ≈ 26 TB ingested At an illustrative $0.50 per GB ingested ≈ $13,000/month, for one service Sample successes to 1%, keep all errors (say 0.5% of requests) → roughly 1.5% of the volume

Log volume scales with traffic, so it grows exactly when the business grows. That is why mature teams treat logging as a budget, push most aggregate questions to metrics, and keep detailed logs only where they are needed for debugging and audit.

Metrics

A metric is a numeric measurement recorded over time, identified by a name and a set of labels, such as http_requests_total{service="checkout", route="/cart", status="500"}. Each unique combination of name and label values is one time series. Metrics are aggregated at the source, so 1 request per second and 100,000 requests per second cost the same to store.

Metric types

Counter

Only goes up (and resets to 0 on restart). Requests served, bytes sent, errors. You almost always query its rate: rate(http_requests_total[5m]).

Gauge

A value that goes up and down. Queue depth, memory in use, open connections, temperature. Read it as it is.

Histogram

Counts observations into fixed buckets, such as latency up to 5, 10, 25 ms and so on. Lets you compute percentiles at query time, and aggregate across instances correctly.

Summary

Computes percentiles inside each process. Accurate per instance, but the percentiles cannot be combined across instances. Prefer histograms in a fleet.

Percentiles from a histogram

Averages hide the users who suffer. A service with a 40 ms mean can have 1% of requests taking over 400 ms, and with a few dozen calls per page load, most users will hit that tail. So you measure percentiles: p50 is the latency half of requests beat, p99 the latency 99% beat. (The Latency, Throughput & Availability chapter covers why tails dominate.)

Storing every request's latency to compute exact percentiles is too expensive at scale. A histogram stores only a count per bucket. To estimate the p99, find the bucket that contains the 99th-percentile request and interpolate inside it, assuming requests are spread evenly across the bucket. This is what PromQL's histogram_quantile does.

# Latency histogram as a Prometheus-style exporter would expose it:
# cumulative counts of requests with latency <= upper bound (seconds).
BUCKETS = [  # (le, cumulative_count)
    (0.005, 1_200), (0.01, 4_800), (0.025, 31_000), (0.05, 71_500),
    (0.1, 91_000), (0.25, 97_600), (0.5, 99_300), (1.0, 99_820),
    (2.5, 99_990), (float("inf"), 100_000),
]


def quantile(q, buckets):
    """Same idea as PromQL histogram_quantile: find the bucket holding the
    q-th request, then interpolate linearly inside it."""
    total = buckets[-1][1]
    rank = q * total
    prev_le, prev_count = 0.0, 0
    for le, count in buckets:
        if count >= rank:
            if le == float("inf"):
                return prev_le            # cannot interpolate into +Inf
            frac = (rank - prev_count) / (count - prev_count)
            return prev_le + (le - prev_le) * frac
        prev_le, prev_count = le, count


for q in (0.5, 0.9, 0.99, 0.999):
    print(f"p{q * 100:g}: {quantile(q, BUCKETS) * 1000:.1f} ms")

# p50: 36.7 ms
# p90: 97.4 ms
# p99: 455.9 ms
# p99.9: 1705.9 ms

Two practical consequences:

  • Put bucket boundaries at your thresholds. If the SLO is "99% under 300 ms", a bucket edge at exactly 300 ms makes "fraction under 300 ms" an exact count instead of an interpolation. Here the 250 to 500 ms bucket is wide, so the p99 of 456 ms could really be anywhere from 250 to 500 ms.
  • Never average percentiles. The mean of ten pods' p99s is not the fleet p99. Sum the bucket counts first, then compute the quantile: histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))). Newer formats (Prometheus native histograms, OpenTelemetry exponential histograms) choose buckets automatically with a bounded relative error.

Cardinality explosion

Cardinality is the number of distinct time series a metric produces, which is the product of the number of values each label takes. It is the main cost driver of a metrics system, because each active series takes memory in the time-series database and disk for every sample.

http_requests_total{method, route, status, pod} 5 methods × 60 routes × 8 status codes × 300 pods = 720,000 series (upper bound) Add user_id with 1,000,000 users = 720 billion series: the TSDB falls over Add a request_id label = one new series per request, forever

The rule: labels must have small, bounded value sets. Route templates (/users/{id}), not raw paths (/users/4412). Status classes or codes, not error messages. Per-user and per-request detail belongs in logs and trace attributes, which are built for high cardinality. A single engineer adding customer_id as a label is one of the most common ways a Prometheus server runs out of memory.

What to measure: RED, USE and the Four Golden Signals

Three checklists cover almost every dashboard. They differ in what they look at.

MethodApplies toSignalsExample
REDRequest-driven servicesRate, Errors, Durationcheckout: 1,800 req/s, 0.2% 5xx, p99 380 ms
USEResources: CPU, disk, NIC, connection pools, queuesUtilization, Saturation, ErrorsDB pool: 92% of connections busy, 40 waiters, 3 timeouts/min
Four Golden SignalsAny user-facing systemLatency, traffic, errors, saturationRED plus "how full are we": queue depth, memory headroom

RED (from Tom Wilkie) tells you whether users are happy. USE (from Brendan Gregg) tells you which resource is the bottleneck. The Four Golden Signals, from Google's SRE book, are essentially RED plus saturation. Two details matter: measure latency separately for successes and failures (a fast 500 makes average latency look better), and saturation is about the most constrained resource, which is often a pool or queue rather than CPU.

Distributed tracing

Metrics say checkout p99 is 420 ms. Logs from each service say each one was "fine". Neither says where the time went, because the request crossed six services. A distributed trace records one request's whole journey as a tree of timed operations.

Traces and spans

A span is one timed operation: an incoming HTTP request, a database query, a call to another service. Each span has a trace ID (shared by every span of the request), its own span ID, the ID of its parent span, start and end timestamps, a status, and attributes such as http.route or db.system. The spans with the same trace ID form a tree, and drawing that tree against a time axis gives the waterfall view.

Traces answer questions the other pillars cannot: which hop is slow, which calls run sequentially that could run in parallel, which service retries, and what the fan-out of a request really is. A trace showing 200 sequential calls to the same cache is the classic way an N+1 query is found.

Context propagation and W3C traceparent

For spans in different processes to join one trace, each outgoing call must carry the trace context. This is context propagation: the caller injects the trace ID and its own span ID into the request headers, and the callee extracts them and makes its span a child of that span. The standard format is the W3C Trace Context traceparent header:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 │ │ │ └ trace-flags: 01 = sampled │ │ └ parent-id: 8 bytes, the caller's span ID │ └ trace-id: 16 bytes, same for every span in the request └ version

A companion tracestate header carries vendor-specific data. The context must survive every hop, including asynchronous ones: put it in Kafka message headers and job payloads too, or the trace breaks at the queue. One service that drops the header splits every trace through it in two. Instrumentation libraries for common HTTP and gRPC frameworks do the injection and extraction automatically, which is why auto-instrumentation is the usual starting point.

Sampling: head vs tail

Tracing every request at 50,000 requests per second with 20 spans each is a million spans per second. Most teams keep a fraction. When the keep-or-drop decision is made matters a lot.

  • Head sampling decides at the root span, typically at random ("keep 10%"), and propagates the decision in the sampled flag so every service agrees. It is cheap: unsampled requests create almost no work anywhere. Its flaw: the decision is made before anything is known, so a rare error is sampled at the same 10% as a boring success.
  • Tail sampling buffers all spans of a trace until it completes, then decides: keep every trace with an error, every trace above the p99 latency, and a small random baseline. You keep exactly the interesting traces. The cost is that every span must be sent and buffered first, and all spans of a trace must reach the same collector instance, which needs routing by trace ID.

A common hybrid is head sampling at a moderate rate in the SDK to cap volume, with tail sampling in the collector on top. Metrics are never sampled: rates and percentiles come from metrics computed on 100% of traffic, and traces provide examples.

Linking the pillars

Three links make the pillars one tool. Trace IDs in log lines let you jump from a span to its logs. Exemplars attach a sample trace ID to a histogram bucket, so clicking the spike in a latency chart opens a real slow request. Shared resource attributes (service name, version, region, pod) on every signal let you pivot from "p99 rose in eu-west-1" to "only on version 2026.10.08-3".

SLOs, error budgets and burn rates

A service level indicator (SLI) measures something users feel, ideally as a ratio of good events to total events: the fraction of checkout requests that succeed in under 500 ms. A service level objective (SLO) sets a target for it over a window: 99.9% over 30 days. The availability chapter covers choosing them; here the question is how to alert on them.

The SLO implies an error budget: the 0.1% of requests that are allowed to fail. Over 30 days at 500 requests per second that is about 1.3 million requests, or the equivalent of 43 minutes of total outage. The budget turns reliability into a quantity. If plenty is left, ship faster. If it is nearly spent, slow down and fix things.

Burn rate

The burn rate is how fast you are spending the budget compared with the rate that would spend it exactly over the window:

burn rate = observed error rate / (1 - SLO) SLO 99.9% → allowed error rate 0.1% Error rate 0.1% → burn rate 1 budget lasts exactly 30 days Error rate 0.6% → burn rate 6 budget gone in 30 / 6 = 5 days Error rate 1.44% → burn rate 14.4 budget gone in 30 / 14.4 = 2.08 days (50 hours) Budget consumed in time t at burn rate b = b × t / 30 days 14.4 for 1 hour → 14.4 × 1 / 720 = 2% of the monthly budget

Multiwindow, multi-burn-rate alerts

Alerting directly on "error rate above 0.1%" is too sensitive: a 30-second blip at 1% errors pages someone at night for something that spent about 0.01% of the budget. Alerting on "budget consumed in the last 30 days" is too slow: by the time it fires, the damage is done. Google's SRE workbook recommends alerting on the burn rate over a long window (is this significant?) combined with a short window (is it still happening?), at several severities:

SeverityBudget spentLong windowShort windowBurn rate
Page2%1 hour5 minutes14.4
Page5%6 hours30 minutes6
Ticket10%3 days6 hours1

The short window is about one twelfth of the long one. It does not make the alert fire faster; it makes it stop faster. Without it, a 1-hour window stays above threshold for up to an hour after the fix, and the alert keeps firing on a healthy system. Detection is still quick for a real outage: at a 100% error rate, the 1-hour error rate passes 1.44% after 0.0144 hours, about 52 seconds.

# Error budget and burn rate for a 99.9% availability SLO over 30 days.
SLO = 0.999
budget = 1 - SLO                       # 0.1% of requests may fail
window_h = 30 * 24


def burn_rate(errors, requests):
    return (errors / requests) / budget


def should_page(long_window, short_window, threshold=14.4):
    """Multiwindow rule: both the 1h and the 5m burn rate must exceed the
    threshold. The long window proves it is significant, the short window
    proves it is still happening."""
    return burn_rate(*long_window) > threshold and burn_rate(*short_window) > threshold


# (errors, requests) per window, for a service doing ~500 req/s
slow_leak = ((2_700, 1_800_000), (230, 150_000))       # 0.15% errors
outage    = ((36_000, 1_800_000), (3_100, 150_000))    # 2% errors
recovered = ((30_100, 1_800_000), (12, 150_000))       # fixed 10 min ago

for name, (lw, sw) in [("slow_leak", slow_leak), ("outage", outage), ("recovered", recovered)]:
    br = burn_rate(*lw)
    print(f"{name:9}  1h burn {br:5.1f}x  5m burn {burn_rate(*sw):5.1f}x  "
          f"budget gone in {window_h / br / 24:4.1f} d  page={should_page(lw, sw)}")

# slow_leak  1h burn   1.5x  5m burn   1.5x  budget gone in 20.0 d  page=False
# outage     1h burn  20.0x  5m burn  20.7x  budget gone in  1.5 d  page=True
# recovered  1h burn  16.7x  5m burn   0.1x  budget gone in  1.8 d  page=False

The slow leak at 1.5x is real but would take 20 days to exhaust the budget, so it should become a ticket from the 3-day rule, not a page. The outage pages. The recovered case shows the short window doing its job: the 1-hour burn is still 16.7, but nothing is happening any more, so nobody is woken.

Alerting on symptoms, not causes

Every page should mean "users are hurting now, or will be soon, and a human must act". Alerts that fire on causes (high CPU, one pod restarted, disk at 80%) break that rule in both directions: they fire when users are fine (CPU at 95% while latency is normal is just efficient use of hardware), and they stay silent for failures nobody anticipated (a bad config that returns empty results with low CPU).

Cause-based alertProblemSymptom-based alternative
CPU above 90% on any hostFires on healthy batch jobsCheckout latency SLO burning at 14.4x
Pod restartedKubernetes already handled itError-rate SLO burn, which includes failed requests during restarts
Replica lag above 5 sMatters only if reads are stale for usersFreshness SLI: fraction of reads newer than 10 s
Disk 80% fullFine as a ticket: predicts a future symptom"Disk full within 4 hours at current rate" pages, "80%" files a ticket

Cause metrics still belong on dashboards: they are how you diagnose, after a symptom alert tells you to look. Every alert should be actionable, link to a runbook, and be reviewed if it fires without action. Alert fatigue is a reliability risk in its own right: a team paged twenty times a week learns to ignore pages, including the real one.

Dashboards

A good service dashboard reads top to bottom like a diagnosis. First row: SLO status and remaining error budget. Second row: RED for the service's endpoints. Third row: RED for each dependency it calls, as seen from the caller. Last: USE for its resources (CPU, memory, pools, queues). Mark deploys and config changes on every graph as vertical lines, because "what changed?" is the first question in most incidents.

Resist the wall of eighty graphs. A dashboard that needs an expert to read it does not help the person on call at 2 a.m. Keep exploratory queries for the exploration tools, and keep dashboards for the questions you ask every incident.

The telemetry pipeline and OpenTelemetry

OpenTelemetry (OTel) is the vendor-neutral standard for producing and shipping telemetry, formed in 2019 by merging OpenTracing and OpenCensus. It defines APIs and SDKs for each language, semantic conventions for attribute names, a wire protocol called OTLP, and the Collector, a pipeline process that receives, transforms and exports telemetry. Instrument once with OTel and you can change backends by changing collector configuration, not application code.

  1. Instrument. Auto-instrumentation covers HTTP servers and clients, gRPC, database drivers and messaging libraries. Add manual spans and attributes for business steps (order.total, payment.method).
  2. Collect locally. The SDK batches and sends OTLP to an agent on the same host or in a sidecar. If the backend is down, the agent buffers and eventually drops; the application never waits on telemetry.
  3. Process centrally. The gateway applies memory_limiter first (so a surge cannot kill the collector), then sampling, attribute filtering and batching. For tail sampling, a first layer routes spans by trace ID so each trace lands on one instance.
  4. Export. Metrics to a time-series database, logs to a log store, traces to a trace store. Keeping the signals in separate, specialised stores is the norm; some newer systems store all three as wide events in one columnar database.
Telemetry must fail open

The observability pipeline must never take the product down. Use bounded queues and drop on overflow, set timeouts on exports, and alert on the pipeline's own drop rate. Equally, the alerting path must not depend on the system it watches: if your alerts run in the same cluster as the outage, they fail with it. Run a small, independent "is the monitoring alive?" check from outside.

Incident response, briefly

Observability pays off during incidents. A minimal process that works:

  1. Detect. An SLO burn alert pages the on-call engineer, ideally before customers report it. Time to detect is a metric worth tracking.
  2. Coordinate. For anything beyond a quick fix, name an incident commander who coordinates and decides, separately from the people debugging, plus someone handling communication to status pages and stakeholders.
  3. Mitigate first. Roll back the last deploy, flip the feature flag, drain the bad region, shed load. Restore service, then find the root cause. "What changed in the last hour?" resolves a large share of incidents.
  4. Learn. Write a blameless postmortem: timeline, impact (in error budget spent), contributing factors, and action items with owners. Missing telemetry discovered during the incident is a standard action item.

In the real world

  • Google: the Dapper paper (2010) introduced the trace and span model that Zipkin, Jaeger and OpenTelemetry follow, including low head-sampling rates in production. Its internal monitoring system Borgmon inspired Prometheus. The SRE book defined the Four Golden Signals, and the SRE workbook the multiwindow burn-rate alerts above.
  • Prometheus: started at SoundCloud in 2012, now a CNCF graduated project. Pull-based scraping, a dimensional data model, PromQL, and the histogram-based percentile approach described here.
  • Uber built Jaeger to trace thousands of microservices and open-sourced it; it is a CNCF graduated project. Twitter open-sourced Zipkin, modelled on Dapper.
  • Honeycomb and others popularised the "wide event" approach: emit one rich, high-cardinality event per request per service, and derive metrics and traces by querying those events.
  • OpenTelemetry is a CNCF project with support from every major vendor, and has become the default way to instrument new services.
Interview angle

When to bring it up

In the wrap-up of every design: "I'd define SLOs for redirect latency and availability, alert on burn rate, emit RED metrics per service and trace requests end to end with OpenTelemetry." In a case study, name the two or three SLIs that matter for that product. It shows you think about running the system, not only drawing it.

Follow-ups to expect

  • How would you find out why p99 latency doubled? (Metrics to find when and where, exemplar trace to find the slow hop, logs for the error.)
  • Why not alert when error rate exceeds the SLO threshold? (Too noisy; use burn rate over long and short windows.)
  • How do you compute fleet-wide p99? (Sum histogram buckets across instances, then interpolate; never average percentiles.)
  • Why can you not put user_id on a metric? (Cardinality: series count is the product of label values.)
  • Head or tail sampling for debugging rare errors? (Tail, with routing by trace ID.)
  • How does a trace survive a Kafka hop? (Propagate traceparent in message headers.)

Red flags

  • Alerting on CPU and memory thresholds as the main paging strategy.
  • Averaging latencies, or averaging p99s across hosts.
  • "We'll log everything" with no thought for cost, sampling or secrets in logs.
  • Treating observability as something added after launch, rather than part of the design.
