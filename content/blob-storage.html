Why it matters

Users of a photo app upload 50 million photos a day. Each one is a few megabytes, written once, read many times, never edited, and expected to exist forever. Putting them in a relational database would bloat its storage, backups and replication with data the database cannot query anyway. Putting them on a server's disk ties them to one machine that will eventually die. The answer every large system uses is an object store: Amazon S3, Google Cloud Storage, Azure Blob Storage, or a self-hosted equivalent such as Ceph or MinIO.

The pattern is the same everywhere: the bytes go to the object store, and a row of metadata (owner, key, size, content type, status) goes to the database. Video platforms, chat attachments, backups, data lakes, machine learning datasets and static websites all follow it. This chapter covers how object stores are built, how they make data survive hardware failure at low cost, and how clients move large files in and out of them safely.

Object, block and file storage

Three storage abstractions are in common use, and interviewers like to check that you can tell them apart.

Block storage

A virtual disk: a range of fixed-size blocks addressed by number, with no notion of files. A file system or database on one host formats and owns it. Lowest latency, attached to one machine at a time. AWS EBS, a SAN LUN, a local NVMe drive.

File storage

A shared POSIX file system: directories, files, permissions, byte-range writes, locks, mounted by many hosts at once over NFS or SMB. Familiar to applications, harder to scale because directory operations and locking need coordination. AWS EFS, NetApp, CephFS.

Object storage

A flat namespace of keys mapped to immutable objects (bytes plus metadata) in buckets, accessed over HTTP with PUT, GET, DELETE and LIST. No in-place edits, no rename, no real directories (photos/2026/10/a.jpg is just a key containing slashes). In return: practically unlimited scale, very high durability and the lowest cost per gigabyte.

Inside an object store

Every large object store separates two very different problems. Metadata (which key maps to which version, which chunks, on which nodes) is small, must be strongly consistent, and is read on every request. Data (the bytes) is enormous, immutable once written, and needs cheap, durable capacity.

  • Front end. Stateless HTTP servers that authenticate the request (for S3, a signature over the request with the caller's key), check bucket policies, and stream bytes to and from storage nodes. They scale horizontally behind load balancers.
  • Metadata service. A sharded, replicated key-value store mapping (bucket, key) to the current version and its chunk locations. It is partitioned by key, often by key prefix ranges that split as they get hot. Writes to it are the commit point: a PUT first writes all the data, then atomically records the new version. A crash before the commit leaves orphaned chunks that garbage collection reclaims later, never a half-visible object.
  • Placement. Chooses which storage nodes receive each chunk: spread across failure domains (disks, hosts, racks, availability zones), weighted by free space, and avoiding hot nodes. Ceph computes placement with a deterministic function (CRUSH) so clients need no lookup at all; S3 and Azure use placement services.
  • Storage nodes. Many disks per host, storing chunks in large append-only files rather than one file per object, so small objects do not each cost a file system inode and seek. Facebook's Haystack showed why: with one file per photo, the file system metadata lookups alone cost several disk reads per photo served.
  • Background work. Scrubbers re-read chunks and verify checksums to catch silent corruption; repair rebuilds chunks from failed disks; garbage collection reclaims deleted and orphaned data; lifecycle jobs move objects between tiers.

Durability: replication vs erasure coding

Disks fail at a rate of roughly 1 to 2% per year each, so a fleet of a million disks loses dozens a day. Durability comes from storing redundant data across independent failure domains and repairing faster than failures accumulate.

Replication

Store r full copies on different nodes. Three copies tolerate two simultaneous losses at 3× the storage. Reads are cheap (any copy), and repair copies one chunk. Simple, fast, and expensive at exabyte scale.

Erasure coding

Erasure coding splits an object into k data chunks and computes m parity chunks such that any k of the k + m chunks reconstruct the original. Reed-Solomon codes, written RS(k, m), are the standard. Storage overhead is (k + m) / k and the scheme tolerates m lost chunks.

How many nines does each buy? A simple model treats disk failures as independent and asks how likely it is that more chunks of one stripe fail within one repair window than the code tolerates:

from math import comb, expm1, log10, log1p

AFR = 0.02                       # 2% of disks fail per year
REPAIR_HOURS = 24                # time to detect a failure and rebuild the lost chunk
p = AFR * REPAIR_HOURS / 8760    # chance a given chunk's disk fails within one repair window
windows = 8760 / REPAIR_HOURS    # repair windows per year


def p_loss(total, tolerate):
    """Chance that more than `tolerate` of `total` chunks fail in the same window."""
    return sum(comb(total, i) * p**i * (1 - p)**(total - i) for i in range(tolerate + 1, total + 1))


schemes = {                      # name: (chunks stored, failures tolerated, storage overhead)
    "3x replication": (3, 2, 3.0),
    "RS(6,3)":        (9, 3, 9 / 6),
    "RS(10,4)":       (14, 4, 14 / 10),
}
for name, (n, m, overhead) in schemes.items():
    annual = -expm1(windows * log1p(-p_loss(n, m)))   # 1 - (1 - x)^windows, without rounding to 0
    print(f"{name:15} overhead {overhead:.1f}x   annual loss {annual:.1e}   ~{-log10(annual):.0f} nines")

# 3x replication  overhead 3.0x   annual loss 6.0e-11   ~10 nines
# RS(6,3)         overhead 1.5x   annual loss 4.1e-13   ~12 nines
# RS(10,4)        overhead 1.4x   annual loss 3.6e-16   ~15 nines

Treat the absolute numbers with suspicion: real failures are correlated (a power event, a bad firmware batch, a whole zone), and those dominate. The relative lesson holds, though. Erasure coding gives more fault tolerance for less storage, and faster repair improves durability sharply: annual loss scales roughly with the repair window raised to the power of the failures tolerated, so halving repair time cuts RS(10,4)'s loss about 16×.

What 11 nines means

S3 is designed for 99.999999999% (11 nines) annual durability of objects. That is an expected annual loss rate of 10-11 per object. AWS's own illustration: store 10 million objects and you can expect to lose one about every 10,000 years. Two things it does not mean:

  • It is not availability. S3 Standard is designed for 99.99% availability, so requests can fail for minutes a month while every byte stays safe.
  • It does not protect you from yourself. A buggy deletion job or a leaked credential destroys data at 100% "durability". Versioning, object lock and cross-account backups cover that risk.

Uploading large files

Multipart and chunked uploads

A single 4 GB PUT over a mobile connection fails at 3.9 GB and starts over. Multipart upload fixes that: start an upload and get an upload id, send the file as independent parts in parallel, retry any part that fails, then complete the upload with the list of part numbers and their ETags, which assembles the object atomically. In S3, parts are 5 MiB to 5 GiB (the last may be smaller), up to 10,000 per upload (so objects up to 48.8 TiB, raised from 5 TiB in December 2025), and a single plain PUT is capped at 5 GB. Parallel parts also raise throughput well beyond one TCP connection. Abandoned uploads keep their parts (and their storage cost) until aborted, so a lifecycle rule to abort incomplete multipart uploads after a few days is standard hygiene.

Resumable uploads

A resumable upload goes one step further for unreliable clients: the server creates an upload session with its own URL, the client sends bytes, and after a disconnect it asks "how much did you receive?" and continues from that offset. Google Cloud Storage's resumable uploads and the open tus protocol work this way, and YouTube and Vimeo uploads are built on the same idea.

Presigned URLs

Proxying every upload through your application servers wastes their bandwidth and memory. A presigned URL lets the client talk to the object store directly while your service keeps control: the server signs a URL that permits one operation (PUT this key, or GET this key), optionally with a fixed content type and size, for a short time.

  • Scope tightly. Sign for a key the server chooses (uploads/u42/7f3a9c.jpg), never one the client chooses, so a client cannot overwrite another user's object. Use a POST policy or signed headers to cap size and fix the content type.
  • Keep expiry short. Minutes, not days. A presigned URL is a bearer credential: anyone holding it can use it until it expires.
  • Trust the event, not the client. Mark the upload complete when the store's notification arrives (S3 event to a queue, then a worker), and validate the file there: real content type, size, malware scan, image dimensions. Then create thumbnails or transcodes.
  • Downloads too. Private files are served with short-lived presigned GET URLs, or through a CDN with signed URLs or cookies, so the application never streams bytes.

Content-addressed storage and deduplication

In content-addressed storage the key is a hash of the content: sha256(bytes). Identical content gets the same key, so it is stored once, and the key doubles as an integrity check. Git stores objects this way, container registries store image layers this way, and backup systems and Dropbox deduplicate at the chunk level: split files into chunks (fixed size, or content-defined chunking so an insertion does not shift every later boundary), hash each chunk, and upload only chunks the server does not already have. Editing one page of a 200 MB document then uploads a few megabytes.

The costs: deleting becomes reference counting, because a chunk may belong to many files, so deletes turn into a garbage collection job. And cross-user deduplication leaks information: if uploading a file completes instantly, the uploader learns someone else already has it. Systems that care deduplicate only within one user's data, or use convergent encryption with care.

Lifecycle and storage tiers

Access to stored objects drops sharply with age: last week's photos get viewed, last decade's almost never. Object stores offer tiers that trade retrieval cost and latency for cheaper storage, and lifecycle rules move objects between them automatically.

Watch the minimum durations and per-request fees: moving millions of tiny objects to a cold tier can cost more in transition requests than it saves.

Consistency

Since December 2020, S3 provides strong read-after-write consistency for all PUTs and DELETEs, including overwrites, and for LIST: once a write is acknowledged, every subsequent read and list sees it. Before that, overwrites and deletes were only eventually consistent, and a lot of folklore (and code) about "S3 eventual consistency" is now out of date. Google Cloud Storage and Azure Blob Storage are also strongly consistent.

Strong consistency is not concurrency control. Two clients that PUT the same key race, and the last write wins. For coordination, use conditional requests: S3 added If-None-Match: * (create only if absent) in 2024 and If-Match on an ETag (replace only if unchanged) shortly after; GCS has had generation preconditions for years. Or design keys so writers never collide: one key per upload, with the database recording which one is current.

Design decisions that follow:

  • Direct uploads with presigned URLs: 15 Gbit/s through application servers would need a fleet just to forward bytes.
  • Keys spread by a random component (u/7f3a9c.../orig.jpg) rather than by date, so no single metadata partition takes all of today's writes. S3 scales request rates per prefix automatically, but spreading keys still avoids warm-up throttling.
  • CDN in front for reads: popular photos are served from the edge, and the store sees mostly cache misses for the long tail. See CDN.
  • Tiering: originals move to infrequent-access after 30 days; resized versions, which are what most views use, stay hot longer.
  • Metadata in the database: one row per photo with owner, key, dimensions and status. The video platform case study follows the same pattern with a transcoding pipeline in place of thumbnailing.

In the real world

  • Amazon S3 stores objects across at least three availability zones for its standard classes and rebuilt its storage node software (ShardStore) in Rust with lightweight formal verification.
  • Facebook moved hot photos into Haystack (OSDI 2010), which packs many photos into large volume files and keeps the per-photo metadata in memory, then moved warm data to f4 (2014), which uses RS(10,4) within a data centre plus XOR across regions for an effective replication factor of 2.1 instead of 3.6.
  • Azure Storage uses Local Reconstruction Codes, which add local parity groups so that most single-chunk repairs read 6 chunks instead of 12.
  • Dropbox moved file storage from S3 to its own system, Magic Pocket, in 2016, using erasure coding and content-addressed blocks.
  • Ceph (open source) places objects with the CRUSH algorithm, so any client can compute where an object lives from the cluster map alone.
Interview angle

When to bring it up

Whenever a design stores files, images, video, documents or backups. Say: "Bytes go to an object store, metadata to the database, uploads go direct with presigned URLs, reads go through a CDN." Then size it, and mention erasure coding if the interviewer asks how the store itself works.

Follow-ups to expect

  • How does a client upload a 10 GB file over a flaky network? (Multipart or resumable, parallel parts, retries per part.)
  • How do you stop users from uploading to each other's paths? (Server-chosen keys in tightly scoped, short-lived presigned URLs.)
  • Replication or erasure coding, and what does each cost? (3× vs 1.4× storage; repair and read amplification.)
  • What does 11 nines of durability mean, and what does it not protect against?
  • How do you know an upload finished and is valid? (Store event, then server-side validation.)

Red flags

  • Storing images or video as BLOB columns in the main database.
  • Streaming every upload and download through application servers.
  • Presigned URLs valid for days, or with client-chosen keys.
  • Confusing durability with availability.
