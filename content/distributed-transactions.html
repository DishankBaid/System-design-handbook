Why it matters

A customer places order ord_1002 for one unit of sku-4471 at $29.99. Three things must happen: the order is recorded, a unit is reserved in inventory, and the card is charged. In a monolith with one database that is a single BEGIN ... COMMIT, and the database guarantees all three happen or none do. Split into an orders service, an inventory service and a payments service, each with its own database, and there is no longer any one system that can promise that.

Without a plan, partial failures leak into the business: a card charged for an order that does not exist, stock reserved forever for an order nobody paid for, an order confirmed but never shipped. A distributed transaction is any mechanism that keeps a multi-step update across several services or databases consistent despite crashes, timeouts and retries. There are two families: protocols that make the update atomic (two-phase commit), and patterns that accept intermediate states and make the update eventually consistent (sagas, outbox, TCC). Knowing when each is appropriate is what interviewers look for.

The dual-write problem

The smallest version of the problem has only one service. The orders service must save the order in its database and publish an OrderPlaced event to Kafka so that inventory and email can react. That is a dual write: two systems updated by one piece of code, with no transaction spanning both.

  • Commit, then publish. If the process crashes between the two, the order exists but no event is ever sent. Inventory never reserves stock, and the customer never gets an email.
  • Publish, then commit. If the commit then fails (a constraint violation, a deadlock, a crash), consumers react to an order that does not exist.
  • Retry on failure. Retrying the publish helps with transient broker errors, but not with a crash: the retry loop dies with the process.

No ordering of the two calls is safe, and the failure window is not theoretical. At 1,000 orders per second, a deploy that kills processes mid-request will hit it every time. Every pattern in this chapter is, at heart, a way to avoid relying on two independent writes both succeeding. The transactional outbox solves this specific case.

Two-phase commit

Two-phase commit (2PC) makes a transaction across several databases atomic. One node acts as coordinator; the databases are participants. Each participant has already done its part of the work inside a local transaction that is still open, with its locks held.

  1. Phase 1, prepare. The coordinator sends PREPARE to every participant. A participant that can commit writes everything needed to commit to its durable log, and replies YES. From that moment it has given up the right to abort on its own: it must commit if told to, even after a crash and restart. A participant that cannot commit replies NO.
  2. Decision. If every vote is YES, the coordinator writes COMMIT to its own log. That log write is the moment the transaction commits. Any NO or a timeout means ABORT.
  3. Phase 2, commit. The coordinator sends the decision to every participant, retrying until each one acknowledges. Participants apply it and release their locks.

Why 2PC is rare between services

2PC is a blocking protocol: a coordinator failure at the wrong moment freezes every participant's locked rows until the coordinator comes back. Database vendors ship tooling for operators to resolve in-doubt transactions by hand for exactly this reason (PostgreSQL lists them in pg_prepared_xacts). Beyond blocking, the costs are:

  • Locks held across the network. Rows stay locked from the participant's local work until phase 2 arrives. Hot rows become a throughput ceiling.
  • Every participant must be up. Availability is the product of all participants and the coordinator, as with any synchronous chain.
  • Every participant must speak the protocol. Databases support XA (the X/Open standard for 2PC). Kafka, Stripe, an email provider and most HTTP APIs do not.

Rough numbers for the time a hot row stays locked, assuming a 1 ms fsync:

Local transaction one commit fsync ≈ 1 ms → ~1,000 updates/s on one row 2PC, one data centre prepare RTT 0.5 + fsync 1 + coordinator log 1 + commit RTT 0.5 + fsync 1 ≈ 4 ms → ~250 updates/s 2PC, across regions 70 + 1 + 1 + 70 + 1 ≈ 143 ms → ~7 updates/s

Inside one database cluster, where the database owns both coordinator and participants, these costs are acceptable and 2PC is everywhere. Between independently owned microservices, it is almost never the right answer.

Three-phase commit

Three-phase commit (3PC, Skeen 1981) adds a PRE-COMMIT round between voting and committing, so that a participant that times out waiting can work out the decision from its peers instead of blocking. It is non-blocking only under assumptions real networks break: no partitions and bounded message delays. During a partition, two sides can reach different decisions. It costs an extra round trip and is almost never used in practice. The modern fix for blocking is different: make the coordinator itself fault tolerant.

2PC over consensus

Google Spanner runs 2PC where every participant and the coordinator are not single machines but Paxos groups, each replicated across zones. If the coordinator's leader dies, another replica of the same group takes over with the log intact, so the in-doubt window shrinks to a leader election. CockroachDB and YugabyteDB use the same idea with Raft. This is how distributed SQL databases offer serializable transactions across shards, and it is covered in Consensus & Leader Election. It works because one system owns every participant; it does not help when the participants are a payments API and a warehouse service.

Sagas

A saga (Garcia-Molina and Salem, 1987) splits a long business transaction into a sequence of local transactions, each committed immediately in one service. For every step that might need undoing there is a compensating transaction that semantically reverses it. If step k fails, the saga runs the compensations for steps k-1 down to 1.

A compensation is not a rollback. The original step committed and other transactions may already have seen its effect. Refunding a charge leaves both the charge and the refund on the customer's statement; cancelling an order leaves a cancelled order, not a missing one. Some actions cannot be compensated at all: an email cannot be unsent, so you send it last or send a correction.

Ordering the steps well removes most of the pain. Chris Richardson's classification is useful:

  • Compensatable steps come first. They can be undone (create a pending order, reserve stock).
  • The pivot step is the go/no-go point (charge the card). If it succeeds the saga will complete.
  • Retriable steps come after the pivot. They cannot fail for business reasons, only transiently, so they are retried until they succeed (confirm the order, send the email).

Choreography vs orchestration

There are two ways to drive a saga. In choreography, there is no central controller: each service listens for events and publishes its own. In orchestration, one component, the orchestrator, holds the saga's state machine and tells each service what to do next. The Event-Driven Architecture chapter discusses the same split more generally.

A minimal orchestrator

The core of an orchestrator is small: run steps in order, remember which ones completed, and on a business failure run their compensations in reverse, retrying each until it succeeds. The run below charges a test card that is always declined and injects one timeout into a compensation.

import time

# Three "services", each with its own local state (in reality: separate databases).
orders = {}                       # order_id -> status
stock = {"sku-4471": 5}           # sku -> units available
reservations = {}                 # order_id -> (sku, qty)
charges = {}                      # order_id -> amount in cents
flaky = {"release_stock": 1}      # inject one transient failure into a compensation


class Declined(Exception):
    pass


def create_order(o):   orders[o["id"]] = "PENDING"           # semantic lock: others see PENDING
def cancel_order(o):   orders[o["id"]] = "CANCELLED"


def reserve_stock(o):
    if o["id"] in reservations:                              # idempotent: a retry is a no-op
        return
    if stock[o["sku"]] < o["qty"]:
        raise Declined("out of stock")
    stock[o["sku"]] -= o["qty"]
    reservations[o["id"]] = (o["sku"], o["qty"])


def release_stock(o):
    if flaky["release_stock"]:
        flaky["release_stock"] -= 1
        raise TimeoutError("inventory timed out")
    sku, qty = reservations.pop(o["id"], (None, 0))          # idempotent: second call finds nothing
    if sku:
        stock[sku] += qty


def charge_card(o):
    if o["card"] == "4000-0000-0000-0002":                   # a test card that is always declined
        raise Declined("card declined")
    charges[o["id"]] = o["amount"]


def refund_card(o):    charges.pop(o["id"], None)
def confirm_order(o):  orders[o["id"]] = "CONFIRMED"


SAGA = [  # (step, compensation). The charge is the pivot: steps after it must not fail for business reasons.
    (create_order, cancel_order),
    (reserve_stock, release_stock),
    (charge_card, refund_card),
    (confirm_order, None),
]


def run_saga(o, steps=SAGA, retries=5):
    done = []   # a real orchestrator persists this log after every step, so it can resume after a crash
    for action, compensate in steps:
        try:
            action(o)
            print(f"  ok    {action.__name__}")
            done.append(compensate)
        except Declined as e:
            print(f"  FAIL  {action.__name__}: {e}")
            for comp in reversed(done):                      # undo completed steps, newest first
                if comp is None:
                    continue
                for attempt in range(1, retries + 1):        # compensations must eventually succeed
                    try:
                        comp(o)
                        break
                    except TimeoutError as err:
                        print(f"  retry {comp.__name__} (attempt {attempt}: {err})")
                        time.sleep(0.01 * 2 ** attempt)      # exponential backoff
                else:
                    raise RuntimeError(f"{comp.__name__} keeps failing: park the saga for a human")
                print(f"  undo  {comp.__name__}")
            return "aborted"
    return "committed"


print("order 1001:", run_saga({"id": 1001, "sku": "sku-4471", "qty": 2, "amount": 5998, "card": "4242-4242-4242-4242"}))
print("order 1002:", run_saga({"id": 1002, "sku": "sku-4471", "qty": 1, "amount": 2999, "card": "4000-0000-0000-0002"}))
print("orders:", orders, "| stock:", stock, "| charges:", charges)

#   ok    create_order
#   ok    reserve_stock
#   ok    charge_card
#   ok    confirm_order
# order 1001: committed
#   ok    create_order
#   ok    reserve_stock
#   FAIL  charge_card: card declined
#   retry release_stock (attempt 1: inventory timed out)
#   undo  release_stock
#   undo  cancel_order
# order 1002: aborted
# orders: {1001: 'CONFIRMED', 1002: 'CANCELLED'} | stock: {'sku-4471': 3} | charges: {1001: 5998}

Three properties carry over to every real implementation:

  • Durable progress. The done list lives in memory here. A real orchestrator writes the saga's state to a database after each step, so a crash halfway resumes instead of leaving the order PENDING forever. This is exactly what workflow engines such as Temporal provide.
  • Idempotent steps and compensations. After a crash, the orchestrator cannot know whether its last command was applied, so it sends it again. reserve_stock and release_stock must tolerate being called twice. See Idempotency & Delivery Semantics.
  • Compensations must not fail for business reasons. "Refund declined" is not an acceptable outcome. If a compensation still fails after retries, the saga is parked and a human is paged.

Sagas have no isolation

A saga is atomic in the eventual sense (all steps or all compensations) and each step is durable, but it gives up the I in ACID. Other requests see the intermediate states. Between T2 and C2 in the figure, a reporting query counts one unit as reserved, and another customer may see "out of stock" for an order that is about to be cancelled. The anomalies are the classic ones from ACID & Isolation Levels: lost updates, dirty reads of uncommitted saga effects, and non-repeatable reads across steps.

Countermeasures, in rough order of how often they are used:

Semantic lock

A step sets a status flag such as PENDING or APPROVAL_PENDING. Other operations check it and either refuse ("order is being processed"), wait, or treat it as tentative. The order's status field is a lock that lives in application data.

Commutative updates

Design updates so order does not matter: stock = stock - 1 and stock = stock + 1 commute, while "set stock to 4" does not. Compensations become safe no matter what ran in between.

Pessimistic view

Reorder steps so the riskiest dirty read cannot happen. For example, increase a credit limit only in a retriable step after the pivot, so nobody spends credit that might be rolled back.

Reread value

Before overwriting a record, reread it and check it has not changed since the saga last read it (optimistic concurrency with a version number). If it has, abort and maybe restart.

Version file

Record operations as they arrive so they can be reordered: if a cancel arrives before the create it cancels, remember the cancel and apply it when the create shows up.

By value

Choose the mechanism per request based on risk: low-value orders use a saga, high-value transfers use a stronger protocol or manual review.

The transactional outbox

Every step of a choreographed saga, and every service that publishes events, hits the dual-write problem from the start of the chapter. The transactional outbox removes it by turning two writes into one. The service writes the business row and the event row to an outbox table in the same local transaction. A separate relay reads committed outbox rows and publishes them to the broker.

BEGIN;
INSERT INTO orders (id, customer_id, status, total_cents)
VALUES ('ord_1002', 'cus_88', 'PENDING', 2999);

INSERT INTO outbox (event_id, aggregate_id, type, payload)
VALUES ('9b2f6c1e-5d4a-4f0e-8a51-3f7d2c9e1b04', 'ord_1002', 'OrderPlaced',
        '{"order_id":"ord_1002","sku":"sku-4471","qty":1,"total_cents":2999}');
COMMIT;

There are two ways to build the relay:

  • Polling publisher. A job runs SELECT ... FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 500, publishes the batch, then marks the rows published. Simple and portable. Costs a polling query and adds up to one polling interval of latency. Multiple relay instances need either a single leader, which preserves order, or FOR UPDATE SKIP LOCKED, which avoids double work but lets events for the same aggregate publish out of order unless rows are partitioned by aggregate id.
  • Change data capture (CDC). A connector such as Debezium tails the database's replication log (PostgreSQL logical decoding, MySQL binlog) and turns each committed outbox insert into a Kafka message. No polling load, latency in milliseconds, and commit order is preserved. The cost is running Kafka Connect and depending on log retention and replication slots.

Either way the relay can crash after publishing and before recording that it did, so it publishes some events twice. The outbox gives at-least-once delivery; consumers make it effectively-once by recording processed event ids, in the same transaction as their own writes. Clean up old outbox rows on a schedule, or with CDC delete them right after insert, since the log already captured them. The mirror image on the consuming side is the inbox pattern: a processed_events table with a unique key on event_id.

Try-Confirm-Cancel

Try-Confirm-Cancel (TCC) is a reservation-based protocol that sits between 2PC and sagas. Each participant exposes three operations:

  1. Try checks business rules and reserves resources without making them final: hold $29.99 on the card, mark one unit of sku-4471 as reserved for ord_1002 until 10:15:00.
  2. Confirm turns every reservation into the real thing (capture the hold, decrement stock). Called only if every Try succeeded. Must be idempotent and must succeed if Try did.
  3. Cancel releases the reservations if any Try failed. Reservations also expire on their own, so a crashed coordinator does not leave resources held forever.

The structure is 2PC's prepare and commit, implemented in business logic instead of in the database. The differences that matter: participants never hold database locks between phases, only business-level reservations with timeouts, so nothing blocks; and the intermediate state is explicit ("reserved", "on hold") rather than invisible. Card networks already work this way (authorise, then capture or void), which is why TCC fits payments, ticket booking and inventory well. The cost is three APIs per participant instead of one, plus handling the awkward cases: a Cancel that arrives before its Try (record it and reject the late Try), and a Confirm retried after a timeout.

The question to ask first is whether you need a distributed transaction at all. If two pieces of data must always change together, they may belong in the same service and the same database, where an ordinary transaction does the job. Redrawing a boundary is often cheaper than coordinating across it; see Monolith vs Microservices.

In the real world

  • Google Spanner: 2PC across shards where every participant is a Paxos group, plus TrueTime timestamps for external consistency. CockroachDB and YugabyteDB follow the same model with Raft.
  • Uber Cadence and Temporal: Uber built Cadence to run long-lived workflows such as trips and payments as durable code; its creators later forked it as Temporal. Workflows are ordinary functions whose progress is persisted after every step, so a saga survives worker crashes and can wait days for a timer or signal. AWS Step Functions offers the same orchestration model as a managed service.
  • Debezium: the open-source CDC platform on Kafka Connect, with connectors for PostgreSQL, MySQL, SQL Server, MongoDB and others, and a built-in outbox event router that turns outbox rows into properly keyed Kafka messages.
  • PostgreSQL and MySQL: both support being a 2PC participant (PREPARE TRANSACTION and XA PREPARE). PostgreSQL disables it by default (max_prepared_transactions = 0) precisely because forgotten prepared transactions hold locks indefinitely.
  • Payment networks: card authorisation followed by capture or void is TCC in production at enormous scale. A hold that is never captured expires on its own after some days.
Interview angle

When to bring it up

Whenever one user action changes data owned by two services: checkout (order, payment, inventory), money transfer between accounts on different shards, booking a trip (flight, hotel, car). Name the pattern and its consistency model in one breath: "an orchestrated saga with compensations, events published through an outbox, idempotent consumers".

Follow-ups to expect

  • Why not 2PC? Blocking on coordinator failure, locks held across the network, participants that do not support it.
  • What does the user see while the saga is running? A PENDING state, and what the UI shows for it.
  • What if a compensation fails? Retry with backoff, compensations must be idempotent, park and alert as a last resort.
  • How do you publish an event reliably after a DB write? Transactional outbox, polling or CDC relay, at-least-once delivery.
  • How do you prevent double-charging if the orchestrator retries? Idempotency key per saga step.

Red flags

  • "Write to the database and then publish to Kafka" with no answer for a crash in between.
  • Calling a compensation a rollback and assuming nobody saw the intermediate state.
  • Reaching for 2PC across HTTP microservices or third-party APIs.
  • No idempotency anywhere in a design that retries.
