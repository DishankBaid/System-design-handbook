Why it matters

Every production request passes through software that is neither the client nor your service: something that terminates TLS, checks a token, picks a backend and writes an access log. Put that work in the right box and forty services stay small and focused. Put it in the wrong box, or let one box swallow everything, and you get a slow, fragile choke point that every team has to queue behind.

A proxy is a server that sits in the middle of a connection and speaks the protocol on both sides: it accepts a request from one party, makes its own request to another, and relays the answer. RFC 9110 names three kinds of HTTP intermediary: a proxy chosen by the client, a gateway (also called a reverse proxy) that acts as the origin for whoever calls it, and a tunnel that blindly relays bytes. The practical questions for a system design are simpler: whose side is the proxy on, and which cross-cutting jobs belong in it?

This chapter covers forward and reverse proxies, what a reverse proxy actually does for a backend, the API gateway and its pipeline, the backend-for-frontend pattern, and how a service mesh moves the same ideas inside the cluster. Spreading load across backends has its own chapter, Load Balancing; edge caching is in Content Delivery Networks.

Forward vs reverse proxy

Both are the same kind of program. The difference is who deploys it, who knows it exists, and who it hides.

How a forward proxy handles HTTPS

For plain HTTP the client sends the full URL to the proxy (GET http://example.com/a HTTP/1.1) and the proxy fetches it. For HTTPS the client sends CONNECT github.com:443; the proxy opens a TCP connection to that host and from then on relays encrypted bytes it cannot read. It sees the hostname, and can allow or deny it, but not the paths or bodies. Inspecting HTTPS content requires the proxy to terminate TLS with its own certificate authority installed on every client, which is what corporate "TLS inspection" products do.

Forward proxies are not only for offices. Server fleets use them as an egress proxy: every outbound call from your services leaves through one controlled point. That gives partners a fixed set of source IPs to allowlist, and it blocks server-side request forgery (SSRF), where an attacker tricks your webhook sender into calling http://169.254.169.254/ or an internal admin API. Stripe open-sourced its egress proxy, Smokescreen, for exactly this.

What a reverse proxy does for a backend

A reverse proxy earns its place by doing work that is identical for every service and expensive to get right in each one. The list below is roughly the order in which a request meets each job.

TLS termination

The proxy holds the certificates and performs the TLS handshake (see TCP, UDP & HTTP for the round trips). Backends receive plain HTTP, or a re-encrypted connection on a long-lived internal link. Centralising this means one place to rotate certificates, enforce TLS 1.2+, enable HTTP/2 and HTTP/3 to clients, and automate certificate renewal. Whether the hop from proxy to backend stays encrypted is a security decision, not a performance one: in a zero-trust network it is re-encrypted, often with mutual TLS (see Security Fundamentals).

Buffering slow clients

This is the least obvious job and often the most valuable. Many application servers handle one request per worker (gunicorn sync workers, Unicorn, PHP-FPM). A worker that writes a response directly to a phone on a weak connection is stuck until the last byte leaves.

Response 400 KB = 3,200 kbit Client link 1 Mbps → 3.2 s to deliver App work per request 20 ms Pool of 200 workers, no proxy buffering each request holds a worker 3.2 s → 200 / 3.2 ≈ 62 req/s With a buffering proxy in front worker hands 400 KB to the proxy over the LAN in ~1 ms and is free each request holds a worker ~20 ms → 200 / 0.02 = 10,000 req/s

The proxy, built on an event loop, holds thousands of slow connections cheaply, each costing a few kilobytes of buffer rather than a whole worker process. NGINX does this in both directions by default: proxy_request_buffering reads the whole request body before contacting the backend, and proxy_buffering reads the backend's response as fast as the backend can send it. The same property protects against Slowloris, an attack that opens many connections and sends headers one byte at a time to exhaust worker pools. Buffering is the wrong choice for streaming responses (server-sent events, large downloads, gRPC streams), which is why it can be switched off per route; see Polling, SSE & WebSockets.

Compression and caching

The proxy can gzip or Brotli-compress text responses based on the client's Accept-Encoding, which often shrinks JSON and HTML several times over and spends proxy CPU instead of application CPU. It can also cache. Even a one-second microcache on a hot, public endpoint changes the load picture: if a product page gets 5,000 requests per second through each proxy, the backend sees about one request per second per proxy for that URL, provided the proxy collapses concurrent misses into one upstream fetch (NGINX proxy_cache_lock). Cache keys, Cache-Control and invalidation are covered in Content Delivery Networks and Caching.

Connection management and headers

  • Connection reuse. Clients open short-lived connections; the proxy keeps a warm pool of keep-alive connections to each backend, so the backend never pays for TCP and TLS setup per client.
  • Protocol translation. HTTP/2 or HTTP/3 to the browser, HTTP/1.1 or gRPC to the backend.
  • Client identity. The backend now sees the proxy's IP as the source. The proxy passes the original in X-Forwarded-For and X-Forwarded-Proto, or the standard Forwarded: for=203.0.113.7;proto=https header from RFC 7239. Backends must only trust these headers when the request came from a known proxy, otherwise any client can claim any IP.
  • Routing and load balancing. Choosing a backend pool by host and path, and a server within the pool. The Load Balancing chapter covers algorithms and health checks.

API gateways

An API gateway is a reverse proxy specialised for APIs: it understands identities, API keys, quotas, routes and versions, not just hosts and paths. It is the single entry point between external clients and a fleet of services, and its job is to do the cross-cutting work once so the services behind it do not each reimplement it.

Authentication

Validate the API key, session cookie or JWT signature and expiry. Forward a trusted identity header such as X-User-Id. Fine-grained authorisation ("may this user cancel this order?") stays in the service that owns the order.

Rate limiting and quotas

Per key, per user or per IP limits, plus monthly quotas for paid plans. Rejects with 429 before any backend work happens. Algorithms are in Rate Limiting.

Routing

Map /v2/orders/* to orders-svc, split 5% of traffic to a canary, route by header or tenant. Backend addresses come from service discovery.

Transformation

Rename fields, add or strip headers, translate REST and JSON to gRPC, keep a deprecated v1 shape alive by mapping it onto v2.

Aggregation

Answer one client call by calling several services and merging the results. Useful in small doses; in large doses it becomes a BFF (below).

Observability

Assign a request ID, start the trace, emit an access log and per-route latency and error metrics. See Observability.

The request pipeline

Internally a gateway is a chain of filters (Envoy calls them HTTP filters, Kong calls them plugins, Spring Cloud Gateway calls them filters too). Each stage can pass the request on, modify it, or end it with a response. Order matters: put the cheapest rejection first so abusive or invalid traffic costs as little as possible.

Two ordering details come up in practice. A coarse per-IP limit usually runs before authentication, because verifying signatures and looking up API keys costs CPU and an attacker can send unlimited garbage tokens. The fine-grained per-identity limit runs after, since it needs to know who is calling. The diagram shows only the per-identity limiter. Second, timeouts and retries at the gateway must be shorter than the client's own timeout and coordinated with the services' retries, or a single slow dependency multiplies into a retry storm. Timeouts, Retries & Circuit Breakers covers retry budgets.

Common mistake

Trusting X-User-Id on the service side without making sure only the gateway can reach the service. If a pod is reachable directly, anyone inside the network can set that header and become any user. Lock services down with network policy or mutual TLS so the gateway is the only caller that can assert identity, or pass a signed token instead of a bare header.

Backend for frontend

A single general-purpose gateway serves every client the same API. Real clients differ. A web page on fibre can afford a 200 KB response and five calls; a phone on a congested cell link cannot, and wants one call returning exactly the fields its screen shows. A TV app needs yet another shape. When one API tries to serve all of them it either grows a parameter for every client's whim or forces every client to over-fetch and stitch.

The backend for frontend (BFF) pattern, popularised by Sam Newman, gives each kind of client its own thin server-side API, owned by the team that builds that client. The BFF calls shared domain services, fans out in parallel inside the data centre, and returns one response shaped for one screen.

  • Ownership is the point. A BFF is owned by the client team. If a central platform team owns all the BFFs, they become one shared gateway again, with a queue of feature requests in front of it.
  • Keep it thin. A BFF composes, trims, formats and caches. It owns no database tables and makes no business decisions. If a rule ("orders over $500 need review") appears in two BFFs, it belongs in a domain service.
  • Edge concerns stay at the edge. TLS, authentication and coarse rate limits usually still run in a shared gateway in front of the BFFs, so each BFF does not reimplement them.
  • GraphQL is the main alternative. One flexible endpoint lets each client ask for exactly the fields it needs, which removes much of the reason for per-client BFFs, at the cost of query-cost control and caching complexity. See API Design.

Worked example: a mobile home screen through a BFF

A shopping app's home screen needs data from five services. The phone is on a mobile network with a 100 ms round-trip time to the data centre, and connections are already warm (no TCP or TLS setup). The gateway adds 2 ms. Two calls depend on the profile, because the feed and recommendations are personalised by the user's segment.

Three lessons come out of the numbers. First, round trips over the slow link dominate: server time (90 to 160 ms) is small next to the round trips; the difference is how many 100 ms trips the phone makes. A careful client (option B) gets most of the way, but the dependency between profile and feed forces a second trip that only a server-side composer can remove. Second, payload matters as much as latency on mobile: trimming 180 KB to 24 KB saves more time than the fan-out does, plus battery and the user's data plan. Third, the BFF's own latency is set by its slowest dependency chain, profile then recommendations at 92 ms of the 95 ms server time. Speeding up the feed would change nothing.

Fan-out amplifies tail latency

The BFF's speed comes from calling services in parallel, and parallel fan-out has a cost: the response is only as fast as the slowest call. If each dependency has a 1% chance of a slow response, a request that waits on several of them hits at least one slow call far more often than 1%.

import random

random.seed(7)


def call_latency_ms():
    # 99% of calls take 8-12 ms; 1% hit a slow path (GC pause, cold cache) of 200 ms
    return 200 if random.random() < 0.01 else random.uniform(8, 12)


def median(samples):
    return sorted(samples)[len(samples) // 2]


for fanout in (1, 5, 20, 100):
    # a fan-out request finishes when its slowest parallel call finishes
    trials = [max(call_latency_ms() for _ in range(fanout)) for _ in range(20_000)]
    slow = sum(t >= 200 for t in trials) / len(trials)
    print(f"fan-out {fanout:>3}: {slow:6.1%} slow (theory {1 - 0.99 ** fanout:6.1%}), median {median(trials):.0f} ms")

# fan-out   1:   1.0% slow (theory   1.0%), median 10 ms
# fan-out   5:   4.8% slow (theory   4.9%), median 12 ms
# fan-out  20:  18.5% slow (theory  18.2%), median 12 ms
# fan-out 100:  63.2% slow (theory  63.4%), median 200 ms

The formula is 1 - 0.99^n: the home screen above, waiting on five calls, sees one dependency's p99 on about 5% of requests, so its own p95 is roughly its dependencies' p99. At a fan-out of 100 the slow path becomes the median. Keep BFF fan-out small, give each call a tight timeout with a fallback (render the screen without recommendations rather than wait), and for idempotent reads consider hedged requests: send a second copy to another replica if the first has not answered by the p95 time.

Gateway vs service mesh

A gateway handles north-south traffic: requests entering or leaving the system. Most traffic in a microservice system is east-west: service to service inside the cluster. That traffic needs many of the same things (encryption, retries, timeouts, load balancing, metrics), and putting a central gateway in the middle of every internal call would add a hop and a bottleneck to all of it.

A service mesh solves this by giving every service instance its own proxy, a sidecar, deployed in the same pod. The application talks plain HTTP to localhost; its sidecar intercepts the traffic, finds a healthy instance of the destination, opens a mutual-TLS connection to the destination's sidecar, applies timeouts and retries, and records metrics and trace spans. The sidecars form the data plane. A control plane (Istio's istiod, for example) pushes routes, policies and certificates to them.

TrafficNorth-south: external clients to servicesEast-west: service to service

The two overlap heavily in mechanism (Istio's ingress gateway is just Envoy at the edge) and they are complements, not rivals: a common shape is a gateway at the edge and a mesh inside. The mesh's costs are real: two extra proxy hops on every internal call, each typically adding well under a millisecond to a few milliseconds; a proxy's memory and CPU multiplied by every pod; and a control plane that is now critical infrastructure. These costs pushed the newer sidecarless designs, where a shared per-node proxy handles encryption and a smaller set of proxies handles HTTP features (Istio's ambient mode), or where the kernel does part of the work with eBPF (Cilium). How services find each other with or without a mesh is in Service Discovery.

Risks and how to contain them

Single point of failure

Every external request crosses the gateway, so its availability caps the whole product's availability. Run it as a stateless, horizontally scaled fleet across zones, behind an L4 load balancer or anycast address (see Load Balancing). Keep its hot path free of synchronous calls to anything less available than itself: validate JWTs locally with cached signing keys rather than calling the identity service on each request, and make the rate limiter fail open if its counter store is unreachable. The most dangerous failure is not a crashed instance but a bad configuration push, which breaks every instance at once. Roll gateway config out like code: validated, canaried on a slice of traffic, and quick to revert.

Added latency

Each proxy hop costs a little: parsing, filter execution, and an extra network hop, usually around a millisecond inside one data centre with warm connections. That is negligible against a 100 ms mobile round trip, but it adds up when a request crosses a CDN, a load balancer, a gateway, a BFF and two sidecars per internal call. Count hops on the critical path, keep connection pools warm at every hop, and watch for filters that do I/O (an external auth call or a remote rate-limit check adds its own network round trip).

The gateway becoming a monolith

Because every request passes through it, the gateway is a tempting place to put "just one more rule": a special case for one customer, a field mapping for one screen, a check that really belongs to the orders domain. After a few years it holds business logic from every team, deploys need sign-off from all of them, and it has become the enterprise service bus that microservices were meant to replace. The rule of thumb is smart endpoints, dumb pipes: the gateway does generic, policy-driven work that is the same for every service; anything that needs domain knowledge lives in a service or a BFF owned by the team that has that knowledge.

In the real world

  • NGINX began as a web server built to solve the "C10k" problem with an event loop, which is exactly why it is good at buffering slow clients in front of process-per-request application servers. It remains the default reverse proxy in front of countless Rails, Django and PHP apps.
  • HAProxy is a high-performance TCP and HTTP proxy, best known as a load balancer, used at the edge of high-traffic sites such as Stack Overflow.
  • Envoy, built at Lyft, is designed to be configured dynamically by a control plane through its xDS APIs. It is the data plane of Istio, the engine of Envoy Gateway, and the base of many commercial gateways.
  • Kong is an API gateway built on NGINX and OpenResty, with authentication, rate limiting and transformation shipped as plugins.
  • AWS API Gateway is a managed gateway: Lambda or Cognito authorisers for auth, usage plans with API keys for quotas, and request mapping templates for transformation. You give up some control and pay per request in exchange for running no proxy fleet.
  • Netflix Zuul is the edge gateway in front of Netflix's streaming API, and Netflix's earlier API platform let device teams deploy their own adapter scripts on the server, an early form of backend for frontend.
  • Linkerd runs a purpose-built Rust micro-proxy as its sidecar instead of Envoy, trading features for a smaller footprint per pod.
Interview angle

When to bring it up

In nearly every design, as one box on the diagram: "Clients reach us through an API gateway that terminates TLS, authenticates, rate limits and routes to services." Spend more time on it when the prompt has several client types (propose a BFF), a public developer API (keys, quotas, versioning), or many internal services (mention a mesh for mTLS and retries, and its cost).

Follow-ups to expect

  • What is the difference between a forward and a reverse proxy? Who deploys each and what each hides.
  • Why put NGINX in front of an application server at all? Buffering slow clients, TLS, compression, connection reuse.
  • Is the gateway a single point of failure? Stateless fleet across zones, local JWT validation, fail-open limiter, canaried config.
  • Where does authorisation live? Authentication at the gateway; resource-level authorisation in the owning service.
  • Gateway or service mesh? North-south vs east-west, and usually both.
  • Your BFF calls eight services. What happens to p99? Tail amplification, timeouts with partial responses, hedging.

Red flags

  • Putting business rules or data in the gateway.
  • A gateway that calls an auth service synchronously on every request with no caching.
  • Services that trust identity headers while being reachable without going through the gateway.
  • Adding a service mesh to a five-service system without naming the problem it solves.
