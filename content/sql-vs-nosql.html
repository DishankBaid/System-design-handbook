Why it matters

Picking a database is the one early decision that is genuinely expensive to undo. Code can be refactored in a sprint; moving two billion rows to a different data model, while the product keeps running, takes quarters. In an interview, "which store and why" is where the interviewer learns whether you reason from access patterns or from fashion.

The question is usually framed as "SQL or NoSQL", which is the wrong frame. "NoSQL" is not one thing. It is a label for at least five different data models that have little in common except that they are not relational. The useful question is: given how this data is written and read, which data model makes the common operations cheap and the important invariants easy to keep?

This chapter walks through each family using the same small dataset, a customer and her orders, so the differences are concrete. Then it gives a decision framework, covers NewSQL, retires a few myths, and picks stores for a real e-commerce system.

The relational model

In 1970 Edgar Codd proposed storing data as relations: sets of rows (tuples) with named, typed columns, where relationships are expressed by values rather than by pointers. An order does not contain a pointer to its customer; it contains user_id = 42, and any query can follow that value to the users table with a join. You declare what you want in SQL and the query planner decides how to fetch it, choosing indexes and join algorithms from statistics about the data.

What it is good at

  • Ad-hoc queries. Because data is stored once in a neutral shape, you can ask questions nobody planned for: revenue by country by week, customers who ordered twice but never reviewed. Add an index and the query is fast. Other models make you design for each question up front.
  • Integrity enforced by the database. Foreign keys, UNIQUE, CHECK and NOT NULL constraints hold no matter which service or script writes the data. In a document store these rules live in application code, and every writer must remember them.
  • Multi-row transactions. Moving money between two accounts, or decrementing stock while inserting an order, happens atomically and in isolation from other transactions. See ACID & Isolation Levels.
  • Normalization. Each fact is stored once (Data Modeling covers the normal forms), so updating a customer's email is one row, not a hunt through every document that copied it.
  • Maturity. Fifty years of query optimisation, tooling, backups, replication and people who know how to run it at 3 a.m.

Where it strains

  • One primary for writes. A classic PostgreSQL or MySQL deployment accepts writes on a single node. Read replicas scale reads, but write throughput and data size are bounded by one machine until you shard, and sharding a relational database by hand gives up cross-shard joins and transactions. See Sharding.
  • Rigid schema changes on huge tables. Adding a column is instant in modern PostgreSQL, but changing a type or backfilling a column on a 2 TB table needs careful online migration tooling.
  • The object-relational mismatch. Application code works with nested objects (an order with its items and shipping address); the database stores flat rows. ORMs bridge the gap, and that bridge is where N+1 query bugs come from.

The non-relational families

Each family below gave up some part of the relational model (joins, a fixed schema, multi-row transactions, or a general query language) to gain something specific: easier partitioning, a data shape closer to the application, or much faster writes. Step through the same customer, Asha (user 42), with her two orders, in each model.

Key-value stores

A key-value store is a giant distributed hash map: GET key, PUT key value, DELETE key. The value is opaque bytes, so the store cannot filter on anything inside it. That restriction is the point. Every operation touches exactly one key, so the data partitions trivially by hashing the key (see Consistent Hashing), and latency is predictable: Redis answers in well under a millisecond from memory, DynamoDB in single-digit milliseconds at any table size.

The cost shows up the first time someone asks "find the user with this email". Either you scan everything, or the application maintains a second key (email:asha@example.com → 42) and keeps it in sync on every write, with no transaction to protect it. Use key-value stores when the key is always known: sessions, carts, rate-limit counters, feature flags, cached objects, idempotency keys.

Document stores

A document store keeps self-describing, nested records (JSON or BSON) grouped in collections. Unlike key-value, the store understands the structure: MongoDB can index email or orders.created and filter on them. The big win is locality: an aggregate that is always read together (a product page with its variants, a user profile with settings) is one document, fetched with one disk read and no joins, in the same shape the code uses.

The trade-off is relationships. Embedding works for one-to-few data that belongs to its parent. It breaks for many-to-many data (products appear in many orders; you do not copy the product into each) and for unbounded growth (a user with 40,000 orders makes a 40,000-element array, and MongoDB caps a document at 16 MB). Then you reference by id and do the join in application code, which is a slower, hand-written version of what SQL does for you. Schema flexibility is real but is better described as schema-on-read: the schema still exists, it just lives in every piece of code that reads the data.

Wide-column stores

Cassandra, ScyllaDB, HBase and Google Bigtable are usually called wide-column stores, a name inherited from Bigtable's column families. The model that matters in practice is a two-part primary key. The partition key (here user_id) is hashed to pick the nodes that own the data. The clustering key (here created_at, order_id) keeps rows sorted inside that partition on disk. "The 20 newest orders for user 42" becomes one seek and a sequential read on one node.

These stores are built on LSM trees, so writes are sequential appends and a cluster can absorb millions of writes per second. In return, queries must name the partition: there are no joins, secondary indexes are limited, and you usually store the same data several times, once per query (an orders_by_user table and an orders_by_day table). You design tables from queries, not from entities. Discord's message store (trillions of messages, partitioned by channel and time bucket) is the canonical fit.

Graph databases

A graph database stores nodes and typed edges with properties, and its query languages (Cypher, Gremlin, SPARQL) express paths: "products bought by people who bought what Asha bought". In SQL that is a chain of self-joins whose number must be fixed in the query; recursive CTEs can do variable depth but get slow as depth grows. Native graph engines like Neo4j store adjacency directly, so each hop costs roughly the number of edges followed, not a lookup in a table-wide index.

Use a graph store when traversal is the main workload: fraud rings (accounts sharing devices and cards), access-control hierarchies, knowledge graphs, network topology. Do not use one as a general-purpose system of record; graph databases are hard to partition, because any cut through a graph severs edges that queries will want to follow.

Time-series databases

A time-series database stores measurements: a metric name, a set of tags, a timestamp and values. Data arrives in time order, is almost never updated, is queried by time range with aggregation (rate per minute, p99 per hour), and loses value as it ages. Engines exploit all four facts. Facebook's Gorilla showed that delta-of-delta timestamps and XOR-compressed floats shrink a 16-byte point to about 1.37 bytes on average. Old data is downsampled and whole time chunks are dropped at once instead of deleting rows one by one. Prometheus, InfluxDB and TimescaleDB (a PostgreSQL extension) are common choices. Note that the orders themselves do not belong here; the per-minute order rate does.

Search engines

Elasticsearch, OpenSearch and Solr store documents in an inverted index (term to list of documents) and rank results by relevance. They answer "running shoes waterproof" with typo tolerance, stemming and facets, which no B-tree index can do well. They are almost always a secondary store: fed from the system of record via change data capture, rebuilt from it if lost, and never the place where an order is first committed. The Search & Inverted Indexes chapter covers how they work.

A decision framework

Four questions, asked in this order, settle almost every choice. Write the main queries down first, with rough rates; the answers fall out of them.

1. Access pattern

List the reads and writes the system must serve and how often. "Get cart by user id, 20k/s" is a key-value pattern. "Latest 50 messages in a channel, 100k/s" is a partition-plus-range pattern. "Revenue by category last quarter, a few times a day" is an analytical query that belongs in a warehouse, not in the operational store. If the list includes many different filters on the same data, or you cannot predict the queries yet, that is a strong signal for relational.

2. Consistency and invariants

Ask which rules must never be broken. "Stock never goes below zero", "a seat is sold once", "a transfer debits and credits or does neither". Rules that span rows need multi-row transactions or a careful single-row design. Relational and NewSQL make these easy. In Cassandra you would need lightweight transactions on every write that touches the invariant, at several times the latency. If the data tolerates staleness (a like count, a product description), eventual consistency is fine and buys availability; see CAP & PACELC.

3. Scale, honestly estimated

Compute the numbers before reaching for a distributed store. A single PostgreSQL primary on modern hardware handles tens of thousands of simple writes per second and tens of terabytes of data, more with read replicas absorbing reads. Most products never exceed that. Reach for a natively partitioned store when sustained writes are in the hundreds of thousands per second, when the dataset is hundreds of terabytes, or when you need active writes in several regions. See Back-of-Envelope Estimation.

4. Schema shape and change

Heterogeneous records (a catalog where a laptop has ram_gb and a shirt has sleeve_length) fit documents naturally, though a relational table with a JSONB column also handles them. Strongly interconnected data with many-to-many relationships fits relational or graph. Schema flexibility is about who enforces the schema, not whether one exists.

Common mistake

Picking the store per system instead of per dataset. A real product has several datasets with different access patterns: orders, carts, a catalog, search, metrics. Using one database for all of them forces compromises; using a different store for each without reason multiplies operational cost. Choose per dataset, then consolidate where the differences do not matter.

NewSQL: SQL that shards itself

NewSQL (or distributed SQL) databases keep the relational model, SQL and ACID transactions (serializable by default in Spanner and CockroachDB; TiDB and YugabyteDB default to snapshot isolation), and partition data automatically across many nodes. Google Spanner (2012) proved it could be done at planet scale; CockroachDB, YugabyteDB and TiDB brought the design to everyone else.

The common architecture: the key space of every table and index is split into contiguous ranges (CockroachDB) or tablets/regions (YugabyteDB, TiDB). Each range is replicated three or five ways and kept consistent by a Raft or Paxos group. One replica holds a lease and serves reads and proposes writes. Ranges split when they grow or get hot and move between nodes to balance load, which gives you the elasticity of a NoSQL store with the semantics of a relational one.

What you pay for this:

  • Write latency. Every commit waits for a quorum of replicas. Within one region that is a millisecond or two of network; with replicas spread across regions it is a cross-region round trip, often 50 to 150 ms.
  • Clock uncertainty. Serializable ordering across nodes needs timestamps that mean something. Spanner uses TrueTime, GPS and atomic clocks with a bounded uncertainty of a few milliseconds, and waits out that uncertainty before acknowledging a commit (commit wait). CockroachDB uses hybrid logical clocks and restarts reads that hit values inside its uncertainty window.
  • Cross-range transactions cost more than single-range ones, and contention between transactions shows up as retries that the application must handle.
  • Operational complexity is lower than hand-sharding but higher than a single PostgreSQL node.

Do not confuse NewSQL with Amazon Aurora or AlloyDB. Those separate compute from a distributed, replicated storage layer, which makes storage, failover and read replicas far better, but they still have a single writer node (outside Aurora's separate Limitless sharded option). They scale storage and reads, not writes.

The lines have blurred

The 2010 version of this debate no longer describes the products. PostgreSQL has a binary JSON type (jsonb) with GIN indexes, so a relational table can hold schema-flexible documents and query inside them. MongoDB added multi-document ACID transactions in 4.0 (2018) and across shards in 4.2. DynamoDB has TransactWriteItems covering up to 100 items. Cassandra has lightweight transactions for compare-and-set. Even SQLite, in the Python standard library, can store JSON and return document-shaped results:

import json
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE users  (id INTEGER PRIMARY KEY, name TEXT, email TEXT UNIQUE);
CREATE TABLE orders (id INTEGER PRIMARY KEY, user_id INTEGER REFERENCES users(id),
                     total REAL, created_at TEXT,
                     attrs TEXT);                       -- free-form JSON column
CREATE INDEX orders_by_user ON orders(user_id, created_at);
INSERT INTO users  VALUES (42, 'Asha Rao', 'asha@example.com');
INSERT INTO orders VALUES (9001, 42, 64.50, '2026-10-02', '{"gift": true, "coupon": "FALL10"}'),
                          (9002, 42, 18.00, '2026-10-07', '{"gift": false}');
""")

# Relational storage, document-shaped answer: one query builds the aggregate.
row = db.execute("""
SELECT json_object('id', u.id, 'name', u.name,
         'orders', json_group_array(json_object('id', o.id, 'total', o.total)))
FROM users u JOIN orders o ON o.user_id = u.id
WHERE u.id = 42 GROUP BY u.id
""").fetchone()
print(json.loads(row[0]))

# Schema-flexible attributes, still queryable with SQL.
print(db.execute("SELECT id FROM orders WHERE json_extract(attrs, '$.coupon') = 'FALL10'").fetchall())

# {'id': 42, 'name': 'Asha Rao', 'orders': [{'id': 9001, 'total': 64.5}, {'id': 9002, 'total': 18.0}]}
# [(9001,)]

So the real question is rarely "can this database do X". It is "which operations does this engine make cheap by default, and which does it merely allow". A multi-document transaction in MongoDB works, but the engine and its documentation still steer you toward single-document atomicity. A JSONB column works, but a catalog that is 95% free-form attributes is fighting the relational planner, whose statistics know nothing about the inside of a JSON value.

Myths to retire

"NoSQL scales, SQL doesn't"

Relational databases scale; what is hard is scaling writes and joins across machines. YouTube ran MySQL behind Vitess, Instagram, Notion and Figma shard PostgreSQL, and Spanner is relational at global scale. Meanwhile a NoSQL store with a hot partition key does not scale either.

"NoSQL is schemaless"

The schema moved from the database into the code that reads the data. Every reader must handle every historical shape of every record, which is harder to get right than a migration.

"NoSQL can't do transactions"

Most can now, with limits: single-partition, a capped number of items, or higher latency. Know the limits of the one you pick.

"Joins are slow"

An indexed join of an order to its items on one machine costs a few page reads. What is slow is a join across shards or over unindexed columns. Avoiding joins by denormalizing moves the cost to writes and to keeping copies consistent.

"Pick the right database"

Singular. Large systems use several stores, a pattern called polyglot persistence, with one system of record per dataset and derived stores fed from it.

"Document stores are faster"

Reading one pre-assembled aggregate is faster than joining three tables. Updating a field duplicated in a million documents is much slower than updating one row. Speed depends on the access pattern, not on the family.

Two decisions here deserve to be said out loud in an interview. First, the derived stores are fed by change data capture (reading the database's replication log) rather than by services writing to two stores, because dual writes drift apart on partial failures; see Event Streaming. Second, if this store grew 50 times, the order database would be the first thing to change, by sharding by user_id or moving to a distributed SQL database, and the rest of the design would stay.

In the real world

  • Amazon DynamoDB descends from the 2007 Dynamo paper, written after shopping-cart outages during peak season. AWS's own guidance is to design DynamoDB tables from access patterns, often with several entity types in one table (see Data Modeling).
  • Discord stores trillions of messages in a wide-column store partitioned by channel and time bucket, moving from Cassandra to ScyllaDB in 2022 to cut tail latency, while its other data lives elsewhere.
  • Google built Bigtable (2006) for web-scale sparse tables, then Spanner (2012) partly because teams found Bigtable hard to use for applications that needed cross-row transactions and strong consistency across regions, as the Spanner paper explains.
  • Instagram, Notion and Figma all scaled on sharded PostgreSQL rather than switching data models, keeping SQL and transactions within each shard.
  • Uber built Schemaless, an append-only, sharded store on top of MySQL, which shows that the line between "SQL" and "NoSQL" is often just an API layered over the same engine.
Interview angle

When to bring it up

In the data model step of every design. State the main queries, then name a store per dataset with one sentence of reasoning: "Orders need atomic stock updates and the write rate is about 2k/s, so PostgreSQL; messages are append-heavy and always read by channel and time, so Cassandra partitioned by channel." Then move on.

Follow-ups to expect

  • Why not just use PostgreSQL for everything? (Often you can. Say what would force a change: write rate, data size, multi-region writes.)
  • Your NoSQL choice: how do you enforce a uniqueness constraint, like one account per email? (Conditional write on a key derived from the email.)
  • How do you query by a field that is not the partition key? (Secondary index, a second table, or a search engine fed by CDC.)
  • What happens to cross-entity transactions after you shard? (See Distributed Transactions.)
  • How does Spanner offer serializable transactions across continents, and what does it cost?

Red flags

  • "NoSQL because it scales" with no numbers showing that one relational node is not enough.
  • Putting money or inventory in an eventually consistent store without a plan for the invariants.
  • Using a search engine or cache as the system of record.
  • One database for clickstream analytics and order processing.
