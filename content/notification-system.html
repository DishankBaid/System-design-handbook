A notification system is the shared service every other team calls to reach users: "your order shipped" as a push notification, a login code by SMS, a receipt by email, a badge in the app. It has to send a billion messages a day through third-party providers that rate-limit, fail and occasionally lie, while respecting each user's preferences and quiet hours, never sending the same message twice, and making sure a one-time password is never stuck behind a marketing campaign.

How to use this case study

Sections follow the order of a real interview. Concepts used here have their own chapters: Message Queues (retries and dead letters), Idempotency, Rate Limiting, Timeouts, Retries & Circuit Breakers, Event Streaming.

1. Requirements

Functional

Other services send notifications by type and user. Channels: mobile push (APNs, FCM), SMS, email, in-app inbox. Per-user preferences by category and channel, and quiet hours in the user's time zone. Templates with localisation. Scheduled sends and bulk campaigns. Delivery, open and click tracking.

Non-functional

Critical messages (login codes, fraud alerts) delivered in seconds even during a campaign. No duplicates from the user's point of view. No silent loss: every notification ends delivered, suppressed by a rule, or in a dead-letter queue. Highly available, and resilient to any single provider failing.

Out of scope

Building SMS or email delivery infrastructure (we use providers), the campaign segmentation UI, and the content of notifications. Mention them, then park them.

The key observation: this is a pipeline of decisions in front of unreliable external providers. Most of the engineering is deciding whether, when, where and how to send, and then retrying sends safely. The send itself is an HTTP call to someone else's API.

Callers send a type and data, never rendered text or a channel list. That keeps wording, localisation and channel choice in one place, so the product team can change "Your order is on its way" without redeploying the order service, and the preference rules always apply. The API returns 202 because acceptance is all it can promise: delivery is asynchronous.

Notification categories carry policy. security (login codes, password changes) cannot be turned off and ignores quiet hours. transactional (orders, payments) can be moved between channels but not fully disabled. social and promotions are fully under the user's control and subject to frequency caps. Encoding this in the type registry, not in each caller, is what makes the system safe to call.

5. High-level design

  1. Accept. The API authenticates the calling service, validates the type and data against the type registry, checks the idempotency key and dedup key in Redis (a claimed key that has no notification row yet is treated as free, so a crash cannot swallow a retry), writes the notification row and an outbox entry in one transaction, relays the outbox to the Kafka topic for its priority, and returns 202.
  2. Plan. Planner workers consume from the priority topics (critical first), load the user's preferences and devices from cache, decide the channels, apply quiet hours and frequency caps, render the template per channel and locale, and write one delivery row per channel.
  3. Send. Each channel has its own queue and worker pool, so a slow email provider never delays push. Workers throttle to each provider's contracted rate, call the provider, and record the outcome.
  4. Track. Provider webhooks (delivered, bounced, complained), push receipts where available, tracked clicks and in-app reads become delivery events, which update status and feed analytics.

6. Deep dive: preferences, quiet hours and templates

The planner is a sequence of filters. Step through three notifications for the same user in India, whose quiet hours are 22:00 to 08:00 and who has turned off promotional email.

  • Preferences are read on every notification, so they sit in a cache in front of the database, with write-through on change. When a user turns a category off, the change must apply within seconds, including to notifications already queued, which is why the check happens in the planner, as late as possible, and not in the API.
  • Quiet hours are evaluated in the user's time zone, taken from the profile or the device. A deferred notification goes to the scheduler with a not_before time. Campaigns usually avoid quiet hours entirely by scheduling "08:00 local", which the scheduler fans out by time zone over the day.
  • Templates are versioned, per channel and locale, with a declared list of required fields. The renderer fails loudly on a missing field (a notification saying "Your order {order_id} shipped" is worse than none) and falls back to the default locale when a translation is missing. SMS templates are checked for length: one SMS holds 160 GSM-7 characters, or only 70 when the text needs Unicode (UCS-2); longer messages are split into segments of 153 or 67 characters, because each carries a concatenation header, and every segment is billed.
  • Channel choice is part of the type registry: an OTP prefers SMS and push, a receipt prefers email, a "someone liked your photo" prefers push and in-app. If the user has no push token, fall back to the next allowed channel.

7. Deep dive: retries, idempotency and dead letters

Providers fail in two different ways, and the worker must tell them apart. A transient failure (timeout, HTTP 429, 5xx) may succeed later. A permanent failure (APNs reporting the device token is unregistered, an invalid phone number, a hard email bounce) will never succeed, and retrying it only wastes money and provider goodwill. Permanent failures also carry information: an unregistered token should be deleted, a hard-bounced address should be suppressed for all future email.

import random

BASE_S, CAP_S, MAX_ATTEMPTS = 2.0, 600.0, 6
RETRYABLE = {"timeout", 429, 500, 502, 503}
PERMANENT = {"Unregistered", "BadDeviceToken", 400}     # retrying can never succeed


def backoff(attempt, rng):
    """Full jitter: random wait in [0, min(cap, base * 2^attempt)]."""
    return rng.uniform(0, min(CAP_S, BASE_S * 2 ** attempt))


def deliver(notification_id, responses, rng):
    t = 0.0
    for attempt, result in enumerate(responses[:MAX_ATTEMPTS]):
        if result == 200:
            return f"{notification_id}: delivered on attempt {attempt + 1} at t={t:.1f}s"
        if result in PERMANENT:
            return f"{notification_id}: permanent error {result!r}, token removed, no retry"
        if result not in RETRYABLE or attempt + 1 == MAX_ATTEMPTS:
            break
        t += backoff(attempt, rng)                      # wait, then try again
    return f"{notification_id}: failed {attempt + 1} times by t={t:.1f}s, sent to dead-letter queue"


rng = random.Random(42)
print(deliver("n_1", [503, 503, "timeout", 200], rng))
# n_1: delivered on attempt 4 at t=3.6s
print(deliver("n_2", ["Unregistered"], rng))
# n_2: permanent error 'Unregistered', token removed, no retry
print(deliver("n_3", [503] * 10, rng))
# n_3: failed 6 times by t=25.9s, sent to dead-letter queue
  • Retries without blocking. A worker never sleeps on a failed message. It writes the message to a delay queue (a Kafka retry topic per delay tier, a scheduled-message feature in SQS or RabbitMQ, or a Redis sorted set scored by due time) and moves on. The retry comes back to the same channel queue when due.
  • Dead-letter queue. After the last attempt, or for an error the worker does not recognise, the message goes to a dead-letter queue with its full history. An alert fires on DLQ growth; an operator can inspect and replay once the cause is fixed. Nothing disappears silently.
  • Retry budgets per priority. An OTP is worthless after 5 minutes, so it gets fast retries and a short deadline, then fails over to another provider or channel. A weekly digest can retry for hours.
  • Circuit breakers per provider. When a provider's error rate spikes, stop sending to it for a short period and route critical traffic to a secondary provider. Large senders often hold accounts with two SMS providers for exactly this reason.

Idempotency and deduplication

The pipeline is at-least-once at every hop: the API can be retried by its caller, Kafka redelivers after a consumer crash, a worker can time out on a send that actually succeeded. Three layers stop that from becoming duplicate messages on the user's phone:

  • Request idempotency. The caller's Idempotency-Key is stored for 24 hours with the resulting notification_id; a retried request returns the same id without creating a second notification.
  • Semantic dedup. The dedup_key ("order:9921:shipped") collapses different requests that mean the same thing, for example two services both reporting the shipment. A SET NX with a TTL in Redis decides which one proceeds.
  • Delivery state machine. Before sending, a worker moves the delivery row from queued to sending with a conditional update, and only the worker that wins the update sends. Redelivered queue messages for a delivery already sent are dropped.

The remaining gap is the send itself: if the provider accepted the message but the response was lost, a retry sends it again. Where providers accept an idempotency token, pass the delivery id. Where they do not, accept the rare duplicate for non-critical messages, and for OTPs make the duplicate harmless (the same code, valid once).

8. Deep dive: priorities and rate limits

  • Separate lanes per priority. Separate topics or queues for critical, high and bulk, consumed with strict priority (or heavy weights) by every channel's workers. A 50-million-message campaign fills the bulk lane; an OTP arriving behind it waits only for the worker to finish its current send. Separate worker pools per lane are even safer for the critical path.
  • Per-provider throttles. A shared token bucket per provider account (in Redis, or split across workers) matches the contracted rate. Sending faster only produces 429s that then have to be retried. Campaigns also carry their own max_per_second so they drain over an hour instead of a minute.
  • Per-user frequency caps. Counters such as "promotional pushes to u_481 today" with a TTL. Caps protect users from the sum of many well-meaning teams, and protect the company's sender reputation: users who are spammed disable notifications, and email providers route mail from senders with high complaint rates to spam.
  • Collapsing. Twenty "new comment" events in a minute become one push saying "20 new comments". APNs (apns-collapse-id) and FCM (collapse_key) let a newer notification replace an older one: FCM keeps only the latest undelivered message per key, and APNs also replaces a notification already displayed on the device.

9. Tracking delivery and engagement

Each channel reports outcomes differently, and none reports everything:

All of these arrive as events, keyed by notification_id and channel, on a Kafka topic. A consumer updates the delivery row's status (only moving forward: sent → delivered → opened, never back), and a stream job aggregates per type, template version and campaign into an analytics store. That feedback closes the loop: template A/B tests, automatic suppression of addresses that bounce, and alerts when a provider's delivery rate drops in one country.

11. Key trade-offs to state

  • Types and data in, rendering inside: consistent policy and wording, in exchange for a central registry every team must use.
  • Per-channel queues: one slow provider cannot stall others, in exchange for more moving parts.
  • At-least-once with dedup: nothing is silently lost, at the cost of idempotency machinery and an occasional duplicate at the provider boundary.
  • Late preference checks: opt-outs apply even to queued messages, in exchange for a cache lookup on every send.
  • Throttling to contracts: predictable, provider-friendly sending, in exchange for campaigns that take an hour instead of minutes.
Interview angle

What the interviewer is checking

Whether you design for unreliable third parties (retries that distinguish error types, DLQs, provider failover), protect critical messages from bulk traffic, and treat user preferences and duplicates as correctness requirements rather than nice-to-haves.

Follow-ups to expect

  • A campaign is sending 50 million pushes. A user requests a login code. How long does it take?
  • The SMS provider times out. Did the message send? What do you do?
  • How do you make sure a user never gets the same "order shipped" message twice?
  • A user in Tokyo has quiet hours from 22:00 to 08:00. Your campaign is scheduled for 15:00 UTC. What happens?
  • How do you know a push notification was actually delivered?
  • How would you add WhatsApp as a channel?

Red flags

  • Sending synchronously inside the caller's request.
  • One shared queue for OTPs and marketing.
  • Retrying every error the same way, immediately and forever.
  • Checking preferences only in the calling service.
  • No answer for what happens to a message after the last retry.
