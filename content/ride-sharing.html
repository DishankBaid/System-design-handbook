A ride-sharing service like Uber or Lyft has to know where a million moving cars are, right now, and answer "which available driver can reach this rider fastest?" within a couple of seconds. Then it has to make sure that driver goes to exactly one rider, track the trip as it happens, and price it according to supply and demand in that neighbourhood at that minute. The core challenges are a firehose of location updates, fast geospatial queries, and a matching process that never double-books a driver.

How to use this case study

Sections follow the order of a real interview. Concepts used here have their own chapters: Sharding, WebSockets, Event Streaming, Transactions, Consensus.

1. Requirements

Functional

Drivers go online and stream their location. Riders see nearby cars on a map, get a fare estimate, and request a ride. The system offers the trip to a suitable driver, who accepts or declines. Both sides see each other's live location and ETA. Trips move through pickup, ride and drop-off, then payment.

Non-functional

A match within a few seconds of the request. Location on the map at most a few seconds old. A driver is never assigned to two trips, and a trip never gets two drivers. Highly available per city: an outage in one city must not affect others.

Out of scope

Payments internals, driver onboarding, ratings, shared rides (pooling), food delivery. Mention pooling as a harder matching variant.

The key observation: the workload is local. A rider in Mumbai is only ever matched with drivers in Mumbai. The global system is really hundreds of independent city-sized systems that share code, which makes sharding by geography natural and keeps every hot query inside one shard.

2. Estimation

Assume 1.5 million drivers online at peak, each sending a location every 4 seconds; 20 million trips per day; and 2 million riders with the app open at peak, refreshing nearby cars every 5 seconds.

The index is tiny. What makes location hard is the rate: 375,000 writes per second that are each obsolete four seconds later. That rules out writing every update to a durable database and points to an in-memory index, sharded by city for isolation rather than for size. Trip requests, by contrast, are few, but each one needs strong consistency.

Three details matter. The nearby endpoint returns positions without driver identities, so the map cannot be used to track individuals. The quote fixes the price for a few minutes, so the rider pays what they saw even if surge changes before they tap. And trip creation takes an idempotency key, because a rider on a bad connection will tap "Request" again and must not get two cars.

Driver state and trips live in the same city shard on purpose. Assigning a driver means changing a driver row and a trip row together, and keeping both on one shard turns that into a local transaction instead of a distributed one.

5. High-level design

  1. Ingest. Each driver app keeps a connection to a location gateway and sends a position every 4 seconds. Gateways validate and publish to Kafka keyed by city, so each city's updates stay ordered on one partition.
  2. Index. Location index workers consume their cities' partitions and update an in-memory map of hexagonal cells to available drivers. A driver's entry carries a timestamp and is dropped if no update arrives for 30 seconds.
  3. Quote and request. The rider gets a quote (route distance and time from the ETA service, multiplied by the current surge for the pickup cell), then requests the trip. The trip row is created in state matching.
  4. Match and offer. Dispatch finds nearby available drivers, ranks them by road ETA, locks the best one and sends an offer down the driver's connection. On accept, the trip is assigned; on decline or timeout, the next driver gets the offer.
  5. Track. During the trip, the same location stream is routed to the rider's app and to the trip's route history, which later feeds the fare and receipt.

6. Deep dive: geospatial indexing

"Drivers within 2 km of this point" cannot be answered by a B-tree on latitude and a B-tree on longitude: each index returns a huge strip of the city and the intersection is expensive. Every practical solution maps 2D space to cells with ids, so that "nearby" becomes "in this cell or one of its neighbours".

For moving drivers, fixed grids beat quadtrees: an update is "compute the new cell id, move the driver between two sets if it changed", with no rebalancing. Uber built H3 for exactly this. At resolution 9 a hexagon averages about 0.1 km², roughly a city block or two; a query takes the rider's cell plus one or two rings of neighbours (k-ring), and hexagons make "rings" approximate circles far better than squares do. Resolution 7 cells (about 5 km²) are a natural unit for surge pricing.

The same idea with geohash, runnable with the standard library. The rider's cell is 9q8yyk; the nearest driver is in 9q8yym, which a single-cell lookup would miss.

import math
from collections import defaultdict

BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"


def geohash(lat, lng, precision=6):
    """Interleave longitude and latitude bisection bits, 5 bits per base32 char."""
    lat_lo, lat_hi, lng_lo, lng_hi = -90.0, 90.0, -180.0, 180.0
    bits, even, out = 0, True, []
    for i in range(precision * 5):
        if even:                                     # even bits refine longitude
            mid = (lng_lo + lng_hi) / 2
            bit = lng >= mid
            lng_lo, lng_hi = (mid, lng_hi) if bit else (lng_lo, mid)
        else:                                        # odd bits refine latitude
            mid = (lat_lo + lat_hi) / 2
            bit = lat >= mid
            lat_lo, lat_hi = (mid, lat_hi) if bit else (lat_lo, mid)
        bits = bits * 2 + bit
        even = not even
        if i % 5 == 4:
            out.append(BASE32[bits])
            bits = 0
    return "".join(out)


def km(a, b):
    """Haversine distance between two (lat, lng) points."""
    (la1, lo1), (la2, lo2) = [(math.radians(x), math.radians(y)) for x, y in (a, b)]
    h = math.sin((la2 - la1) / 2) ** 2 + math.cos(la1) * math.cos(la2) * math.sin((lo2 - lo1) / 2) ** 2
    return 6371 * 2 * math.asin(math.sqrt(h))


class DriverIndex:
    """Drivers bucketed by geohash-6 cell (~1.2 km x 0.6 km)."""
    CELL_LAT, CELL_LNG = 180 / 2 ** 15, 360 / 2 ** 15     # 30 bits: 15 lat, 15 lng

    def __init__(self):
        self.cells = defaultdict(dict)    # cell -> {driver_id: (lat, lng)}
        self.where = {}                   # driver_id -> cell

    def update(self, driver, lat, lng):   # called every 4 s per driver
        cell = geohash(lat, lng)
        old = self.where.get(driver)
        if old and old != cell:
            del self.cells[old][driver]
        self.cells[cell][driver] = (lat, lng)
        self.where[driver] = cell

    def nearby(self, lat, lng, radius_km=1.0, k=3):
        # the rider's cell plus its 8 neighbours, so drivers just over a cell edge are found; one ring only guarantees ~0.6 km in every direction, so widen the ring for larger radii
        cells = {geohash(lat + dy * self.CELL_LAT, lng + dx * self.CELL_LNG)
                 for dy in (-1, 0, 1) for dx in (-1, 0, 1)}
        found = [(km((lat, lng), pos), d) for c in cells for d, pos in self.cells[c].items()]
        return sorted((round(dist, 2), d) for dist, d in found if dist <= radius_km)[:k]


idx = DriverIndex()
idx.update("d_17", 37.7793, -122.4192)   # SF City Hall
idx.update("d_42", 37.7810, -122.4110)
idx.update("d_88", 37.7700, -122.4470)   # Haight, ~2.5 km away
idx.update("d_51", 37.7755, -122.4120)
rider = (37.7764, -122.4172)
print(geohash(*rider), idx.where)
# 9q8yyk {'d_17': '9q8yym', 'd_42': '9q8yym', 'd_88': '9q8yve', 'd_51': '9q8yyk'}
print(idx.nearby(*rider))
# [(0.37, 'd_17'), (0.47, 'd_51'), (0.75, 'd_42')]

Straight-line distance is only a filter. A driver 300 m away across a river or on the wrong side of a highway may be 10 minutes out. Dispatch takes the 10 to 20 closest candidates by distance and asks the ETA service for road-network times, then ranks by those.

7. Deep dive: matching and dispatch

Matching is a loop: find candidates, offer the trip to the best one, wait, and move on if they decline or ignore it. The subtle part is that the same driver must not receive two offers at once, and must not end up assigned to two trips.

No double booking

Two dispatch workers handling two nearby riders will often pick the same best driver at the same moment. The index is eventually consistent and cannot arbitrate; the driver's state row can. Every transition is a compare-and-set that succeeds only from the expected state:

-- Lock: only an available driver can receive an offer
UPDATE drivers SET status = 'offered', trip_id = 't_5Kq2', offer_expires = now() + interval '15 seconds'
 WHERE driver_id = 'd_17' AND status = 'available';          -- 0 rows → someone else got them; try the next

-- Accept: only the offer that is still live, for this trip
BEGIN;
UPDATE drivers SET status = 'on_trip'
 WHERE driver_id = 'd_17' AND trip_id = 't_5Kq2' AND status = 'offered' AND offer_expires > now();
                                                             -- 0 rows → ROLLBACK: offer expired
UPDATE trips SET driver_id = 'd_17', state = 'driver_assigned'
 WHERE trip_id = 't_5Kq2' AND state = 'matching';            -- 0 rows → ROLLBACK: rider cancelled
COMMIT;                                                      -- only if both updated one row; same city shard

If the first update matches zero rows, the worker moves to the next candidate. A late "accept" after the offer expired matches zero rows, the transaction rolls back and the driver app shows "offer expired"; a rider who cancelled first makes the second update miss, which also rolls back. Because both rows live on the city's shard, this is a single-shard transaction; no two-phase commit is needed. A distributed lock service (an etcd or Redis lock per driver) can do the same job, but a conditional write on the row that is the source of truth is simpler and cannot drift from it. See Distributed Transactions for what changes when the rows cannot share a shard.

Greedy versus batched matching

Offering each request its closest driver one by one is greedy, and greedy is often worse overall: give the driver 2 minutes from rider X to X, and rider Y, for whom that driver was the only one under 10 minutes, waits 10 minutes. Large platforms collect requests for a second or two, build a matrix of ETAs between waiting riders and available drivers in the area, and solve an assignment problem that minimises total pickup time. The added second of batching is repaid many times in shorter average waits.

8. Deep dive: ETA, surge and sharding

ETA

ETAs come from a routing engine over the road graph with live edge speeds. Raw Dijkstra over a city graph with millions of edges is too slow at thousands of queries per second, so routing engines precompute shortcuts (contraction hierarchies or similar) that answer point-to-point queries in milliseconds. Edge speeds are learned from the drivers' own location stream: the same 375,000 updates per second that feed the index also measure traffic on every road with cars on it. A machine-learned correction on top of the routing time, trained on actual pickup times, removes systematic errors such as time spent finding a parking spot at an airport.

Surge pricing at a high level

Every minute or two, a stream job counts demand (requests and app opens) and supply (available drivers) per H3 resolution-7 cell, computes a multiplier from the ratio, smooths it across neighbouring cells and over time so prices do not flicker, and caps it. The multiplier is written to a small cache that the pricing service reads when building quotes. The quote carries the multiplier it was built with and an expiry, which is what the rider is charged. Surge does two jobs: it rations rides during a spike, and it pulls drivers from quieter areas towards busy ones, which the driver app shows as a heat map.

Sharding by city

  • The unit is a city or region, not a hash of the driver id. Every query in matching is local, so a city shard holds the location index, driver state and active trips for that area. A Tokyo outage never touches São Paulo.
  • Boundaries. Airports and suburbs sit between cities. Assign every H3 cell to exactly one shard, and let dispatch query a neighbouring shard's index (read-only) when the pickup is near a border.
  • Uneven sizes. One huge city may need more than one index worker. Split it by H3 parent cells, the same way, with neighbour lookups across the split.
  • Failover. The location index is soft state: a replacement worker replays the last 30 seconds of the city's Kafka partition and is complete. Driver state and trips live in a replicated, strongly consistent store with automatic leader failover, because losing an assignment is not acceptable.

10. Key trade-offs to state

  • In-memory, lossy location index: handles 375,000 updates per second cheaply, in exchange for rebuilding from the stream after a failure.
  • Strong consistency only where it matters: assignment and trip state use conditional writes; locations, maps and surge are eventually consistent.
  • Fixed hex grid over quadtree: trivial updates for moving objects and uniform neighbours, in exchange for no adaptation to density, which ring size compensates for.
  • Sequential offers with timeouts: simple and fair to drivers, in exchange for up to 15 seconds lost per non-responding driver. Batched matching improves the global outcome at the cost of complexity.
  • Sharding by geography: local queries and fault isolation, in exchange for border handling and uneven shard sizes.
Interview angle

What the interviewer is checking

Whether you size the location write rate and conclude it belongs in memory, can explain a geospatial index and its neighbour problem, and can guarantee that a driver is never double-booked with a concrete mechanism rather than "use a lock".

Follow-ups to expect

  • How do you find drivers within 2 km? Why not a SQL query on latitude and longitude?
  • Two riders request at the same moment and the best driver is the same. What happens?
  • The driver accepts just as the offer expires. Who wins?
  • The index server for London crashes. How long until matching works again?
  • How would you implement surge, and how do you avoid prices flickering?
  • How would you match shared rides, where one car picks up several riders?

Red flags

  • Writing every location update to a relational database.
  • Searching a single geohash cell without neighbours.
  • Ranking drivers by straight-line distance only.
  • Preventing double booking with an in-memory flag on one dispatch server.
  • One global shard for all cities.
