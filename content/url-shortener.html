A URL shortener turns https://shop.example.com/products/9481?utm_source=newsletter&utm_campaign=fall into sho.rt/aB3x9Kq and sends anyone who opens the short link to the original. The product is simple. The interesting parts are generating billions of unique short codes without a bottleneck, answering redirects in a few milliseconds at hundreds of thousands of requests per second, and counting clicks without slowing that path down.

How to use this case study

Sections follow the order of a real interview: requirements, estimation, API, data model, high-level design, then deep dives. Try each step yourself before reading it. Concepts used here have their own chapters: Caching, Distributed ID Generation, Bloom filters, Event Streaming.

1. Requirements

Spend the first few minutes agreeing on scope. Each answer below changes the design, so ask rather than assume.

Functional

Create a short link for a long URL. Redirect a short link to its URL. Optional custom alias (sho.rt/fall-sale). Optional expiry. Click counts per link, by day, country and referrer.

Non-functional

Redirects are fast (p99 under 20 ms server side) and highly available, because a broken link is visible to every reader of a tweet. Codes are short and not trivially enumerable. Creation can be slower and briefly unavailable.

Out of scope

Editing a link's target, user accounts beyond an API key, link previews, QR codes. Mention them, then park them.

The single most important observation: this is a read-heavy system with a tiny, immutable record. A link is written once and read many times, and the mapping never changes. Almost every later decision follows from that.

Two conclusions come out of these numbers. Storage is large but simple, a sharded key-value store handles it comfortably. And the read rate is high enough that the redirect path must be served from memory, not from disk.

301 or 302?

This choice decides whether analytics are possible, so state it explicitly.

301 Moved Permanently302 Found (or 307)
Browser behaviourCaches the redirect, often indefinitelyAsks the server on every click
Load on usLower: repeat clicks never arriveEvery click arrives
AnalyticsRepeat clicks are invisibleEvery click is counted
Expiry and takedownsCached copies keep redirectingTake effect immediately

Because click analytics and abuse takedowns are requirements, use 302. A 301 is right for a pure vanity shortener with no analytics.

4. Data model

created_at, expires_attimestampexpires_at doubles as a store-level TTL.

Every read is "get one row by its exact key", there are no joins, and the record never changes. That is the textbook case for a key-value or wide-column store such as DynamoDB or Cassandra, partitioned by code. A sharded relational database also works; nothing here needs it, and you would be paying for transactions and joins you never use. See SQL vs NoSQL for the general argument.

Click data is a different shape entirely (append-only, huge, queried by time range), so it does not go in this table. It flows to an analytics store, covered below.

5. High-level design

Split the system along the read/write asymmetry. Creating a link and following a link have different load, latency and availability needs, so they are separate services that scale independently and share only the store.

  1. Create. The write API validates the URL (scheme, length, a malware/phishing blocklist check), takes the next ID from its locally leased block, turns it into a 7-character code, and writes the row. Custom aliases use a conditional write ("insert only if absent") so two users cannot claim the same alias.
  2. Redirect. The redirect service looks the code up in Redis. On a hit it returns 302 immediately. On a miss it reads the store, fills the cache, then returns.
  3. Count. After responding, the redirect service publishes a click event (code, timestamp, country from IP, referrer, user agent) to Kafka. Aggregators consume and roll up counts. The redirect never waits on analytics.

6. Deep dive: generating short codes

This is the part interviewers push on. We need 183 billion unique 7-character codes, created by many servers in parallel, without a single bottleneck and ideally without codes that are easy to enumerate.

ApproachHowStrengthWeakness
Hash the URLFirst 7 base62 chars of md5(long_url)Same URL gives same code, so deduplication is freeCollisions: with billions of codes in 3.5T slots, they happen. Each write needs a check and a retry with a salt
Random code7 random base62 charsUnguessable, no coordinationSame collision check on every write; gets worse as the space fills
Single counterDB auto-increment, base62-encodedNo collisions, simplestOne hot row for every write; codes are sequential and enumerable
Counter rangesEach server leases a block of 1M ids, uses them locallyNo collisions, one coordinator call per million linksUnused ids lost when a server dies (harmless); codes enumerable unless scrambled
Pre-generated keysA key service fills a table of unused random codes ahead of timeNo collisions at write time, random codesAnother service and table to run; must hand out each key exactly once

Recommendation: counter ranges plus a reversible scramble. A coordinator (an etcd key, or a single SQL row updated with UPDATE ... SET next = next + 1 RETURNING next) hands each write server a block of one million ids. At 3,500 writes per second across the fleet, the coordinator sees about one request every five minutes. Each id is then passed through a bijective scramble so consecutive ids do not produce consecutive codes, and encoded in base62.

import string
import threading

ALPHABET = string.digits + string.ascii_lowercase + string.ascii_uppercase  # 62 symbols
CODE_LEN = 7
SPACE = 62 ** CODE_LEN            # 3.5 trillion codes
A, B = 1_580_030_173, 1_234_567  # A is odd and not a multiple of 31, so it is invertible mod SPACE


def base62(n: int) -> str:
    out = []
    for _ in range(CODE_LEN):     # fixed width: pad with leading '0'
        n, r = divmod(n, 62)
        out.append(ALPHABET[r])
    return "".join(reversed(out))


def scramble(n: int) -> int:
    """Bijective shuffle of [0, SPACE): consecutive ids no longer look consecutive.
    Obfuscation only; anyone who knows A and B can reverse it."""
    return (n * A + B) % SPACE


class IdAllocator:
    """Hands out ids from a block leased from a coordinator (one network call per block)."""

    def __init__(self, lease_block, block_size=1_000_000):
        self.lease_block = lease_block   # e.g. atomic INCR on a counter in etcd or a SQL row
        self.block_size = block_size
        self.next = self.end = 0
        self.lock = threading.Lock()

    def next_id(self) -> int:
        with self.lock:
            if self.next == self.end:            # block used up: lease a new one
                start = self.lease_block() * self.block_size
                self.next, self.end = start, start + self.block_size
            self.next += 1
            return self.next - 1


def new_code(alloc: IdAllocator) -> str:
    return base62(scramble(alloc.next_id()))   # block 3 → "ZX0Apj9", "ZYJw3kM", "00srHmp", ...
Know the limits of the scramble

An affine scramble hides the counter from casual eyes, but neighbouring ids still produce related codes (note the shared prefix of the first two above), and anyone who recovers A and B can enumerate every link. If links may point to private documents, use a keyed block cipher over the id (for example a small Feistel network with a secret key), or switch to random codes from a pre-generated key pool.

7. Deep dive: the redirect path

At 350,000 requests per second, every millisecond and every disk read matters. The path has three cases worth walking through.

  • Cache-aside with a long TTL. Links are immutable, so stale data is not a concern and there is no invalidation problem, except for deletes and takedowns, which explicitly delete the cache key. Popularity is heavily skewed (a link in a viral post gets millions of clicks, most links get a handful), so a cache holding a small fraction of links serves the vast majority of requests.
  • Negative lookups. Bots probe random codes. Without protection each probe is a cache miss and a store read. A Bloom filter of all issued codes answers "definitely not issued" from memory. 183 billion codes at a 1% false-positive rate needs about 220 GB, so in practice you keep one filter per shard or only cover recent years, or cache short-lived "not found" entries instead.
  • Edge caching. A CDN can cache 302 responses for a short time (say 60 seconds) with Cache-Control. That absorbs viral spikes at the edge, at the cost of counting those clicks at the CDN (from its logs) instead of in our service.
  • Hot keys. A single viral link can push one Redis shard past its limit. Keep a small in-process LRU in each redirect instance for the top few thousand codes; it removes the network hop entirely for the hottest links.

8. Deep dive: analytics without slowing redirects

Writing to a database on every click would put a write on the hot path and turn a 2 ms read into a 10 ms read-plus-write. Instead the redirect service emits an event and moves on.

  • Buffered publish. The Kafka producer batches events in memory and sends them every few milliseconds. If Kafka is slow, the buffer absorbs it; if the buffer fills, drop events rather than delay redirects. Losing a tiny fraction of click counts is acceptable, a slow redirect is not. That is a product decision worth saying out loud.
  • Partition by code. All events for one link land on one partition, so a single consumer can count it without coordination.
  • Roll up. A stream processor aggregates per code per minute and writes the rollups to a columnar store (ClickHouse, Druid, BigQuery). The stats API reads rollups, never raw events.
  • Unique visitors. Counting distinct visitors exactly needs memory proportional to visitors. A HyperLogLog per link per day gives about 1% error in 12 KB. See Probabilistic Data Structures.

9. Expiry and cleanup

Use two mechanisms together. On read, the redirect service checks expires_at and returns 410 Gone, so an expired link stops working at exactly the right moment. In the background, a store-level TTL (DynamoDB TTL, Cassandra USING TTL) or a periodic sweep deletes the rows to reclaim space. Do not recycle expired codes: someone may still have the old link saved, and silently sending them somewhere new is a security problem.

11. Key trade-offs to state

  • 302 over 301: more traffic to us, in exchange for analytics and working takedowns.
  • Counter ranges over hashing: no collision checks and a coordinator touched once per million writes, in exchange for codes that need scrambling to look random.
  • No deduplication of identical long URLs: two users shortening the same URL get different codes, so each gets their own stats. Deduplication would need an extra index on long_url for a small storage saving.
  • Lossy click counting: dropping events under pressure protects redirect latency.
  • Key-value store over relational: simpler horizontal scaling for a workload with no joins or transactions.
Interview angle

What the interviewer is checking

Whether you notice the 100:1 read/write ratio and design the read path first, whether you can do the code-length arithmetic (62⁷ vs the number of links), and whether you can defend a key generation scheme against collision and coordination questions.

Follow-ups to expect

  • How do two servers avoid issuing the same code? (Leased ranges, or conditional writes for random codes.)
  • What happens if the ID coordinator is down? (Leased blocks keep writes going; redirects never touch it.)
  • How do you stop people enumerating links? (Scrambling, random codes, rate limits, longer codes for private links.)
  • A link goes viral at 1M clicks/sec. What fails and what do you do?
  • How would you support editing the target URL? (Now the record is mutable: cache invalidation and a 302-only policy become mandatory.)

Red flags

  • Writing to the database on every redirect to count clicks.
  • Hashing the URL and truncating, without any plan for collisions.
  • A single auto-increment column as the code generator for a multi-region system.
  • Choosing 301 and then promising accurate analytics.
