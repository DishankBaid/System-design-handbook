Why it matters

A mobile app sends POST /v1/charges for $29.99. The payment service charges the card and returns 201 Created, but the phone switches from Wi-Fi to 4G and the response never arrives. After 10 seconds the app times out and, like any well-behaved client, retries. The customer is charged twice.

Nothing in that story is a bug in the usual sense. Timeouts and retries are what make distributed systems survive failures (Timeouts, Retries & Circuit Breakers), and every queue redelivers messages that were not acknowledged. Retries are necessary, and retries create duplicates. The way to have both is idempotency: an operation is idempotent if performing it several times has the same effect as performing it once. This chapter covers what delivery guarantees are actually possible, how idempotency keys turn an unsafe API call into a safe one, and how consumers deduplicate messages.

Delivery semantics

Every messaging system, RPC framework and queue falls into one of three categories, depending on what it does when it is unsure whether a message got through.

At-most-once

Send once, never retry. A message is never duplicated but may be lost. Fine for metrics samples, presence pings and log lines where a gap is harmless.

At-least-once

Retry until acknowledged. A message is never lost but may be processed more than once. The default for SQS, RabbitMQ, Kafka consumers, webhooks and nearly every HTTP client with retries.

Exactly-once

Each message has its effect exactly one time. Not achievable as a pure delivery guarantee over an unreliable network. Achievable as a processing guarantee: at-least-once delivery plus idempotent or deduplicating handling.

The reason exactly-once delivery is impossible is the same ambiguity as in the opening story. The sender can only learn that a message arrived through an acknowledgement, and the acknowledgement can be lost too. When it is, the sender must pick: resend (risking a duplicate, at-least-once) or give up (risking a loss, at-most-once). No protocol escapes this choice; it is a version of the Two Generals problem.

So when a system advertises "exactly-once", read it as effectively-once: duplicates still happen on the wire, but they are detected and discarded before they change state twice. Kafka's exactly-once semantics, Flink's exactly-once state and Stripe's idempotent requests all work this way. The useful formula is:

effectively-once = at-least-once delivery + idempotent processing
At-most-onceAt-least-onceEffectively-once
Lost messagesPossibleNoneNone
Duplicate effectsNonePossibleNone
What it costsNothingRetries and acksRetries, acks, plus dedup state or idempotent design
Typical useTelemetry, UDP game stateQueues, webhooks, notifications that tolerate a repeatPayments, orders, balances, inventory

Why retries create duplicates

From the client's point of view, three very different failures look identical. The request may have been lost on the way in, the server may have crashed halfway through, or the work may be done and only the response lost. All three end in the same timeout.

Not retrying is not an option either: then the "request lost" case silently drops the payment. The fix has to make the third case behave like the first, which means the server must recognise the retry as the same operation it already performed.

Naturally idempotent operations

Some operations are idempotent by their nature, and the cheapest fix is to design APIs and handlers out of those. HTTP itself defines GET, HEAD, PUT, DELETE and OPTIONS as idempotent methods, which is why proxies and clients may retry them automatically; POST and PATCH are not guaranteed to be.

OperationIdempotent?Why
SET balance = 120, PUT /users/42/emailYesAssigning a value twice leaves the same value
DELETE /carts/77/items/3Yes, in effectSecond delete finds nothing; it may return 404, but state is the same
INSERT ... ON CONFLICT (order_id) DO NOTHINGYesThe natural key makes the second insert a no-op
UPDATE ... SET status='SHIPPED' WHERE status='PACKED'YesA conditional state transition only fires once
balance = balance + 10NoEach run adds another 10
POST /charges, POST /ordersNoEach call creates a new resource
Append to a list, send an email or SMSNoEach call has a new visible effect

Three techniques convert the "No" rows into "Yes":

  • Use a natural or client-supplied identifier. Let the client choose the order id (PUT /orders/ord_7f3a) so a retry targets the same resource instead of creating a new one.
  • Turn deltas into conditional writes. Instead of "add 10 points", write "apply event evt_88 if not yet applied", or use an optimistic version check: UPDATE accounts SET balance = 130, version = 8 WHERE id = 42 AND version = 7. A retry finds version 8 and changes nothing.
  • Attach an idempotency key when neither is possible, for example when the operation calls a third party. That is the general mechanism, covered next.

Idempotency keys

An idempotency key is a unique value the client generates for one logical operation and sends with every attempt of it, usually as an HTTP header: Idempotency-Key: 8e0f2b6c-4a1d-4c55-9f3e-2b7d91c0a6e4. The server records the key with the outcome of the first attempt. A later attempt with the same key gets the recorded outcome instead of running again.

Client-side rules

  • One key per operation, not per attempt. Generate it before the first attempt and reuse it for every retry. A new key per retry defeats the whole mechanism.
  • Persist it if the client can restart. A checkout page that reloads should reuse the key stored with the cart, otherwise a crash-and-retry still double charges.
  • Use enough randomness. A UUIDv4 (122 random bits) makes accidental collisions between clients irrelevant. The server scopes keys per account anyway, so one client cannot replay another's result.

Server-side storage

The server keeps a table keyed by account and idempotency key. Along with the stored response it keeps a request fingerprint, a hash of the method, path and body, so it can detect a client that mistakenly reuses a key for a different request.

CREATE TABLE idempotency_keys (
  account_id     text         NOT NULL,
  idem_key       text         NOT NULL,
  request_hash   bytea        NOT NULL,   -- sha256 of method + path + canonical body
  state          text         NOT NULL,   -- 'started' | 'done'
  response_code  int,
  response_body  jsonb,
  locked_at      timestamptz,             -- for detecting abandoned 'started' rows
  created_at     timestamptz  NOT NULL DEFAULT now(),
  PRIMARY KEY (account_id, idem_key)
);

-- Claim the key. Exactly one concurrent request gets a row back.
INSERT INTO idempotency_keys (account_id, idem_key, request_hash, state, locked_at)
VALUES ('acct_42', '8e0f2b6c-4a1d-4c55-9f3e-2b7d91c0a6e4', '\x9c1f...', 'started', now())
ON CONFLICT (account_id, idem_key) DO NOTHING
RETURNING idem_key;

The primary key is what makes concurrent duplicates safe. Two requests with the same key that arrive at the same millisecond on two different servers both try the INSERT; the database lets exactly one succeed. The loser reads the existing row and responds according to its state.

The hard cases

  • Crash while started. If the server dies after claiming the key, the row stays started and every retry gets 409 forever. Store locked_at and let a retry take over a row older than, say, 60 seconds. Taking over is only safe if the work itself can be resumed or repeated safely, which leads to the next point.
  • External side effects. If the key row and the charge live in the same database, update both in one transaction and the problem disappears. When the side effect is a call to another system, pass an idempotency key derived from yours (for example 8e0f...:charge) to that system, so a takeover that repeats the call is deduplicated downstream. Stripe-style implementations break a request into atomic phases, each committed with a recovery point on the key row, so a retry resumes from the last completed phase.
  • Which responses to store. Store the result of any request that started executing, including server errors, because a retry should not run a half-done operation again. Do not store results of requests rejected before doing anything, such as validation failures or a 409 for concurrency, so the client can fix and retry with the same key.
  • Expiry. Keys cannot be kept forever. Stripe removes keys after they are at least 24 hours old, which comfortably exceeds any sensible retry window. After expiry the key is treated as new, so clients must not retry for longer than the retention period.

A middleware simulation

Idempotency belongs in shared middleware rather than in each handler. The sketch below wraps a charge handler, simulates a client whose first response is lost, then shows a duplicate that arrives mid-request and a key reused with a different body.

import hashlib
import json
import time
import uuid

charges = []   # the side effect we must never duplicate


def create_charge(body):
    charges.append(body["amount"])
    return 201, {"id": f"ch_{len(charges)}", "amount": body["amount"]}


class KeyStore:
    """Stands in for a table with PRIMARY KEY (account_id, idem_key)."""

    def __init__(self, ttl=24 * 3600):
        self.rows, self.ttl = {}, ttl

    def insert_if_absent(self, k, fingerprint):          # INSERT ... ON CONFLICT DO NOTHING
        row = self.rows.get(k)
        if row and row["expires_at"] > time.time():
            return False
        self.rows[k] = {"fp": fingerprint, "state": "started", "response": None,
                        "expires_at": time.time() + self.ttl}
        return True


store = KeyStore()


def idempotent(handler):
    def wrapped(account, key, body):
        if key is None:
            return handler(body)
        fp = hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()
        k = (account, key)
        if store.insert_if_absent(k, fp):                 # we won the race: do the work once
            try:
                response = handler(body)
            except Exception:
                del store.rows[k]                         # simplification: assumes the handler failed before any side effect; otherwise store the 5xx (as Stripe does)
                raise
            store.rows[k].update(state="done", response=response)
            return response
        row = store.rows[k]
        if row["fp"] != fp:
            return 422, {"error": "idempotency key reused with a different request"}
        if row["state"] == "started":
            return 409, {"error": "original request still in progress, retry later"}
        return row["response"]                            # replay the stored response
    return wrapped


def client_with_retries(api, body, use_key, lose_first_response=True):
    key = str(uuid.uuid4()) if use_key else None          # one key per logical operation, reused on retry
    for attempt in (1, 2, 3):
        code, resp = api("acct_42", key, body)
        if lose_first_response and attempt == 1:
            continue                                      # server did the work; the client saw a timeout
        return attempt, code, resp


raw = lambda account, key, body: create_charge(body)
safe = idempotent(create_charge)

print("no key:  ", client_with_retries(raw, {"amount": 2999}, use_key=False), "charges:", charges)
charges.clear()
print("with key:", client_with_retries(safe, {"amount": 2999}, use_key=True), "charges:", charges)


# A duplicate that arrives while the first request is still running
def slow_charge(body):
    print("  duplicate during processing ->", api("acct_42", "k-77", body))
    return create_charge(body)


api = idempotent(slow_charge)
print("first:   ", api("acct_42", "k-77", {"amount": 500}))
print("reused:  ", api("acct_42", "k-77", {"amount": 900}))
print("charges: ", charges)

# no key:   (2, 201, {'id': 'ch_2', 'amount': 2999}) charges: [2999, 2999]
# with key: (2, 201, {'id': 'ch_1', 'amount': 2999}) charges: [2999]
#   duplicate during processing -> (409, {'error': 'original request still in progress, retry later'})
# first:    (201, {'id': 'ch_2', 'amount': 500})
# reused:   (422, {'error': 'idempotency key reused with a different request'})
# charges:  [2999, 500]

Without a key the lost response turns into a second charge ([2999, 2999]). With a key the retry receives ch_1, the response of the first attempt, and the card is charged once. In production the KeyStore is the SQL table above, and the update(state="done") is committed in the same transaction as the business write whenever the two share a database.

Deduplicating in consumers

Message consumers face the same problem from the other side. A consumer reads message m-1043, adds 300 loyalty points, and crashes before acknowledging. The broker redelivers m-1043 to another consumer. Every at-least-once queue behaves this way (Message Queues, Pub/Sub & Event Streaming), and so does the transactional outbox relay that publishes events.

The standard fix is a processed-messages table (also called an inbox) written in the same database transaction as the consumer's own state change.

BEGIN;
INSERT INTO processed_messages (message_id, processed_at) VALUES ('m-1043', now());
-- a duplicate fails here with a unique violation: ROLLBACK, then ack the message
UPDATE loyalty_points SET balance = balance + 300 WHERE customer_id = 'cus_88';
COMMIT;
-- ack the message only after COMMIT

Practical details:

  • Ack after commit, never before. Acking first turns a crash into a lost message (at-most-once).
  • The message id must be stable. Use an id assigned by the producer (the outbox event_id), not a broker-assigned delivery id that changes on redelivery.
  • Bound the table. Delete ids older than the longest possible redelivery delay (for example 7 days, matching topic retention). With Kafka, a single partition is consumed in order, so a consumer can instead store the last processed offset per partition in the same transaction and skip anything at or below it.
  • Prefer idempotent effects when you can. If the event says "order ord_1002 is now SHIPPED, version 5", an upsert that applies it only when version > current_version needs no dedup table at all, and also handles events arriving out of order.
  • When the effect is not in your database (sending an email, calling an API), you cannot commit both atomically. Pass the message id as an idempotency key downstream, or accept a small chance of a duplicate email.

Kafka's idempotent producer and transactions

Kafka shows how effectively-once is built into infrastructure. The producer-to-broker hop has the same lost-ack problem: a producer sends a batch, the broker appends it, the ack is lost, the producer retries, and the log contains the batch twice.

  • Idempotent producer (enable.idempotence=true, the default since Kafka 3.0): each producer gets a producer id, and each batch per partition carries an increasing sequence number. The broker rejects sequences it has already appended. This removes duplicates caused by producer retries within a producer session.
  • Transactions extend this to read-process-write pipelines. A stream processor consumes from topic A, writes results to topic B, and commits its consumer offsets, all in one Kafka transaction. Consumers with isolation.level=read_committed never see output from aborted transactions. That is Kafka's "exactly-once semantics".
  • The boundary. These guarantees hold only while data stays inside Kafka. The moment a consumer writes to PostgreSQL or calls a payment API, you are back to idempotent consumers and dedup tables.

In the real world

  • Stripe: every POST accepts an Idempotency-Key header. Stripe saves the status code and body of the first request that started executing for that key, returns the same result for retries (including server errors), rejects reuse of a key with different parameters, and prunes keys once they are at least 24 hours old. Its official client libraries generate keys and retry automatically.
  • Apache Kafka: the idempotent producer and transactions (introduced in 0.11 through KIP-98) provide effectively-once processing inside Kafka; Kafka Streams turns it on with one setting, processing.guarantee=exactly_once_v2.
  • Amazon SQS FIFO queues: deduplicate messages with the same deduplication id sent within a 5-minute window. Messages sent outside that window are not deduplicated, so consumers still need their own protection.
  • AWS EC2: RunInstances takes a ClientToken, so a retried launch request does not start a second fleet of instances.
  • IETF: the Idempotency-Key HTTP header is being standardised by the HTTPAPI working group, codifying what payment APIs already do.
Interview angle

When to bring it up

Any time your design has retries, a queue, or money. Say it proactively when you draw a payment or order API ("clients send an idempotency key; we store it with the response for 24 hours") and when you draw a consumer ("delivery is at-least-once, so the consumer records processed message ids in the same transaction"). It also comes up in API design and in the notification system case.

Follow-ups to expect

  • Is exactly-once delivery possible? No; explain the lost-ack ambiguity and effectively-once processing.
  • Two requests with the same key arrive concurrently. What happens? Unique constraint, one wins, the other gets 409 or waits.
  • The server crashes after charging but before saving the response. Then what? Same transaction where possible; otherwise recovery points and downstream idempotency keys.
  • How long do you keep keys, and what happens after? Longer than the client's retry window; after expiry a retry is a new request.
  • How do you make a counter increment idempotent? Record the event id, or convert it to a versioned conditional write.

Red flags

  • "We use Kafka, so it's exactly-once" for a consumer that writes to an external database.
  • Checking for a key with a SELECT and then inserting it, without a unique constraint: two concurrent duplicates both pass the check.
  • Generating a new idempotency key on every retry.
  • Acknowledging a message before the state change commits.
