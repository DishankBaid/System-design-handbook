Why it matters

One server stops being enough long before it stops being convenient. The moment you run two copies of a service, something has to decide which copy gets each request, notice when a copy dies, and keep doing that without becoming the thing that takes the site down. That something is a load balancer.

A load balancer publishes one stable address, usually a virtual IP (VIP) such as 203.0.113.10, and spreads the traffic arriving there across a pool of backends with private addresses. Clients never learn how many backends exist. That indirection is what lets you add capacity before a sale, replace a host during a deploy, or lose a machine at 3am without anyone outside noticing.

A load balancer has four jobs, and the rest of this chapter takes them in turn: distribute requests so every backend is equally busy, detect failure and stop sending traffic to broken backends, change the pool safely during deploys and autoscaling, and stay up itself, since every request passes through it.

L4 vs L7: what the balancer can see

The most important property of a load balancer is the layer it works at, because that decides what information it can route on. The names come from the OSI model.

  • A layer 4 (L4) balancer works on TCP and UDP. It sees IP addresses, ports and TCP flags. It picks a backend when a connection opens and then forwards that connection's packets without reading them.
  • A layer 7 (L7) balancer speaks the application protocol, almost always HTTP. It terminates the client's TCP and TLS connection, parses each request, picks a backend per request, and opens its own connection to that backend.

How an L4 balancer forwards packets

An L4 balancer must send every packet of a connection to the same backend, otherwise the backend receives a fragment of a TCP stream it never opened. It does that either by recording the choice in a connection table keyed by the 5-tuple (source IP, source port, destination IP, destination port, protocol), or by hashing the 5-tuple so the same connection always maps to the same backend. Then it delivers packets in one of three ways:

NAT

The balancer rewrites the destination address to the backend's, and the source address on the way back. Simple, but every response byte flows back through the balancer.

Direct server return

The balancer forwards the packet unchanged (or encapsulated), the backend also owns the VIP, and replies go straight to the client. Responses are usually much larger than requests, so the balancer handles a small fraction of the bytes.

Proxy

The balancer terminates TCP and opens a second connection to the backend, copying bytes between them. This is how HAProxy and NGINX run in TCP mode: two connections, no parsing.

What L7 buys you, and what it costs

Because an L7 balancer sees each request, it can do things an L4 one cannot: route /checkout to one pool and /search to another, send 5% of traffic to a canary build, retry an idempotent request on a different backend after a 503, enforce timeouts per route, and attach headers such as X-Request-Id or X-Forwarded-For. Much of this overlaps with what a reverse proxy or API gateway does; the Proxies & API Gateways chapter covers those responsibilities.

The cost is work per request. It holds TLS keys and does the handshake crypto, parses every request, often buffers bodies, and keeps two TCP connections per client conversation. An L7 tier needs noticeably more CPU per gigabit than an L4 tier and adds latency, typically well under a millisecond for a simple proxy hop, more with heavy filtering.

Common mistake: gRPC behind an L4 balancer

gRPC runs over HTTP/2, which multiplexes many requests on one long-lived TCP connection (see TCP, UDP & HTTP). An L4 balancer balances connections, so if a client service opens one connection, every one of its requests lands on the same backend forever, and newly added backends receive nothing. Use an L7 balancer that understands HTTP/2 streams, or client-side balancing across several connections.

Large sites use both: an L4 tier takes packets at line rate and spreads them across L7 proxies, which route each request.

Balancing algorithms

The algorithm answers one question: given this request and this pool, which backend? Algorithms differ in what they know about backends. Some know nothing, some count connections, some measure latency, some hash the request.

Round robin and weighted round robin

Round robin hands requests to backends in order: app-1, app-2, app-3, app-4, app-1, and so on. It needs no state beyond a counter and is perfectly even when every request costs the same and every backend is the same size.

Weighted round robin gives larger machines a bigger share. With weights 4, 2, 1, the first backend gets 4 of every 7 requests. A naive implementation sends four in a row to the big server; NGINX uses a smooth variant that interleaves them (a b a c a b a instead of a a a a b b c) so no backend gets a burst. Weights are also how you run a canary: give the new version weight 1 against 99.

Round robin's weakness is that it ignores how busy a backend actually is. If one request generates a 3-second report and the next is a 2 ms lookup, round robin still alternates, and a backend unlucky enough to receive several slow requests builds a queue while its neighbours idle.

Least connections and least response time

Least connections sends each new request to the backend with the fewest open connections (or, for an L7 balancer, the fewest outstanding requests). Open connections are a decent proxy for current work, so slow requests naturally steer traffic away from the backend handling them. It is the usual default for long-lived connections such as WebSockets or database sessions.

Least response time also weighs a moving average of recent latency, so it steers away from a backend slowed by garbage collection or a noisy neighbour. It can oscillate: everyone piles onto the fast backend, which then becomes slow.

Power of two choices

Least connections has a hidden problem at scale. It assumes the balancer knows every backend's current load. With ten balancer instances each tracking only their own connections, or with load reports that arrive every few hundred milliseconds, every instance sees the same "least loaded" backend at the same moment and they all send their next requests to it. This is herding, and it can make least connections worse than random.

The power of two choices (P2C) fixes it with almost no work: pick two backends at random and send the request to the less loaded of the two. Picking only two means different balancer instances rarely pick the same pair, so stale information cannot make them all agree on one victim. Yet comparing two is enough to avoid the worst choices. The theory is striking: when n requests go to n servers, the busiest server under random placement gets about log n / log log n requests, and with two choices that drops to about log log n / log 2, an exponential improvement from one extra sample.

The simulation below sends requests to a pool and reports the busiest server. The second experiment gives the balancer a load snapshot that is only refreshed every refresh requests, which is what several independent balancer instances or delayed load reports look like.

import random


def max_load(servers, requests, policy, refresh=1, seed=42):
    """Send `requests` to `servers` and return the busiest server's count.
    The balancer only sees a load snapshot refreshed every `refresh` requests,
    which models several balancer instances or delayed load reports."""
    rng = random.Random(seed)
    load = [0] * servers
    seen = load[:]
    for i in range(requests):
        if i % refresh == 0:
            seen = load[:]
        if policy == "random":
            pick = rng.randrange(servers)
        elif policy == "two-choices":
            a, b = rng.randrange(servers), rng.randrange(servers)
            pick = a if seen[a] <= seen[b] else b
        else:  # "least-loaded": scan every server, random tie-break
            low = min(seen)
            pick = rng.choice([s for s in range(servers) if seen[s] == low])
        load[pick] += 1
    return max(load)


for n, m in [(100, 10_000), (1_000, 1_000_000)]:
    print(f"{n} servers, {m:,} requests, mean {m // n}:",
          {p: max_load(n, m, p) for p in ("random", "two-choices")})

for refresh in (1, 100, 1_000):
    print(f"snapshot every {refresh:>5} requests:",
          {p: max_load(100, 10_000, p, refresh) for p in ("least-loaded", "two-choices", "random")})

# 100 servers, 10,000 requests, mean 100: {'random': 126, 'two-choices': 102}
# 1000 servers, 1,000,000 requests, mean 1000: {'random': 1128, 'two-choices': 1003}
# snapshot every     1 requests: {'least-loaded': 100, 'two-choices': 102, 'random': 126}
# snapshot every   100 requests: {'least-loaded': 124, 'two-choices': 103, 'random': 126}
# snapshot every  1000 requests: {'least-loaded': 528, 'two-choices': 114, 'random': 126}

Three findings. With fresh information, choosing among all servers is best, as expected, and two choices is within 2% of it. Random placement leaves the busiest server 26% above average with 100 servers, and still 13% above with 1,000 servers and a million requests. And with stale information, least-loaded collapses: when the snapshot is 1,000 requests old, every request goes to the same "idle" servers and the busiest one ends up at more than five times the mean, while two choices barely moves. That robustness is why Envoy's least-request policy and NGINX's random two are built on P2C.

Hashing and sticky sessions

Sometimes the goal is sending the same client or key to the same backend: a cache node that holds a user's data, or an application with in-memory sessions. Three common ways:

  • Source IP hash. hash(client_ip) % N. Needs no state, but every client behind one corporate NAT or mobile carrier gateway lands on one backend, and changing N remaps almost everyone.
  • Consistent hashing on a key. Hash a header, URL or user id onto a ring so adding or removing a backend moves only about 1/N of keys. This is how L7 balancers front cache fleets; the Consistent Hashing chapter explains the ring, Maglev hashing and bounded loads.
  • Cookie affinity. On the first response the balancer sets a cookie naming the backend (AWS ALB uses AWSALB), and later requests carrying it go back there. Precise per user, but only works for HTTP clients that keep cookies.

Treat sticky sessions as a smell. A machine's failure logs its users out, deploys must drain slowly, and load drifts as some users stay longer. Prefer stateless servers with sessions in a shared store (see Scalability), and keep affinity for cases where locality is the point, such as caches.

Health checks

An algorithm that spreads traffic evenly across a pool containing a dead server sends a quarter of requests to a black hole. The balancer needs to know which backends are healthy, and it learns this two ways.

Active checks

The balancer probes each backend on a timer, for example GET /healthz every 2 seconds with a 1 second timeout. A backend is marked down after fall consecutive failures (often 3) and up again after rise consecutive successes (often 2). Detects failure even with no traffic, at the cost of probe load and a detection delay of several intervals.

Passive checks

The balancer watches real traffic: connection refusals, timeouts and 5xx responses. After, say, 5 consecutive errors it ejects the backend for 30 seconds. Envoy calls this outlier detection. Reacts within a handful of requests at high traffic, but sees nothing when traffic is low.

Production setups use both: passive checks for speed, active checks to bring ejected backends back and to cover quiet pools.

What a health check should test

A shallow check (the process answers /healthz with 200) tells you the server is up. A deep check also queries the database and calls dependencies, and tells you the server can do useful work. Deep checks are tempting and dangerous. If the shared database has a 10 second hiccup, every backend's deep check fails at once, the balancer ejects the entire pool, and a partial slowdown becomes a total outage that lasts until checks pass again.

The safe pattern is to check what is local to the instance (process alive, not overloaded, finished warming up, not shutting down) and let the application return errors for dependency problems, which circuit breakers handle better than ejection does. Balancers also add a safety net: Envoy's panic threshold ignores health status and spreads traffic across all hosts once fewer than 50% are healthy, on the theory that mass failure is more likely a bad check than a dead fleet.

Worked example: how many requests fail before ejection

An orders service handles 20,000 requests per second across 10 backends, 2,000 each. One backend hangs: it accepts connections but never answers. How many requests are hurt before the balancer stops sending it traffic?

Active only, interval 2 s, timeout 1 s, fall 3 best case hang just before a probe: probes at 0, 2, 4 s fail → down at 4 + 1 = 5 s worst case hang just after a probe: probes at 2, 4, 6 s fail → down at 6 + 1 = 7 s affected 2,000 req/s × 5..7 s = 10,000 to 14,000 requests Active only, interval 10 s, timeout 2 s, fall 3 window 20 + 2 = 22 s to 30 + 2 = 32 s affected 2,000 req/s × 22..32 s = 44,000 to 64,000 requests Passive, eject after 5 consecutive errors, request timeout 1 s 5 errors arrive within 5 / 2,000 req/s = 2.5 ms of the first timeout window ≈ 1 s (time for the first requests to time out) affected ≈ 2,000 requests, retried on healthy backends if idempotent

Two lessons. First, a hang is far worse than a crash: a crashed process refuses connections instantly and a passive check catches it in milliseconds, while a hang has to wait for timeouts, so the request timeout sets the floor on detection time. Second, a short probe interval is cheap compared with tens of thousands of failed requests. Ten balancers probing 10 backends every 2 seconds is 50 probes per second, nothing next to 20,000 real requests.

Connection draining and slow start

Most backend removals are planned: a deploy, a scale-in, a kernel patch. Pulling a backend out of the pool instantly would cut off its in-flight requests. Connection draining (AWS calls it the deregistration delay, default 300 seconds) splits removal into two phases:

  1. Stop new work. The balancer marks the backend as draining and sends it no new connections or requests.
  2. Let old work finish. Existing connections continue until they complete or the drain timeout expires, then they are closed.
  3. Tell clients to move. For keep-alive connections, the backend answers with Connection: close on HTTP/1.1 or sends an HTTP/2 GOAWAY frame, so clients open their next connection elsewhere instead of waiting to be cut off.

In Kubernetes the same dance is a readiness probe that starts failing when the pod receives SIGTERM, a short preStop sleep so every balancer notices before the process stops accepting, and a terminationGracePeriodSeconds (default 30) long enough for in-flight requests. Long-lived connections such as WebSockets are the hard case: a drain timeout of minutes still cuts them, so clients must reconnect gracefully (see Polling, SSE & WebSockets).

The reverse problem is a new backend that is cold: empty caches, an unwarmed JIT, empty connection pools. Least connections makes this worse, since an idle new server looks like the best choice and gets flooded. Slow start ramps its weight from near zero to full over a configured window, typically 30 to 60 seconds.

Keeping the load balancer itself available

A load balancer removes single points of failure from the backend tier and then becomes one itself. There are three standard ways out, and large systems layer them.

Active-passive with a floating IP

Two balancer machines share one VIP. The active one owns it and answers ARP for it, while the standby listens. They speak VRRP (Virtual Router Redundancy Protocol), usually through keepalived: the active node multicasts an advertisement every second, and if the standby misses about three in a row it claims the VIP and sends a gratuitous ARP so the network switch starts delivering the VIP's packets to it.

This is simple, but half the hardware idles, the pair must share a layer 2 segment, and one machine's capacity caps the site. Managed cloud balancers (AWS ALB and NLB, Google Cloud Load Balancing) hide this layer behind a DNS name or static IP.

Active-active: DNS, ECMP and anycast

  • Multiple balancers behind DNS. Publish several balancer IPs for one name. Clients spread across them, and health-checked DNS removes a dead one. Failover is limited by how long resolvers and clients cache the old answer; the DNS chapter has the TTL arithmetic.
  • ECMP. The upstream router announces the VIP towards several balancer machines with equal-cost multi-path routing and hashes each flow's 5-tuple to one of them. All machines are active. When one dies, the router rehashes, and flows that move to a new balancer arrive mid-connection. The fix is for every balancer to choose backends with the same consistent hash, so a flow lands on the same backend whichever balancer receives it. This is exactly Maglev's design.
  • Anycast. The same VIP is announced over BGP from many sites, and the internet routes each client to the nearest one. A site that fails withdraws its route and traffic shifts elsewhere within seconds to a minute. Cloudflare and Google's global front ends work this way; see Content Delivery Networks.

Global vs local load balancing

Balancing happens at two scales, and interviews often blur them.

Global (GSLB)

Chooses a region or data center: Frankfurt or Virginia. Inputs are client location, region health and region capacity. Implemented with geo or latency-based DNS, or with anycast. Decisions change on the order of seconds to minutes.

Local

Chooses a server inside a region: app-3 or app-7. Inputs are per-backend health and load. Implemented with L4 and L7 balancers. Decisions are made per connection or per request.

A typical request goes through both: DNS or anycast picks the nearest healthy region, an L4 tier spreads packets across L7 proxies, and the proxies route each request to an instance. When a region fails, the other regions need the headroom to absorb its traffic, which is a capacity decision, not a balancing one.

Client-side load balancing

Inside a data center there is a third option: no balancer box at all. Each client gets the list of healthy instances from a registry and picks one itself, using round robin or P2C. This is client-side load balancing, used by gRPC clients, Netflix's Ribbon library and Twitter's Finagle.

In the real world

  • NGINX: an L7 (and L4 stream) proxy. Default is weighted round robin, with least_conn, ip_hash, hash ... consistent and random two least_conn. Open-source NGINX has passive health checks only (max_fails, fail_timeout); active checks are in the commercial NGINX Plus.
  • HAProxy: L4 and L7, known for performance and detailed stats. Algorithms include roundrobin, leastconn, source, uri and random with configurable draws. Active checks default to a 2 s interval with rise 2 and fall 3, and slowstart ramps returning servers.
  • Envoy: the L7 proxy behind most service meshes. Its least-request policy uses power of two choices, it supports ring hash and Maglev, and it combines active health checking with outlier detection and a 50% panic threshold.
  • AWS ALB and NLB: ALB is a managed L7 balancer with host and path routing, round robin or least outstanding requests, and cookie stickiness. NLB is L4, gives one static IP per availability zone, preserves client source IPs, and handles very high connection rates.
  • Google Maglev: Google's software L4 balancer, in production since 2008. Routers spread packets across Maglev machines with ECMP, each machine picks backends with Maglev consistent hashing so any machine makes the same choice, and responses return directly from backends. The NSDI 2016 paper reports one machine saturating a 10 Gbps link with small packets.
Interview angle

When to bring it up

In almost every design, as one box in front of each stateless tier. Say what kind: "an L7 balancer in front of the API servers, least outstanding requests, active and passive health checks; the balancers themselves are a managed, multi-AZ service." Go deeper when the interviewer asks about failure, long-lived connections, or multi-region traffic.

Follow-ups to expect

  • L4 or L7 here, and why? (What does the routing decision need to see? Is TLS terminated here?)
  • Your load balancer dies. What happens? (Active-passive with VRRP, ECMP or anycast active-active, managed multi-AZ service.)
  • How fast do you detect a dead backend, and what happens to requests meanwhile? (Interval × fall, passive checks, retries for idempotent requests.)
  • Why might least connections perform badly with many balancer instances? (Stale counts cause herding; power of two choices fixes it.)
  • How do you deploy without dropping requests? (Draining, readiness probes, GOAWAY, slow start.)
  • Users lose their session when a server dies. Why, and how do you fix it? (Sticky sessions with in-memory state; move state to a shared store.)

Red flags

  • Drawing one load balancer box with no answer for its own failure.
  • Deep health checks on a shared dependency, which can eject the whole pool at once.
  • Putting long-lived HTTP/2 or gRPC connections behind an L4 balancer and expecting per-request balance.
  • Reaching for sticky sessions by default instead of stateless services.
  • Treating DNS round robin as instant failover.
