Why it matters

A web app that serves 1,000 users from one server will not serve 10 million users from one server. Somewhere along the way the database runs out of connections, the disk fills, a deploy takes the whole site down, or a single slow query locks a table every user needs. Scalability is about knowing which of those walls you will hit next and how to get past it without a rewrite.

Scalability is a system's ability to handle more load by adding resources, while keeping performance per request acceptable. "Load" must be named concretely: requests per second, concurrent connections, rows written per second, data stored, or the fan-out of one action. A system can scale well along one of these and badly along another. A chat service may handle twice the users easily and still fall over when one group grows to 100,000 members.

This chapter covers the two basic directions of scaling, the single most important design property that enables one of them (statelessness), how reads and writes scale differently, the mathematical limits that stop adding machines from helping, and a staged worked example of growing a web app from 1,000 to 10 million users.

Vertical vs horizontal scaling

Vertical scaling (scaling up) means a bigger machine: more cores, more RAM, faster disks. Horizontal scaling (scaling out) means more machines, each doing part of the work.

VerticalHorizontal
Code changesNoneRequires stateless services, or partitioned data
CeilingThe largest machine you can buy: hundreds of cores, terabytes of RAMPractically none for stateless work
Cost curveSuperlinear near the top endRoughly linear with commodity machines
FailureOne machine is one failure domainLosing one of N costs 1/N of capacity
ConsistencyEasy: one memory, one disk, local transactionsHard: coordination across a network
Operational loadOne thing to runLoad balancing, discovery, deploys across a fleet

Vertical scaling is underrated. A single modern server with a few dozen cores and a few hundred gigabytes of RAM handles far more than most startups ever need, and every distributed-systems problem you avoid is a class of bugs you never write. The well-known example is Stack Overflow, which for years served one of the busiest sites on the internet from a handful of web servers and a few large SQL Server machines. A good default is: scale the stateless tier horizontally from day one (it is cheap), and scale the database vertically until it stops being enough.

Stateless services: the precondition for scaling out

A service is stateless when any instance can serve any request, because nothing a request needs lives only in one instance's memory or disk. State still exists, but it lives in shared stores built for it: a database, a cache cluster, an object store. Stateless instances are interchangeable, so you can add them, remove them, restart them and route to any of them freely.

The common hidden state that blocks this:

Sessions in memory

A login session stored in the server's memory forces sticky sessions: the load balancer must pin each user to one server. Move sessions to Redis, or use signed tokens (such as JWTs) that carry the session in the request itself.

Files on local disk

Uploads written to /var/uploads exist on one server only. Write them to object storage (S3, GCS) and serve them through a CDN. See Blob & Object Storage.

In-process caches

A local cache is fine as an optimisation if a miss is harmless. It becomes state when correctness depends on it, such as a rate-limit counter that only one instance sees.

Singletons and cron

"This server also runs the nightly job" breaks when there are 20 of them (it runs 20 times) or when that server is replaced. Use a scheduler with leader election or a job queue.

The state did not disappear; it moved into components that are built to be shared, replicated and backed up. Those components now have their own scaling problem, which is the subject of most of the Data part of this handbook. That is the general pattern: push state down into a few specialised tiers, keep everything above them stateless.

Scaling reads vs scaling writes

Once the stateless tier scales out, the bottleneck moves to the data tier, and there reads and writes scale by different means.

Scaling readsScaling writes
Core ideaMake copies; serve each read from any copySplit the data; each write goes to one owner
ToolsCaches, read replicas, CDNs, precomputed viewsSharding, batching, append-only logs, async processing with queues
CostStaleness: copies lag the sourceCross-shard queries and transactions become hard
DifficultyUsually incrementalOften a major migration

Copies help reads because each read needs only one copy. They do not help writes, because every write must reach every copy: ten replicas means each write is applied ten times. Only partitioning divides write load, since each partition receives only its share of writes. That is why most systems put off sharding as long as possible and do everything else first: caching, replicas, moving heavy work off the request path, and buying a bigger primary.

Where scaling stops: Amdahl and the USL

Doubling the machines rarely doubles throughput. Two models explain why, and the second one explains why adding machines can even make things worse.

Amdahl's law: the serial fraction

If a fraction σ of the work is serial (it cannot be split: a single lock, a single leader, one hot row), then the speedup with N workers is

S(N) = 1 / ( σ + (1 - σ) / N ) and as N → ∞, S → 1 / σ

With just 5% serial work, no number of machines gives more than a 20× speedup, and 64 machines give only 15.4×. Gene Amdahl stated this argument in 1967 for parallel processors; it applies equally to a fleet of servers sharing a database row.

The Universal Scalability Law: the cost of coordination

Amdahl assumes the serial part has a fixed cost. In distributed systems the cost of coordinating grows with the number of participants: every node must keep its caches coherent with every other, every lock is contended by more parties, every consensus round includes more voters. Neil Gunther's Universal Scalability Law (USL) adds a term for this:

C(N) = N / ( 1 + α(N - 1) + βN(N - 1) ) α contention: queueing for a shared resource (Amdahl's serial fraction) β coherency: pairwise coordination, which grows with N² peak at N* = √( (1 - α) / β )

The β term is quadratic, so for large enough N it dominates and throughput falls as you add nodes. Every node added past the peak spends more time agreeing with the others than doing work.

Here are the same curves as code. The output in the comments is from a real run.

import math


def amdahl(n, serial):
    """Speedup with n workers when a fraction `serial` of the work cannot be parallelised."""
    return 1 / (serial + (1 - serial) / n)


def usl(n, alpha, beta):
    """Universal Scalability Law: relative capacity with n nodes.
    alpha = contention (queueing on a shared resource), beta = coherency (pairwise coordination)."""
    return n / (1 + alpha * (n - 1) + beta * n * (n - 1))


alpha, beta = 0.05, 0.001
peak_n = math.sqrt((1 - alpha) / beta)
print(f"USL peak at N = {peak_n:.1f}, capacity {usl(peak_n, alpha, beta):.1f}x one node")
for n in (1, 8, 16, 32, 64):
    print(f"N={n:3d}  linear {n:3d}x   Amdahl {amdahl(n, alpha):5.1f}x   USL {usl(n, alpha, beta):5.1f}x")

# USL peak at N = 30.8, capacity 9.0x one node
# N=  1  linear   1x   Amdahl   1.0x   USL   1.0x
# N=  8  linear   8x   Amdahl   5.9x   USL   5.7x
# N= 16  linear  16x   Amdahl   9.1x   USL   8.0x
# N= 32  linear  32x   Amdahl  12.5x   USL   9.0x
# N= 64  linear  64x   Amdahl  15.4x   USL   7.8x

In practice you fit α and β to load-test measurements at a few cluster sizes (throughput at 1, 2, 4, 8 nodes), then use the fitted curve to predict where adding hardware stops paying. It is one of the few capacity models that captures retrograde scaling.

Coordination is the real limit

The USL makes a practical point precise: systems scale to the degree that their parts do not need to talk to each other. Every design technique that scales well removes coordination:

  • Stateless services need no coordination between instances at all, so β ≈ 0 for that tier.
  • Sharding keeps each request on one partition, so partitions do not coordinate, until a query or transaction spans shards.
  • Asynchronous processing replaces "wait until everyone agrees" with "record it now, reconcile later".
  • Weaker consistency lets replicas answer without consulting each other; see CAP & PACELC and Consistency Models.

And the components that scale badly are the ones that coordinate by design: a single global lock, a counter row every request increments, a consensus group (which is why consensus clusters stay at 3 or 5 members), a distributed transaction across many shards, or a gossip protocol where every node talks to every other.

The scale cube

The AKF scale cube, from Martin Abbott and Michael Fisher's The Art of Scalability, names three independent ways to split a system. Real systems use all three.

Autoscaling and elasticity

Elasticity is the ability to add and remove capacity automatically as load changes, so you pay for what you use. It is related to scalability but different: scalability says the architecture can use more machines effectively; elasticity says it can do so quickly and automatically, in both directions. A sharded database may scale to 100 shards yet take days to rebalance, so it is scalable but not elastic. A stateless service on Kubernetes can be both.

Autoscalers come in three common forms:

  1. Target tracking. Keep a metric near a target, for example average CPU at 60%. Simple, and the default for most services. The headroom (here 40%) absorbs spikes while new instances boot.
  2. Scheduled. Add capacity before known peaks: weekday mornings, a product launch, a televised event. Cheap insurance, because reactive scaling always lags.
  3. Predictive. Forecast load from history and scale ahead of it. Useful for strong daily cycles.

Things that go wrong with autoscaling, and are worth saying in an interview:

  • Lag. A new VM can take minutes to boot, pull an image and warm up caches. A spike shorter than that is absorbed only by existing headroom. Containers start faster than VMs, and keeping a warm pool helps.
  • The wrong metric. CPU is a poor signal for I/O-bound services. Scale queue consumers on queue depth or consumer lag, and request-serving tiers on concurrency or latency.
  • Moving the bottleneck. Scaling the app tier from 10 to 100 instances multiplies database connections by ten. Without a connection pooler (such as PgBouncer), autoscaling the stateless tier can take down the stateful one.
  • Flapping. Scaling in too eagerly causes oscillation. Use cooldowns, and scale in more slowly than you scale out.

Worked example: from 1,000 to 10 million users

A typical consumer web app (accounts, a feed of user content, photo uploads) grows through five stages. Assume each daily active user makes about 50 requests a day, with peak traffic three times the average. Use the buttons to walk through the architecture at each stage.

StagePeak req/sWhat breaks or worries youChange
1k users~2Nothing on capacity. One disk failure loses everythingBackups. Stay simple
10k users~17App and database compete for RAM; deploys restart the database hostSeparate database server with a standby; scale both vertically
100k users~170Still within one server's capacity, but one app server is a single point of failure and deploys cause downtimeLoad balancer, 2+ stateless app servers across zones; sessions to Redis; uploads to object storage and CDN
1M users~1,700Database reads: at ~10 queries per request, ~17k queries/s on one primary; slow requests that resize images or send emailCache-aside for hot reads, read replicas, a queue with workers for slow jobs, connection pooling
10M users~17,000Write volume and data size outgrow the largest primary; one codebase and one deploy for many teamsShard by user_id, split services by domain, second region, autoscaling per service

Two observations make this sequence credible in an interview. First, the early changes are driven by availability, not capacity: 170 requests per second fits on one server, but one server means every deploy and every hardware fault is an outage. Second, each change is the cheapest one that removes the current bottleneck. Sharding at 10,000 users would cost months of engineering for a problem you do not have; sharding at 10 million users is unavoidable. Say which numbers would move you to the next stage, so the interviewer sees you would measure rather than guess.

In the real world

  • Stack Overflow is the standard example of vertical scaling done well: for years it ran on about nine web servers and a few large SQL Server machines, with heavy use of caching, and published its architecture in detail.
  • Instagram scaled its early growth on Django and PostgreSQL, then sharded PostgreSQL into thousands of logical shards mapped onto fewer physical servers, so shards could be moved between machines without re-splitting data.
  • Shopify partitions merchants into "pods", each a full slice of the stack with its own databases. That is Z-axis scaling with a blast-radius benefit: a pod failure affects only its merchants.
  • Amazon and many large platforms use cell-based architecture: many identical, independent copies of a service, each serving a subset of customers, with a thin routing layer in front.
  • Kubernetes provides the Horizontal Pod Autoscaler, which scales a deployment's replica count to hold a metric (CPU, memory or a custom metric such as queue depth) at a target.
Interview angle

When to bring it up

In every design, when you draw the service tier: "these are stateless, so they scale horizontally behind the load balancer". Then again when the data tier becomes the bottleneck: say whether the pressure is on reads (cache, replicas) or writes (sharding), and justify the step with numbers.

Follow-ups to expect

  • "What happens at 10 times the traffic?" Name the first component to saturate and the change that relieves it.
  • "Why not just buy a bigger database server?" Often a good answer up to a point; know where that point is (write volume, data size, failover time).
  • "How do you make this service stateless?" Sessions, uploads, local caches, scheduled jobs.
  • "Why doesn't doubling the nodes double throughput?" Contention and coordination; Amdahl and the USL.
  • "How would you autoscale this?" Which metric, what headroom, what about boot time and database connections.

Red flags

  • Sharding or microservices at the first mention of scale, with no numbers to justify them.
  • Saying "add more servers" for a stateful component without a partitioning plan.
  • Read replicas proposed as the fix for a write bottleneck.
  • Treating scalability and availability as the same thing, or autoscaling as a substitute for capacity planning.
