A chat system like WhatsApp or Messenger delivers a message from Alice's phone to Bob's phone in a fraction of a second when both are online, holds it safely when Bob is offline, and shows Alice one tick, two ticks and then blue ticks as it is stored, delivered and read. The hard parts are keeping hundreds of millions of connections open, never losing or duplicating a message across flaky mobile networks, keeping order within a conversation, and syncing every one of a user's devices.

How to use this case study

Sections follow the order of a real interview. Concepts used here have their own chapters: Polling, SSE & WebSockets, Idempotency, Event Streaming, Blob Storage, Sharding.

1. Requirements

Functional

1:1 and group chat (groups up to 1,000 members). Text and media. Sent, delivered and read receipts. Online status and "last seen". Messages reach users who were offline when they were sent. Several devices per user (phone, laptop, tablet), all in sync. Push notifications.

Non-functional

Delivery under 300 ms p99 when both users are online. No lost messages, no visible duplicates. Messages in a conversation appear in the same order for every participant. End-to-end encrypted. Highly available: chat is used during emergencies.

Out of scope

Voice and video calls, stories, payments, message search on the server (impossible under end-to-end encryption anyway). Mention them, then park them.

The key observation: a chat message is a small write that must be durably acknowledged before the sender sees one tick, and then pushed to an open connection. Unlike most read-heavy systems, chat is write-heavy and push-based. The server's job is to be a reliable, ordered mailbox plus a switchboard of live connections.

2. Estimation

Assume 500 million daily active users sending 40 messages each per day. A quarter of messages go to groups, with 30 members on average. At peak, 200 million users are connected at once.

Messages 500M × 40 = 20B/day → 20B / 86,400 s ≈ 231,000/s (×3 for peak ≈ 700,000/s) Deliveries 1:1 75% × 20B × 1 recipient = 15B/day group 25% × 20B × 29 recipients = 145B/day total 160B / 86,400 s ≈ 1.9M deliveries/s (groups are 91% of them) Connections 200M concurrent / 200,000 per gateway = 1,000 gateways Heartbeats 200M / one every 30 s ≈ 6.7M/s (must end at the gateway) Storage 20B × ~200 B (ciphertext + metadata) = 4 TB/day ≈ 1.46 PB/year, ×3 replicas ≈ 4.4 PB Media 5% of messages × 200 KB average = 1B × 200 KB ≈ 200 TB/day (blob store + CDN)

Three conclusions. Group fan-out, not message count, dominates delivery work, so groups need their own deep dive. Heartbeats at 6.7 million per second cannot each touch a database, so presence must be derived from connections held in gateway memory. And media is fifty times the text volume, so it never travels through the chat servers at all.

3. API

Clients keep one long-lived WebSocket for everything real-time, and use plain HTTPS for bulk operations. Frames are shown as JSON; production clients use a compact binary encoding.

// client → server over the WebSocket
{ "type": "send", "client_msg_id": "c-7f1e9a", "conv_id": "a1b2", "body": "<ciphertext>" }
{ "type": "delivered", "up_to_inbox_seq": 8815 }        // receipt watermark for this device
{ "type": "read", "conv_id": "a1b2", "up_to_conv_seq": 4812 }
{ "type": "ping" }                                       // heartbeat every 30 s

// server → client
{ "type": "ack", "client_msg_id": "c-7f1e9a", "msg_id": "m-90ab", "conv_seq": 4812 }
{ "type": "msg", "inbox_seq": 8813, "conv_id": "a1b2", "conv_seq": 4812,
  "sender": "u_alice", "body": "<ciphertext>", "sent_at": "2026-10-09T10:41:07Z" }
{ "type": "receipt", "conv_id": "a1b2", "user": "u_bob", "read_up_to": 4812 }

// HTTPS
GET  /v1/sync?since_inbox_seq=8812&limit=500   → entries 8813..8817 and the new cursor
POST /v1/media                                  → presigned upload URL + media_id
POST /v1/conversations  { "members": [...] }    → conv_id

Two fields carry most of the design. client_msg_id is generated on the phone and makes sends idempotent: if the phone retries after losing the ack, the server returns the original msg_id instead of storing a second copy. inbox_seq is a per-user sequence number that lets any device ask "what did I miss since 8812?"

Receipts are stored as watermarks, not per message: "Bob has read conversation a1b2 up to 4812". One small write covers every earlier message, so reading a backlog of 200 messages costs one receipt, not 200. The bucket in the message key (for example one per 10,000 sequence numbers) keeps a busy group's partition from growing without bound.

Why a wide-column store

The write rate is high (231,000 messages and up to 1.9 million inbox appends per second), records are immutable, and the dominant read is "the latest 50 messages of one conversation, in order". That is the shape wide-column stores such as Cassandra, ScyllaDB and HBase are built for: a partition per conversation, rows sorted by sequence number on disk, appends that go to a memtable and a commit log, and linear scaling by adding nodes. Facebook Messages ran on HBase; Discord stores trillions of messages in ScyllaDB with the same (channel, bucket) idea, where Discord's bucket is a fixed 10-day time window. A relational database could store the data, but sharding it by hand at this write rate gains nothing, since chat needs no joins and no multi-row transactions. See SQL vs NoSQL and LSM trees.

5. High-level design

  1. Connect. The phone opens a TLS WebSocket through an L4 load balancer to any gateway. The gateway authenticates the token and writes conn:u_bob = {phone: gw-42} into the registry with a TTL refreshed while the socket lives.
  2. Send. Alice's frame reaches gateway 17, which forwards it to the chat service. The chat service checks the dedup table, assigns the next conv_seq, writes the message and Bob's inbox entry, and only then acks Alice.
  3. Route. The chat service looks up Bob's devices in the registry and sends the message to gateway 42 over an internal RPC; gateway 42 writes it into Bob's socket.
  4. Fallback. If Bob has no live connection, the push service sends a notification through APNs or FCM. Nothing is lost either way: the inbox entry is already durable, and Bob's next sync collects it.

Gateways are the only stateful tier, and their state is just sockets. They hold no messages: if gateway 42 dies, Bob's phone reconnects to another gateway within seconds and syncs from its last inbox cursor. That is what makes 1,000 of them manageable.

6. Deep dive: message flow and receipts

Each tick is a promise backed by a specific durable event. Walk through them one at a time.

At-least-once, deduplicated

Mobile networks drop packets, sockets die mid-frame and phones get killed in the background. Exactly-once delivery is not available, so the design is at-least-once with deduplication at both ends:

  • Sender side. Alice's app keeps the message in a local outbox and resends it with the same client_msg_id until it gets an ack. The chat service checks (sender_id, client_msg_id) first; a repeat returns the original msg_id and conv_seq, after re-applying the idempotent inbox and fan-out writes in case the first attempt crashed halfway (alternatively, write the message, inbox entry and dedup row in one logged batch, with the dedup row last).
  • Receiver side. The server may push a message twice (once live, once again in a sync after a reconnect). Bob's app keys messages by msg_id and ignores repeats.
  • Write before ack. The message, plus the recipient's inbox entry for a 1:1 chat or the fan-out event in Kafka for a group, is durably written before the sender's ack. If the chat service crashes in between, the sender retries and the dedup check makes the retry safe.

Ordering within a conversation

Two people in a group send at the same instant from different continents. Everyone must see the same order. Timestamps cannot decide it: phone clocks are wrong, and even server clocks differ by milliseconds, which is enough to reorder a fast exchange. Instead, every message gets a conv_seq from a single authority per conversation:

  • Requests for a conversation are routed to one chat-service instance by consistent hashing on conv_id. That instance holds the conversation's counter in memory and assigns 4811, 4812, 4813 in arrival order.
  • The counter's value is persisted with each message. If the instance dies, the next owner reads the highest stored conv_seq and continues. A lease in the membership service stops two instances from owning one conversation at the same time.
  • Clients sort by conv_seq, not by arrival. If 4813 arrives before 4812, the client shows a placeholder or waits briefly, and a gap that persists triggers a sync.

Order is only promised within a conversation. Global ordering across conversations is never needed and would require a global sequencer, a bottleneck for no benefit.

7. Deep dive: offline delivery and multi-device sync

Each user has an inbox: an append-only log of everything that should reach their devices, numbered by a per-user inbox_seq (assigned by an atomic per-user counter, for example on the owner of the user's inbox partition, since 1:1 sends and group fan-out workers append concurrently). New messages, receipts and membership changes are all appended to it. Each device stores the highest inbox_seq it has processed, its cursor, and sync is one question: "give me everything after my cursor".

Why a per-user log rather than "query every conversation for new messages"? Bob may be in 300 conversations. Without an inbox, a reconnect means 300 queries to find the four that changed. With it, sync is one range read on one partition, ordered, paginated and resumable. The cursor also makes sync safe to interrupt: a phone that loses signal halfway through a 2,000-entry catch-up resumes from the last entry it processed.

The inbox also solves multi-device. Each device has its own cursor, so the laptop that was closed all weekend catches up without affecting the phone. Read state syncs the same way: when Bob reads on his phone, a read receipt is appended to his own inbox, and the laptop clears its unread badge when it processes that entry.

Common mistake

Using "messages since timestamp T" for sync. Two messages can share a millisecond, clocks differ between servers, and a message written slightly late can land behind the cursor and never be fetched. A server-assigned sequence number per log has none of these problems.

Presence and last seen

Presence is the feature most likely to be over-built. The client sends a heartbeat every 30 seconds; the gateway answers it locally and never forwards it. Only transitions leave the gateway: when a socket opens, or when it closes or misses heartbeats past a grace period.

Presence is published lazily. Nobody needs to know that one of their 400 contacts came online unless they are looking at that contact. Clients subscribe to presence only for the chat that is open on screen, and the presence service pushes changes to those subscribers alone. Broadcasting every transition to every contact would turn 200 million users into billions of useless updates per hour.

8. Deep dive: group messages and push

A message to a 30-member group is written once to the conversation, then fanned out to 29 inboxes and up to 29 live sockets. The estimate showed this is 91% of delivery work, so it runs asynchronously behind a log.

  • Small groups (most of them). Fan out on write as shown. The member list is cached in the worker; each member gets an inbox append and, if online, a push to their gateway. Workers batch registry lookups and inbox writes per group.
  • Large groups and channels. A 100,000-member broadcast channel cannot append 100,000 inbox entries per message. Switch to fan-out on read: members' inboxes get one "channel has new messages" marker (coalesced), and clients page the conversation's own log directly by conv_seq. This is the same trade-off as in the news feed.
  • Push notifications. The push service maps users to device tokens, batches requests to APNs and FCM, and collapses bursts: twenty messages in a busy group become one notification that says "20 new messages". It also respects mute settings and per-device token invalidation (APNs reports tokens that are no longer valid; delete them). See Design a Notification System for the full pipeline.

9. Media and end-to-end encryption

Media

A 3 MB video should never pass through a gateway that is sized for 200-byte frames. The sender encrypts the file locally with a fresh random key, asks for a presigned upload URL, and uploads the ciphertext straight to the blob store. The chat message then carries only the media_id, the decryption key, a hash for integrity and a tiny blurred thumbnail. Recipients download through the CDN. Because the blob is encrypted, the CDN and the storage provider hold only noise, and a viral forward of the same video can reuse the uploaded blob instead of uploading it again.

End-to-end encryption at a high level

WhatsApp and Signal use the Signal protocol, and it shapes the server more than you might expect:

  • Key setup without both parties online. Each device uploads public identity and one-time "prekeys" to a key server. Alice fetches Bob's prekey bundle and derives a shared secret (X3DH) even if Bob's phone is off.
  • A new key per message. The Double Ratchet derives a fresh key for every message, so stealing today's key does not decrypt yesterday's messages (forward secrecy) and the session heals itself after a compromise.
  • Groups use sender keys. Each member distributes a sender key to the others once, then encrypts each group message once instead of once per member.
  • Every device is a recipient. Bob's phone and laptop have separate keys, so Alice's app encrypts each message once per device of each recipient. Fan-out partly moves to the client.

The consequences for the server design: it stores and routes opaque ciphertext, so it cannot search messages, scan content or render notification previews (the phone decrypts the push payload itself). It still sees metadata (who talks to whom, and when), which is why some systems also minimise what they log.

11. Key trade-offs to state

  • At-least-once plus dedup over exactly-once: retries are always safe, at the cost of client-side and server-side dedup by id.
  • Per-conversation sequence over timestamps: consistent order for everyone, at the cost of routing each conversation to one sequencer.
  • Per-user inbox log: one cheap range read per sync and natural multi-device support, at the cost of extra writes on every message (the pointer appends).
  • Fan-out on write for small groups, on read for large ones: fast delivery where it matters, bounded write amplification where it would explode.
  • Watermark receipts: one write per catch-up instead of one per message, at the cost of not tracking delivery of individual messages in a backlog.
  • Stored history vs store-until-delivered: WhatsApp historically deleted messages from the server once delivered, which minimises storage and exposure; persistent history (Messenger, Slack) enables new-device restore and costs petabytes.
Interview angle

What the interviewer is checking

Whether you separate connection handling from message logic, whether "delivered" and "read" are backed by real events, and whether your offline and multi-device story survives retries, reconnects and crashes without losing or duplicating messages.

Follow-ups to expect

  • How does the server know which gateway holds Bob's socket? (Connection registry, refreshed by the gateway.)
  • Alice's ack is lost and she resends. What prevents a duplicate? (client_msg_id dedup.)
  • Two users send to a group at the same instant. Who comes first, and does everyone agree?
  • Bob was offline for a week on his laptop. How does it catch up, and how much data does it pull?
  • How would you support a 100,000-member channel?
  • What changes with end-to-end encryption? (Ciphertext only, per-device keys, no server search, decrypt-in-app notifications.)

Red flags

  • HTTP polling every second for new messages from 200 million clients.
  • Ordering by client timestamps.
  • Marking a message delivered when the server sends it, rather than when a device acknowledges it.
  • Sending heartbeats or every presence change to a database.
  • Routing media through the chat servers.
