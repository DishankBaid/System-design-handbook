Why it matters

A single API key sends 40,000 requests per second to your search endpoint. Maybe it is a scraper, maybe a customer's retry loop gone wrong after a deploy. Either way the database behind search saturates, latency climbs for every other customer, and the on-call engineer gets paged. A rate limiter caps how many requests a client can make in a period of time and rejects the rest cheaply, before they reach anything expensive.

Rate limits exist for four reasons, and naming the one you care about decides where and how strictly you enforce it:

  • Abuse. Credential stuffing, scraping, spam sign-ups and enumeration attacks all depend on volume. A login endpoint limited to 5 attempts per minute per account makes brute force useless.
  • Fairness. In a multi-tenant system one noisy tenant should not consume capacity everyone else paid for. Limits turn shared capacity into per-tenant quotas.
  • Cost. Some requests cost real money: an SMS, a call to a paid LLM API, a GPU inference. A limit is a budget.
  • Protecting downstreams. A database that handles 30,000 queries per second falls over at 60,000. Shedding the excess with fast rejections keeps the system serving the requests it can handle, instead of timing out on all of them.

This chapter covers the algorithms and how to enforce them across many servers. The Design a Rate Limiter case study builds a complete limiter service on top of these ideas.

The five algorithms

Every algorithm answers the same question, "may this request proceed right now?", with different state and different behaviour at the edges. Throughout this section the example limit is 100 requests per minute per client.

Fixed window counter

Divide time into fixed windows (12:00:00 to 12:00:59, 12:01:00 to 12:01:59, ...) and keep one counter per client per window. Each request increments the counter; once it passes 100 the rest of the window is rejected. The key is something like rl:key_42:1739876460, the window start, so old windows simply expire.

It is the cheapest algorithm there is: one integer per client and one atomic increment per request. Its flaw is the window boundary. The limit is applied to each calendar window, not to any 60-second span, so a client can spend its full quota at the end of one window and again at the start of the next.

Whether this matters depends on the reason for the limit. For a daily quota on a paid API, a 2x spike at midnight is harmless. For protecting a database sized for 100 requests per minute, a 200-request burst is exactly the overload you were trying to prevent.

Sliding window log

Store the timestamp of every accepted request, for example in a Redis sorted set. On each new request, delete timestamps older than 60 seconds, count what remains, and accept only if the count is under 100. This is exact: any 60-second span contains at most 100 accepted requests, with no boundary effect.

The cost is memory proportional to the limit. A limit of 10,000 requests per hour across 1 million active users needs up to 10 billion timestamps. At 8 bytes each that is 80 GB before data-structure overhead, and a sorted set adds several times that. The log is the right choice only when limits are small (5 login attempts per 15 minutes) and exactness matters.

Sliding window counter

The sliding window counter keeps the memory of the fixed window and gets close to the accuracy of the log. Keep two counters per client: the previous window's total and the current window's count so far. Then assume the previous window's requests were spread evenly, and count only the part of it that still overlaps the last 60 seconds:

estimate = prev_count × (1 - elapsed / window) + curr_count allow if estimate + 1 ≤ limit

Here elapsed is how far we are into the current window. The weight on the previous window falls linearly from 1 at the start of the current window to 0 at its end.

The even-spread assumption is the only source of error. If all 84 previous requests came in the first second of that window, they are no longer in the sliding window and the estimate is too strict; if they all came in the last second, it is too lenient. In practice the error is small. Cloudflare measured it on real traffic and found that only 0.003% of requests were wrongly allowed or limited compared with an exact log. Memory is two integers per client, and the state is a pair of counters that work with plain atomic increments.

Token bucket

The token bucket separates two things the window algorithms blend together: the sustained rate and the largest burst. A bucket holds up to capacity tokens and is refilled at rate tokens per second. Each request takes a token; a request that finds the bucket empty is rejected. A client that has been idle has a full bucket and can burst up to capacity requests at once, but over any long period it cannot exceed rate.

No timer is needed to add tokens. Store the token count and the time of the last update; on each request, credit (now - last) × rate tokens, capped at capacity, then try to spend one. The state is two numbers per client.

Two parameters make the token bucket the most widely deployed algorithm: real clients are bursty (a page load fires 20 API calls at once, then nothing for a minute), and operators can tune burst and rate independently. Requests can also cost more than one token, so an expensive export endpoint can take 50 tokens while a cheap read takes 1.

Leaky bucket

The leaky bucket name covers two different things, and interviewers notice when you mix them up.

  • Leaky bucket as a queue. Requests go into a FIFO queue of fixed size. A worker drains it at a constant rate, say 2 per second. If the queue is full, new requests are dropped. The output is perfectly smooth no matter how bursty the input is. This is traffic shaping: requests are delayed, not just accepted or rejected.
  • Leaky bucket as a meter. A counter "leaks" at a constant rate and each request adds to it; if a request would overflow the bucket, it is rejected immediately. This version never queues, and it is mathematically equivalent to a token bucket viewed upside down (a full meter is an empty token bucket). The Generic Cell Rate Algorithm (GCRA) from ATM networks is an efficient form of it that stores a single timestamp per client.

Use the queue form in front of something that genuinely needs a steady input rate: a third-party API with a strict per-second cap, an SMS gateway, a batch job writer. Avoid it on interactive request paths, where a request that waits 4 seconds in a queue has probably already timed out at the client.

Implementation

Three single-process limiters with an injected clock, so the behaviour is deterministic. The test replays the boundary burst from the fixed window figure: 100 requests during second 59 and 100 more during second 60, against a limit of 100 per minute.

class TokenBucket:
    """capacity = largest burst; rate = tokens added per second (the sustained limit)."""

    def __init__(self, capacity, rate):
        self.capacity, self.rate = capacity, rate
        self.tokens, self.last = capacity, 0.0

    def allow(self, now, cost=1):
        # refill lazily: no timer, just credit the time since the last call
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False


class SlidingWindowCounter:
    """limit requests per window seconds, estimated from two fixed-window counters."""

    def __init__(self, limit, window):
        self.limit, self.window = limit, window
        self.idx, self.curr, self.prev = 0, 0, 0

    def allow(self, now):
        idx = int(now // self.window)
        if idx != self.idx:                      # crossed into a new window
            self.prev = self.curr if idx == self.idx + 1 else 0
            self.curr, self.idx = 0, idx
        elapsed = (now - idx * self.window) / self.window
        estimate = self.prev * (1 - elapsed) + self.curr
        if estimate + 1 > self.limit:
            return False
        self.curr += 1                           # count only what we let through
        return True


class FixedWindow:
    def __init__(self, limit, window):
        self.limit, self.window, self.idx, self.count = limit, window, -1, 0

    def allow(self, now):
        idx = int(now // self.window)
        if idx != self.idx:
            self.idx, self.count = idx, 0
        if self.count < self.limit:
            self.count += 1
            return True
        return False


# Limit: 100 requests per minute. A client sends 100 requests spread over
# 59.0-59.99 s, then 100 more over 60.0-60.99 s: 200 requests in two seconds.
burst = [59 + i / 100 for i in range(100)] + [60 + i / 100 for i in range(100)]
for limiter in (FixedWindow(100, 60), SlidingWindowCounter(100, 60), TokenBucket(100, 100 / 60)):
    allowed = sum(limiter.allow(t) for t in burst)
    print(f"{type(limiter).__name__:21} allowed {allowed} of 200")

# FixedWindow           allowed 200 of 200
# SlidingWindowCounter  allowed 101 of 200
# TokenBucket           allowed 103 of 200

The fixed window lets the whole double burst through. The sliding counter allows one extra request near the end of second 60, as the previous window's weight starts to fall. The token bucket allows 100 from its full bucket plus the 3 tokens that refilled at 1.67 per second during the two seconds. All three are correct implementations; they encode different definitions of "100 per minute".

Two choices in this code are policy, not mechanism. Counting only accepted requests lets a client that backs off recover quickly; counting rejected ones too punishes clients that keep hammering. And the token bucket's full initial state means a new client may burst immediately, which is usually what you want for a real user and not what you want for a brand new API key during a sign-up spam wave.

Rate limiting across many servers

Everything above assumes one process sees every request. In production, a client's requests are spread by the load balancer across 50 gateway instances. If each instance enforces 100 per minute on its own, the client actually gets up to 5,000. The counters have to be shared.

A central store and atomic updates

The standard design keeps limiter state in Redis, keyed by client. Redis is fast enough (well under a millisecond per operation on a local network), supports TTLs so idle clients' keys disappear, and executes commands one at a time, which is what makes atomic updates possible.

The trap is the read-modify-write race. If the gateway reads the counter, decides in its own code, and then writes back, two gateways can both read 99, both decide "allow", and both write 100.

For a fixed window, INCR is enough, but the expiry needs care. The common INCR followed by EXPIRE if the result was 1 has a gap: if the gateway crashes between the two commands, the key never expires and that client is blocked forever. Send both in a MULTI/EXEC transaction or a Lua script.

For a token bucket the logic does not fit in one command, so put it in a Lua script. Redis runs the script atomically, and the gateway makes a single round trip:

-- KEYS[1] = bucket key, ARGV[1] = capacity, ARGV[2] = refill per second, ARGV[3] = cost
local capacity, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local t = redis.call('TIME')                        -- Redis clock (Redis 5+): no skew between gateways
local now = tonumber(t[1]) + tonumber(t[2]) / 1e6

local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts = tonumber(b[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate)

local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) + 1)   -- idle bucket is full anyway
return {allowed, tostring(tokens)}

Details that matter:

  • Whose clock. If each gateway passes its own timestamp, a gateway whose clock runs 2 seconds fast hands out 2 seconds of free tokens. Reading TIME inside the script uses one clock for everyone.
  • Expiry. A bucket idle for capacity / rate seconds is full, which is the same as not existing. Expiring it then keeps memory proportional to active clients.
  • Sharding. All state for one client lives under one key, so it lands on one Redis Cluster shard and the script never needs keys from two shards. Throughput scales by adding shards.
  • Return value. Lua numbers returned to Redis are truncated to integers, so the remaining tokens are returned as a string for the response headers.

Local plus global

A central store puts a network round trip on every request and makes Redis a dependency of every API call. At 1 million requests per second that is 1 million Redis operations per second, plus about half a millisecond of added latency each. Large systems relax exactness to avoid both:

  • Local buckets with periodic sync. Each gateway counts locally and pushes its deltas to Redis every 100 ms, reading back the global total. Overshoot is bounded by how many requests the gateways can admit within one sync interval, and Redis load drops from once per request to once per interval per active client per gateway.
  • Static split. Give each of N gateways limit / N. It needs no coordination at all, but it only works when the load balancer spreads each client evenly. With sticky or skewed routing, a client whose traffic all hits one gateway gets one Nth of its quota.
  • Two tiers. A generous local limit in every instance (Envoy's local rate limit filter, an in-process token bucket) sheds floods without any network call, and a precise global limit in Redis enforces the actual quota. The local tier also keeps working if Redis is down.

When the limiter fails

Decide in advance what happens when Redis times out. Fail open (allow the request) keeps the product working and is the usual choice for fairness and quota limits; a few minutes without rate limits rarely hurts. Fail closed (reject) is right when the limit protects money or safety, such as SMS sends or payouts. Either way, put a tight timeout of a few milliseconds on the limiter call and a circuit breaker around it, so a slow Redis cannot add latency to every request.

Where to enforce limits

Limits belong at several layers, each catching what the one before cannot see.

The API gateway is the default answer in an interview because it sees authenticated identity and sits in front of every service. Services still need their own protection, because internal callers bypass the gateway and only the service knows that one request scans a million rows.

What to key on

  • User or account. The fairest key once a request is authenticated.
  • API key. Maps directly to a billing plan: 1,000 requests per minute on the free tier, 10,000 on the paid one.
  • IP address. The only key before authentication, and a blunt one. Thousands of users behind a corporate NAT or a mobile carrier's NAT share one IPv4 address, while one IPv6 attacker controls billions of addresses, so IPv6 limits usually key on the /64 prefix.
  • Endpoint. POST /exports and GET /users/me do not cost the same. Separate limits per endpoint, or a token bucket where each request costs tokens in proportion to its expense.
  • Global. A ceiling across all clients that protects a dependency regardless of who is calling.

Real systems combine several: a request passes only if every applicable limit allows it, for example 20 per second and 10,000 per day per key, plus 100 per minute per IP on the login page. Check the cheapest and most likely to reject first.

Telling clients they were limited

A rejected request should fail fast, cheaply and clearly. HTTP has a dedicated status for it: 429 Too Many Requests (RFC 6585). Use 503 Service Unavailable instead when the server sheds load because it is overloaded, rather than because this client exceeded its quota; the client did nothing wrong.

HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Policy: "per-minute";q=100;w=60
RateLimit: "per-minute";r=0;t=12
Content-Type: application/problem+json

{ "type": "https://api.example.com/errors/rate-limited",
  "title": "Rate limit exceeded",
  "detail": "100 requests per minute allowed for key ak_live_7Hq2. Retry in 12 seconds." }
  • Retry-After (seconds, or an HTTP date) tells the client exactly when to try again, so it does not guess and retry immediately.
  • Many APIs send X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset on every response, so well-behaved clients slow down before they hit the wall. GitHub's REST API is the best-known example.
  • The IETF HTTPAPI working group is standardising this as the RateLimit and RateLimit-Policy fields. Earlier drafts used three separate RateLimit-Limit, -Remaining and -Reset headers, which some servers already emit; the draft is still changing, so check its current version before relying on the exact syntax.

Clients receiving 429 should wait for Retry-After, then retry with exponential backoff and jitter. Without jitter, every client limited at the same moment retries at the same moment, and the burst repeats.

In the real world

  • Stripe runs token buckets in Redis for per-user request rate limits, and described three more limiters next to it: a concurrent-requests limiter (caps requests in flight, which catches slow expensive calls a rate limit misses), and two load shedders that reserve capacity for critical traffic such as charges when the fleet is under strain.
  • Cloudflare uses the sliding window counter for its rate limiting product, counting across its edge, and reported the 0.003% error figure above from production traffic.
  • NGINX implements limit_req with the leaky bucket method. The burst parameter sets the queue size, and nodelay forwards queued requests immediately, which turns the shaper into a meter.
  • GitHub allows 5,000 REST requests per hour for an authenticated user and 60 per hour per IP for unauthenticated ones, reported through x-ratelimit-* headers, plus secondary limits on concurrency and content creation.
  • Envoy offers a local rate limit filter (a token bucket per instance) and a global mode that calls an external gRPC rate limit service; Lyft's open source implementation of that service stores counters in Redis.
  • AWS API Gateway throttles with a token bucket per account and Region, with separate steady-state rate and burst settings that can be narrowed per stage, method and usage plan.
Interview angle

When to bring it up

In almost every design with a public API: one sentence such as "the gateway enforces per-key token buckets backed by Redis and returns 429 with Retry-After". It becomes central when the system sends costly messages (a notification system), accepts user content, or must survive abusive clients. If the question is "design a rate limiter", follow the case study.

Follow-ups to expect

  • Why not a fixed window? Draw the boundary burst and give the 2x number.
  • How does the sliding window counter estimate? Write the weighted formula and name its assumption.
  • Token bucket vs leaky bucket? Bursts allowed and immediate decision, vs smoothed output with queueing delay.
  • How do 50 gateways share a limit? Central Redis with atomic Lua scripts, then local-plus-global to cut latency and dependency.
  • What if Redis is down? Fail open or closed, chosen per limit, with a short timeout and a local fallback tier.
  • What do you key on before login? IP, with its NAT and IPv6 caveats.

Red flags

  • Reading a counter, deciding in application code, then writing it back: the race lets limits leak under exactly the load they exist for.
  • Per-instance limits with no mention that the real limit is multiplied by the number of instances.
  • Rejecting with 500 or a silent drop instead of 429 and Retry-After.
  • Treating a client-side limit as protection.
