A rate limiter service decides, for every API request, whether the caller is still within its allowance: 10 requests per second for a free key, 10,000 per day, 5 password attempts per minute per account. The algorithms are small. The design problem is everything around them: making the decision in well under a millisecond at a million requests per second, keeping counts correct when hundreds of gateways update them at once, staying up when the counter store does not, and changing limits without a deploy.

How to use this case study

The algorithms themselves (token bucket, leaky bucket, fixed, sliding log and sliding window counter) are explained in Rate Limiting. This page assumes them and focuses on the service: where it runs, how counters are stored and updated atomically, how it fails, and how it spans regions. Related chapters: Proxies & API Gateways, Caching, Timeouts, Retries & Circuit Breakers.

1. Requirements

Ask who is being limited, by what, and what happens to the rejected request. The answers decide where the limiter lives and how exact it must be.

Functional

Limit requests per key (API key, user id, IP, or a combination with the route). Several limits per request, for example 20 per second and 10,000 per day. Limits defined as data and changed without deploys. Reject with HTTP 429 and headers telling the client when to retry. A shadow mode that logs would-be rejections without enforcing them.

Non-functional

Adds under 1 ms at p99 to the request path. Handles 1M checks per second at peak. Accurate to within a few percent of the configured limit. Highly available: a limiter outage must never become an API outage.

Out of scope

Volumetric DDoS at the network layer (the CDN and edge firewalls absorb that before requests reach us), and billing-grade quota accounting, which needs exact, durable counts rather than fast approximate ones.

The central tension: a rate limiter sits on every request, so its latency and availability are added to everything. Accuracy is negotiable, those two are not. That one sentence justifies most of the design below, including the decision to accept small overshoots instead of paying for perfect global counts.

Two conclusions. Memory is trivial, so the store choice is about operations per second and latency, not capacity. And the latency budget leaves room for exactly one round trip to a nearby store per request: no second hop, no cross-zone call, no cross-region call. Every later decision has to respect that.

3. API

There are three interfaces: the internal check that gateways call, the rules that operators write, and the headers that API clients see.

The check call

Model it on Envoy's rate limit service, which is the de facto standard shape. The gateway sends a list of descriptors, key-value tuples that describe the request, and the service matches them against rules.

ShouldRateLimit(RateLimitRequest)      // gRPC, or an in-process library call
{ "domain": "public_api",
  "descriptors": [
    [{"key": "api_key", "value": "k_8f3a"}, {"key": "tier", "value": "free"}],
    [{"key": "api_key", "value": "k_8f3a"}, {"key": "route", "value": "POST /v1/payments"}]
  ],
  "hits_addend": 1 }                    // cost; a bulk endpoint may charge 10
→ { "overall_code": "OVER_LIMIT",
    "statuses": [
      {"code": "OK",         "limit": "20/second",  "remaining": 7,  "reset_ms": 420},
      {"code": "OVER_LIMIT", "limit": "100/minute", "remaining": 0,  "reset_ms": 18000}
    ] }

Rules as data

domain: public_api

  - match: { tier: free }

      - { requests: 20,     per: second, algorithm: token_bucket }
      - { requests: 10000,  per: day,    algorithm: sliding_window }
  - match: { route: "POST /v1/payments" }
    limits:
      - { requests: 100,    per: minute, algorithm: sliding_window }
  - match: { api_key: k_vip_partner }       # an override beats the tier rule

What the client sees

HTTP/1.1 429 Too Many Requests

Status 429 is defined in RFC 6585 and Retry-After in HTTP semantics. The X-RateLimit-* trio is a convention (GitHub and many others use it), and an IETF draft standardises the same idea as RateLimit and RateLimit-Policy fields. Send the remaining-count headers on successful responses too: well-behaved clients slow down before they hit the wall, which is cheaper for everyone than retries after a 429.

4. Data model

Two kinds of data with opposite profiles. Rules are small, change a few times a day and must be identical on every gateway. Counters are tiny, change a million times a second and can be lost without real harm.

DataWhereShapeNotes
RulesGit repo or Postgres, compiled into a versioned snapshot~10,000 rules, a few MBEvery gateway holds the full snapshot in memory; never fetched per request
Sliding window counterRedis hash rl:{k_8f3a}:r17win, cur, prevTTL of two windows, so idle keys vanish on their own
Token bucketRedis hash rl:{k_8f3a}:r03tokens, tsTTL of the time to refill from empty
Decision logKafka topic, then an OLAP storekey, rule, outcome, timestampSampled for allowed requests, complete for denials and shadow hits

The {k_8f3a} part of the key is a Redis Cluster hash tag: only the text inside the braces is hashed to pick the slot. All of one client's counters therefore live on the same shard, which is what lets a single Lua script check and update every matched rule in one call. Without the tag, the per-second and per-day counters could sit on different shards and the request would need two round trips.

Redis fits because the workload is "atomic read-modify-write on a small hot key, in memory, with expiry". Durability is not needed: if a shard restarts empty, every client briefly gets a fresh allowance, which is an acceptable failure for a limiter. Memcached lacks server-side scripting; a disk-backed database would blow the latency budget.

5. High-level design

The limiter is a library inside the API gateway, backed by a shared Redis cluster, with rules pushed out of band. It is not a separate network service on the request path, because a separate service would add a second hop and a second thing to fail.

  1. Match. The gateway authenticates the request, builds descriptors (API key, tier, route, client IP) and matches them against the in-memory rule snapshot. This is a hash lookup, a few microseconds.
  2. Short-circuit. If a local deny cache says this key is already over a limit until a known reset time, reply 429 immediately without calling Redis.
  3. Count. Otherwise send one EVALSHA to the shard that owns the client's hash tag. The script checks every matched limit and increments them only if all pass.
  4. Decide. Allowed: forward upstream and attach the remaining-count headers to the response. Denied: return 429 with Retry-After, and remember the denial locally until the reset.
  5. Record. Push the decision into an in-memory buffer that is flushed to Kafka in batches, for dashboards, abuse detection and shadow-mode analysis.

Why the gateway, and not elsewhere

PlacementStrengthWeakness

Use layers: a coarse per-IP limit at the edge for floods, the main identity-aware limiter at the gateway, and occasional in-service limits for expensive operations such as report exports. Envoy supports both modes: a local, per-instance limit and a global limit that calls an external service. If you choose the service form, deploy it as a sidecar or on the same host so the "extra hop" is a loopback call.

6. Deep dive: atomic counters in Redis

The naive implementation reads the counter, compares it with the limit, and writes it back. With hundreds of gateways, two of them read the same value at the same moment and both admit a request that only one should.

Three ways to make it atomic, in order of preference:

  • Lua script (EVAL/EVALSHA). Redis runs a script to completion without interleaving other commands, so read, compare and write become one step. Load it once with SCRIPT LOAD and call it by SHA so the script body is not resent per request.
  • INCR then compare. Atomic, and fine for a plain fixed window: increment first, and if the result exceeds the limit, deny. It cannot express token buckets or sliding windows, and a denied request still consumed a count.
  • WATCH/MULTI. Optimistic transactions retry on conflict, which is exactly the hot-key case where conflicts are constant. Avoid.

This is the sliding window counter as a script. It reads the time from Redis itself, so gateways with skewed clocks still agree on which window they are in.

-- KEYS[1] rl:{k_8f3a}:r17   one hash per client per rule: win, cur, prev
-- ARGV    limit, window_ms, cost
local t = redis.call('TIME')                       -- one clock for every gateway
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
local limit, window, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local win = math.floor(now / window)

local h = redis.call('HMGET', KEYS[1], 'win', 'cur', 'prev')
local w, cur, prev = tonumber(h[1]) or win, tonumber(h[2]) or 0, tonumber(h[3]) or 0
if win == w + 1 then prev, cur = cur, 0             -- rolled into the next window
elseif win > w + 1 then prev, cur = 0, 0 end        -- idle for two windows or more

local into = now % window
local estimate = prev * (window - into) / window + cur
local reset_ms = window - into
if estimate + cost > limit then
  return {0, 0, reset_ms}                           -- denied: nothing is written
end
redis.call('HSET', KEYS[1], 'win', win, 'cur', cur + cost, 'prev', prev)
redis.call('PEXPIRE', KEYS[1], window * 2)
return {1, math.floor(limit - estimate - cost), reset_ms}

Called six times against a real Redis with a limit of 5 per minute, it returned {1, 4, 29726}, {1, 3, ...} down to {1, 0, ...}, then {0, 0, 29704}: five allowed, the sixth denied. The third value is only the end of the current window; with a sliding window counter the previous window's weight still counts after the boundary (here the next request succeeds about 12 s after it), so derive Retry-After from the weighted formula, or accept that early retries are denied again. The production version takes several keys and checks all matched rules before incrementing any, so a request rejected by the daily quota does not also burn a per-second token.

Sliding window counter or token bucket?

Both store two numbers per key and run in constant time, which is why they are the only two worth offering in a high-volume service. A sliding log stores one timestamp per request, which at a 10,000-per-day quota is 10,000 entries per key. The difference between the two is what they promise the client.

class SlidingWindowCounter:
    """Two counters per key: this window and the previous one."""

    def __init__(self, limit, window):
        self.limit, self.window = limit, window
        self.win, self.cur, self.prev = 0, 0, 0

    def allow(self, now, cost=1):
        win = int(now // self.window)
        if win == self.win + 1:
            self.prev, self.cur = self.cur, 0
        elif win > self.win + 1:
            self.prev, self.cur = 0, 0
        self.win = win
        elapsed = (now % self.window) / self.window
        estimate = self.prev * (1 - elapsed) + self.cur   # weighted guess of the last full window
        if estimate + cost > self.limit:
            return False
        self.cur += cost
        return True


class TokenBucket:
    def __init__(self, rate, burst):
        self.rate, self.burst = rate, burst
        self.tokens, self.ts = burst, 0.0

    def allow(self, now, cost=1):
        self.tokens = min(self.burst, self.tokens + (now - self.ts) * self.rate)
        self.ts = now
        if self.tokens < cost:
            return False
        self.tokens -= cost
        return True


# 100 requests per minute. The client sends 100 at t=59s and another 100 at t=61s.
swc = SlidingWindowCounter(limit=100, window=60)
tb = TokenBucket(rate=100 / 60, burst=100)
for name, lim in (("sliding window", swc), ("token bucket", tb)):
    a = sum(lim.allow(59.0) for _ in range(100))
    b = sum(lim.allow(61.0) for _ in range(100))
    print(f"{name:15} t=59s: {a:3} allowed   t=61s: {b:3} allowed")
# sliding window  t=59s: 100 allowed   t=61s:   1 allowed
# token bucket    t=59s: 100 allowed   t=61s:   3 allowed

A plain fixed window would have admitted all 200 requests in two seconds, because the boundary at t=60 resets the count. Both algorithms close that hole. The choice then follows the rule's meaning:

  • Token bucket for rate limits ("20 per second, bursts of 40"). It explicitly models burst size and sustained rate as separate knobs, which is what protects a backend from spikes.
  • Sliding window counter for quotas ("10,000 per day"). Clients and support staff think in "requests in the last N", and the counter maps to that directly. Cloudflare measured its error on real traffic at a tiny fraction of requests, because it assumes the previous window's requests were spread evenly.

Hot keys

Hash tags put all of one client's counters on one shard. A single abusive client sending 150,000 requests per second would then exceed one shard's whole budget. Two defences keep that from becoming everyone's problem:

  • Local deny cache. Once a key is denied with a reset in 18 seconds, every gateway that saw the denial answers 429 locally until then. An attacker's flood becomes 200 Redis calls (one per gateway) instead of millions.
  • Token leasing for very high limits. For a partner allowed 50,000 requests per second, each gateway takes tokens in batches of 100 (one script call) and spends them locally. Redis load drops 100 times; the cost is that leased but unspent tokens are invisible to other gateways: 200 gateways holding up to 100 each can strand 20,000 tokens, 40% of the limit, so size batches to a fraction of each gateway's share (50,000 / 200 = 250 per second, so batches of 25 to 50) and let unused leases expire after a fraction of a second. Only worth it for the few keys whose limits are high enough to hurt.

7. Deep dive: latency budget and failure modes

Under a millisecond leaves no slack for anything unplanned. The budget only holds with these habits:

  • One round trip. All matched rules in one script, enabled by the hash tag. Persistent pooled connections; no TLS handshake or DNS lookup per call.
  • Same availability zone. Gateways call a Redis replica set in their own zone. A cross-zone hop often costs about as much as the whole budget.
  • Tight timeout. The client timeout is a few milliseconds, not the library default of seconds. A limiter that waits 5 seconds for a dead Redis has turned a counter outage into an API outage.
  • No retries on the hot path. A retry doubles the latency of exactly the requests that are already slow. Fall back instead.

Fail open or fail closed?

Fail open (allow)Fail closed (deny)Degrade to local limits
API availabilityUnaffectedTotal outage while Redis is downUnaffected

Typical useLow-risk read APIsLogin attempts, OTP sends, paymentsThe default for everything else

The default is the third column. When the error rate or latency to Redis crosses a threshold, a circuit breaker opens and each gateway enforces limit / gateway_count from an in-process token bucket, with a small slack factor because the load balancer does not spread one client perfectly evenly. With 200 gateways, a 20-per-second limit becomes 0.1 per second per gateway, which is too coarse; for small limits use a floor of a few requests per gateway and accept the looseness. Security-sensitive rules are marked fail: closed in their config, because letting unlimited password guesses through during a Redis incident is worse than briefly blocking logins.

Redis itself runs with a replica per shard and automatic failover. A failover loses the last few writes, which means some clients get a few extra requests. That is fine, and it is why the counters do not need persistence (appendonly no).

8. Deep dive: multiple regions

A client with a 6,000-per-minute limit may hit us in us-east, eu-west and ap-south at once. A single global Redis would make every check a cross-region call of 70 to 200 ms, so that is out. Three workable options:

Split the limit

Each region enforces a fixed share, say a third. Zero coordination, but a client whose traffic is all in one region gets a third of what they paid for.

Local counts, async sync

Each region counts locally and periodically shares its totals. Decisions use the local live count plus the other regions' last reports. Small, bounded overshoot.

Home region

Route all of a client's traffic to one region. Exact, but it couples routing to rate limiting and adds latency for global clients.

The middle option is the usual answer. Its error is easy to bound: a region can over-admit at most the traffic the other regions accepted since their last report. If this client sends 50 requests per second to each region and regions sync every 500 ms, each region is blind to at most 2 × 50 × 0.5 = 50 requests, under 1% of a 6,000-per-minute limit. Faster sync shrinks the error and costs more cross-region bandwidth; only keys active in several regions need syncing at all, which is a small fraction.

The sync itself is cheap because it batches: every 500 ms, each region publishes one message containing the deltas for all keys that changed, and each region's sync worker writes the others' slots into its local Redis. Request-path latency is untouched.

9. Deep dive: rules propagation

A wrong rule is an outage: set the limit for the payments route to 10 per minute instead of 10 per second and every merchant gets 429s within a minute. Rules are code-adjacent config, and they deserve the same pipeline as code.

  • Compile and validate. Reject unknown descriptor keys, overlapping rules with no clear precedence, and limits that changed by more than 10 times without an explicit override flag. Replay the last hour of decision logs against the new rules and report how many keys would newly be denied.
  • Immutable, versioned snapshots. A snapshot is a single file, content-hashed, stored in object storage. A small pointer key in etcd names the current version. Gateways watch the key, download the snapshot, build the lookup index off to the side, and swap one pointer. A request sees either v41 or v42, never half of each.
  • Last known good. A gateway that cannot reach etcd or object storage keeps its current snapshot and keeps serving. It also writes the snapshot to local disk, so a restart during a control-plane outage still has rules.
  • Counter continuity. Counter keys include a rule id, not a rule version. Changing a limit from 100 to 200 per minute keeps the existing count, so clients do not get a free reset every time an operator touches a rule.

11. Key trade-offs to state

  • Library in the gateway over a separate service: no extra hop or extra failure domain, in exchange for shipping limiter changes with gateway releases.
  • Approximate over exact: sliding window counters, per-gateway fallback and async region sync all allow small overshoots, in exchange for sub-millisecond checks that never block traffic.
  • Redis without persistence: losing counters on a crash gives a few clients a fresh window, in exchange for speed and simpler operations.
  • Degrade, do not fail: local limits during a Redis outage, with fail-closed reserved for security-sensitive rules.
  • Hash tags per client: one round trip for all rules, in exchange for concentrating a hot client on one shard, which the deny cache and leasing then handle.
Interview angle

What the interviewer is checking

Whether you treat the limiter as part of the request path, with a latency and availability budget, rather than as an algorithm question. Strong answers name the race condition and fix it with an atomic script, explain where the limiter sits, and have a concrete answer for "Redis is down".

Follow-ups to expect

  • Two gateways update the same counter at once. What goes wrong and how do you fix it?
  • Redis is unreachable. Do you allow or deny? Does the answer differ for login attempts?
  • How do you limit a client that calls you from three regions without a cross-region call per request?
  • One customer is allowed 50,000 requests per second. What happens to the shard holding their counter?
  • How do you change a limit safely, and how fast does the change take effect?
  • How does the client know when to retry? (429, Retry-After, remaining-count headers.)

Red flags

  • A separate limiter microservice called synchronously, with no thought about its latency or what happens when it is down.
  • GET-then-SET counters across many servers.
  • Gateway-local clocks deciding window boundaries for a shared counter.
  • A sliding log for large quotas, storing one entry per request.
  • A global, cross-region counter on the hot path.
