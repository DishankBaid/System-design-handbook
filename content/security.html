Why it matters

Every request that reaches your system carries a claim: "I am user 8412, and I want to read order 77310." Security is the machinery that checks both halves of that sentence on every request, protects the data while it moves and while it sits on disk, and keeps working when one layer is bypassed.

Treat the cryptography as well-tested building blocks. Your job is to assemble them correctly, and most real breaches come from assembly mistakes, not broken ciphers.

Authentication vs authorization

Authentication (authn) answers "who is this?" It turns a credential (a password, a passkey, a certificate, a signed token) into a verified identity such as user_8412 or spiffe://prod/ns/billing/sa/invoicer. Authorization (authz) answers "may this identity do this action on this resource?" It takes the identity, the action and the resource, and returns allow or deny.

They fail differently, which is why it pays to keep them apart in your head and in your code:

  • HTTP says so explicitly: 401 Unauthorized means "I do not know who you are" (despite the name, it is about authentication), and 403 Forbidden means "I know who you are, and the answer is no."
  • Authentication is usually centralized: one identity provider, one login page, one token format. Authorization is spread out, because only the orders service knows that order 77310 belongs to user 8412.
  • Authentication bugs tend to be loud (nobody can log in). Authorization bugs are silent: one user reads another user's invoices by changing an id in the URL.

Storing passwords

If your system stores passwords, assume the database will leak one day, through a backup, a misconfigured replica or an SQL injection. The goal of password storage is that a leaked table does not hand the attacker the passwords, and that cracking them costs so much that most survive.

Hash, salt, and make it slow

Three rules, each closing a specific attack:

  1. Never store the password, store a one-way hash. At login, hash what the user typed and compare. Encryption is the wrong tool, because whoever holds the key can decrypt every password at once.
  2. Add a unique random salt per user. A salt is 16 or so random bytes stored next to the hash and mixed into it. Without salts, two users with the password Summer2026! have the same hash, and an attacker can use a precomputed table (a rainbow table) to reverse common hashes instantly. With salts, every hash must be attacked separately.
  3. Use a deliberately slow, memory-hard function. SHA-256 is designed to be fast, which is exactly wrong here: the attacker's cost per guess is your cost per login. Password hashing functions have a tunable work factor so each guess costs tens of milliseconds and, for the memory-hard ones, tens of megabytes of RAM, which is what makes GPUs and custom chips much less effective.

Measured on one laptop core with Python's hashlib, the gap between a fast hash and a password hash is enormous:

FunctionTime per hashGuesses per second per core8-char [a-z0-9] space (2.8 × 1012)
SHA-256 + salt0.0002 ms~4.8 million~6.8 days on one core, minutes on a GPU
PBKDF2-HMAC-SHA256, 600,000 iterations~44 ms~23~4,000 core-years
scrypt, N = 217, r = 8, p = 1 (128 MiB)~189 ms~5~16,900 core-years, and memory-bound on GPUs

Attackers try leaked password lists before brute force, so weak passwords fall even against a slow hash. The slow hash buys time for everyone else, and time to force resets.

Which function to choose

Argon2id

Winner of the 2015 Password Hashing Competition and the first choice in OWASP's guidance. Tunable memory, iterations and parallelism. OWASP's minimum is 19 MiB of memory, 2 iterations, parallelism 1.

scrypt

Memory-hard, older than Argon2, available in many standard libraries (including Python's hashlib). A good choice when Argon2 is not available.

bcrypt

From 1999, still widely used and acceptable with a cost of 10 or more. Not memory-hard, and it silently ignores input beyond 72 bytes, so long passphrases are truncated.

PBKDF2

Iterated HMAC. Not memory-hard, so GPUs love it, but it is the one to use when FIPS-140 compliance is required. OWASP recommends 600,000 iterations with SHA-256.

Two operational details matter in a design. First, store the algorithm and parameters with each hash (the standard encodings such as $argon2id$v=19$m=19456,t=2,p=1$... do this), so you can raise the cost later and rehash each user at their next successful login. Second, password hashing is CPU and memory heavy on purpose. A login endpoint doing 2,000 logins per second at 50 ms of CPU each needs about 100 cores just for hashing, and is an easy denial-of-service target, so put it behind a rate limiter and lock out or slow down repeated failures per account and per IP.

Better: do not store passwords at all

Delegating login to an identity provider (OIDC, below) or using passkeys (WebAuthn, where the user's device holds a private key and the server stores only the public key) removes the password table entirely. A leaked public key is useless to an attacker. For a new system, say this out loud.

Sessions vs tokens

After login, the user should not send a password on every request. The server issues something the client presents instead. There are two families.

A session is server-side state. The server generates a random, unguessable session id (128 bits or more), stores session_id → {user_id, expires_at, ...} in a database or Redis, and sends the id in a cookie marked HttpOnly (JavaScript cannot read it), Secure (HTTPS only) and SameSite=Lax or Strict (not sent on most cross-site requests, which blunts CSRF). Every request costs a lookup, and logging out is a delete.

A self-contained token carries the identity and its claims inside itself, signed so that any service holding the verification key can check it without a lookup. The most common format is the JWT.

Production systems often use both: a session cookie from the browser to the edge, exchanged there for a short-lived token that travels between internal services.

JSON Web Tokens

A JWT (RFC 7519) is three base64url-encoded parts joined by dots: a header, a payload of claims, and a signature over the first two. The header and payload are encoded, not encrypted. Anyone holding the token can read them, so never put secrets or personal data you would not show the user into a JWT.

Claims and signing algorithms

The registered claims are short on purpose: iss (issuer), sub (subject, the user or service), aud (audience, which service the token is for), exp (expiry, Unix seconds), nbf (not before), iat (issued at) and jti (a unique token id). Applications add their own, such as scope or tenant_id.

The signing algorithm decides who can verify. HS256 is HMAC with a shared secret: whoever can verify can also mint tokens, so it only fits when issuer and verifier are the same service. RS256 (RSA) and ES256 (ECDSA P-256) use a private key to sign and a public key to verify, so the identity provider keeps the private key and publishes public keys at a JWKS (JSON Web Key Set) endpoint. Every service fetches and caches them, and the kid header says which key signed a token, which is what makes key rotation possible without downtime.

Validating a token correctly

Most JWT vulnerabilities are validation shortcuts. A correct validator does all of these, in this order:

  1. Pin the algorithm. Accept only the algorithm you expect. Two classic attacks come from trusting the header: "alg": "none" (an unsigned token that weak libraries accepted), and algorithm confusion, where a server expecting RS256 is handed an HS256 token that was HMAC-signed using the server's own public key as the secret.
  2. Verify the signature with the key named by kid from your trusted JWKS, using a constant-time comparison for HMAC.
  3. Check the claims: exp and nbf with a small clock-skew allowance (30 to 60 seconds), iss equals your identity provider, and aud equals this service. Skipping the audience check means a token issued for a low-value service can be replayed against a high-value one.
  4. Then authorize: a valid token proves identity and carries scopes; whether this user may read this specific order is still your service's decision.

The revocation problem, and access plus refresh tokens

A self-contained token is valid until exp, and no lookup happens, so there is nowhere to say "this one is cancelled." If an employee is fired or a laptop is stolen, a token with a 24-hour expiry keeps working for up to 24 hours. The options:

  • Keep access tokens short-lived, typically 5 to 15 minutes. Revocation then takes effect within one lifetime.
  • Pair them with a long-lived refresh token that the client exchanges for a new access token. The refresh token is checked against a database on every use, so it can be revoked immediately. You get stateless validation on the hot path (every API call) and a stateful check on the cold path (once per 15 minutes per client).
  • Rotate refresh tokens: each use returns a new refresh token and invalidates the old one. If an old one is ever presented again, someone copied it, so revoke the whole family and force a new login.
  • A denylist of revoked jti values for emergencies, held in memory or Redis. It only needs entries until their tokens would have expired anyway, so it stays small. It does reintroduce a lookup, which is the price of instant revocation.

For browsers, keep tokens out of localStorage, where any injected script can read them. An HttpOnly cookie, or a backend-for-frontend that holds tokens server-side and gives the browser only a session cookie, removes that exposure.

A signed token in 40 lines

The mechanics are simple enough to write with the standard library, which makes the validation rules concrete. This is a teaching example, not production code: real systems should use a maintained library and, across services, asymmetric keys.

# TEACHING EXAMPLE ONLY. In production use a vetted library (PyJWT, jose, a platform SDK).
import base64
import hashlib
import hmac
import json

HEADER = {"alg": "HS256", "typ": "JWT"}


def b64url(raw: bytes) -> str:
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()


def unb64url(text: str) -> bytes:
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))


def sign(claims: dict, key: bytes) -> str:
    head = b64url(json.dumps(HEADER, separators=(",", ":")).encode())
    body = b64url(json.dumps(claims, separators=(",", ":")).encode())
    mac = hmac.new(key, f"{head}.{body}".encode(), hashlib.sha256).digest()
    return f"{head}.{body}.{b64url(mac)}"


def verify(token: str, key: bytes, now: int, audience: str) -> dict:
    try:
        head, body, sig = token.split(".")
    except ValueError:
        raise ValueError("malformed token")
    # 1. Pin the algorithm: never let the token choose how it is checked.
    if json.loads(unb64url(head)) != HEADER:
        raise ValueError("unexpected header")
    # 2. Check the signature in constant time BEFORE trusting any claim.
    expected = hmac.new(key, f"{head}.{body}".encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(expected, unb64url(sig)):
        raise ValueError("bad signature")
    claims = json.loads(unb64url(body))
    # 3. Only now check the claims.
    if claims["exp"] <= now:
        raise ValueError("expired")
    if claims["aud"] != audience:
        raise ValueError("wrong audience")
    return claims


key = bytes.fromhex("8f2b6c1e9d4a7f3b0c5e8a1d6f2b9c4e7a0d3f6b1c8e5a2d9f4b7c0e3a6d1f8b")
now = 1_791_504_000                       # 2026-10-09 00:00:00 UTC
token = sign({"sub": "user_8412", "aud": "orders-api", "scope": "orders:read",
              "iat": now, "exp": now + 900}, key)
print(token)
print(verify(token, key, now + 60, "orders-api")["sub"])

head, body, sig = token.split(".")
forged = b64url(unb64url(body).replace(b"orders:read", b"orders:admin"))
for label, tok, t in [("tampered", f"{head}.{forged}.{sig}", now + 60),
                      ("expired", token, now + 901),
                      ("wrong key", sign({"sub": "x", "aud": "orders-api", "exp": now + 900}, b"guess"), now)]:
    try:
        verify(tok, key, t, "orders-api")
    except ValueError as err:
        print(f"{label:9} -> rejected: {err}")

OAuth 2.0 and OpenID Connect

OAuth 2.0 (RFC 6749) is a framework for delegated authorization: a user lets an application act on their behalf at some API, without giving the application their password. "Let this budgeting app read my bank transactions" is the canonical case. Four roles take part: the resource owner (the user), the client (the app), the authorization server (which logs the user in and issues tokens) and the resource server (the API).

OAuth defines several flows, called grants. For anything with a user, the answer today is the authorization code grant with PKCE. The implicit grant (tokens returned directly in the browser URL) and the password grant (the app collects the user's password) should no longer be used, per the OAuth 2.0 Security Best Current Practice (RFC 9700, 2025). For machine-to-machine calls with no user, the client credentials grant lets a service authenticate as itself and get a token.

Authorization code with PKCE

PKCE (Proof Key for Code Exchange, RFC 7636, pronounced "pixie") closes a specific hole. The authorization code comes back through a browser redirect, where malicious apps registered for the same custom URL scheme, browser extensions or logs might capture it. PKCE binds the code to a secret that never leaves the client, so a captured code cannot be redeemed. Step through the flow:

Details that interviewers probe:

  • The verifier is 43 to 128 characters of high-entropy randomness. With method S256, the challenge is BASE64URL(SHA256(verifier)). The plain method exists but offers no protection if the authorize request itself is observed.
  • state is a random value tied to the user's browser session. Without it an attacker can complete a flow with their code in your browser and link your account to theirs.
  • Redirect URIs must match exactly against a pre-registered list. Pattern matching on redirect URIs has caused real token theft.
  • Codes are single-use and short-lived. RFC 6749 recommends a lifetime of at most 10 minutes, and many servers use under a minute. If a code is presented twice, the server should revoke the tokens already issued for it.
  • Confidential clients (a server-side web app that can keep a secret) also send a client_secret at the token endpoint. Public clients (single-page and mobile apps) cannot, which is why PKCE was invented; it is now recommended for every client.

OpenID Connect: login on top of OAuth

OAuth answers "may this app call this API?" It does not, by itself, tell the app who the user is; an access token is meant for the API, not the client. OpenID Connect (OIDC) adds authentication: request the openid scope and the token response includes an ID token, a JWT whose audience is the client and whose claims describe the login (sub, iss, auth_time, a nonce echoed from the request to stop replay, optionally email and name). OIDC also standardizes discovery at /.well-known/openid-configuration, which lists the endpoints and the JWKS URL. "Sign in with Google" and corporate single sign-on through Okta or Microsoft Entra ID are OIDC (or its older cousin, SAML).

Common mistake

Sending the ID token to your API as if it were an access token. The ID token's audience is the client app; the API should only accept access tokens whose aud names the API. Mixing them up is how a token for one app ends up authorizing calls to another.

API keys

An API key is a long random string that identifies a calling program, typically a customer's backend. Keys are simpler than OAuth and fine for server-to-server integrations, but they are bearer secrets that rarely expire, so treat them like passwords:

  • Store only a hash. A key has 128+ bits of randomness, so a fast hash like SHA-256 is enough (no salt or slow function needed, because there is no dictionary to guess from). Show the key to the customer once, at creation.
  • Give keys a recognizable prefix, as Stripe (sk_live_) and GitHub (ghp_) do. Secret scanners in code hosts can then spot leaked keys and alert or revoke them automatically, and support staff can tell a test key from a live one at a glance.
  • Scope and expire them: per-key permissions, per-key rate limits, a last-used timestamp, and support for two active keys at once so customers can rotate without downtime.

Service-to-service: TLS and mTLS

TLS gives a connection confidentiality, integrity and server authentication. In TLS 1.3 the client sends its key share in the first message, so the handshake completes in one round trip before application data flows; the server proves its identity with a certificate chained to a trusted certificate authority and a signature over the handshake. The TCP, UDP & HTTP chapter covers the round trips and the 0-RTT resumption trade-off.

Ordinary TLS authenticates only the server. Mutual TLS (mTLS) makes the client present a certificate too, so both sides know who they are talking to. It replaces "anything inside the VPC is trusted" with "every call carries a verifiable workload identity", the core of zero trust networking.

The hard part of mTLS is not the handshake, it is certificate lifecycle: issuing a certificate to every workload, rotating it before it expires, and revoking it. Service meshes such as Istio and Linkerd automate this with an internal CA and certificates that live for about a day, so a stolen certificate is useful only briefly and revocation lists are rarely needed. SPIFFE standardizes the identity format (spiffe://trust-domain/path) so different platforms can agree on who a workload is.

mTLS authenticates the calling service. When the call is on behalf of a user, also forward the user's identity, usually as a short-lived token, so the downstream service can apply user-level authorization and you avoid the confused deputy problem, where a privileged service is tricked into acting for a caller who lacks the permission.

Authorization models

Once you know who is calling, something has to decide what they may do. Three models cover almost every system, and real systems often combine them.

ModelDecision is based onExample ruleStrengthWeakness
RBACRoles assigned to usersUsers with role support_agent may read ticketsSimple to audit; maps to org chartsRole explosion when access depends on the specific resource or context
ABACAttributes of user, resource, action and environmentAllow if user.dept == doc.dept and request is from a managed device during business hoursVery expressive, context awarePolicies get hard to reason about; "who can see X?" is hard to answer
ReBACRelationships in a graphA user may view a doc if they are a viewer of it, a member of a group that is, or a viewer of its parent folderNatural for sharing, folders, orgs and teamsNeeds a dedicated, fast, consistent graph service

Role-based access control (RBAC) is the default for internal tools and admin consoles. Attribute-based access control (ABAC) is usually expressed in a policy language and evaluated by an engine such as Open Policy Agent or AWS Cedar. Relationship-based access control (ReBAC) is what document sharing in Google Drive, GitHub repository permissions and Notion workspaces need: "can Ana view this doc?" depends on a chain of relationships, not a single role.

Zanzibar and relation tuples

Google's Zanzibar paper (2019) describes the ReBAC system behind Drive, YouTube, Cloud and other products. Permissions are stored as relation tuples of the form object#relation@subject, and a schema says how relations imply each other ("viewers of a folder are viewers of the documents in it"). A check walks the graph.

Zanzibar's paper reports trillions of tuples, millions of checks per second, a 95th-percentile check latency under 10 ms and availability above 99.999%. Its most interesting idea is consistency. Imagine Ana removes Raj from a doc and then adds confidential content. If an authorization replica is stale and still lets Raj read the new content, that is the "new enemy" problem. Zanzibar solves it with zookies, opaque consistency tokens: the content write records a zookie, and later checks must be evaluated at a snapshot at least that fresh. Open-source implementations of the model include SpiceDB and OpenFGA.

Wherever the decision is made, two design rules hold. Deny by default: a missing rule means no access. And enforce on the server for every request, on the object being touched; hiding a button in the UI is not authorization.

Secrets management

A secret is any value that grants access: database passwords, API keys, signing keys, TLS private keys. Most leaked secrets come from the same few places: committed to Git, baked into container images, printed in logs, or shared in chat. The design answer is a secrets manager (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault) with these properties:

  • Central storage, encrypted, with access by workload identity. A service authenticates as itself (its cloud IAM role, Kubernetes service account or SPIFFE identity) and gets only the secrets its policy allows. No bootstrap password is baked into the image.
  • Audit logs of every read, plus secret scanning in CI so a key pushed by mistake is revoked within minutes.
  • Rotation without deploys. Applications fetch secrets at startup and refresh them, so a rotated password is picked up automatically.
  • Dynamic, short-lived credentials where possible. Vault can create a database user on request with a one-hour lease and drop it afterwards; cloud IAM roles hand out temporary credentials that expire within hours. A credential that expires on its own cannot be leaked for long.

Encryption in transit and at rest

In transit means TLS on every hop, including internal ones: load balancer to service, service to database, service to cache. "TLS terminates at the load balancer and the inside is plaintext" was common, and is exactly what an attacker who gets onto the internal network hopes for.

At rest means data on disks, in backups and in object storage is encrypted with keys the storage medium does not hold. Cloud databases and object stores do this transparently, which protects against stolen disks and careless decommissioning, but not against an attacker who can query the database through the application, because the database decrypts for any authorized reader. For the most sensitive fields (card numbers, national ids, health data) add application-level encryption, where the service encrypts the field before it reaches the database, or tokenization, where the field is replaced with a meaningless token and the real value lives in a separate, tightly guarded vault.

Envelope encryption with a KMS

A key management service (KMS) keeps master keys inside hardware security modules (HSMs) that never export them. But you cannot send terabytes through a KMS API: AWS KMS, for example, encrypts at most 4 KB per direct call, and every call is a network round trip. Envelope encryption solves this with two levels of keys.

The service asks KMS for a fresh data encryption key (DEK) and receives it twice: in plaintext, and wrapped under the key encryption key (KEK) that never leaves the HSM. It encrypts locally with an authenticated cipher such as AES-256-GCM, wipes the plaintext DEK, and stores the wrapped DEK beside the ciphertext. Services often cache unwrapped DEKs for a few minutes to cut KMS calls and latency.

The benefits are why the major cloud storage services use this pattern: bulk crypto runs at local speed, the master key stays in hardware, access to data reduces to access to a KMS key (with an audit trail), and crypto-shredding becomes possible: delete a tenant's KEK and all their data, including old backups, becomes unreadable at once.

Common vulnerabilities

The OWASP Top 10 is the standard shortlist of web application risks. The current 2025 edition is led by broken access control, security misconfiguration and software supply chain failures, with cryptographic failures and injection close behind; server-side request forgery, its own entry in 2021, is now folded into broken access control. Three deserve design-level answers.

Broken access control

The API checks that you are logged in but not that order 77310 is yours, so changing the id in the URL reads someone else's order (an IDOR, insecure direct object reference). Fix: check ownership or relationship on every object access, deny by default, and test it with a second user account.

Injection

User input is concatenated into an SQL query, shell command or template, and becomes code. ' OR '1'='1 is the classic. Fix: parameterized queries everywhere, never string-building, and least-privilege database users so a successful injection reaches less.

SSRF

A feature fetches a user-supplied URL (webhooks, link previews, image import) and the attacker points it at internal addresses such as the cloud metadata endpoint 169.254.169.254, which can hand out credentials. The 2019 Capital One breach used this path. Fix: fetch through an egress proxy with an allowlist, block private and link-local ranges after DNS resolution, and require session-based metadata access (AWS IMDSv2).

Defense in depth

No single control is perfect, so layer them so that one failure is not a breach. Walk a request inward and name a control at each layer:

LayerControlsStops
EdgeWAF, DDoS protection, TLS, rate limiting, bot detectionVolumetric attacks, credential stuffing, known exploit patterns
GatewayToken validation (signature, issuer, audience, expiry), coarse scopesUnauthenticated and forged requests before they reach services; see API gateways
ServiceFine-grained authorization per object, input validation, parameterized queriesIDOR, injection, privilege escalation
NetworkmTLS between services, network policies, egress allowlistsLateral movement after one service is compromised, SSRF
DataEncryption at rest, envelope encryption for sensitive fields, least-privilege DB usersStolen disks and backups, over-broad queries
OperationsSecrets manager, audit logs, alerting on anomalies, patchingLeaked credentials living forever, undetected intrusions

Two principles tie the layers together. Least privilege: every user, service and key gets only the permissions it needs, so a compromise is contained. And assume breach: design as if one service is already compromised, and ask what it can reach. Security events also belong in your observability pipeline: failed logins, permission denials and token validation failures are signals, but never log the tokens or passwords themselves.

In the real world

  • Google: Zanzibar serves authorization for Drive, YouTube and Cloud; BeyondCorp replaced the trusted corporate network with per-request device and user checks, an early zero-trust model.
  • AWS: KMS with envelope encryption underpins S3, EBS and DynamoDB encryption; IAM roles hand out short-lived credentials; IMDSv2 was introduced to blunt SSRF against the metadata service.
Interview angle

When to bring it up

In every design, briefly: "Clients authenticate through our identity provider with OIDC, the gateway validates short-lived JWT access tokens, services authorize per object, internal traffic is mTLS, and sensitive data is encrypted with KMS-managed keys." Go deeper when the problem involves sharing (Google Docs, Dropbox: ReBAC), payments (tokenization, envelope encryption), third-party integrations (OAuth, API keys) or user-supplied URLs (SSRF).

Follow-ups to expect

  • How do you revoke a JWT? (Short expiry plus refresh tokens checked against a store; a jti denylist for emergencies.)
  • Why PKCE if you already have state? (state stops CSRF; PKCE stops a stolen code from being redeemed.)
  • Where is authorization enforced? (Coarse at the gateway, fine-grained in the service that owns the object.)
  • How do you store passwords, and how do you upgrade the hashing cost later?
  • How would you implement "share this folder with a team" at scale? (Relation tuples, Zanzibar-style checks, consistency tokens.)

Red flags

  • Storing passwords with SHA-256 or MD5, or encrypting them.
  • Long-lived JWTs with no revocation story, or JWTs in localStorage for a high-value app.
  • Trusting the JWT alg header, or skipping the audience check.
  • Authorization only in the UI, or only "is logged in" checks on object endpoints.
  • Secrets in environment files committed to the repository.
