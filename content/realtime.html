Why it matters

HTTP was built for the client to ask and the server to answer. A chat message, a stock tick, a "your driver is 2 minutes away" update or a token from a language model all start on the server, at a moment the client cannot predict. Getting that data to the client quickly, for millions of clients at once, is the problem this chapter is about.

There are four common answers, in roughly historical order: short polling, long polling, server-sent events and WebSockets. They differ in latency, in how much they cost the server per idle client, in whether data can flow both ways, and in how well they survive proxies, load balancers and flaky mobile networks. Picking one is the easy part. The hard parts come with long-lived connections: holding millions of them, routing a message to the server holding one user's socket, and recovering when connections drop, which they constantly do.

This chapter assumes you know how TCP and HTTP connections work; see TCP, UDP & HTTP. The chat system case study puts these pieces together.

The four transports

Step through the four sequence diagrams. In each, message 42 is created on the server at some moment, and the question is how and when it reaches the client.

Short polling

Short polling means the client asks "anything new since 41?" on a fixed timer, and the server answers immediately, usually with nothing. It is ordinary request/response, so it works through every proxy, CDN and corporate firewall, needs no special server code, and each request can go to any stateless server.

The cost is a direct trade between latency and load. With a 5-second interval, an event waits 2.5 seconds on average and up to 5 seconds before the client sees it. One million clients polling every 5 seconds is 200,000 requests per second, almost all returning empty arrays, each paying for headers, authentication, routing and a database or cache lookup. Halving the latency doubles that bill.

Short polling is right more often than people expect: a dashboard refreshing every 30 seconds, an order status page, a job progress bar.

Long polling

Long polling keeps the request-response shape but lets the server delay its answer. If nothing is new, the server holds the request open until an event arrives or a timeout passes (typically 20 to 60 seconds), then replies. The client immediately sends the next request. Delivery latency drops to roughly one network trip, and empty responses only happen once per timeout instead of once per interval.

The costs move rather than disappear:

  • A held request per client. Thread-per-request servers run out of threads quickly. Long polling needs an event-driven server (NGINX, Node.js, Netty, Go) where a waiting request is a small object, not a blocked thread.
  • A gap after each message. Between the response and the next request, events can arrive with nobody waiting. The client must send a cursor (after=42) so the server can return whatever accumulated in the gap. Without a cursor, long polling silently loses messages.
  • Timeouts everywhere. Every proxy and load balancer on the path has an idle timeout. The server's hold time must be shorter than all of them, or the client sees a 504 instead of a clean empty response.

Long polling is a fine choice for infrastructure APIs where clients are programs, not browsers. Consul's blocking queries and Amazon SQS's WaitTimeSeconds (up to 20 seconds) are both long polling.

Server-sent events

Server-sent events (SSE) are a standard format for streaming a sequence of events down one HTTP response. The browser opens it with the EventSource API, the server replies with Content-Type: text/event-stream, and never finishes the body. Each event is a few field: value lines followed by a blank line:

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-store

retry: 5000

id: 42
event: message
data: {"room":"ops","from":"maya","text":"deploy is green"}

: keep-alive comment, ignored by the client

id: 43
event: presence
data: {"user":"arjun","status":"away"}

Three details make SSE more than "a long response":

  • Automatic reconnection. If the connection drops, EventSource reconnects by itself after the retry delay (the browser picks a default of a few seconds if the server sends none).
  • Resume. On reconnect the browser sends the last id it saw in a Last-Event-ID request header, so the server can replay what the client missed. This is built into the standard; with WebSockets you build it yourself.
  • It is plain HTTP. Authentication cookies, HTTP/2 multiplexing, compression and most proxies work unchanged.

The limits are real but narrow. SSE is server-to-client only; the client sends data with normal POST requests. Payloads are UTF-8 text, so binary data must be base64-encoded. The browser EventSource API cannot set custom headers, so token authentication has to use a cookie or a query parameter, or the client must use fetch with a streaming reader instead. Over HTTP/1.1, browsers allow only about six connections per origin, so a user with seven tabs open can starve the seventh; over HTTP/2 every stream shares one connection and the problem disappears. Buffering proxies are the most common production bug: an NGINX or corporate proxy that buffers the response delivers events in batches, minutes late. Send Cache-Control: no-store, disable proxy buffering for the route (NGINX honours X-Accel-Buffering: no), and send a comment line every 15 to 30 seconds.

SSE is the best default when updates flow one way: notifications, live scores, dashboards, progress, and token streaming from LLM APIs, which is exactly what most of them use.

WebSockets

A WebSocket is a full-duplex message channel over a single TCP connection, defined in RFC 6455. It starts as an HTTP/1.1 request that asks to change protocols:

GET /ws HTTP/1.1
Host: chat.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://app.example.com

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

The accept value is the base64 SHA-1 of the key plus a fixed GUID. It only proves the server speaks WebSocket; it authenticates nothing. After the 101, HTTP is gone from that connection. Both sides exchange frames: text, binary, close, ping and pong, with 2 to 14 bytes of header each. Frames from the browser are masked with a random key, which stops a malicious page from crafting bytes that a naive intermediary would misread as HTTP.

What you get is the lowest overhead and latency of the four, binary support, and true two-way traffic, which matters for chat with typing indicators, multiplayer games and collaborative editors where the client sends as often as it receives. What you give up is everything HTTP did for you:

  • No reconnection, no resume, no message IDs. The browser API reports close and stops. Reconnect, backoff, sequence numbers and replay are your protocol to design.
  • No request semantics. No status codes, no per-message caching, no standard way to correlate a reply with a request. Teams invent a small envelope ({"type", "id", "payload"}) or adopt one (Socket.IO, STOMP).
  • Intermediaries must cooperate. Every proxy and load balancer on the path must pass the Upgrade and then treat the connection as an opaque byte stream with a long idle timeout. Corporate proxies that do not understand it break it, which is why libraries like Socket.IO fall back to long polling. Over TLS (wss://) this is rare today.
  • Security checks are on you. Browsers do not apply CORS to WebSockets. The server must check the Origin header itself, or any website can open an authenticated socket using the user's cookies (cross-site WebSocket hijacking).

The original upgrade only exists in HTTP/1.1. RFC 8441 defines WebSockets over HTTP/2 using an extended CONNECT, so a socket can share a multiplexed connection, and RFC 9220 does the same for HTTP/3.

WebTransport, and why HTTP/2 push is not an option

WebTransport is a newer browser API over HTTP/3 and QUIC. It gives a page multiple independent streams (no head-of-line blocking between them) and unreliable datagrams, which suit games and live media where a late packet is worthless. It is promising, but browser and infrastructure support is far less complete than for WebSockets, so treat it as a specialised choice in 2026, not a default.

HTTP/2 server push sounds like it belongs on this list and does not. It let a server send extra resources (a stylesheet, a script) into the browser's cache alongside a response it was already sending. Page JavaScript never saw pushed data as events, so it never solved this chapter's problem. It also rarely improved page loads. Chrome removed support in 2022 and Firefox later did the same. If an interviewer brings it up, say it was a cache-warming feature, not a messaging channel, and that it is deprecated.

A useful rule: start from the direction of traffic. If the client mostly listens, SSE gives you reconnection and resume for free and stays inside HTTP. Scaling persistent connections

SSE and WebSockets turn the server from stateless to stateful. A request-response server forgets each client after a few milliseconds; a connection server holds every client for hours. That changes what you measure, how you route and how you deploy.

What limits one server

An idle connection costs almost no CPU. The limits are memory and operating-system resources:

File descriptors

Each socket is a file descriptor. The default per-process soft limit on Linux is often 1,024. Raise ulimit -n (LimitNOFILE in systemd) and fs.file-max into the millions before anything else.

Memory per connection

Kernel socket buffers, TLS state, and your own read buffers and session object. Tuned stacks reach roughly 10 to 30 KB per idle connection; naive ones use several times that. Measure yours under load.

Ephemeral ports

A server accepting on port 443 has no port limit, since each connection is a distinct (client IP, client port) pair. A proxy connecting to backends does: Linux's default range 32768 to 60999 gives 28,232 ports per backend address. Add backend IPs or source IPs to go further.

Events, not threads

A thread per connection costs a stack (often 1 to 8 MB reserved) and scheduler time. Connection servers use epoll-based event loops or lightweight tasks (goroutines, Erlang processes, async I/O).

With those fixed, one machine can hold a very large number of idle connections. WhatsApp reported more than two million TCP connections on a single Erlang server in 2012, and the Phoenix framework team demonstrated two million WebSockets on one machine in 2015. Production fleets usually run far lower, around 50,000 to a few hundred thousand per server, because the real constraint is blast radius: when a server dies or restarts, every one of its clients reconnects at once, and the rest of the fleet has to absorb that.

Routing: who holds this user's socket?

With stateless HTTP, any server can answer any request. With persistent connections, a message for user 456 must reach the specific gateway holding user 456's socket. Two problems follow.

Getting the connection there. The load balancer must support long-lived connections: WebSocket upgrade support at L7, or plain TCP passthrough at L4, and an idle timeout longer than your heartbeat interval (AWS ALB defaults to 60 seconds). Least-connections balancing beats round robin here, because connections live for hours and round robin ignores how many each server already holds. Sticky routing (sending a client back to the same server) matters for long polling and Socket.IO's fallback, where several HTTP requests make up one logical session; a real WebSocket is one connection and is sticky by nature. See Load Balancing for the algorithms.

Getting messages to the connection. The service that creates a message (chat, notifications, trading) should not need to know which gateway holds which user. The standard answer is a pub/sub backplane: each gateway subscribes to topics for the users and rooms it currently holds, and producers publish to the topic. The broker does the routing.

Design choices inside the backplane:

  • Topic granularity. A topic per user is simple and gives exact routing. A topic per room or document means one publish reaches every gateway holding a member, which is the fan-out you want for group chat. For a room with 100,000 members spread over 100 gateways, the broker sends 100 copies and each gateway does the last-mile fan-out to its local sockets. That split, broker to gateways then gateway to sockets, is what keeps large rooms affordable.
  • Fire-and-forget versus durable. Redis pub/sub delivers only to currently connected subscribers and keeps nothing. That is fine if every message is also written to a durable store that clients resume from. If the backplane itself must buffer for replay, use a log such as Kafka or Redis Streams; see Pub/Sub & Event Streaming.
  • Broker scale. Classic Redis pub/sub broadcasts every message to every node in a cluster. Redis 7 added sharded pub/sub (SSUBSCRIBE), which keeps a channel on one shard. Alternatively, keep a connection registry (user to gateway, in Redis or a consistent-hash ring) and have producers send directly to the right gateway.

Deploys and draining

Restarting a gateway disconnects every client on it. Do it gradually: stop routing new connections to the server, then close existing ones in small batches over minutes, with a close code or a "reconnect" message so clients come back promptly to a different server.

Heartbeats and reconnection

Long-lived connections die silently. A phone switches from Wi-Fi to cellular, a NAT gateway forgets an idle mapping, a load balancer reaps a connection it considers idle. Often neither side receives a TCP reset, so each believes the connection is fine until it tries to send and waits for a timeout that can take many minutes.

A heartbeat is a small message sent on a fixed interval so both sides can detect a dead connection quickly, and so idle-timeout-based intermediaries see traffic. WebSockets have ping and pong frames for this (browsers answer pings automatically but cannot send them, so client-initiated heartbeats are application messages). SSE uses comment lines. Pick an interval shorter than the shortest idle timeout on the path, commonly 25 to 30 seconds against a 60-second load balancer timeout, and declare the connection dead after two or three missed beats.

Backoff with jitter

When a client loses its connection it should reconnect, but how it waits matters enormously at scale. If 100,000 clients all retry on the same schedule, they retry at the same instants, and a gateway fleet that has just recovered gets hit by all of them in the same second. This is the thundering herd, and it can knock the fleet over again. Exponential backoff doubles the wait after each failure up to a cap; jitter randomises each wait so clients spread out. The simulation below drops 100,000 clients at once, keeps the servers unreachable for 20 seconds, and counts connection attempts per second.

import random
from collections import Counter

BASE, CAP = 1.0, 30.0        # seconds: first retry delay, maximum delay
CLIENTS = 100_000            # one gateway's worth of connections
DOWN_UNTIL = 20.0            # the gateway fleet is unreachable for 20 s


def delay(attempt: int, jitter: bool) -> float:
    ceiling = min(CAP, BASE * 2 ** attempt)
    return random.uniform(0, ceiling) if jitter else ceiling   # "full jitter"


def simulate(jitter: bool) -> Counter:
    """Count reconnect attempts per second after every client drops at t=0."""
    per_second = Counter()
    for _ in range(CLIENTS):
        t, attempt = 0.0, 0
        while True:
            t += delay(attempt, jitter)
            per_second[int(t)] += 1
            if t >= DOWN_UNTIL:          # server is back: this attempt succeeds
                break
            attempt += 1
    return per_second


random.seed(7)
for jitter in (False, True):
    load = simulate(jitter)
    after = {s: n for s, n in load.items() if s >= DOWN_UNTIL}
    peak_s, peak = max(after.items(), key=lambda kv: kv[1])
    print(f"jitter={jitter!s:5}  attempts={sum(load.values()):,}  "
          f"busiest second after recovery: t={peak_s}s with {peak:,} connects")

# jitter=False  attempts=500,000  busiest second after recovery: t=31s with 100,000 connects
# jitter=True   attempts=597,436  busiest second after recovery: t=20s with 8,643 connects

Two more details from production clients. First, reset the attempt counter only after a connection has stayed healthy for a while (say 30 seconds), otherwise a server that accepts and immediately drops connections keeps clients retrying at the fastest rate. Second, let the server push back: an HTTP 503 with Retry-After during the handshake, or an application message telling clients to wait, gives the operator a lever during an incident. The general theory of retries, budgets and circuit breakers is in Timeouts, Retries & Circuit Breakers.

Message ordering and resume

Reconnecting is only half of recovery. The client also needs the messages sent while it was gone, without duplicates, in order. The standard pattern is a sequence number per stream:

  1. Number every message. The server assigns a monotonically increasing id per stream (per user, room or document). The id comes from the durable store or log that the message was written to, not from the gateway, so it survives gateway restarts.
  2. Client tracks the last id it processed. In SSE, the id: field does this automatically. Over WebSockets, put seq in your envelope and store it.
  3. Resume from it. On reconnect, the client sends Last-Event-ID: 42 (SSE) or {"type":"resume","after":42} (WebSocket). The server replays 43 onward from a buffer, then switches to live delivery.
  4. Fall back to a full sync. If the requested id is older than the buffer holds, the server says so and the client refetches current state over normal HTTP. Buffers are finite; plan for this case.

Three consequences to state in an interview:

  • Delivery is at-least-once. A message can be delivered, then the connection drops before the client records the id, so it is replayed. Clients must ignore ids they have already applied. See Idempotency & Delivery Semantics.
  • Order is per stream, not global. One TCP connection preserves order between one server and one client, but two producers publishing to one room through a backplane can interleave differently on different gateways. If order matters, sequence at a single point per stream (one partition per room in a log, or one owner service per room) and let clients reorder by seq.
  • The transport is not the source of truth. Sockets are a fast notification path. The durable store or log is the record, and every client must be able to rebuild state from it over plain HTTP.

The conclusions are not about bandwidth or message rate, which are both modest. They are about state and recovery. The fleet is sized by connection count and by how much reconnect load the survivors can take, and the single most dangerous event is a correlated disconnect: a bad deploy, a load balancer change, or a network blip that drops millions of sockets at once. Ten million clients reconnecting in one minute is about 167,000 TLS handshakes per second, far more than steady state. Jittered backoff, gradual draining, and server-controlled retry hints are what keep that a bump instead of an outage.

The 100,000 per server limit is a choice. At 500,000 the fleet shrinks to about 30 servers, but each failure is five times larger.

In the real world

  • Discord: clients hold a WebSocket to the Gateway. The server's first message tells the client its heartbeat interval; a client that misses heartbeats is disconnected. After a drop, the client sends a Resume with its session id and the last sequence number it saw, and the gateway replays missed events, which is the resume pattern above.
  • Slack: clients connect over WebSockets to gateway servers at the edge; backend channel servers own each channel's message stream and push to the gateways that have subscribers, a backplane design.
  • LLM APIs: OpenAI's and Anthropic's APIs stream generated tokens as server-sent events. One-way traffic, plain HTTP, and easy to proxy made SSE the natural fit.
  • Kubernetes and Consul: the Kubernetes API server's watch streams changes over one long-lived HTTP response; Consul's blocking queries are long polling with an index cursor. Both use resource versions so clients resume where they left off.

For full designs that use these pieces, see the chat system, notification system and ride-sharing case studies.

Interview angle

When to bring it up

Any time the server must tell the client something first: chat, notifications, live location, collaborative editing, dashboards. State the choice in one sentence with the reason ("updates are one-way, so SSE, which gives reconnection and resume for free"), then spend your time on the gateway tier, the backplane and recovery, because that is where the interviewer will go next.

Follow-ups to expect

  • How does a message for user 456 find the server holding their socket? (Pub/sub backplane, or a connection registry.)
  • How many connections per server, and what limits it? (File descriptors and memory, then blast radius.)
  • What happens when a gateway dies? (Clients reconnect with jittered backoff to other gateways and resume from their last sequence number.)
  • How does a client get messages it missed while offline? (Sequence numbers, replay buffer, full-sync fallback.)
  • How do you deploy the gateway tier without dropping everyone? (Drain gradually, tell clients to reconnect.)
  • Why not just poll? (Have a real answer: sometimes you should.)

Red flags

  • Choosing WebSockets by reflex for one-way updates, then not mentioning reconnection or resume.
  • Assuming any server can deliver to any user, as if the gateway tier were stateless.
  • Reconnecting immediately or on a fixed interval with no jitter.
  • Treating the socket as the source of truth, so messages sent while a client was offline are simply gone.
  • Mentioning HTTP/2 server push as a way to push messages to application code.
