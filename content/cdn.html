Why it matters

A user in Sydney opens a product page served from a data centre in Virginia. Light in fibre covers about 200 km per millisecond, the cable path is longer than the great circle, and the round trip comes out around 200 ms. A fresh HTTPS connection needs three round trips before the first byte of the response arrives, so the page has waited 600 ms before the server has done any work at all.

No amount of server tuning fixes that, because the cost is distance. A content delivery network (CDN) is a fleet of caching reverse proxies placed close to users. If the Sydney user talks to a server in Sydney at 10 ms round-trip time, the same three round trips cost 30 ms, and if that server already holds the response, the request never crosses the Pacific at all.

That second effect is the other half of the value. Every response served from the edge is a request your origin never sees and a byte your origin never sends. A site with a 95% hit ratio runs its origin for one twentieth of the traffic its users generate. CDNs also give you a very large, very spread-out front door that absorbs traffic spikes and attacks that would flatten a single region.

Origin

The system that owns the content: your application servers, or an object store bucket. The CDN fetches from it on a miss.

PoP

A point of presence: a CDN site in a city, a rack or a building of cache servers, routers and load balancers.

Hit ratio

The fraction of requests answered from cache. Also measured in bytes (byte hit ratio), which is what drives egress cost.

TTL

How long a cached response counts as fresh. Set by the origin through HTTP headers or overridden by CDN configuration.

Anatomy of a CDN

A CDN is not one cache but a hierarchy of them. The tiers exist because two goals pull in opposite directions: you want caches as close to users as possible, which means many small sites, and you want as few cache misses as possible reaching the origin, which means a few large sites that see all the traffic.

The tiers

  1. Edge PoPs. Hundreds of sites in major cities and inside ISP networks. They terminate the user's TCP and TLS connections, so the handshake round trips are short. Each one has limited disk and only sees local traffic, so it holds the locally popular objects.
  2. Regional or mid-tier caches. A smaller number of larger sites, one per continent or large region. When the Sydney and Tokyo PoPs both miss on the same object, the regional tier fetches it once and serves both. CloudFront calls these Regional Edge Caches; Cloudflare and Akamai call the idea tiered caching or tiered distribution.
  3. Origin shield. One designated cache location in front of the origin, usually in the same region. Every miss from every tier funnels through it, so the origin sees at most one request per object per TTL, no matter how many PoPs exist.
  4. Origin. Your service. With a shield in place it can be provisioned for the shield's miss rate rather than the world's request rate.

Every extra tier adds a hop on a miss, so a full miss is slower through a three-tier CDN than through a single edge going straight to origin. It pays off for long-tail content, which a single PoP rarely sees twice but a continent-wide tier does.

Getting users to the right PoP

A CDN has to steer each user to a nearby, healthy PoP. Two techniques dominate, and both are covered in the DNS chapter:

  • DNS-based steering. The CDN's authoritative DNS answers img.shop.example with the address of a PoP chosen from the resolver's location, measured latency and PoP load. It is precise, but only as precise as the resolver's location, and changes are delayed by DNS caching.
  • Anycast. Every PoP announces the same IP prefix over BGP, and the internet's routing delivers each packet to the topologically nearest one. Failover is a route withdrawal, which takes effect within seconds to a minute without waiting for DNS TTLs. Cloudflare runs almost entirely on anycast; many CDNs combine both.

Inside a PoP, a layer-4 load balancer spreads connections across servers, and each server then forwards a request to the cache server that owns that URL by a consistent hash so the PoP's disks hold one copy of each object, not one per server. That is consistent hashing again, applied to URLs. See Load Balancing for the machinery.

Request collapsing

When a popular object expires, hundreds of requests for it can arrive at a PoP in the same few milliseconds. Without protection, each one is a miss and each one goes upstream: a cache stampede aimed at your origin. CDNs prevent this with request collapsing (also called coalescing): the first miss goes upstream and every concurrent request for the same key waits for that one response. NGINX exposes this as proxy_cache_lock; Varnish, Fastly and CloudFront do it by default for cacheable responses.

Pull vs push

There are two ways content gets into the CDN. In a pull CDN the edge fetches from the origin on the first miss and caches the result. In a push CDN you upload content to the CDN's storage ahead of time, and the CDN distributes it.

Pull (origin pull)Push (pre-positioned)
SetupPoint the CDN at an origin hostnameUpload pipeline, storage management

Pull is the default for almost everything because it is self-managing: the cache contents track demand automatically. Push wins when you know what will be popular before users do. A game studio releasing a 40 GB patch at 18:00 does not want the first million downloads to be misses, so it pre-warms the CDN in the hours before. Netflix takes this furthest, as described below.

Cache keys

The cache key is the identifier a CDN uses to decide whether two requests can share one stored response. By default it is roughly scheme, host, path and full query string. Getting the key right is the single biggest lever on hit ratio, and getting it wrong is how private data leaks.

The rule is simple to state: the key must include everything that changes the response bytes, and nothing else. Anything extra splits one object into many copies that each miss separately. Anything missing serves one user's response to another.

  • Query strings. Allow-list the parameters that matter rather than block-listing the ones that do not. Sort them, so ?w=400&q=80 and ?q=80&w=400 hit the same entry.
  • Headers and Vary. When an origin sends Vary: Accept-Encoding, it tells caches that the response depends on that request header, and caches store one variant per distinct value. Accept-Encoding strings from real browsers come in many spellings, so CDNs normalise them to a few buckets (br, gzip, none). Vary: User-Agent is the classic mistake: there are thousands of user-agent strings, so the hit ratio collapses. Normalise to a device class (mobile, desktop) at the edge if you need per-device responses.
  • Cookies. Keep them out of the key for shared content. Many CDNs will not cache a response that sets a cookie at all, because a Set-Cookie header served to the wrong user is a session hijack.
Cache poisoning and cache deception

If a request header changes the response but is not in the key (an unkeyed input), an attacker can send one crafted request, for example with X-Forwarded-Host: evil.example, get a poisoned response cached, and have the CDN serve it to everyone. The reverse attack, web cache deception, tricks a cache into storing a logged-in user's page under a URL like /account/settings/x.css because the path looks static. Defend with strict keys, origins that ignore unexpected headers, and caching rules based on the response's Cache-Control, not on file extensions.

Controlling freshness with HTTP headers

The origin tells every cache on the path what it may do through response headers, defined in RFC 9111. A CDN is a shared cache (one copy serves many users); the browser is a private cache. Most directives let you treat the two differently.

DirectiveMeaningTypical use
max-age=NFresh for N seconds in any cacheStatic assets, public pages
s-maxage=NOverrides max-age for shared caches onlyBrowser keeps 60 s, CDN keeps 1 hour
no-cacheMay be stored, but must be revalidated before every useHTML that must never be stale, but is often unchanged

privateOnly the browser may store it, never the CDNPersonalised pages
immutableThe content will never change at this URL; skip revalidation (RFC 8246)Fingerprinted assets
stale-while-revalidate=NFor N seconds after expiry, serve stale and refresh in the background (RFC 5861)Anything where slightly old beats slow
stale-if-error=NFor N seconds after expiry, serve stale if the origin errors (RFC 5861)Survive origin outages

Two more headers complete the picture. Age is added by caches to say how long a response has been sitting in cache, so a downstream cache does not restart the clock. CDN-Cache-Control (RFC 9213) and the older Surrogate-Control let you give the CDN instructions that browsers and other proxies ignore, which is cleaner than overloading s-maxage.

Revalidation with ETag

Expiry does not mean the object changed. Instead of downloading it again, a cache can ask "is my copy still current?" with a conditional request. The origin labels each version of a response with an ETag (an opaque version string, often a content hash) or a Last-Modified time. The cache sends the label back in If-None-Match or If-Modified-Since. If nothing changed, the origin answers 304 Not Modified with no body, and the cache resets the object's age. A 304 still costs a round trip to the origin, but it costs almost no bandwidth and no rendering work.

GET /products/9481.jpg?w=400 HTTP/1.1
Host: img.shop.example
If-None-Match: "v42-9f3c1a"

HTTP/1.1 304 Not Modified
ETag: "v42-9f3c1a"
Cache-Control: public, max-age=60, s-maxage=3600, stale-while-revalidate=600

If the origin sends neither max-age nor Expires, caches may invent a lifetime from Last-Modified. RFC 9111 suggests 10% of the time since the last modification as a typical heuristic, so a file last changed 10 days ago may be cached for a day without anyone choosing that. Always send explicit Cache-Control.

Invalidation

A TTL is a promise that you will tolerate stale content for that long. When you cannot tolerate it, for a price change, a takedown or a broken deploy, you need to remove content from caches you do not run, in hundreds of locations at once. There are two approaches, and mature systems use both.

Purging

A purge (or invalidation) is an API call that tells every PoP to drop or mark stale a set of cached objects. CDNs support several granularities:

  • By URL: purge https://img.shop.example/products/9481.jpg. Precise, but you have to know every URL and every variant.
  • By tag: the origin labels responses with a header such as Surrogate-Key: product-9481 category-shoes (Fastly) or Cache-Tag (Cloudflare). One purge of product-9481 removes the product page, its images at every width and every listing page that showed it. This is the form that scales to real applications.
  • By prefix or wildcard: /products/*. Convenient, expensive for the CDN, and often rate-limited or billed.
  • Everything: the emergency lever. It turns a 98% hit ratio into 0% for a few minutes, so be sure the origin can survive the refill first.

Purges are fast on modern CDNs, from under a second to a few minutes depending on the provider, but they are still asynchronous and a PoP that is briefly unreachable can miss one. Browsers are worse: a purge never reaches the copy already in a user's browser cache. That is why HTML usually gets a short or zero browser TTL (max-age=0, s-maxage=3600) even when the CDN keeps it longer: the CDN copy can be purged, the browser copy cannot.

Versioned URLs

The cleanest invalidation is not needing one. Put a content hash in the file name at build time, so app.js becomes app.3f9a2c71.js, and serve it with Cache-Control: public, max-age=31536000, immutable. When the file changes, its name changes, and the HTML references the new name. The old object is never invalidated; it just stops being requested and ages out. This gives a near-100% hit ratio for every asset once each cache has it, zero purge traffic, and atomic deploys: a user either gets the old HTML with the old assets or the new HTML with the new ones, never a mix.

The pattern pushes the freshness problem up to one place: the HTML (or API response) that contains the versioned links. That small document gets a short TTL and is revalidated or purged on deploy. Everything heavy is immutable.

A sensible default policy

Fingerprinted assets: one year, immutable. Images keyed by content id: long TTL plus tag purge. HTML: max-age=0 for browsers, minutes to an hour at the CDN with purge on publish and stale-while-revalidate. Personalised responses: private or no-store. Everything gets stale-if-error so an origin outage serves slightly old pages instead of errors.

Dynamic content and edge compute

Not everything can be cached. A shopping cart, a search result for a rare query or a POST /checkout must go to the origin. A CDN still helps these requests, just less dramatically.

Dynamic content acceleration

  • Short client handshakes. The user's TCP and TLS handshakes complete against the nearby PoP. Only the request itself crosses the long path.
  • Warm long-haul connections. PoPs keep pools of established, already-warmed connections to the origin (or to the shield), so there is no handshake and no TCP slow start on the long leg. For a 200 ms path, skipping two round trips saves 400 ms. See TCP, UDP & HTTP for why fresh connections are slow.
  • Better routes. The CDN's backbone often beats the default BGP path between continents.
  • Microcaching. Even "dynamic" pages are often identical for everyone for a second. Caching a busy anonymous page for 1 to 5 seconds turns 2,000 requests per second for it into one origin request per second per PoP, with staleness no user notices.

Edge compute

Edge compute runs your code inside the PoP, on the request path. Cloudflare Workers run JavaScript and WebAssembly in V8 isolates that start in milliseconds; Fastly Compute runs WebAssembly; AWS offers lightweight CloudFront Functions at the edge and Lambda@Edge at the regional tier. Good uses are small and latency-sensitive:

  • Rewriting the cache key, normalising headers, A/B test bucketing that stays cacheable.
  • Validating a JWT or a signed URL before the request touches the origin.
  • Redirects, geo-based routing, header injection, bot challenges.

The trap is putting business logic at the edge that needs your database. The code then runs 10 ms from the user and 200 ms from its data, and a request that makes three sequential queries is slower than if it had run at the origin. Edge compute pays off when the data it needs is in the request, in the cache, or in an edge-replicated key-value store.

TLS and security at the edge

Because the CDN terminates the user's connection, it holds a certificate for your domain. CDNs automate certificate renewal and offer modern TLS and HTTP/3 at the edge whatever your origin speaks. Organisations that cannot hand a private key to a third party can use schemes such as Cloudflare's Keyless SSL, where the edge asks a key server in the customer's network to perform the one private-key operation in the handshake. Edge to origin is a separate connection and should also be TLS, ideally with the origin verifying that the caller really is the CDN.

The CDN also becomes your first line of defence:

  • DDoS absorption. A volumetric attack of hundreds of gigabits per second would saturate a single region's links. Spread by anycast across hundreds of PoPs, it becomes a manageable slice per site, and network-layer floods (SYN floods, UDP reflection) are dropped at the edge before they reach any application.
  • Web application firewall. A WAF inspects HTTP requests at the edge and blocks known attack patterns such as SQL injection and path traversal, plus rules you write. Edge rate limiting and bot management run here too.
  • Origin cloaking. All of this is worthless if attackers can reach the origin directly. Firewall the origin to accept only the CDN's published IP ranges, or require a secret header or mutual TLS on edge-to-origin requests, and never expose the origin's address in DNS.
  • Signed URLs and cookies. For paid or private content, the application issues a URL with an expiry and an HMAC signature; the edge verifies it without calling the origin. This is how video platforms protect their segments, see Design a Video Platform. The broader topics are in Security Fundamentals.

And the origin still has to survive a purge-all or a cold PoP, so provision for the miss rate during refill, not the steady state.

How much does a shield help?

Without a shield, each PoP misses independently, so an object popular in 20 cities is fetched from the origin 20 times. The simulation below sends 1 million Zipf-distributed requests for 100,000 objects to 20 PoPs, each with an LRU cache holding 10% of the catalogue, with and without a shared shield that holds half of it.

import bisect
import itertools
import random
from collections import OrderedDict


class LRU:
    def __init__(self, capacity):
        self.capacity, self.items = capacity, OrderedDict()

    def get(self, key):
        if key in self.items:
            self.items.move_to_end(key)
            return True
        return False

    def put(self, key):
        self.items[key] = True
        if len(self.items) > self.capacity:
            self.items.popitem(last=False)   # evict least recently used


def simulate(shield, pops=20, objects=100_000, requests=1_000_000,
             edge_size=10_000, shield_size=50_000, seed=7):
    rng = random.Random(seed)
    # Zipf-like popularity: object k is requested with weight 1 / k^0.9
    cum = list(itertools.accumulate(1 / k ** 0.9 for k in range(1, objects + 1)))
    edges = [LRU(edge_size) for _ in range(pops)]
    mid = LRU(shield_size)
    edge_hits = origin = 0
    for _ in range(requests):
        obj = bisect.bisect(cum, rng.random() * cum[-1])
        edge = edges[rng.randrange(pops)]          # user lands on a random PoP
        if edge.get(obj):
            edge_hits += 1
            continue
        if not (shield and mid.get(obj)):
            origin += 1                            # nobody had it: go to origin
            if shield:
                mid.put(obj)
        edge.put(obj)
    return edge_hits / requests, origin / requests


for shield in (False, True):
    edge_hit, origin_share = simulate(shield)
    print(f"shield={shield!s:5}  edge hit ratio {edge_hit:.1%}  "
          f"origin sees {origin_share:.1%} of requests")
# shield=False  edge hit ratio 56.5%  origin sees 43.5% of requests
# shield=True   edge hit ratio 56.5%  origin sees 15.6% of requests

The edge hit ratio is identical in both runs, because the shield does not change what the edges hold. But origin traffic falls by almost two thirds: most edge misses are for objects some other PoP fetched recently, and the shield answers those. The absolute hit ratios here are low because each simulated PoP only sees 50,000 requests and starts cold; production PoPs run warm for weeks. The ratio between the two runs is the point.

The structural cost of any CDN is that a third party now sits on your critical path. A CDN control-plane bug or a bad configuration push can take down every site behind it at once, as major CDN outages have shown several times. Large companies mitigate this with a multi-CDN setup, steering traffic between two providers with DNS, at the cost of maintaining two configurations and losing some cache efficiency.

In the real world

  • Netflix Open Connect: Netflix runs its own CDN of Open Connect Appliances, storage servers placed inside ISP networks and at internet exchange points. It is a push design: Netflix predicts what each region will watch and fills the appliances during off-peak hours, so evening playback is served from inside the viewer's ISP and very little crosses the wider internet at peak.
  • Cloudflare: a single anycast network in which every server in every data centre runs the full stack (cache, WAF, DDoS mitigation, Workers). Tiered Cache adds upper tiers in front of origins, and Workers run customer code in V8 isolates at every location.
  • Akamai: grew out of the consistent hashing research at MIT and places servers deep inside thousands of ISP networks rather than in a few large sites. Its published architecture paper describes the tiered distribution and overlay routing ideas used across the industry.
  • Amazon CloudFront: edge locations backed by Regional Edge Caches, with an optional Origin Shield in front of S3 or any HTTP origin. CloudFront Functions and Lambda@Edge provide edge compute; signed URLs and cookies protect private content.
  • Fastly: built on Varnish, known for purges that complete across the network in well under a second and for surrogate-key purging, which makes long TTLs on dynamic-but-cacheable content such as news articles practical.
Interview angle

When to bring it up

Any design that serves static or shareable content to users in more than one region: images, video, downloads, web assets, public API responses. Say what goes through the CDN, what the TTLs are, how content is invalidated, and what hit ratio you assume, then use the miss ratio to size the origin. In Design a URL Shortener it absorbs viral redirects; in Design a Video Platform it carries almost all of the bandwidth.

Follow-ups to expect

  • How do you update a cached file? (Versioned URLs for assets; purge by tag for content; short TTLs on HTML.)
  • What is in your cache key, and why does Vary: User-Agent hurt?
  • The CDN expires a hot object and the origin melts. What happened? (Stampede: request collapsing, shield, stale-while-revalidate.)
  • How would you serve private content through a CDN? (Signed URLs or cookies verified at the edge, private for personalised responses.)
  • How much origin capacity do you need? (Total rate times miss ratio, plus headroom for refill after a purge.)
  • What if the CDN itself goes down? (Multi-CDN with DNS steering, or fall back to origin with enough capacity for a degraded mode.)

Red flags

  • "Put it behind a CDN" with no word on TTLs, keys or invalidation.
  • Planning to purge on every write for content that changes thousands of times a second.
  • Caching personalised or authenticated responses in a shared cache without the user in the key.
  • Sizing the origin from the hit ratio as if 95% and 99% were similar.
  • Leaving the origin reachable from the internet, so the CDN's DDoS protection can be bypassed.
