Why it matters

Any system that spreads data or requests across machines has to answer one question millions of times per second: which node owns this key? The answer must be fast, computable by every client without coordination, and stable when nodes come and go.

The obvious answer is node = hash(key) % N. It is fast and spreads keys evenly. Its flaw only shows up when N changes, and in production N changes all the time: a cache node dies, you add capacity before a sale, a host is replaced during a deploy.

For a database, that means migrating almost every row. For a cache it is worse, because nothing gets migrated: almost every lookup suddenly goes to a node that has never seen that key, the hit rate collapses, and the full read load lands on the database behind it. Adding a node to relieve pressure is exactly what takes the system down.

Consistent hashing fixes this. When a node joins or leaves, only the keys that belong to that node move, about 1/N of the total, and every other key stays put.

The hash ring

Take the output range of a hash function, say 0 to 232 - 1, and bend it into a circle so the largest value wraps around to 0. Then place two kinds of things on it with the same hash function:

  • Nodes, at hash(node_id), for example hash("cache-07").
  • Keys, at hash(key), for example hash("user:42").

A key belongs to the first node you meet walking clockwise from the key's position. Equivalently, each node owns the arc between its predecessor and itself. Use the buttons to change the cluster and watch which keys move.

Two properties fall out of this geometry:

  • Minimal movement. A joining node only takes keys from one neighbour, and a leaving node only gives keys to one neighbour. Everything else is untouched. On average that is K/N keys for K keys and N nodes.
  • No coordination per lookup. Any client holding the same node list computes the same owner. The only shared state is cluster membership, which changes rarely compared with lookups.

Virtual nodes fix the two flaws of the basic ring

With one position per node the ring has two problems. Both are visible in the figure above, where C owns more than a quarter of the ring and inherits all of B's keys when B leaves.

  1. Uneven load. Node positions are random, so arc lengths are random too. With only a handful of nodes, one node routinely owns two or three times its fair share.
  2. Uneven recovery. When a node fails, its single successor absorbs its entire load. A cluster at 60% utilisation can see that neighbour jump to 120% and fail too, and the failure walks around the ring.

The fix is to give each physical node many positions, called virtual nodes or tokens. Node A is hashed as A#0, A#1, ... A#99, and so on for every node. Arcs from different physical nodes interleave, so the law of large numbers evens out the share each node owns, and when a node dies its many small arcs are inherited by many different successors.

How many virtual nodes?

The imbalance shrinks roughly with the square root of the token count, so going from 10 to 100 tokens per node helps a lot and going from 100 to 1,000 helps much less. These are measured numbers from the implementation below, for 10 nodes and 100,000 keys:

The cost of more tokens is a bigger ring to store and gossip, and more, smaller ranges to stream when a node joins. That is why Cassandra lowered its default num_tokens from 256 to 16 in version 4.0 and paired it with a smarter token allocator: random placement needs many tokens to balance, deliberate placement needs few.

Virtual nodes also give you weighting for free. A server with twice the RAM gets twice the tokens and therefore about twice the keys.

Implementation

The ring is just a sorted array of token positions plus a map from position to physical node. A lookup is a binary search for the first token greater than the key's hash, wrapping to index 0 past the end. That is O(log(N·V)) for N nodes with V tokens each, which is a few dozen comparisons even for large clusters.

import bisect
import hashlib


def h(value: str) -> int:
    """Map a string to a point on a 2^32 ring. md5 is used for spread, not security."""
    return int.from_bytes(hashlib.md5(value.encode()).digest()[:4], "big")


class HashRing:
    def __init__(self, nodes=(), vnodes=100):
        self.vnodes = vnodes
        self.tokens = []   # sorted ring positions
        self.owner = {}    # position -> physical node
        for node in nodes:
            self.add(node)

    def add(self, node):
        for i in range(self.vnodes):
            pos = h(f"{node}#{i}")
            bisect.insort(self.tokens, pos)
            self.owner[pos] = node

    def remove(self, node):
        for i in range(self.vnodes):
            pos = h(f"{node}#{i}")
            self.tokens.remove(pos)
            del self.owner[pos]

    def lookup(self, key):
        # first token clockwise from the key; wrap to index 0 past the top of the ring
        i = bisect.bisect_right(self.tokens, h(key)) % len(self.tokens)
        return self.owner[self.tokens[i]]


ring = HashRing([f"cache-{i}" for i in range(10)])
before = {k: ring.lookup(k) for k in (f"user:{n}" for n in range(100_000))}
ring.add("cache-10")
moved = sum(ring.lookup(k) != node for k, node in before.items())
print(f"{moved / len(before):.1%} of keys moved")   # ~10% (ideal is 1/11), all of them to cache-10

Details that matter in real implementations:

  • Hash choice. The hash needs good spread, not cryptographic strength. MD5 is the classic choice (the ketama Memcached client uses it); Cassandra uses Murmur3; xxHash is common in newer code. Every client must use the same function and the same token naming scheme, or they will disagree about ownership.
  • Collisions. Two tokens hashing to the same position is rare at 232 and vanishingly rare at 264. Production code breaks ties deterministically, for example by node id.
  • Membership is the hard part. The lookup is trivial. Making every client agree on the node list is not. Systems either gossip it (Cassandra, Dynamo), store it in a coordination service such as ZooKeeper or etcd, or let a proxy own it so clients never see it.

Replication on the ring

Storage systems need each key on several nodes. The ring gives a natural rule: store the key on the first R distinct physical nodes clockwise from its position. Dynamo calls this list the preference list. With virtual nodes, the walk must skip tokens that belong to a node already chosen, otherwise two replicas could land on the same machine.

This rule composes well with node changes. If N2 fails, the next distinct node clockwise (N3 here) temporarily takes its place. Dynamo-style stores mark these writes with a hint and hand them back when N2 returns, which is called hinted handoff. The Replication chapter covers quorums over these replicas.

Worked example: losing a cache node

A product catalogue is served from 10 Memcached nodes holding 100 million keys. The service handles 200,000 reads per second with a 95% hit rate, so the database normally sees 10,000 reads per second and is provisioned for about 30,000. One cache node's host fails.

The consistent-hashing column is still tight. Real deployments add protection on top: request coalescing so one miss fetches a hot key once, and warm standby nodes. The Caching chapter covers stampede protection in detail. The key point is that consistent hashing turns a full outage into an incident the rest of the system can absorb.

Alternatives and when they win

The ring is the best-known scheme, but not the only one with the minimal-movement property, and in several settings it is not the best one.

Rendezvous (HRW) hashing

For each key, score every node with hash(key, node) and pick the highest. No ring, no tokens, perfectly even, and removal only moves that node's keys. Lookup is O(N), so it suits tens of nodes, not thousands.

Jump consistent hash

A five-line function from Google that maps a key to a bucket number in O(log N) with no memory and near-perfect balance. Buckets must be numbered 0 to N-1, so you can only add or remove at the end. A good fit for numbered shards, not for arbitrary node failure.

Maglev hashing

Builds a fixed-size lookup table (e.g. 65,537 slots) filled from per-node permutations. Lookup is one array index. Used in Google's Maglev load balancer and in Envoy. Slightly more keys move on change than with a ring, in exchange for speed and balance.

Fixed hash slots

Hash keys into a fixed number of slots and keep an explicit slot-to-node table. Redis Cluster uses 16,384 slots. Rebalancing moves whole slots, and the table is small enough to ship to every client. Simple, explicit and easy to reason about.

Hot keys and bounded loads

Consistent hashing balances the key space, not the traffic. If one celebrity's profile gets 50,000 reads per second, the node that owns it is overloaded no matter how evenly the ring is cut. Two tools help:

  • Consistent hashing with bounded loads caps every node at (1 + ε) times the average load. If a key's owner is full, the request spills to the next node clockwise. Vimeo added this to HAProxy and cut cache bandwidth substantially; Envoy and Google's load balancers use variants.
  • Hot-key replication detects very popular keys and serves them from several nodes or from a local in-process cache, which is a caching decision rather than a hashing one.

In the real world

  • Akamai: the 1997 paper by Karger et al. introduced consistent hashing to spread web caching across a changing set of servers, and became the basis of Akamai's CDN.
  • Amazon Dynamo (2007): ring with virtual nodes, preference lists and hinted handoff. Cassandra, Riak and Voldemort copied the design. DynamoDB, the managed service, later moved to a partition map managed by a control plane.
  • Apache Cassandra: each node owns num_tokens ranges on a Murmur3 ring; the default dropped from 256 to 16 in 4.0 thanks to a balance-aware token allocator.
  • Memcached clients: the ketama algorithm (ring with MD5-derived tokens) is the standard way clients choose a server, so the cluster itself needs no coordination at all.
  • Load balancers: Envoy offers RING_HASH and MAGLEV policies for sticky routing; HAProxy supports consistent hashing with bounded loads.
Interview angle

When to bring it up

Whenever you shard a cache or a datastore and the cluster can grow or lose nodes. Say it in one sentence ("I'll partition by key with consistent hashing and virtual nodes so adding a node only moves about 1/N of the data") and move on unless the interviewer wants depth. In the key-value store case it is the core of the design.

Follow-ups to expect

  • Why not hash % N? Give the N/(N+1) movement number and the cache-stampede consequence.
  • What are virtual nodes for? Balance, even redistribution on failure, and weighting by capacity.
  • How do clients learn the ring? Gossip, a coordination service, or a routing proxy.
  • How do you replicate? Next R distinct nodes clockwise, skipping same-rack nodes.
  • What about a hot key? Consistent hashing does not help; use bounded loads, replication of hot keys, or local caching.

Red flags

  • Claiming consistent hashing guarantees even load. It balances key space statistically, and does nothing for skewed traffic.
  • Forgetting that replicas must be on distinct physical machines when vnodes are in play.
  • Using it where range scans are needed. Range-partitioning is the right tool there; see Sharding.
