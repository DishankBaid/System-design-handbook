Why it matters

A shopper types waterproof running shoes. The catalog has 20 million products. WHERE title LIKE '%running%' cannot use a B-tree index, so it scans every row; it would not match "Run" or "shoe"; it cannot say which match is best; and it would take seconds. Search engines answer the same question in tens of milliseconds, tolerate plurals and typos, and rank the best results first. They do it with one data structure, the inverted index, plus a scoring function and a lot of engineering around keeping both fresh at scale.

Search shows up in interviews in two ways: as a feature (product search, message search, log search) where you are expected to put a search engine next to the primary database and keep it in sync, and as a deep dive into how the index works. This chapter covers both. Prefix suggestions while typing are a different problem with different data structures, covered in the autocomplete case study.

From text to terms

Before anything is indexed, text goes through an analyzer: a pipeline that turns a string into a list of terms. The same analyzer runs on documents at index time and on queries at search time, which is what makes "Running-Shoes" in a title match "running shoe" in a query.

  • Tokenization splits text into tokens on whitespace and punctuation. Languages without spaces (Chinese, Japanese, Thai) need dictionary or statistical segmenters, and the Unicode text segmentation rules handle most of the rest.
  • Normalization lowercases, applies Unicode normalization (so that the precomposed and combining forms of "é" match), and often folds accents ("café" to "cafe").
  • Stop words such as "the" and "for" carry little meaning and appear everywhere. Removing them shrinks the index; modern engines often keep them because BM25 already gives them almost no weight and phrases like "to be or not to be" need them.
  • Stemming strips suffixes by rule (Porter and Snowball stemmers: "running" to "run", "boots" to "boot"). Lemmatization uses a dictionary to find the base form ("mice" to "mouse"). Both trade precision for recall: "university" and "universe" stem to the same term in Porter.
  • Synonyms map "sneakers" and "trainers" to the same terms, either at index time or query time.

The inverted index

A normal index maps a document to its contents. An inverted index maps each term to the list of documents that contain it, called its postings list. Step through it with three product titles:

Real postings lists hold more than document ids:

  • Term frequency per document, for scoring.
  • Positions of each occurrence, for phrase queries: "running shoes" matches only where shoe appears at the position right after run.
  • Compression. Document ids are stored as gaps between consecutive ids (1000, 1003, 1010 becomes 1000, 3, 7), and the small gaps are bit-packed in blocks. Lucene packs blocks of 128 gaps, so a postings list costs a few bits per entry.
  • Skip data, so an intersection can jump ahead in a long list instead of reading every entry.

The term dictionary itself is stored compactly: Lucene uses a finite state transducer (FST), which shares prefixes and suffixes between terms and fits in memory even for hundreds of millions of terms. The same automaton machinery makes fuzzy queries ("shoos" within edit distance 1 of "shoes") fast.

Boolean queries

Because postings are sorted by document id, boolean operators are merges:

  • AND: intersect. Walk both lists with a pointer each and advance the one with the smaller id; output ids present in both. Start from the shortest list and use skip data to leap through the longest, so waterproof AND shoe costs roughly the length of the rarer term's list.
  • OR: union, merging lists with a heap.
  • NOT: difference, skipping ids that appear in the excluded list.

Most real queries are not strict booleans. A search box query is usually "OR the terms, then rank", with a minimum number of terms that must match, so a document matching two of three words can still appear below documents matching all three.

Ranking: TF-IDF and BM25

Matching finds candidates; ranking orders them. Classic relevance scoring rests on two observations:

  • Term frequency (tf). A document that mentions "waterproof" several times is probably more about waterproofing than one that mentions it once.
  • Inverse document frequency (idf). A term that appears in few documents is more informative. Matching "gore-tex" says more than matching "shoe" in a shoe shop. With N documents and n containing the term, idf grows as n shrinks, roughly log(N / n).

TF-IDF multiplies the two and sums over query terms. It has two flaws. Raw term frequency grows without limit, so a page repeating "running" fifty times beats a better page that says it twice. And long documents contain more of every term, so they win by sheer size. BM25, the default in Lucene, Elasticsearch, OpenSearch and Solr, fixes both:

score(D, Q) = Σ over terms q in Q of IDF(q) × f(q, D) × (k1 + 1) / ( f(q, D) + k1 × (1 - b + b × |D| / avgdl) ) IDF(q) = ln( 1 + (N - n(q) + 0.5) / (n(q) + 0.5) ) Lucene's form, always positive f(q, D) = occurrences of q in D |D| = length of D in terms avgdl = average document length N = documents, n(q) = documents containing q k1 = 1.2 controls how fast term frequency saturates (Lucene default) b = 0.75 controls how strongly long documents are penalised (Lucene default)

A small search engine

The whole pipeline (analyze, index, score with BM25) fits in about 50 lines. The fourth document stuffs "running" four times into a long title, to show saturation and length normalisation at work:

import math
import re
from collections import Counter, defaultdict

STOP = {"a", "an", "and", "for", "the", "of", "with"}


def stem(word):
    """A deliberately tiny stemmer: real engines use Porter/Snowball or dictionaries."""
    for suffix, repl in (("ning", ""), ("ing", ""), ("es", "e"), ("s", "")):
        if word.endswith(suffix) and len(word) - len(suffix) >= 3:
            return word[: len(word) - len(suffix)] + repl
    return word


def analyze(text):
    return [stem(t) for t in re.findall(r"[a-z0-9]+", text.lower()) if t not in STOP]


class Index:
    def __init__(self, k1=1.2, b=0.75):              # Lucene / Elasticsearch defaults
        self.k1, self.b = k1, b
        self.postings = defaultdict(dict)             # term -> {doc_id: term frequency}
        self.length = {}                              # doc_id -> number of terms

    def add(self, doc_id, text):
        terms = analyze(text)
        self.length[doc_id] = len(terms)
        for term, tf in Counter(terms).items():
            self.postings[term][doc_id] = tf

    def idf(self, term):
        n, df = len(self.length), len(self.postings.get(term, {}))
        return math.log(1 + (n - df + 0.5) / (df + 0.5))   # Lucene's BM25 idf, never negative

    def search(self, query, require_all=False):
        terms = analyze(query)
        docs = [set(self.postings.get(t, {})) for t in terms]
        candidates = set.intersection(*docs) if require_all else set.union(*docs)
        avgdl = sum(self.length.values()) / len(self.length)
        scores = {}
        for d in candidates:
            norm = self.k1 * (1 - self.b + self.b * self.length[d] / avgdl)
            scores[d] = sum(self.idf(t) * tf * (self.k1 + 1) / (tf + norm)
                            for t in terms if (tf := self.postings[t].get(d)))
        return sorted(scores.items(), key=lambda kv: -kv[1])


idx = Index()
idx.add(1, "Waterproof running shoes for trail running")
idx.add(2, "Lightweight road running shoes")
idx.add(3, "Waterproof hiking boots")
idx.add(4, "Running socks, running shorts and running shoes for running clubs")
print(dict(idx.postings["run"]), dict(idx.postings["waterproof"]))
for doc, score in idx.search("waterproof running shoes"):
    print(doc, round(score, 3))
print("AND:", [d for d, _ in idx.search("waterproof running shoes", require_all=True)])

# {1: 2, 2: 1, 4: 4} {1: 1, 3: 1}
# 1 1.54
# 4 0.833
# 3 0.829
# 2 0.777
# AND: [1]

Three things are worth reading off the output. D1 wins clearly: it matches all three terms. D4 mentions "running" four times but gains little over a single mention, because term frequency saturates and its length is penalised. And D3, which matches only "waterproof", nearly ties with D4 and beats D2, which matches two terms: "waterproof" appears in 2 of 4 documents while "run" and "shoe" appear in 3, so it carries more weight. The tiny stemmer here turns "hiking" into "hik"; real engines use Snowball stemmers or dictionaries.

Production ranking layers more on top: field boosts (a match in the title counts more than in the description), recency and popularity signals, personalisation, and increasingly a second-stage learning-to-rank or neural re-ranker that rescores the top few hundred BM25 results. Vector search (approximate nearest neighbour indexes such as HNSW, built into Lucene since version 9) adds semantic matching, and hybrid systems combine both scores.

Scaling the index

Document vs term partitioning

An index too big or too busy for one machine is split into shards. There are two ways to cut it:

With document partitioning, a search runs in two phases. In the query phase, every shard scores its own documents and returns the ids and scores of its top k; the coordinating node merges them into a global top k. In the fetch phase it retrieves the full documents for just those k ids. Deep pagination is expensive because page 500 needs the top 5,000 from every shard; use search-after cursors instead of offsets. Each shard computes idf from its own documents, which can skew scores when shards are small or unevenly filled; Elasticsearch's dfs_query_then_fetch mode gathers global term statistics first, at the cost of an extra round trip.

The tail-latency arithmetic from Sharding applies directly: a query fans out to every shard and waits for the slowest. Fewer, larger shards (Elasticsearch suggests roughly 10 to 50 GB each) keep fan-out down.

Replicas

Each shard has replicas on other nodes. They serve two purposes: availability (a node failure promotes a replica to primary) and read throughput (a query can use any copy of each shard). Search clusters scale reads by adding replicas and writes by adding shards, and the number of primary shards is fixed when an index is created, so plan for growth or use index aliases to roll over to new indexes. See Replication.

Near-real-time indexing: segments and refresh

Updating a compressed, sorted postings list in place for every new document would be ruinously expensive. Lucene borrows the LSM idea instead:

  1. Buffer. New documents are analysed and held in an in-memory buffer, and appended to a translog (Elasticsearch's write-ahead log) for durability.
  2. Refresh. Periodically (every 1 second by default) the buffer is written as a new, small, immutable segment: a complete mini inverted index. Only now are those documents searchable. This is why Elasticsearch is called near-real-time: a write is visible within about a second, not immediately.
  3. Search. A query runs over every segment and merges the results.
  4. Merge. Background merges combine small segments into larger ones, as compaction does in an LSM tree. Deletes and updates mark the old document as deleted in a bitmap; the space is reclaimed when its segment is merged.
  5. Flush. Less often, a Lucene commit fsyncs the segments and the translog can be trimmed.

The refresh interval is a throughput knob. During a bulk reindex, set it to 30 seconds or disable it entirely, then restore it: fewer, bigger segments mean far less merge work.

Keeping the index in sync with the database

A search engine is almost never the system of record. Products, messages or tickets live in the primary database; the search index is a derived view that must follow it. How you feed it decides how often they disagree.

ApproachHowProblem
Dual writeThe service writes the database, then the indexA crash between the two, or two concurrent updates arriving out of order, leaves them permanently different
Periodic batchEvery N minutes, reindex rows changed since the last runMinutes of lag; deletes are easy to miss
Change data captureTail the database's replication log (Debezium to Kafka), an indexer consumes and upsertsSeconds of lag, nothing missed, ordered per row

With CDC, the indexer must still cope with retries and reordering: use the row's version or the log position as an external version on each index request (Elasticsearch's version_type=external), so an older update arriving late is rejected rather than overwriting a newer one. Keep a full reindex path for mapping changes and disasters: build a new index from a snapshot of the database while CDC keeps the old one current, replay the changes since the snapshot, then switch an index alias from old to new in one atomic step. See Event Streaming and CQRS for the general pattern.

Worked example: product search

A marketplace has 20 million products, 3,000 searches per second at peak, and about 300 product updates per second (prices and stock), with a target of p99 under 200 ms.

Source size 20M products × ~4 KB JSON ≈ 80 GB Index size ~1.2 × source (postings, stored fields, doc values) ≈ ~100 GB Primary shards 100 GB / ~25 GB per shard = 4 primaries Query load 3,000 searches/s × 4 shards = 12,000 shard-searches/s Per node 16 cores, ~10 ms CPU per shard-search ≈ 1,600 shard-searches/s Nodes 12,000 / 1,600 ≈ 7.5 nodes fully busy → 12 nodes at ~63% CPU Copies 4 primaries × 3 copies (1 primary + 2 replicas) = 12 shard copies, one per node Writes 300 updates/s × 3 copies ≈ 900 indexing ops/s, refresh every 1 s

Notes on the design. Products are indexed with a title field (heavily boosted), brand, category, description, and facet fields (price, size, colour) stored as doc values for aggregations. The catalog database feeds the index through CDC, so a price change is searchable in about two seconds. Stock is filtered at query time from a frequently refreshed field rather than hiding out-of-stock items at index time. Facet counts and aggregations for popular queries are cached per shard (Elasticsearch's shard request cache, which by default caches only size=0 results, not hits), and the top suggestions come from the separate autocomplete service.

In the real world

  • Apache Lucene is the library underneath Elasticsearch, OpenSearch and Solr: analyzers, FST term dictionaries, block-compressed postings, segments and BM25.
  • Elasticsearch adds distribution: shards, replicas, the query and fetch phases, and a JSON API. OpenSearch is the Apache-licensed fork of Elasticsearch 7.10.2 created by AWS in 2021 after Elastic changed its licence.
  • Web search engines use document-partitioned indexes at enormous scale; Google's 2003 paper "Web Search for a Planet" describes index shards each served by a pool of replicas, with a query fanned out to every shard.
  • Log search (Elasticsearch for logs, Splunk, Loki) stretches the model: time-based indexes rolled over daily and dropped whole, which is cheaper than deleting documents. Loki indexes only labels, not log text, and scans chunks instead.
  • Slack and GitHub run large search clusters over messages and code; GitHub built its own code search engine because general-purpose analyzers handle source code poorly.
Interview angle

When to bring it up

Whenever users search free text: products, posts, messages, documents, logs. Say: "The database stays the source of truth; I'll stream changes through CDC into an Elasticsearch index sharded by document, with replicas for query throughput. Results are near-real-time, about a second behind." Be ready to go one level deeper into the inverted index and BM25.

Follow-ups to expect

  • How does the inverted index answer a two-word query? (Look up both postings lists, intersect or union, score.)
  • Why does a just-written document not show up in search? (Refresh interval, segments.)
  • How do you keep the index consistent with the database? (CDC, external versions, alias swap for reindexing.)
  • Why BM25 instead of raw term counts? (Saturation and length normalisation.)
  • How would you shard a 2 TB index, and what happens to tail latency?

Red flags

  • Using LIKE '%term%' on the primary database for user-facing search.
  • Treating the search index as the system of record.
  • Dual writes from the application to the database and the index.
  • Expecting read-your-writes from a search engine without discussing refresh.
