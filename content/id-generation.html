Why it matters

Every row, message, order and event needs a primary key, and on one database server that is a solved problem: an auto-increment column hands out 1, 2, 3. The moment writes spread across many shards, regions or services, nobody owns "the next number" any more. Each node must mint IDs on its own, millions of times per second, and those IDs must never collide.

The choice of ID format looks like a detail and turns out to touch almost everything: how fast your database inserts (random keys can make a B-tree index several times slower), whether you can sort by ID instead of by timestamp, whether a JavaScript client silently corrupts it, how many bytes every foreign key and secondary index carries, and whether a competitor can count your orders by watching the numbers climb.

This chapter walks through the options practitioners actually use, from database sequences to UUIDs, ticket servers, Twitter's Snowflake and its descendants, and gives the numbers you need to pick one in an interview.

What a good ID needs

Write the requirements down before picking a scheme, because they pull in different directions.

Unique

Never issued twice, across every node, every restart and every region. This is the only non-negotiable property.

Sortable

Later IDs compare greater than earlier ones, at least roughly. Lets you paginate by ID and keeps index inserts at the right edge of a B-tree.

Compact

64 bits fits a BIGINT, a CPU register and a hash table slot. 128 bits doubles the size of every index entry and foreign key that holds it.

No coordination

Minting an ID should not need a network call on the hot path. A central counter is a bottleneck and a single point of failure.

Two more matter case by case. Opacity: should an outsider be unable to guess neighbouring IDs or infer volume? Embedded meaning: is it useful to read the creation time or the owning shard straight out of the ID? A scheme that is time-sortable is, by construction, not opaque about time. You cannot have both.

A useful term: an ID scheme is k-sortable (or roughly time-ordered) when IDs generated far enough apart in time sort correctly, but IDs generated within a small window, on different machines, may come out in either order. Almost every distributed scheme in this chapter is k-sortable, not strictly ordered, because strict global order needs exactly the coordination we are trying to avoid.

Auto-increment and where it stops

A database sequence (BIGSERIAL in PostgreSQL, AUTO_INCREMENT in MySQL) is compact, strictly ordered and free. Keep it whenever one primary database owns the table. It breaks down in four ways:

  • One writer. The sequence lives on one node. With sharding, each shard has its own sequence, so shard 1 and shard 2 both issue order 1001. Merging shards, moving rows between them, or querying across them now needs a composite key.
  • The ID exists only after the insert. The client cannot know the ID before the database responds, which makes idempotent retries and building related rows in one batch awkward.
  • Multi-region writes. Two primaries in two regions cannot share one counter without a cross-region round trip per insert.
  • Information leak. Sequential public IDs tell the world your volume. Create an order on Monday and another on Friday, subtract, and you know how many orders the shop took that week. This is the German tank problem: the Allies estimated German tank production from serial numbers on captured tanks. Sequential IDs also invite enumeration (/invoices/1002, /invoices/1003), which turns any missing authorization check into a data breach.

A cheap extension for a fixed number of writers is to interleave sequences: MySQL's auto_increment_increment = N and auto_increment_offset = k make server k issue k, k+N, k+2N, .... Values never collide, but the number of writers is baked into every future ID, so adding a fifth server to a scheme built for four means a migration. The ticket servers below build on this trick.

UUIDs

A UUID (universally unique identifier) is a 128-bit value, usually written as 36 characters of hex and hyphens, such as 3f2b8c1e-9d4a-4f7b-a1c2-5e6d7f8a9b0c. RFC 9562 (2024) defines the versions in use today. The version is stored in 4 bits of the value itself, and 2 more bits mark the variant, so not all 128 bits are free.

UUIDv4: random

Version 4 fills the remaining 122 bits with random data from a cryptographically secure generator. No state, no coordination, no clock. The only question is collisions, and the birthday bound answers it: with n IDs drawn from N = 2122 values, the chance of any collision is about n2 / 2N.

Space N = 2^122 ≈ 5.3 × 10^36 1 trillion IDs p ≈ (10^12)^2 / (2 × 5.3 × 10^36) ≈ 9.4 × 10^-14 1 billion IDs/s for a year (3.2 × 10^16 IDs) ≈ 9.4 × 10^-5 50% chance of a collision needs ≈ 2.7 × 10^18 IDs (1 billion per second for 86 years)

In practice a collision is far more likely to come from a bug than from the math: a forked process that copies its parent's random state, a VM snapshot cloned with its entropy pool, or someone using a non-cryptographic generator seeded with the time. Use the platform's UUID function (uuid.uuid4(), gen_random_uuid(), crypto.randomUUID()), which reads from the OS random source.

Still, put a unique constraint on the column. It costs nothing extra on a primary key and turns a one-in-a-quintillion event into a retryable error instead of silent corruption.

The index locality problem

UUIDv4's weakness is not uniqueness, it is where new keys land in an index. A B-tree keeps keys sorted in fixed-size pages (8 KB in PostgreSQL, 16 KB in InnoDB). A random key lands on a random leaf page. With millions of inserts, every leaf in the index is a write target, so the whole index must stay in memory to keep inserts fast. Once the index outgrows the buffer pool, almost every insert reads a page from disk, modifies it, and later writes it back.

To put numbers on it, a small simulation inserted one million keys into leaf pages of 100 keys each, with an LRU buffer pool of 500 pages:

Insert orderLeaf pagesAvg fillCache missesPages hit by last 10k
Random (UUIDv4)14,40569%84%7,114
Time-ordered (UUIDv7)10,000100%1%101

Random inserts split pages in half and leave them about 69% full on average (the classic result for random B-tree insertion is ln 2, about 69%), so the index is 44% larger for the same data. And with a cache holding 3.5% of the index, 84% of inserts miss. Time-ordered inserts only ever touch the rightmost page: each new page is read once, filled, and never touched again. Real engines leave some free space in right-edge splits (PostgreSQL's default B-tree fillfactor is 90), but the shape of the result is the same.

The effect is worst in MySQL's InnoDB, where the table itself is a B-tree clustered on the primary key: a random primary key scatters the rows, not just an index. Every secondary index also stores the primary key, so a 16-byte UUID instead of an 8-byte BIGINT grows all of them. Storing a UUID as CHAR(36) text instead of 16 binary bytes more than doubles it again.

UUIDv7: time first

RFC 9562 added UUIDv7 to fix the locality problem while keeping the UUID format. The first 48 bits are a big-endian Unix timestamp in milliseconds, followed by the version bits and 74 bits of randomness (some of which an implementation may use as a counter for ordering within one millisecond). Because the timestamp comes first, byte order is time order, and v7 values sort correctly as raw bytes, as hex strings, and in a database uuid column.

v7 keeps every advantage of v4 (no coordination, no machine IDs, any client can mint one) and adds right-edge inserts. Collisions now need two IDs in the same millisecond with the same 74 random bits: even a million IDs inside one millisecond gives a collision chance around 3 × 10-11. The cost is that v7 reveals creation time to anyone who can see it. For a new system that wants UUIDs, v7 is the default choice; PostgreSQL 18 ships a built-in uuidv7() function.

What about v1 and v6?

UUIDv1 holds a 60-bit timestamp and the machine's MAC address, but stores the low bits of the timestamp first, so it does not sort by time, and it leaks hardware identity. v6 is v1 with the timestamp reordered to sort. Both exist for legacy compatibility; new designs use v4 or v7.

Ticket servers and range allocation

If you want compact 64-bit IDs and do not mind a network call, centralise the counter but make it cheap and redundant. Flickr did exactly this in 2010 with ticket servers: dedicated MySQL instances whose only job is to hand out numbers. Each ticket server has one table with one row; asking for an ID is a REPLACE INTO that bumps the auto-increment, followed by LAST_INSERT_ID().

CREATE TABLE Tickets64 (
  id   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  stub CHAR(1) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  UNIQUE KEY stub (stub)
) ENGINE=InnoDB;

-- one round trip per ID; the table never holds more than one row
REPLACE INTO Tickets64 (stub) VALUES ('a');
SELECT LAST_INSERT_ID();

The weak points are visible in the diagram. Every ID costs a network round trip to a ticket server. IDs from A and B interleave by load, not by time, so ID order only roughly tracks creation order. And recovering a failed server needs care: if B is restored from an old backup, its counter is behind and it will reissue numbers. Bump its counter well past the last value it could have issued before putting it back.

Range allocation

The fix for the round trip is to ask for many IDs at once. A coordinator (a SQL row updated with UPDATE counters SET next = next + 1000 ... RETURNING next, an etcd key updated with compare-and-swap, or a ZooKeeper node) leases each application server a block of, say, 1,000 or 1,000,000 IDs, which the server then hands out from memory. The coordinator sees one request per block instead of one per ID, and a coordinator outage only stops servers once their current block runs out.

The trade-offs: IDs are only ordered within a server's block, so global order is lost; a server that crashes wastes the rest of its block (harmless with a 64-bit space); and block size trades coordinator load against wasted IDs and against how long servers survive a coordinator outage. The URL shortener case study uses exactly this design to generate short codes. Hibernate's "pooled" and "hi/lo" generators and many in-house ID services are the same idea.

Snowflake

In 2010 Twitter needed tens of thousands of IDs per second, roughly time-sorted, fitting in 64 bits, with no coordination per ID. The result was Snowflake, and its layout has been copied so widely that "snowflake ID" is now a generic term. An ID is a 64-bit integer split into three fields: a millisecond timestamp, a machine ID, and a per-millisecond sequence number.

Each field has a job:

  • Timestamp (41 bits): milliseconds since a custom epoch chosen when the system launched, not since 1970. Twitter's epoch is 2010-11-04 01:42:54.657 UTC. Starting the count at launch instead of 1970 buys back four decades of range.
  • Machine ID (10 bits): unique per running generator. Twitter split it into 5 bits of datacenter and 5 bits of worker. This field is what makes uniqueness possible without coordination: two generators can never produce the same ID because their machine bits differ.
  • Sequence (12 bits): a counter that resets every millisecond, so one generator can issue many IDs within the same millisecond.

Capacity math

Lifetime 2^41 ms = 2,199,023,255,552 ms ≈ 69.7 years epoch 2026-01-01 → runs out 2095-09-07 Per node 2^12 = 4,096 ids per ms = 4,096,000 ids/s Nodes 2^10 = 1,024 generators Fleet 4,096,000 × 1,024 ≈ 4.2 billion ids/s Size 8 bytes, at most 19 decimal digits, fits a signed BIGINT

The bit split is a design parameter, not a law. Fewer machine bits and more sequence bits suits a few very busy generators; more machine bits suits thousands of small ones. Instagram, Discord and Sonyflake (below) all made different choices. What you cannot change cheaply after launch is the epoch and the layout, because every stored ID depends on them.

Assigning machine IDs

Snowflake moves the coordination problem from "every ID" to "every process start". If two live processes ever share a machine ID, they will issue duplicate IDs whenever they land in the same millisecond, and nothing will warn you. Common ways to assign them:

  • Static configuration per host. Simple, and fragile once hosts are replaced automatically.
  • Coordination service: on startup, register the ID as an ephemeral node in ZooKeeper so a second process cannot claim it (Twitter's original approach: a configured worker ID, claimed as an ephemeral znode at startup) or a key with a lease in etcd. The claim disappears when the process dies, and a new process can take it. See Consensus for why leases need care.
  • Orchestrator identity: a Kubernetes StatefulSet gives pods stable ordinals (idgen-0, idgen-1) that map directly to machine IDs.
  • Derived from the network: Sonyflake defaults to the low 16 bits of the private IP address. Convenient, but only safe if your address plan guarantees no two live hosts share those bits.

When the clock goes backwards

Snowflake trusts the wall clock, and wall clocks are not monotonic. NTP normally slews small errors by running the clock slightly fast or slow, but it steps the clock for large offsets, for example after a VM is paused and resumed, on boot, or when an operator fixes a bad time source. Leap seconds used to cause the same thing, which is why large providers now smear them over many hours.

If the clock steps back 50 ms and the generator keeps going, it will revisit milliseconds it has already used and can reissue the same timestamp and sequence: a duplicate. The standard defences, roughly in order of how often they appear:

  1. Remember the last timestamp and compare on every call. Twitter's implementation refused to issue IDs and logged an error until the clock caught up.
  2. Wait out small steps. If the clock moved back by a few milliseconds, sleep or spin until it passes the last timestamp. Refuse, and alert, beyond a threshold.
  3. Persist the high-water mark across restarts. A process that restarts after a big backward step has no memory of the timestamps it used. Writing "last timestamp used" to disk every few seconds, and refusing to start below it, closes that gap.
  4. Use a monotonic clock. Read the wall clock once at startup, then advance with the OS monotonic clock, which never goes backwards. The cost is that the generator drifts from real time over long uptimes.

Clock skew between machines is a separate, milder issue. If node A runs 30 ms ahead of node B, A's IDs sort as if they were created 30 ms later. Uniqueness is unaffected because the machine bits differ; only the ordering across nodes is approximate. That is the "k" in k-sortable, and it is why Snowflake order should never be used to decide which of two concurrent writes happened first.

Implementation

The generator below handles the three tricky cases: several IDs in the same millisecond, the sequence running out within a millisecond, and the clock moving backwards. The clock is injectable so the demo output is deterministic.

import threading
import time

EPOCH_MS = 1_288_834_974_657          # Twitter's epoch: 2010-11-04 01:42:54.657 UTC
TIME_BITS, MACHINE_BITS, SEQ_BITS = 41, 10, 12
MAX_MACHINE = (1 << MACHINE_BITS) - 1  # 1023
MAX_SEQ = (1 << SEQ_BITS) - 1          # 4095
MAX_BACKWARD_MS = 5                    # wait out small clock steps, refuse big ones


class ClockMovedBackwards(Exception):
    pass


class Snowflake:
    def __init__(self, machine_id, clock=lambda: time.time_ns() // 1_000_000):
        if not 0 <= machine_id <= MAX_MACHINE:
            raise ValueError("machine_id must fit in 10 bits")
        self.machine_id = machine_id
        self.clock = clock          # injectable so the demo is deterministic
        self.last_ms = -1
        self.seq = 0
        self.lock = threading.Lock()

    def next_id(self) -> int:
        with self.lock:
            now = self.clock()
            if now < self.last_ms:                        # clock went backwards
                if self.last_ms - now > MAX_BACKWARD_MS:
                    raise ClockMovedBackwards(f"{self.last_ms - now} ms")
                while now < self.last_ms:                 # small step: wait it out
                    now = self.clock()
            if now == self.last_ms:
                self.seq = (self.seq + 1) & MAX_SEQ
                if self.seq == 0:                         # 4,096 ids used this ms
                    while now <= self.last_ms:            # spin until the next ms
                        now = self.clock()
            else:
                self.seq = 0
            self.last_ms = now
            return ((now - EPOCH_MS) << (MACHINE_BITS + SEQ_BITS)) \
                | (self.machine_id << SEQ_BITS) | self.seq


def decode(snowflake_id: int) -> dict:
    ms = (snowflake_id >> (MACHINE_BITS + SEQ_BITS)) + EPOCH_MS
    return {
        "utc": time.strftime("%Y-%m-%d %H:%M:%S", time.gmtime(ms // 1000)) + f".{ms % 1000:03d}",
        "machine": (snowflake_id >> SEQ_BITS) & MAX_MACHINE,
        "seq": snowflake_id & MAX_SEQ,
    }


# Deterministic demo: a fake clock that starts at 2026-10-09 12:00:00.000 UTC.
fake_now = [1_791_547_200_000]
gen = Snowflake(machine_id=37, clock=lambda: fake_now[0])

a, b = gen.next_id(), gen.next_id()       # same millisecond: seq 0, then 1
fake_now[0] += 1
c = gen.next_id()                         # next millisecond: seq resets to 0
for i in (a, b, c):
    print(i, decode(i))
assert a < b < c                          # k-sorted: later ids are larger

fake_now[0] -= 1_000                      # NTP steps the clock back one second
try:
    gen.next_id()
except ClockMovedBackwards as e:
    print("refused: clock moved back", e)
2108527897605197824 {'utc': '2026-10-09 12:00:00.000', 'machine': 37, 'seq': 0}
2108527897605197825 {'utc': '2026-10-09 12:00:00.000', 'machine': 37, 'seq': 1}
2108527897609392128 {'utc': '2026-10-09 12:00:00.001', 'machine': 37, 'seq': 0}
refused: clock moved back 1000 ms

Note how the third ID is 4,194,304 (222) above the first: one millisecond in the timestamp field. Run against the real clock, this pure-Python generator produced a million IDs in about a quarter of a second on a laptop, all unique and in increasing order, with the sequence reaching 4,020 in the busiest millisecond, close to the 4,096 limit. A compiled implementation is not limited by the generator itself but by the 4,096-per-millisecond sequence.

Common mistake: 64-bit IDs in JavaScript

JavaScript numbers are 64-bit floats and represent integers exactly only up to 253 (about 9 × 1015). Any Snowflake ID created more than 25 days after the epoch is larger than that. JSON.parse silently rounds it, and the client then requests a different ID. Twitter's API added a string field, id_str, for this reason. Send 64-bit IDs to browsers as strings.

Variants

Instagram

41-bit ms timestamp, 13-bit logical shard ID, 10-bit sequence, generated inside PostgreSQL by a PL/pgSQL function using a per-shard sequence. The shard is in the ID, so any service can route a lookup without a directory.

Discord

Twitter's layout with an epoch of 2015-01-01 UTC, split as 5 bits worker, 5 bits process, 12 bits increment. Message IDs double as timestamps for pagination.

Sonyflake

39 bits of time in 10 ms units (about 174 years), 8-bit sequence, 16-bit machine ID. Trades per-node throughput (25,600 IDs/s) for more machines and a longer lifetime.

MongoDB ObjectId

12 bytes: 4-byte Unix timestamp in seconds, 5 random bytes per process, 3-byte counter. Coordination-free and roughly sortable, at 96 bits.

ULID and KSUID

Snowflake needs machine IDs. UUIDv4 needs nothing but sorts badly. A family of formats sits in between: timestamp first, then enough randomness that no machine ID is needed.

A ULID (Universally Unique Lexicographically Sortable Identifier) is 128 bits: a 48-bit Unix millisecond timestamp followed by 80 random bits, written as 26 characters of Crockford base32, for example 01M4G8HMG0Q7M2N4P6R8T0V2W4, whose first 10 characters encode 2026-10-09 12:00:00.000 UTC. Base32 avoids ambiguous letters (no I, L, O or U) and sorts in the same order as the bytes, so ULIDs sort correctly as plain strings. The spec defines a monotonic mode: within one millisecond, a generator increments the previous random part by one instead of drawing a new one, guaranteeing order for IDs from the same process. UUIDv7 standardised essentially the same idea, so new systems can usually prefer v7 and get native database support.

A KSUID (K-Sortable Unique Identifier, from Segment) is 160 bits: a 32-bit timestamp in seconds since a custom epoch of 2014-05-13 16:53:20 UTC, followed by 128 random bits, written as 27 base62 characters. The 128-bit random payload makes collisions even less likely than UUIDv4's, at the cost of 4 extra bytes and only one-second time resolution. Its 32-bit timestamp lasts until 2150.

A simple way to choose:

  • One database owns the table: keep auto-increment. Expose a separate random public ID if enumeration or volume leaks matter.
  • Many writers, 128 bits is fine: UUIDv7. No infrastructure, good index behaviour, standard format.
  • Many writers, must be 64 bits (huge tables, many secondary indexes, existing BIGINT columns): Snowflake-style, with a reliable machine ID assignment and clock monitoring.
  • IDs must reveal nothing (password reset tokens, unlisted share links): UUIDv4 or 128+ random bits. A time-ordered ID is not a secret.

Worked example: order IDs for a marketplace

A marketplace takes 50,000 orders per second at peak, written by 300 stateless order-service pods into 64 PostgreSQL shards. Orders are listed newest first, IDs appear in URLs and in partner APIs, and the orders table plus its five secondary indexes, each ending in the order id for newest-first pagination (for example (customer_id, id)), already reaches several terabytes.

Per-pod load 50,000 / 300 pods ≈ 167 orders/s (limit 4,096,000/s) Machine IDs 300 pods + headroom fits easily in 1,024 Lifetime epoch 2026-01-01 → 2095 Index savings 8 B vs 16 B key × 6 indexes × 10 billion rows ≈ 480 GB smaller

The decision: Snowflake-style 64-bit IDs, a 2026 epoch, machine IDs leased from etcd at pod start, a 5 ms threshold for clock steps with an alert, and IDs serialised as strings in JSON. Listing newest-first becomes ORDER BY id DESC on the primary key, with no separate timestamp index. Because IDs reveal order volume, public order URLs use the ID only behind authentication; anonymous tracking links use a separate random token. If the team did not want to run machine ID leasing at all, UUIDv7 would be the alternative, at the cost of that 480 GB.

In the real world

  • Twitter built Snowflake in 2010 when moving tweets off MySQL auto-increment; tweet IDs are still Snowflakes, and you can read a tweet's creation time from its ID.
  • Flickr ran two MySQL ticket servers (odd and even) to give every photo, user and comment a globally unique 64-bit ID across its sharded databases.
  • Instagram generated IDs inside each PostgreSQL logical shard so IDs embed the shard, avoiding a separate ID service entirely.
  • Discord uses Snowflake IDs for users, channels, messages and servers, and its API documentation shows how to extract the timestamp.
  • Databases: MongoDB's default _id is an ObjectId; PostgreSQL offers gen_random_uuid() (v4) and, from version 18, uuidv7(); CockroachDB's unique_rowid() combines a timestamp and node ID for the same reasons as Snowflake.
Interview angle

When to bring it up

Whenever data is sharded or written in more than one place: chat messages, tweets, orders, short URLs. Say what the ID needs (unique, 64-bit, time-sortable) and name a scheme in one sentence ("Snowflake-style IDs: 41-bit timestamp, 10-bit worker, 12-bit sequence, so messages sort by ID") unless the interviewer asks for depth. In chat and news feed designs, time-sortable IDs make pagination by ID natural.

Follow-ups to expect

  • Why not just use UUIDv4? Index locality and 16-byte keys; mention v7 as the fix.
  • What is the throughput of one Snowflake node, and how long does the scheme last? (4,096 per ms; about 69.7 years from the epoch.)
  • What happens if the clock goes backwards? Refuse or wait, persist the high-water mark, alert.
  • How are machine IDs assigned, and what if two nodes get the same one? (Leases in ZooKeeper or etcd; duplicates are silent, so this must be airtight.)
  • Can you sort events across nodes by ID? Only approximately: skew between clocks reorders IDs created close together.

Red flags

  • A single auto-increment database as the ID source for a multi-region, high-write system.
  • Hashing or truncating a UUID to 64 bits and assuming it stays unique.
  • Treating time-ordered IDs as unguessable secrets.
  • Ignoring clock behaviour entirely in a timestamp-based scheme.
