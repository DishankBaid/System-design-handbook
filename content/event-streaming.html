Why it matters

An online shop emits an OrderPlaced event. Billing needs it to charge the card, the warehouse needs it to pick items, the recommendation team wants it for training data, and a new fraud team starting next month wants every order from the last 30 days. A queue cannot serve all of them: it deletes each message once one consumer has handled it, and it has nothing left to give a team that arrives late.

Event streaming keeps the events instead. Producers append records to a durable, ordered log. Consumers read the log at their own pace and remember how far they got. Reading does not remove anything, so any number of independent consumers can read the same events, and a new consumer can start from the beginning. Records expire by a retention policy (seven days, a terabyte, or never), not by being consumed.

Apache Kafka is the system that made this model mainstream, and its vocabulary (topics, partitions, offsets, consumer groups) is what interviewers expect. This chapter uses Kafka as the reference and compares the alternatives at the end.

The log trades per-message flexibility for cheap, ordered, replayable fan-out. Tracking a single offset per partition instead of the state of every message is also what lets one Kafka broker handle hundreds of megabytes per second: the broker writes sequentially to disk and serves reads from the page cache, and consumers fetch large batches of contiguous records.

Kafka anatomy

Topics, partitions and offsets

A topic is a named stream of records, such as orders or page-views. Each topic is split into partitions, and each partition is an independent, append-only, totally ordered log stored on one leader broker (plus replicas). Every record in a partition gets a sequential offset: 0, 1, 2, and so on. An offset identifies a record only within its partition, so "offset 4,812" means nothing without "partition 7".

Partitions are the unit of everything that matters at scale: parallelism (one consumer per partition per group), ordering (guaranteed only within a partition), placement (partitions spread across brokers) and throughput (a topic's capacity is roughly the sum of its partitions').

Segments and retention

On disk, a partition is a directory of segment files. Records are appended to the active segment until it reaches segment.bytes (1 GiB by default) or segment.ms, then a new one is rolled. Each segment has a sparse offset index and a time index, so seeking to an offset or a timestamp is a binary search plus a short scan. Retention deletes whole closed segments once they are older than retention.ms (7 days by default) or the partition exceeds retention.bytes. Deleting a file is cheap, which is why retention costs almost nothing compared with deleting individual messages.

Recent Kafka versions add tiered storage: closed segments are copied to object storage like S3 and deleted locally, so retention can be months without buying broker disks for it.

Log compaction

Some topics represent current state rather than history: the latest address for each customer, the latest price for each product. For these, set cleanup.policy=compact. A background cleaner rewrites old segments, keeping only the most recent record for each key. A record with a null value is a tombstone: it marks the key as deleted, and is itself removed after delete.retention.ms.

Brokers and replication

A Kafka cluster is a set of brokers. Each partition has a replication factor (3 is standard): one replica is the leader, which handles all writes and by default all reads, and the others are followers that continuously fetch from the leader. The leader tracks the in-sync replica set (ISR): followers that have caught up within replica.lag.time.max.ms (30 seconds by default). A record is committed once every replica in the ISR has it, and consumers can only read committed records; the boundary is called the high watermark.

Two settings decide durability:

  • acks on the producer. acks=0: do not wait at all. acks=1: wait for the leader only, so a leader crash right after the ack loses the record. acks=all (the default since Kafka 3.0): wait until every in-sync replica has it.
  • min.insync.replicas on the topic. With acks=all, the leader refuses writes if the ISR has shrunk below this number. Without it, acks=all silently degrades to acks=1 when followers drop out, because "all in-sync replicas" is then just the leader.

Cluster metadata (which broker leads which partition, the ISR of each) lives in a controller quorum. Kafka 4.0 completed the move from ZooKeeper to KRaft, a Raft-based quorum of controller nodes inside Kafka itself. See Replication and Consensus for the general mechanisms.

Producers

Keyed partitioning

Each record has an optional key. The Java client's default partitioner hashes the key with murmur2 and takes it modulo the partition count, so all records with the same key land in the same partition, in the order they were sent. Choose the key as the entity whose events must stay ordered: order_id, account_id, device_id. Records without a key are spread across partitions; since Kafka 2.4 the client uses a sticky partitioner that fills a batch for one partition before switching, which gives larger batches than strict round-robin.

Key choice is also where hot partitions come from. If 30% of traffic belongs to one tenant and the key is tenant_id, one partition gets 30% of the load no matter how many partitions exist. The fixes are the same as for hot shards: a finer key, or a salted key for that tenant at the cost of its ordering.

Batching and compression

The producer never sends records one at a time. It accumulates them per partition into batches, sending a batch when it reaches batch.size bytes (16 KiB by default) or when linger.ms expires. A few milliseconds of linger can multiply throughput, because one request carries hundreds of records and compression (lz4, zstd) works much better on a batch than on a single record. The broker stores the compressed batch as is and consumers decompress it, so compression saves network and disk, and the broker avoids recompressing.

The idempotent producer

A producer that sends a batch, loses the response and retries could write the batch twice. With enable.idempotence=true (the default since 3.0), the broker assigns each producer a producer id, and the producer numbers every batch per partition. The leader remembers the last sequence numbers per producer and partition, drops a retried batch it has already written, and rejects one that arrives out of order. Retries can then never create duplicates or reorder records within a partition, for the lifetime of that producer session.

Consumer groups and rebalancing

A consumer group is a set of consumers sharing a group.id that together read a topic. Kafka assigns each partition to exactly one consumer in the group, so the group processes every record once while the work is split. Different groups are completely independent: billing and analytics each get all records.

  • With 6 partitions and 3 consumers, each consumer gets 2 partitions.
  • With 6 partitions and 8 consumers, 2 consumers sit idle. The partition count is the ceiling on a group's parallelism.

When a consumer joins, leaves or stops sending heartbeats, the group rebalances: a group coordinator on one of the brokers collects the members, and in the classic protocol one consumer, the group leader, computes the new assignment with the configured assignor. A consumer is declared dead if it misses heartbeats for session.timeout.ms (45 seconds by default) or does not call poll() within max.poll.interval.ms (5 minutes), which catches consumers that are alive but stuck processing.

Rebalances used to be the main operational pain of Kafka consumers. The original eager protocol revoked every partition from every consumer, then reassigned them all, so the whole group stopped for each change and a rolling deploy of 20 consumers caused 20 stop-the-world pauses. Three improvements matter:

  • Cooperative (incremental) rebalancing, via the CooperativeStickyAssignor: only the partitions that actually move are revoked; everyone else keeps consuming.
  • Static membership (group.instance.id): a consumer that restarts within the session timeout gets its old partitions back with no rebalance at all, which makes rolling restarts cheap.
  • The new consumer group protocol (KIP-848, generally available in Kafka 4.0) moves assignment logic to the broker-side coordinator and makes rebalances incremental by default.

Ordering: per partition only

Kafka guarantees that records in one partition are read in the order they were written. It makes no promise across partitions: if OrderPlaced for order 81723 goes to partition 3 and PaymentCaptured for the same order goes to partition 5, a consumer may see the payment first. The rule follows directly: events that must be ordered relative to each other must share a key, and therefore a partition. Keying both events by order_id fixes the example.

Three things break per-key ordering in practice:

  • Adding partitions. hash(key) % 6 and hash(key) % 8 disagree for most keys (75% of them, measured below), so for a while a key's old records are in one partition and its new records in another. Over-provision partitions up front instead of adding them later.
  • Producer retries without idempotence, if more than one batch is in flight per connection.
  • Parallel processing inside a consumer. A consumer that hands records from one partition to a thread pool has thrown the ordering away. Parallelise by key (one worker per key hash) if you need both.

Delivery semantics and offset commits

A consumer records progress by committing offsets to an internal topic, __consumer_offsets. The committed offset is the next record to read. When a partition moves to another consumer, or a consumer restarts, reading resumes there. The timing of the commit relative to processing sets the delivery guarantee:

Commit timingCrash between the two stepsResult
Commit, then processRecords committed but not processed are skippedAt-most-once: possible loss
Process, then commitRecords processed but not committed are processed againAt-least-once: possible duplicates
Process and commit atomicallyBoth happen or neither doesEffectively once, if the output and the offset share a transaction

The default (enable.auto.commit=true, every 5 seconds) commits the offsets returned by the previous poll() during the next one, which is at-least-once as long as you finish processing a batch before polling again. Hand records to another thread and it quietly becomes at-most-once. Most production consumers disable auto-commit and commit explicitly after processing. Either way, design consumers to tolerate duplicates: see Idempotency & Delivery Semantics.

Exactly-once and its scope

Kafka's exactly-once semantics (EOS) combine the idempotent producer with transactions. A producer configured with a transactional.id can write to several partitions and commit consumer offsets as one atomic unit:

producer.initTransactions();
while (true) {
    ConsumerRecords<String, Order> records = consumer.poll(Duration.ofMillis(100));
    producer.beginTransaction();
    for (ConsumerRecord<String, Order> r : records)
        producer.send(new ProducerRecord<>("orders-enriched", r.key(), enrich(r.value())));
    producer.sendOffsetsToTransaction(offsetsOf(records), consumer.groupMetadata());
    producer.commitTransaction();   // outputs and input offsets become visible together, or not at all
}

Downstream consumers set isolation.level=read_committed so they never see records from aborted transactions. The transactional.id also fences "zombies": if a stalled instance wakes up after its replacement has started, its writes are rejected. Kafka Streams wraps all of this behind processing.guarantee=exactly_once_v2.

Know the scope

Kafka transactions cover read from Kafka, write to Kafka. The moment a consumer sends an email, calls a payment API or writes to PostgreSQL, those side effects are outside the transaction and can happen twice after a crash. For external sinks, either make the write idempotent (upsert by a unique key), or store the consumed offset in the same database transaction as the result and seek to it on startup. "Exactly-once" in an interview answer should always come with "within Kafka" or "via idempotent sinks".

Partitioning and assignment in code

The code below reimplements Kafka's default key partitioner (murmur2, checked against the test vectors in Kafka's own test suite) and the two classic group assignors. RangeAssignor works topic by topic, giving each consumer a contiguous block; RoundRobinAssignor deals all partitions of all subscribed topics across consumers like cards.

def murmur2(data: bytes) -> int:
    """Kafka's murmur2 (the Java client's default partitioner hash), as a signed 32-bit int."""
    m, r, mask = 0x5BD1E995, 24, 0xFFFFFFFF
    h = (0x9747B28C ^ len(data)) & mask
    n4 = len(data) // 4
    for i in range(n4):
        k = int.from_bytes(data[4 * i:4 * i + 4], "little")
        k = (k * m) & mask
        k ^= k >> r
        k = (k * m) & mask
        h = ((h * m) & mask) ^ k
    tail = data[4 * n4:]
    if len(tail) >= 3: h ^= tail[2] << 16
    if len(tail) >= 2: h ^= tail[1] << 8
    if len(tail) >= 1:
        h ^= tail[0]
        h = (h * m) & mask
    h ^= h >> 13
    h = (h * m) & mask
    h ^= h >> 15
    return h - (1 << 32) if h & 0x80000000 else h


def partition_for(key: str, num_partitions: int) -> int:
    return (murmur2(key.encode()) & 0x7FFFFFFF) % num_partitions


def range_assign(partitions: int, consumers: list) -> dict:
    """RangeAssignor for one topic: contiguous blocks, the first (P % C) consumers get one extra."""
    consumers = sorted(consumers)
    per, extra = divmod(partitions, len(consumers))
    out, start = {}, 0
    for i, c in enumerate(consumers):
        n = per + (1 if i < extra else 0)
        out[c] = list(range(start, start + n))
        start += n
    return out


def round_robin_assign(topic_partitions: list, consumers: list) -> dict:
    """RoundRobinAssignor: deal all (topic, partition) pairs across consumers like cards."""
    consumers = sorted(consumers)
    out = {c: [] for c in consumers}
    for i, tp in enumerate(sorted(topic_partitions)):
        out[consumers[i % len(consumers)]].append(tp)
    return out

print("range:      ", {c: [f"{t}-{p}" for t in ("orders", "payments") for p in ps]
                       for c, ps in range_assign(3, ["c1", "c2"]).items()})
tps = [(t, p) for t in ("orders", "payments") for p in range(3)]

Two lessons are visible. Going from 6 to 8 partitions remaps three quarters of the keys, so per-key ordering breaks for any key with records in flight during the change. And the range assignor gives c1 twice as many partitions as c2, because the same leftover lands on the first consumer for every topic. With many topics of the same size, that skew compounds; round-robin or sticky assignors avoid it.

Worked example: how many partitions?

A clickstream topic receives 1 million events per second at peak, averaging 300 bytes each. The consuming service enriches each event with a cache lookup and was benchmarked at 5 MB/s per consumer instance. A single partition can comfortably take 25 MB/s of produce traffic on this cluster's hardware. Plan for 2x growth over two years, because adding partitions later breaks key ordering.

Peak ingress 1,000,000 events/s × 300 B = 300 MB/s Produce-bound 300 / 25 MB/s per partition = 12 partitions Consume-bound 300 / 5 MB/s per consumer = 60 partitions (one consumer each) Partitions max(12, 60) × 2 growth = 120 Round to 120 (divisible by 2, 3, 4, 5, 6, 8, 10, 12, 15, 20, 24, 30, 40, 60) Retention 300 MB/s × 86,400 s × 7 days ≈ 181 TB With RF = 3 181 × 3 ≈ 544 TB of disk before compression Per broker 544 TB / 24 brokers ≈ 23 TB, 15 partition replicas each

The consumer, not the broker, usually sets the partition count, which is why the formula takes the maximum of the two. Choosing a number with many divisors means most likely consumer counts (2, 3, 4, 5, 6, 8, 10, 12, 15, 20, 24, 30, 40, 60) divide the partitions evenly. The disk figure is the other surprise: it argues for compression, shorter retention, or tiered storage before buying 24 brokers.

More partitions are not free. Each partition replica is a set of open files and a fetch session; each partition needs a producer batch buffer; a broker failure means a leader election for every partition it led. KRaft raised the practical limits a lot, but a topic with 10,000 partitions for 10 MB/s of traffic is still a mistake.

Consumer lag

Consumer lag is the distance between the newest record in a partition (the log end offset) and the group's committed offset, summed across partitions. It is the single most important health metric of a streaming pipeline, and the equivalent of queue depth for a queue.

  • Alert on time, not records. 50,000 records of lag is nothing for a topic doing 100,000 per second and a disaster for one doing 10 per second. Convert lag to seconds: lag divided by the consumption rate, or the age of the oldest unconsumed record.
  • Catch-up maths. A group that falls 1.8 million records behind during a deploy, and normally runs at 40,000 records/s against 20,000/s of input, catches up at a net 20,000/s: 90 seconds.
  • Lag that grows forever means the group's capacity is below the input rate. Add consumers (up to the partition count), make processing faster, or batch the downstream writes. Lag that grows on one partition only means a hot key or a stuck consumer.
  • Do not outrun retention. If lag in time exceeds retention.ms, unread records are deleted and the consumer jumps forward according to auto.offset.reset. That is silent data loss.

Tools: kafka-consumer-groups.sh --describe, LinkedIn's Burrow, and lag exporters for Prometheus. KEDA can autoscale consumers on lag the same way it scales queue workers on depth.

In the real world

  • LinkedIn built Kafka around 2010 to replace a tangle of point-to-point data pipelines with one log that every system publishes to and reads from. Jay Kreps' essay "The Log" explains the reasoning, and LinkedIn still runs it at trillions of records per day.
  • Uber, Netflix and most large consumer companies use Kafka as the backbone between online services and analytics: trip and playback events flow through Kafka into stream processors and data lakes.
  • Kafka Connect and Debezium turn database changes into topics (change data capture) and push topics into sinks like Elasticsearch and S3. See Event-Driven Architecture.
  • Kafka Streams and Apache Flink consume topics, keep local state backed by compacted changelog topics, and write results back to Kafka with exactly-once guarantees. See Batch vs Stream Processing.
  • Managed offerings (Confluent Cloud, Amazon MSK, Aiven, Redpanda's Kafka-compatible engine) exist because running brokers, rebalancing partitions and upgrading clusters is the main cost of Kafka.
Interview angle

When to bring it up

When several services or analytics pipelines need the same stream of events, when you need replay, or when the event rate is very high (click tracking, location updates, logs, metrics). Typical phrasing: "Click events go to a Kafka topic keyed by link_id with replication factor 3 and acks=all; the aggregator is a consumer group, and we size partitions for consumer throughput." It appears in the URL shortener, news feed and ride-sharing case studies.

Follow-ups to expect

  • How do you guarantee ordering for one user's events? (Key by user id; ordering is per partition only.)
  • What happens when a consumer crashes? (Rebalance after the session timeout; the new owner resumes from the committed offset and reprocesses anything uncommitted.)
  • How many partitions, and why? (Max of produce-bound and consume-bound counts, plus headroom; hard to change later.)
  • Can you lose data? (Not with RF 3, acks=all, min.insync.replicas=2 and unclean election off, short of losing two brokers' disks or a correlated power loss, since Kafka acks before fsync.)
  • Is it exactly-once? (Within Kafka with transactions; at external sinks only through idempotence.)

Red flags

  • Expecting global ordering across a multi-partition topic.
  • Adding consumers beyond the partition count and expecting more throughput.
  • Using Kafka as a task queue that needs per-message retries and delays without explaining how (retry topics, a DLQ topic).
  • acks=all with min.insync.replicas=1, presented as durable.
