Why it matters

Two customers press "Buy" on the last concert ticket within the same millisecond. Two requests read seats_left = 1, both see a seat, both insert an order. You have sold one seat twice, and no line of your code is wrong on its own. The bug lives in how the two requests interleaved, and whether the database allowed that interleaving is decided by one setting most developers never look at: the isolation level.

Transactions are the database's promise to hide two hard problems from application code: failures part way through a set of writes, and concurrency between requests touching the same data. The promise is weaker than most people assume. The default isolation level in PostgreSQL, MySQL, Oracle and SQL Server allows anomalies that lose money. Knowing exactly which ones, and the cheap fixes for each, is what this chapter is about.

ACID, precisely

A transaction groups several reads and writes into one logical unit that either commits or aborts. The acronym ACID (Haerder and Reuter, 1983) names four guarantees. They are often recited and rarely defined well.

Atomicity

All of a transaction's writes take effect, or none do. If the process crashes, a constraint fails or the client disconnects half way, the database rolls back what was done. It is about abortability, not concurrency: it means retrying a failed transaction is safe.

Consistency

Application invariants hold before and after each transaction: debits equal credits, stock is never negative. This is mostly the application's job. The database helps with declared constraints (CHECK, UNIQUE, foreign keys) and with the other three properties. It is not the "C" of CAP.

Isolation

Concurrent transactions do not see each other's partial work. The ideal is serializability: the result equals some one-at-a-time ordering of the transactions. Real databases offer weaker levels by default because they are cheaper.

Durability

Once commit returns, the data survives a crash. On one machine that means the commit record has been forced to disk with fsync. In a cluster it can also mean the record reached other replicas. No durability is absolute; it is a statement about which failures you survive.

Atomicity and durability are about failures and are implemented by logging, covered at the end of the chapter. Isolation is about concurrency, and it is where the subtlety lies.

The anomalies, one at a time

An anomaly is an outcome that could not happen if the transactions ran one after another. Each isolation level is defined by which anomalies it rules out, so you need the anomalies first. The two diagrams below show each one as a timeline: transaction T1 on top, T2 on the bottom, the database state in between. Accent arrows are writes; plain arrows are reads.

Anomalies on a single item

  • Dirty write: overwriting another transaction's uncommitted write. Every real database prevents it at every level by holding a row lock from the write until commit, because without that even rollback is ill-defined.
  • Dirty read: reading another transaction's uncommitted write. If the writer aborts, the reader acted on a value that never existed.
  • Non-repeatable read (or fuzzy read): reading the same row twice in one transaction and getting different committed values, because someone committed in between.
  • Lost update: two transactions each read a value, compute a new one, and write it back. The second write silently overwrites the first. This is the most common concurrency bug in web applications, because "load the object, change a field, save it" is exactly this pattern.

Anomalies across several items

  • Read skew: a transaction sees part of the database before another transaction committed and part after. Each value is committed, the combination never existed. It wrecks backups, consistency checks and analytics queries that run for minutes.
  • Write skew: two transactions read an overlapping set of rows, check a condition, and then write different rows. Each write is valid alone; together they break the invariant. Since nobody wrote the same row, there is no conflict for a database to detect unless it tracks reads.
  • Phantom: a write in one transaction changes the result of a search query in another. The booking example is the dangerous form: the check "is room 7 free at 14:00?" returns no rows, so there is no row to lock, and both inserts succeed. SELECT ... FOR UPDATE cannot lock a row that does not exist yet.

Isolation levels

The SQL-92 standard defines four levels by three phenomena: dirty read, non-repeatable read and phantom. In 1995 Berenson and colleagues, in A Critique of ANSI SQL Isolation Levels, showed those definitions are ambiguous and incomplete. They added dirty write, lost update, read skew and write skew, and described snapshot isolation, a level the standard does not mention but that most databases actually implement. The table uses their analysis, with RU, RC, RR and SI standing for read uncommitted, read committed, lock-based repeatable read and snapshot isolation.

"Yes" means the anomaly can happen. Two columns deserve a note. Locking repeatable read holds read locks on every row read until commit, so write skew over existing rows ends in a deadlock instead of a bad result, but a phantom insert still slips through. Snapshot isolation reads from a frozen snapshot, so a repeated search never shows new rows, but that does not stop two transactions from each inserting a row the other's search would have found. Snapshot isolation and locking repeatable read are incomparable: each prevents something the other allows.

Common mistake

Saying "we use REPEATABLE READ, so we are safe from lost updates". On PostgreSQL that is true. On MySQL with InnoDB it is not: a read-modify-write that computes the new value in application code will silently lose updates. Martin Kleppmann's Hermitage project tests each database's actual behaviour and is worth checking before you rely on a level.

How isolation is implemented

Three mechanisms cover almost every engine. Knowing them explains why each level allows what it allows and what it costs.

Two-phase locking (2PL)

In two-phase locking, a transaction takes a shared lock on everything it reads and an exclusive lock on everything it writes, and (in the strong strict (rigorous) form databases use) holds them all until commit or abort. Shared locks are compatible with each other; an exclusive lock waits for all other locks on that item. Readers block writers and writers block readers. That is serializable for existing rows. For phantoms the engine must also lock ranges: true predicate locks are too expensive to check, so engines lock index ranges instead, which is what InnoDB's next-key locks and SQL Server's key-range locks are. A search for room = 7 AND slot = '14:00' locks the gap in the index where such a row would go, so a concurrent insert into that gap waits.

The costs are waiting and deadlocks. Two transactions that each hold a lock the other wants form a cycle; the database detects it and aborts one. A long-running read (a report scanning a million rows) holds shared locks on all of them and blocks every writer behind it. That is why 2PL lost favour as the default.

Multi-version concurrency control (MVCC)

MVCC keeps several versions of each row. A write never overwrites in place; it creates a new version tagged with the writing transaction's id. Each transaction (or each statement, under read committed) reads from a snapshot: the set of transactions that had committed when it started. A version is visible if the transaction that created it is in the snapshot and the transaction that deleted or replaced it is not.

The rule that makes MVCC so popular: readers never block writers and writers never block readers. Writers still block other writers on the same row. The cost is garbage: old versions pile up until no snapshot can see them, then PostgreSQL's VACUUM (or InnoDB's purge thread, which cleans up undo logs) removes them. A transaction left open for hours pins every version created since it started, so tables and indexes bloat. Monitor the age of the oldest open transaction.

MVCC gives snapshot isolation almost for free. To also prevent lost updates, the engine adds a check at write time: if the row you are updating has a newer committed version than your snapshot, abort (PostgreSQL's "first updater wins"). That check is the difference between PostgreSQL and InnoDB repeatable read.

Serializable Snapshot Isolation (SSI)

Snapshot isolation fails only on write skew and its phantom variants. Serializable Snapshot Isolation (Cahill, Röhm and Fekete, 2008) keeps MVCC's non-blocking reads and adds tracking of read-write dependencies: transaction T1 read something that T2, running concurrently, later wrote. Every non-serializable execution under snapshot isolation contains a "dangerous structure": a transaction with an incoming and an outgoing read-write dependency among concurrent transactions. When SSI detects one, it aborts a transaction with a serialization failure (SQLSTATE 40001).

In the on-call example, both transactions read the set of on-call doctors and each wrote a row the other had read. SSI sees the two dependencies and aborts the second commit. PostgreSQL tracks reads with predicate locks on index ranges (called SIREAD locks), which never block anyone; they only feed the detector. SSI can abort transactions that would have been fine (false positives), so the application must be prepared to retry the whole transaction. Its throughput is close to snapshot isolation for most workloads and far better than 2PL for read-heavy ones.

Preventing anomalies without SERIALIZABLE

Most applications run at read committed and fix the few places that matter with targeted techniques. These are the ones to know.

Atomic updates

Let the database do the read-modify-write in one statement. The row is locked for the duration of the statement and the new value is computed from the latest committed value, so concurrent increments never get lost.

-- Lost-update-proof at any isolation level
UPDATE accounts SET balance = balance + 10 WHERE id = 7;

-- Conditional: sell a seat only if one is left. Check the row count: 0 means sold out.
UPDATE events SET sold = sold + 1 WHERE id = 912 AND sold < capacity;

Pessimistic locking: SELECT ... FOR UPDATE

When the new value needs application logic, lock the rows you read. FOR UPDATE takes the same lock an update would, so a second transaction doing the same thing waits until the first commits. Under PostgreSQL read committed, the waiting statement then re-checks its WHERE clause against the newly committed row version before proceeding.

BEGIN;
SELECT doctor_id FROM shifts
 WHERE shift_id = 1234 AND on_call
   FOR UPDATE;                         -- locks every on-call row for this shift
-- application checks: more than one doctor left?
UPDATE shifts SET on_call = false WHERE shift_id = 1234 AND doctor_id = 'alice';
COMMIT;

This fixes the write skew because both transactions now lock the same set of rows. It does not fix the booking phantom, because there are no rows to lock. For that, either create the rows ahead of time (one row per room per slot, then lock it), or let a constraint enforce the rule. PostgreSQL's exclusion constraint does exactly that: EXCLUDE USING gist (room WITH =, during WITH &&) rejects any two overlapping bookings for the same room. FOR UPDATE SKIP LOCKED is a related tool for job queues: each worker grabs rows nobody else has locked.

Optimistic concurrency with a version column

Instead of locking, detect the conflict at write time. Each row carries a version number. Read it with the data, and make the update conditional on it not having changed. If the update affects zero rows, someone else got there first: re-read and retry, or report a conflict to the user. This is compare-and-set, and it is how ORMs implement optimistic locking (JPA's @Version, Rails' lock_version) and how HTTP APIs do it with ETag and If-Match.

SELECT balance, version FROM accounts WHERE id = 7;      -- 100, version 41
UPDATE accounts SET balance = 110, version = version + 1
 WHERE id = 7 AND version = 41;                          -- 1 row: success, 0 rows: retry

A small simulation shows the difference. Two deposits of 10 and 5 run concurrently against a balance of 100. A barrier forces the bad interleaving: both read before either writes.

import threading


class Row:
    """One database row with a version column, guarded like a real row latch."""

    def __init__(self, balance):
        self.balance, self.version = balance, 0
        self._latch = threading.Lock()

    def read(self):
        with self._latch:
            return self.balance, self.version

    def write(self, balance):                      # blind write: UPDATE ... SET balance = ?
        with self._latch:
            self.balance, self.version = balance, self.version + 1

    def compare_and_set(self, balance, expected_version):
        # UPDATE accounts SET balance = ?, version = version + 1
        #  WHERE id = ? AND version = ?        -- then check the row count
        with self._latch:
            if self.version != expected_version:
                return False
            self.balance, self.version = balance, self.version + 1
            return True


def deposit_naive(row, amount, both_read):
    balance, _ = row.read()
    both_read.wait()                               # force the bad interleaving: both read first
    row.write(balance + amount)


def deposit_cas(row, amount, both_read, retries):
    first = True
    while True:
        balance, version = row.read()
        if first:
            both_read.wait()
            first = False
        if row.compare_and_set(balance + amount, version):
            return
        retries.append(amount)                     # someone else won: re-read and retry


def run(worker, *extra):
    row, barrier = Row(100), threading.Barrier(2)
    threads = [threading.Thread(target=worker, args=(row, amt, barrier, *extra)) for amt in (10, 5)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return row.balance


print("naive read-modify-write:", run(deposit_naive))
retries = []
print("compare-and-set:        ", run(deposit_cas, retries), "after", len(retries), "retry")
# naive read-modify-write: 110        (or 105, whichever write lands last; never 115)
# compare-and-set:         115 after 1 retry

Optimistic concurrency shines when conflicts are rare: no locks held across user think-time, no deadlocks, works across HTTP requests. Under heavy contention on one row it degrades into retry storms, where pessimistic locking or an atomic update queues requests more efficiently.

Worked example: the last seats of a flash sale

An event has 5,000 seats and 50,000 people trying to buy in the first minute. Every purchase touches one hot row, events.sold. The question is how many purchases per second each approach can push through that row. Throughput on one row is bounded by how long each transaction holds its lock: at most 1 / hold_time commits per second.

FOR UPDATE, then app logic, then payment call inside the txn hold ≈ 5 ms DB + 300 ms payment API → 1 / 0.305 s ≈ 3 purchases/s FOR UPDATE, payment moved outside the txn hold ≈ 5 ms (round trips between statements) → 1 / 0.005 s ≈ 200 purchases/s Single conditional UPDATE ... The lessons generalise. Never hold a lock across a network call to another service. Prefer a single statement that the database can execute atomically. When one row is the bottleneck, split it. And when you do need a multi-statement check-then-write, either lock the rows the check depends on or run at SERIALIZABLE and retry.

Durability and the write-ahead log

Atomicity and durability both come from the write-ahead log (WAL; InnoDB calls it the redo log). The rule: before a change to a data page reaches disk, a log record describing it must already be on disk. At commit, the database appends a commit record and forces the log with fsync. Only then does it tell the client "committed".

  • Why it is fast. The log is append-only, so a commit costs one sequential write. Data pages change in memory and are flushed later in bulk by a checkpoint. Group commit lets many concurrent transactions share one fsync, which is how a database commits tens of thousands of transactions per second on a device that completes far fewer flushes.
  • Crash recovery. After a crash, the database replays the log from the last checkpoint, redoing committed changes whose pages never reached disk. Engines that update pages in place also need undo information to roll back changes from transactions that never committed (the ARIES algorithm describes both). PostgreSQL mostly avoids undo because MVCC leaves uncommitted versions invisible.
  • Torn pages. A crash in the middle of writing an 8 KB page can leave half old and half new. PostgreSQL writes a full page image to the WAL the first time a page changes after each checkpoint; InnoDB uses a doublewrite buffer.
  • Knobs that trade durability for speed. PostgreSQL's synchronous_commit = off and MySQL's innodb_flush_log_at_trx_commit = 2 acknowledge before the fsync, risking roughly the last second of commits on a crash, without corrupting anything. Fine for click counts, not for payments.
  • Beyond one machine. fsync protects against a process or OS crash, not a dead disk or a lost data centre. For that the WAL is shipped to replicas, and synchronous replication waits for a replica to confirm before acknowledging. See Replication.

In the real world

  • PostgreSQL shipped SSI in 9.1 (2011), the first production implementation; its SERIALIZABLE READ ONLY DEFERRABLE mode lets long reports run without any risk of serialization failure.
  • MySQL keeps repeatable read as its default partly for historical replication reasons: statement-based binary logging needed it to replay correctly. Many large deployments switch to read committed with row-based logging to reduce gap-lock contention.
  • Google Spanner and CockroachDB run serializable by default across machines and tell clients to wrap transactions in retry loops; the client libraries do it automatically.
  • Stripe and most payment systems combine database transactions with idempotency keys, because a transaction cannot protect against a client retrying a request whose response it never received.
  • Jepsen analyses have repeatedly found databases whose isolation was weaker than documented, which is why "test your actual guarantees" is real advice and not paranoia.

Transactions that span several databases or services are a different problem with different tools (two-phase commit, sagas, outboxes), covered in Distributed Transactions.

Interview angle

When to bring it up

Whenever money, inventory, bookings or unique usernames appear. Name the anomaly and the fix in one breath: "Two buyers can both see one seat left, which is a lost update; I'll make the decrement a single conditional UPDATE and check the row count." For booking systems, mention phantoms and an exclusion or unique constraint.

Follow-ups to expect

  • What does READ COMMITTED not protect against? (Non-repeatable reads, lost updates, read skew, write skew, phantoms.)
  • Explain write skew and why snapshot isolation allows it.
  • Optimistic or pessimistic locking here? (Depends on contention and whether a user's think-time sits between read and write.)
  • How does MVCC let readers avoid blocking writers, and what does it cost? (Old versions, vacuum, long-transaction bloat.)
  • What exactly happens on COMMIT, and what is lost if the machine loses power?

Red flags

  • "The database is ACID, so concurrency is handled." The default level is not serializable anywhere except a few distributed SQL databases.
  • Assuming REPEATABLE READ means the same thing on PostgreSQL and MySQL.
  • Using SERIALIZABLE without a retry loop.
  • Holding a row lock while calling a payment provider.
