Why it matters

Some questions get expensive at scale only because the answer has to be exact. "Have I crawled this URL before?" over 5 billion URLs, "how many distinct users opened the app today?" across 100 million users, "which 10 products are viewed most this minute?" over a million events per second. Exact answers need memory that grows with the number of items. Probabilistic data structures answer the same questions in a fixed, small amount of memory, in exchange for a small, bounded error that you choose up front, and for Bloom filters and Count-Min Sketch that error only goes in one direction.

A web crawler that remembers 5 billion seen URLs in a hash set needs hundreds of gigabytes: the URLs alone average around 80 bytes, before pointers and hash-table overhead. A Bloom filter answering the same question with a 1% false-positive rate needs about 6 GB and fits on one machine. Counting unique visitors exactly for one day means storing every visitor id, about 800 MB for 100 million 8-byte ids, per counter. A HyperLogLog does it in 12 KB with under 1% error, and you can keep one per page per day.

The three structures in this chapter each answer one kind of question:

StructureQuestionErrorMemory

HyperLogLogHow many distinct items have I seen?About 1.04/√m relative error (0.81% at 12 KB)Fixed, independent of the count
Count-Min SketchHow often has x occurred? What are the top k?Overestimates by at most εN, with probability 1 - δFixed, set by ε and δ

The common trick is hashing. Each structure hashes items into a small array and keeps only a summary per slot, so collisions are the source of the error, and the maths of collisions lets you size the array for the error you can tolerate.

Bloom filters: is this item in the set?

A Bloom filter is an array of m bits, all 0 at the start, plus k independent hash functions that each map an item to one of the m positions.

  • Add an item: compute its k positions and set those bits to 1.
  • Query an item: compute its k positions. If any of those bits is 0, the item was definitely never added. If all are 1, the item was probably added.

Step through the figure: two inserts, one query that the filter answers correctly, and one false positive.

Why the error only goes one way

Bits only ever go from 0 to 1. If an item was added, its k bits were set and stay set, so a query for it always finds all 1s. A false negative is impossible. A false positive happens when other items have, between them, set all k bits of an item that was never added.

That asymmetry decides where a Bloom filter fits. It works as a cheap pre-check in front of an expensive exact lookup: a "no" skips the lookup entirely, a "maybe" falls through to the real data, which gives the exact answer. The false-positive rate is then just the fraction of wasted lookups. It does not work where a false "yes" is acted on without checking, for example deciding a username is taken and refusing it, unless an occasional wrong refusal is acceptable.

Sizing: m and k from n and p

You pick two numbers: n, how many items you expect to add, and p, the false-positive rate you can accept. Everything else follows from the probability that a given bit is still 0.

  • One hash sets a given bit with probability 1/m. After n items with k hashes each, a bit is still 0 with probability (1 - 1/m)kn ≈ e-kn/m.
  • A false positive needs all k bits of a new item to be 1: p ≈ (1 - e-kn/m)k.
  • For fixed m and n, that is smallest when k = (m/n) ln 2. At that point exactly half the bits are 1, and p = (1/2)k.
  • Substituting back and solving for m gives the sizing formula.
m = -n · ln p / (ln 2)² bits in the array k = (m / n) · ln 2 hash functions, rounded to an integer

Notice that m/n, the bits per item, depends only on p. The size of the items does not matter at all: a filter of 100-byte URLs and a filter of 8-byte ids cost the same per item.

Worked example. A crawler wants to remember 1 billion URLs with a 1% false-positive rate.

n = 1,000,000,000 p = 0.01 m = 1e9 × ln(100) / (ln 2)² = 1e9 × 4.605 / 0.4805 = 9.585e9 bits ≈ 1.2 GB k = 9.585 × 0.693 = 6.64 → 7 hashes Exact set: 1e9 URLs × ~80 B = 80 GB of strings, before hash-table overhead Cost of a false positive: 1 in 100 new URLs is wrongly skipped as "seen"

Each tenfold improvement in p costs the same 4.79 extra bits per item, because ln 10 / (ln 2)² ≈ 4.79:

Rule of thumb

About 10 bits per item gives about 1% false positives. RocksDB exposes exactly this knob as "bits per key", and 10 is the commonly recommended value.

What happens when the filter overfills

A Bloom filter cannot grow. If you size it for 100,000 items and insert more, more bits turn to 1 and the false-positive rate climbs steeply. Nothing fails loudly: the filter just says "maybe" more and more often until it says it about everything.

For sets that grow without a known bound, a scalable Bloom filter chains filters: when the current one reaches its design load, it starts a new, larger one with a tighter target rate. Queries check every filter in the chain, and the total false-positive rate converges to a chosen bound. RedisBloom's BF.ADD works this way when a filter fills up. The other common fix is rotation: a new filter per day or per hour, so old entries age out with the filter.

Implementation

Computing k independent hashes is wasteful. Kirsch and Mitzenmacher showed that two hashes are enough: position i is h1 + i · h2 mod m, with no loss in false-positive rate. The filter below uses one 128-bit BLAKE2 hash split into two 64-bit halves, packs bits into a bytearray, and measures the false-positive rate against the formula.

import hashlib
import math


class BloomFilter:
    def __init__(self, n: int, p: float):
        self.m = math.ceil(-n * math.log(p) / math.log(2) ** 2)   # bits
        self.k = max(1, round(self.m / n * math.log(2)))           # hash functions
        self.bits = bytearray((self.m + 7) // 8)

    def _positions(self, item: str):
        # Kirsch-Mitzenmacher: k positions from two 64-bit hashes, g_i = h1 + i*h2
        d = hashlib.blake2b(item.encode(), digest_size=16).digest()
        h1, h2 = int.from_bytes(d[:8], "big"), int.from_bytes(d[8:], "big") | 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, item: str):
        for pos in self._positions(item):
            self.bits[pos >> 3] |= 1 << (pos & 7)

    def __contains__(self, item: str) -> bool:
        return all(self.bits[pos >> 3] & (1 << (pos & 7)) for pos in self._positions(item))


n, p = 100_000, 0.01
bf = BloomFilter(n, p)
for i in range(n):
    bf.add(f"user:{i}")

assert all(f"user:{i}" in bf for i in range(n))            # no false negatives, ever
trials = 200_000
fp = sum(f"other:{i}" in bf for i in range(trials))         # keys never inserted
theory = (1 - math.exp(-bf.k * n / bf.m)) ** bf.k
print(f"m = {bf.m:,} bits ({bf.m / 8 / 1024:.0f} KiB), k = {bf.k}")
print(f"false positives: measured {fp / trials:.3%}, theory {theory:.3%}")

# m = 958,506 bits (117 KiB), k = 7
# false positives: measured 0.988%, theory 1.004%

The measured rate matches the theory to within sampling noise, and 100,000 items cost 117 KiB. A Python set of the same 100,000 strings takes about 9 MB.

Deletion: counting Bloom filters and cuckoo filters

You cannot delete from a plain Bloom filter. Clearing an item's bits would also clear bits shared with other items (bit 11 in the step-through belongs to both alice and bob), and those items would then return false negatives, breaking the one guarantee the filter makes.

A counting Bloom filter replaces each bit with a small counter, typically 4 bits. Add increments the k counters, delete decrements them, and a query checks that all k are non-zero. The cost is 4 times the memory. Fan et al. showed that 4-bit counters overflow with negligible probability at sensible loads, but deleting an item that was never added still corrupts the filter, so deletes must be of items you know were inserted.

A cuckoo filter stores a short fingerprint of each item in one of two candidate buckets, moving existing fingerprints around cuckoo-hashing style when both are full. It supports deletion directly, and for false-positive rates below about 3% it uses less space than a Bloom filter. The catch is that inserts can fail when the table is nearly full, so it must be sized with headroom.

HyperLogLog: how many distinct items?

Counting distinct items, the cardinality of a set, exactly requires remembering every item seen, because you cannot tell a repeat from a new item otherwise. HyperLogLog estimates it from a few kilobytes no matter whether the true answer is a thousand or a billion.

The intuition: leading zeros

Hash every item to a uniformly random bit string. A hash starts with 0 half the time, with 00 a quarter of the time, and with r zeros followed by a 1 with probability 2-(r+1). So if the longest run of leading zeros you have seen is 20, you have probably hashed around a million distinct items: seeing a 1-in-221 pattern needs that many tries. Duplicates do not matter, because the same item always produces the same hash and cannot set a new record.

One such estimate is very noisy: a single lucky hash with 30 leading zeros makes it a billion. HyperLogLog fixes the noise with two moves.

  • Stochastic averaging. Use the first p bits of the hash to pick one of m = 2p registers, and the rest of the hash to compute a rank: the position of the first 1 bit. Each register keeps the largest rank it has seen. Each register is now an independent estimator over about 1/m of the items.
  • Harmonic mean. Combine registers with the harmonic mean of 2M[j], which damps the effect of the few registers that got an unusually high rank. Multiply by m (for the number of registers) and a bias-correcting constant α ≈ 0.7213 / (1 + 1.079/m).

When most registers are still 0 (small cardinalities), the formula is biased, so implementations switch to linear counting: with V empty registers, estimate m · ln(m/V). Google's HyperLogLog++ goes further with a 64-bit hash, an empirical bias-correction table, and a sparse representation that stores only non-zero registers while the count is small.

Error and memory

The relative standard error is 1.04 / √m. Each register needs only 6 bits: with a 64-bit hash and p = 14, the rank is at most 64 - 14 + 1 = 51, well under the 63 that 6 bits can hold. Quadrupling memory halves the error:

Redis uses p = 14: 16,384 six-bit registers, 12 KB per key in its dense encoding, 0.81% standard error. Standard error means about two thirds of estimates land within 0.81% of the truth and about 95% within 1.6%.

import hashlib
import math


class HyperLogLog:
    def __init__(self, p: int = 14):
        self.p, self.m = p, 1 << p                 # 2^14 = 16,384 registers
        self.reg = bytearray(self.m)               # one byte each here; Redis packs 6 bits
        self.alpha = 0.7213 / (1 + 1.079 / self.m)

    def add(self, item: str):
        x = int.from_bytes(hashlib.blake2b(item.encode(), digest_size=8).digest(), "big")
        idx = x >> (64 - self.p)                   # first p bits pick the register
        rest = x & ((1 << (64 - self.p)) - 1)      # remaining 50 bits
        rank = (64 - self.p) - rest.bit_length() + 1   # position of the first 1 bit
        self.reg[idx] = max(self.reg[idx], rank)

    def count(self) -> int:
        est = self.alpha * self.m ** 2 / sum(2.0 ** -r for r in self.reg)
        zeros = self.reg.count(0)
        if est <= 2.5 * self.m and zeros:          # small range: fall back to linear counting
            est = self.m * math.log(self.m / zeros)
        return round(est)


hll = HyperLogLog()
for n in range(1, 2_000_001):
    hll.add(f"visitor-{n}")
    if n in (1_000, 100_000, 2_000_000):
        print(f"true {n:>9,}  estimate {hll.count():>9,}  error {hll.count() / n - 1:+.2%}")
print(f"standard error 1.04/sqrt(m) = {1.04 / math.sqrt(hll.m):.2%}")

# true     1,000  estimate     1,000  error +0.00%
# true   100,000  estimate    99,842  error -0.16%
# true 2,000,000  estimate 2,004,223  error +0.21%
# standard error 1.04/sqrt(m) = 0.81%

Errors of 0.16% and 0.21% are well inside one standard error. At 1,000 items almost every register is empty, so the linear-counting branch is used, and it is close to exact.

Merging is the superpower

Two HyperLogLogs built with the same hash and the same m merge by taking the register-wise maximum. The result is exactly the sketch you would have built from the union of both streams. That makes them ideal for distributed counting and rollups:

  • Each of 50 web servers keeps its own sketch for a page; a central job merges them. No coordination per event.
  • Store one sketch per page per day. Monthly unique visitors is the merge of 30 daily sketches. Adding 30 daily unique counts would double-count everyone who visited on more than one day; merging does not.
  • Sketches are mergeable in any order and any grouping, so they work as pre-aggregated values in OLAP stores and stream processors (see Batch vs Stream Processing).
Intersections are not free

There is no register-wise operation for intersection. You can estimate |A ∩ B| = |A| + |B| - |A ∪ B|, but the absolute error of each term is relative to the large sets, so a small overlap between two big sets can come out wildly wrong or even negative. If you need set intersections, look at theta sketches (Apache DataSketches) instead.

Count-Min Sketch: how often has each item occurred?

A Count-Min Sketch estimates the frequency of any item in a stream. It is a grid of counters with d rows and w columns, and one independent hash function per row.

  • Add an item with count c: in every row, hash the item to a column and add c to that counter.
  • Estimate an item: read its counter in every row and return the minimum.

Every counter for an item includes all of that item's occurrences, plus whatever other items collided into the same cell. Collisions can only add, so each row overestimates, and the minimum is the row with the least collision noise.

Error bounds and sizing

Let N be the total of all counts added. Cormode and Muthukrishnan proved that with

w = ⌈e / ε⌉ columns d = ⌈ln(1/δ)⌉ rows the estimate â of any item with true count a satisfies a ≤ â ≤ a + ε·N with probability at least 1 - δ

For example, to keep the error under 0.05% of the stream with 99% confidence: ε = 0.0005 gives w = 5,437, and δ = 0.01 gives d = 5. That is 27,185 counters, about 106 KB at 4 bytes each, whether the stream has a thousand distinct keys or a hundred million. On a stream of one million page views the error bound is 500 views.

The error is relative to the whole stream, not to the item. An item seen 80,000 times with an error of up to 500 is measured well. An item seen 3 times can read as 300. So Count-Min Sketch is the right tool for finding and measuring heavy hitters, and a poor one for the long tail.

A cheap improvement is conservative update: on add, raise only the counters that are below the new estimate, instead of incrementing all d of them. It cuts overestimation noticeably on skewed data, at the cost of no longer supporting decrements.

Heavy hitters and top-k

A sketch answers "how often has x occurred?" but cannot list its keys, because it does not store them. To find the top k, pair it with a small candidate set: after each add, look up the item's estimate, and if it beats the smallest candidate, swap it in. Memory is the sketch plus k keys. This is the standard pattern for trending hashtags, most-requested URLs, top talkers in network traffic, and hot keys in a cache cluster. The autocomplete case study uses the same idea to keep popular queries per prefix.

The implementation below sizes a sketch for ε = 0.0005, δ = 0.01, feeds it a million page views drawn from a Zipf-like popularity curve over 200,000 URLs, checks the error bound against exact counts, and tracks the top 5 while streaming.

import hashlib
import math
import random
from collections import Counter


class CountMinSketch:
    def __init__(self, eps: float, delta: float):
        self.w = math.ceil(math.e / eps)           # columns: error <= eps * N
        self.d = math.ceil(math.log(1 / delta))    # rows: with probability >= 1 - delta
        self.rows = [[0] * self.w for _ in range(self.d)]

    def _cols(self, item: str):
        for r in range(self.d):
            h = hashlib.blake2b(item.encode(), digest_size=8, salt=r.to_bytes(16, "big")).digest()
            yield r, int.from_bytes(h, "big") % self.w

    def add(self, item: str, count: int = 1):
        for r, c in self._cols(item):
            self.rows[r][c] += count

    def estimate(self, item: str) -> int:
        return min(self.rows[r][c] for r, c in self._cols(item))   # never below the true count


random.seed(7)
urls = [f"/product/{i}" for i in range(200_000)]
weights = [1 / (rank + 1) for rank in range(len(urls))]           # Zipf-like popularity
stream = random.choices(urls, weights, k=1_000_000)

cms = CountMinSketch(eps=0.0005, delta=0.01)
top = {}                                   # candidate heavy hitters, at most K entries
K = 5
for url in stream:
    cms.add(url)
    est = cms.estimate(url)
    if url in top or len(top) < K:
        top[url] = est
    else:
        smallest = min(top, key=top.get)       # O(K) scan; use a heap for large K
        if est > top[smallest]:
            del top[smallest]
            top[url] = est

true = Counter(stream)
N = len(stream)
errors = [cms.estimate(u) - true[u] for u in urls]
assert min(errors) >= 0                                           # only ever overestimates
print(f"sketch: {cms.d} x {cms.w} = {cms.d * cms.w:,} counters vs {len(true):,} distinct keys")
print(f"bound eps*N = {0.0005 * N:.0f}; keys over it: {sum(e > 0.0005 * N for e in errors) / len(urls):.2%}")
print(f"mean overestimate {sum(errors) / len(errors):.1f}, max {max(errors)}")

for url, est in sorted(top.items(), key=lambda kv: -kv[1]):
    print(f"{url:13} estimate {est:6,}  true {true[url]:6,}")

# sketch: 5 x 5437 = 27,185 counters vs 120,865 distinct keys
# bound eps*N = 500; keys over it: 0.00%
# mean overestimate 46.0, max 373
# /product/0    estimate 77,858  true 77,826
# /product/1    estimate 39,333  true 39,291
# /product/2    estimate 26,146  true 26,101
# /product/3    estimate 19,747  true 19,720
# /product/4    estimate 15,676  true 15,648

No item exceeded the 500-view bound, the average overestimate was 46 views, and the streaming top 5 is exactly the true top 5, each within 0.2% of its real count. The exact Counter here is only for checking; in production it is what the sketch replaces.

In the real world

Bloom filters in storage engines

The most important production use of Bloom filters is in LSM-tree databases. A key can live in any of many immutable SSTable files on disk, so a point lookup for a key that is not in a file would cost a disk read per file. Each SSTable carries a Bloom filter of its keys, held in memory, and a lookup skips every file whose filter says no.

  • Apache Cassandra keeps a Bloom filter per SSTable, off the JVM heap, tunable per table with bloom_filter_fp_chance. Lowering it trades memory for fewer wasted disk reads on tables with many SSTables.
  • RocksDB (and LevelDB before it) builds a filter per SST file, configured in bits per key. RocksDB also offers Ribbon filters, which reach the same false-positive rate in about 30% less memory at some extra CPU cost.
  • HBase stores row-level Bloom filters in its store files, and PostgreSQL ships a bloom index extension for equality queries over many columns.

Other well-known uses

  • Redis: PFADD, PFCOUNT and PFMERGE implement HyperLogLog with 12 KB per key and 0.81% standard error, using a compact sparse encoding while the count is small. The RedisBloom module adds Bloom filters (BF.*), cuckoo filters (CF.*), Count-Min Sketch (CMS.*) and a top-k structure (TOPK.*).
  • Analytics engines: BigQuery's APPROX_COUNT_DISTINCT and HLL_COUNT functions use HyperLogLog++, and Spark, Presto/Trino, Druid and ClickHouse all offer approximate distinct counts built on HLL-style sketches. A dashboard of daily active users is almost always an HLL underneath.
  • CDNs: Akamai uses a Bloom filter to avoid caching "one-hit wonders", objects requested once and never again. An object is cached only on its second request, when the filter already contains it, which keeps disk space for content that will be reused. See CDNs.
  • Crawlers: a Bloom filter of seen URLs (or of content fingerprints) in front of the URL frontier, so the common case of "already seen" is answered from memory. See the web crawler case study.
  • Browsers: early versions of Chrome's Safe Browsing checked URLs against a local Bloom filter of hash prefixes of known-bad URLs, and only contacted Google on a "maybe". It was later replaced by a more compact prefix set, but the pattern (local probabilistic check, remote exact check) is unchanged.
  • Short links: the URL shortener uses a Bloom filter so bots probing random codes never reach the cache or the database.

When choosing, start from the question, then ask three more:

  • Which error direction can you live with? Bloom filters never miss a member; Count-Min never undercounts. Design the caller so that the safe direction is the one that matters.
  • Do you need to merge? Bloom filters, HLLs and Count-Min Sketches built with the same parameters merge cheaply, which is what makes them useful across shards, servers and time windows. Fix the parameters and hash function once, system-wide.
  • Is the set small enough to be exact? A million 8-byte ids is 8 MB. If an exact hash set fits comfortably, use it: no error, no tuning, deletes work. Probabilistic structures pay off at hundreds of millions of items, or when you keep thousands of independent sketches (one per page, per day, per customer).

Other structures worth knowing by name: quotient and xor filters (more compact static membership filters), theta sketches (distinct counts with set intersection and difference), and t-digest or DDSketch (approximate percentiles, the latency version of the same idea, used by metrics systems; see Observability).

Interview angle

When to bring it up

Whenever an exact set or counter would need memory proportional to a huge number of items, and an approximate answer is acceptable. Typical prompts: "has this crawler seen this URL", "skip disk reads for missing keys" (key-value store), "unique visitors per page per day", "trending topics in the last five minutes", "detect hot keys". State the error budget out loud: "a Bloom filter at 1% costs about 10 bits per URL, so 1.2 GB for a billion URLs, and a false positive only means we skip one new page".

Follow-ups to expect

  • Size this Bloom filter for n items at rate p. Give m = -n ln p / (ln 2)² and k = (m/n) ln 2, or the 10-bits-per-key shortcut.
  • Can you delete from it? No; counting Bloom filters or cuckoo filters can, at a memory cost.
  • What happens if more items arrive than planned? The false-positive rate rises sharply; rotate or chain filters.
  • How do you get monthly uniques from daily counts? Merge daily HLL sketches, never add daily counts.
  • Why does Count-Min take the minimum, and why is it bad for rare items? Collisions only add; the error is relative to the total stream.

Red flags

  • Saying a Bloom filter can return false negatives, or using its "yes" as a final answer where a wrong yes is harmful.
  • Reaching for a probabilistic structure when the exact set fits in a few megabytes.
  • Summing per-shard or per-day distinct counts instead of merging sketches.
  • Promising exact top-k from a sketch without saying the counts are upper bounds.
