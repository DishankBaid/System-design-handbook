Why it matters

Finance wants yesterday's revenue, exact to the cent, by 6 a.m. Operations wants revenue for the last minute, per region, on a wall screen, so they notice within seconds when checkout breaks in Brazil. Both are "sum the order amounts", but they are different problems: one has all of its data and can take an hour; the other never has all of its data and must answer now.

Batch processing runs a job over a bounded dataset (yesterday's files) and produces a complete result. Stream processing runs continuously over an unbounded sequence of events and produces results incrementally as data arrives. Batch is simpler and easier to get right. Streaming is faster but must deal with questions batch never asks: when is a minute "finished", what to do with an event that arrives ten minutes late, and how to survive a crash without counting anything twice.

Batch processing

The MapReduce model

Google's 2004 MapReduce paper gave large-scale batch processing its shape. The programmer writes two pure functions, and the framework handles distribution, scheduling and failures:

  1. Map. Each input split (a 128 MB chunk of a file, say) is read by a mapper that emits key-value pairs. For word count: for every word, emit (word, 1).
  2. Shuffle. The framework partitions pairs by hash(key), sends each partition to one reducer over the network, and sorts it so all values for a key are together. This is the expensive step: it moves data between machines and spills to disk.
  3. Reduce. Each reducer receives a key with all its values and emits the result: (word, sum(values)).

Fault tolerance comes from determinism: inputs are immutable and the functions are pure, so a failed or slow task is simply rerun on another machine, possibly twice in parallel (speculative execution), and the first result wins. That is the deep property of batch: a job can be rerun from scratch and produce the same output, so bugs are fixed by fixing the code and rerunning.

Spark and dataflow engines

Hadoop MapReduce wrote every intermediate result to disk, and a multi-step pipeline was a chain of separate jobs. Apache Spark generalised the model into a DAG of operators (map, filter, join, groupBy, aggregate) planned as a whole, keeps intermediate data in memory where it fits, and recovers lost partitions by recomputing them from their lineage rather than from replicated disk copies. Spark SQL and DataFrames added a query optimiser, so most batch jobs today are written as SQL or DataFrame code rather than map and reduce functions, on Spark, Trino, BigQuery, Snowflake or similar engines.

Data lakes and lakehouses

Batch jobs read from and write to a data lake: cheap object storage (S3, GCS, ADLS; see Blob & Object Storage) holding raw events and derived tables, usually in columnar Parquet files partitioned by date (s3://lake/orders/dt=2026-10-08/). Table formats such as Apache Iceberg, Delta Lake and Apache Hudi add a transactional metadata layer on top, giving atomic commits, schema evolution and time travel to plain files; this combination is often called a lakehouse. Partitioning by date is what makes daily jobs cheap: yesterday's job reads only yesterday's directory.

Stream processing

A stream processor (Apache Flink, Kafka Streams, Spark Structured Streaming, Google Dataflow) is a long-running job that consumes events, usually from a log such as Kafka (Pub/Sub & Event Streaming), keeps state, and emits results continuously. The hard parts all come from the input never ending.

Event time vs processing time

Every event has two timestamps. Event time is when it happened: the order was placed at 12:00:55. Processing time is when the stream job sees it: 12:01:26, because the phone was in a tunnel, a Kafka partition was lagging, or the job was restarting. The gap between them, the skew, is variable and unbounded.

Grouping by processing time is easy and wrong for most business questions: a restart that delays 10 minutes of events would show a dip followed by a spike in "revenue per minute" that never happened. Grouping by event time gives the true answer, but raises a new question: if events can arrive late, when can the job declare the 12:00 minute complete?

Windows

Aggregations over an infinite stream need a finite scope. A window assigns each event, by its event time, to one or more finite buckets:

Tumbling

Fixed size, no overlap, every event in exactly one window. "Revenue per minute." The default for dashboards and billing.

Sliding (hopping)

Fixed size, advancing by a smaller step, so windows overlap and an event belongs to several. "Requests in the last 30 seconds, updated every 10." Used for moving averages and rate alerts.

Session

Dynamic size, per key: a window stays open while events keep arriving within a gap, and closes after a period of inactivity. "A user's browsing session ends after 30 minutes idle."

Watermarks and late data

A watermark is the stream processor's estimate of event-time progress: a watermark of 12:01:05 asserts "I do not expect any more events with event time before 12:01:05". When the watermark passes the end of a window, the window fires and emits its result. Watermarks are generated at the sources, most often with a bounded-out-of-orderness heuristic: watermark = highest event time seen minus a fixed delay (10 seconds in the example).

The delay is a direct trade-off between latency and completeness. A 10-second delay emits each minute's result 10 seconds after the minute ends and misses events delayed by more. A 5-minute delay catches almost everything and makes the dashboard 5 minutes stale. Since no heuristic is perfect, engines offer three tools for events that arrive behind the watermark:

  • Allowed lateness. Keep a fired window's state for a while longer; a late event updates it and the window emits a corrected result. Downstream must accept updates (an upsert into a table, not an append).
  • Side outputs. Events later than the allowed lateness go to a separate stream instead of being silently dropped, so they can be counted, alerted on, or merged by a batch correction.
  • Triggers. Emit early, speculative results before the watermark (every 5 seconds of processing time), then the on-time result, then late corrections. Apache Beam formalises this as the what, where, when and how of the Dataflow model.

State and checkpointing

Windows, joins, deduplication and per-user counters all need state that lives across events. Stream processors keep it local to each parallel task, partitioned by key like the input (all events for region=BR go to the same task), in memory or in an embedded RocksDB instance when it is larger than memory. Local state is what makes streaming fast: no network call per event.

Local state must survive crashes. Flink takes periodic checkpoints using asynchronous barrier snapshotting, a variant of the Chandy-Lamport algorithm: the sources inject a barrier into the stream; when an operator has received the barrier on all inputs, it snapshots its state to durable storage (S3, HDFS) and forwards the barrier. A completed checkpoint is a consistent cut: the state of every operator plus the exact source offsets (Kafka partition offsets) that produced it. Kafka Streams does the equivalent differently: every state store change is also written to a compacted changelog topic, and a restarted task restores its store by replaying the changelog.

Exactly-once via checkpoints

On failure, Flink restores every operator from the last completed checkpoint and rewinds the sources to the offsets recorded in it. Events after the checkpoint are processed again, but against state that has not seen them, so the state reflects each event exactly once. The output is the remaining problem: results emitted between the checkpoint and the crash will be emitted again. Two ways to close the gap:

  • Idempotent sinks. Write results as upserts keyed by (window, key): writing "12:00 BR = $41,230" twice is harmless.
  • Transactional sinks. The sink writes into a transaction that commits only when the checkpoint completes (a two-phase commit coordinated with the checkpoint), for example Flink's Kafka sink using Kafka transactions, read with read_committed. Output becomes visible once per checkpoint interval, which adds latency equal to that interval.

As with Kafka, "exactly-once" means exactly-once effect on state and on cooperating sinks. A stream job that sends an email per event still needs idempotency at the email service.

A tumbling window with a watermark

The code implements event-time tumbling windows of one minute, a watermark trailing the highest event time by 10 seconds, 30 seconds of allowed lateness, and a side output for anything later. The events are orders arriving out of order; they are the dots in the skew chart above.

from collections import defaultdict

WINDOW = 60             # tumbling windows of 60 s of event time
MAX_DELAY = 10          # watermark = max event time seen - 10 s (bounded out-of-orderness)
ALLOWED_LATENESS = 30   # keep a fired window's state 30 s more of event time for late updates


def ts(sec):
    return f"12:{sec // 60:02d}:{sec % 60:02d}"


def run(events):
    sums = defaultdict(int)            # window start -> revenue in cents
    fired = set()
    watermark = -1
    for event_time, cents in events:   # events arrive in processing order, not event order
        start = event_time - event_time % WINDOW
        if start + WINDOW + ALLOWED_LATENESS <= watermark:
            print(f"  {ts(event_time)} ${cents / 100:.2f} too late, sent to side output")
            continue
        sums[start] += cents
        if start in fired:             # late but within allowed lateness: emit a correction
            print(f"  {ts(event_time)} late, window {ts(start)} updated to ${sums[start] / 100:.2f}")
        watermark = max(watermark, event_time - MAX_DELAY)
        for s in sorted(sums):
            if s not in fired and s + WINDOW <= watermark:
                fired.add(s)
                print(f"watermark {ts(watermark)}: window [{ts(s)}, {ts(s + WINDOW)}) = ${sums[s] / 100:.2f}")
            if s + WINDOW + ALLOWED_LATENESS <= watermark:
                del sums[s]            # state is freed for good
                fired.discard(s)
    for s in sorted(set(sums) - fired):    # end of input: the watermark jumps to infinity
        print(f"end of input: window [{ts(s)}, {ts(s + WINDOW)}) = ${sums[s] / 100:.2f}")


# (event time in seconds after 12:00:00, order value in cents), in arrival order
run([(5, 2000), (12, 3500), (58, 1500), (61, 4000), (49, 1000), (75, 2500), (71, 500),
     (55, 3000), (130, 5000), (52, 9900), (185, 1000)])

Output:

watermark 12:01:05: window [12:00:00, 12:01:00) = $80.00
  12:00:55 late, window 12:00:00 updated to $110.00
watermark 12:02:00: window [12:01:00, 12:02:00) = $70.00
  12:00:52 $99.00 too late, sent to side output
end of input: window [12:02:00, 12:03:00) = $50.00
end of input: window [12:03:00, 12:04:00) = $10.00

Walk through it. The 12:00:49 order arrives after 12:01:01 but before the watermark reaches 12:01:00, so it lands in the first window on time. The window fires when the 12:01:15 event pushes the watermark to 12:01:05. The 12:00:55 order arrives after that, but within the allowed lateness, so the window is corrected from $80 to $110. Once the watermark passes 12:01:30 (window end plus lateness), the window's state is deleted, and the 12:00:52 order is diverted to the side output. A batch job over the full day would have counted it, which is exactly the kind of discrepancy the worked example below has to deal with.

Micro-batching

Between batch and true streaming sits micro-batching: run a small batch job every few hundred milliseconds or seconds over whatever arrived since the last one. Spark Streaming introduced it, and Spark Structured Streaming still uses it by default. It reuses the batch engine's fault tolerance (a failed micro-batch is just rerun) and gets good throughput from batching, at the cost of latency at least equal to the batch interval plus scheduling overhead. For a dashboard that refreshes every 10 seconds, micro-batching is fine. For fraud scoring inside a 100 ms payment authorisation, it is not.

The distinction is blurring: true streaming engines batch internally for throughput (network buffers, bundled state writes), and micro-batch engines have shrunk their intervals. The useful question is the end-to-end latency you need, not the label.

Lambda vs Kappa architectures

Around 2011, stream processors were fast but could not be trusted to be exact, and batch was exact but slow. Nathan Marz's Lambda architecture ran both: a batch layer recomputes complete views from all historical data, a speed layer covers the hours since the last batch run with approximate streaming results, and a serving layer merges the two at query time.

Jay Kreps' 2014 critique proposed the Kappa architecture: if the stream processor can be exact (event time, watermarks, exactly-once state) and the log retains enough history, one streaming code path is enough. To reprocess after a bug fix or logic change, start a second instance of the job reading the log from the beginning into a new table, and switch readers over when it catches up.

Today most teams land in between: streaming for operational, low-latency outputs; scheduled batch over the lake for finance-grade numbers, backfills, and machine learning training sets; and unified APIs (Apache Beam, Flink's Table API, Spark's DataFrames) so the logic is written once even when it runs in two modes.

A good default: use batch unless someone will act on the result within minutes. Alerting, fraud detection, live dashboards, real-time personalisation and keeping search indexes fresh justify streaming. Monthly reports, billing, reconciliation and model training rarely do.

Worked example: real-time and daily revenue dashboards

A retailer takes 2 million orders a day across 50 regions, peaking at 10 times the average rate during sales. Operations wants revenue per region per minute on a live screen. Finance wants the daily total per region, exact, by 6 a.m. Assume (from the mobile team's metrics) that 0.5% of orders reach the backend more than 30 seconds after they were placed, mostly from apps that were offline, and a few arrive hours later.

Orders 2,000,000 / 86,400 s ≈ 23/s average, ~230/s peak Raw events 2M × 1 KB = 2 GB/day into Kafka and the lake Live windows 1-minute tumbling × 50 regions = 72,000 results/day (1,440 × 50) State ~12 windows (current + 10 min lateness) × 50 regions → kilobytes; a single Flink task could hold it Watermark delay 30 s → each minute appears ~30 s after it ends Late events 0.5% beyond 30 s ≈ 10,000 orders/day go to the update path Allowed lateness 10 min; anything later goes to the side output Daily batch read 2 GB of Parquet for one date → a few minutes on a small Spark cluster

The resulting design:

  1. Live path. Orders flow from the order service's outbox into Kafka, keyed by region. A Flink job assigns event-time one-minute windows, with a 30-second watermark delay and 10 minutes of allowed lateness, and upserts (region, minute) → revenue into a serving table that the dashboard polls. Late corrections overwrite the earlier value, so the chart quietly fixes itself.
  2. Side output. Orders later than 10 minutes go to a late-orders topic. The dashboard does not show them; an alert fires if their rate exceeds a threshold, because a spike usually means an upstream outage.
  3. Daily batch. At 01:00, once the lake partition for the previous day is closed, a Spark job computes the daily totals from the raw events, including every late order, refunds and currency conversion at the official daily rate. This is the number finance reports.
  4. Reconciliation. A check compares the stream's daily sum with the batch result per region and alerts if they differ by more than 0.5%. Small differences are expected (late orders, refunds); large ones indicate a bug in one of the paths.

Two consequences are worth saying in an interview. The live number is operationally correct, good enough to spot a 30% drop within a minute, and is explicitly not the financial number. And this is a Lambda-shaped system, deliberately: the batch path exists not because streaming is unreliable but because finance's definition of revenue (refunds, FX, accounting cut-offs) differs from operations', and a daily rerunnable job is the simplest way to compute it exactly.

In the real world

  • Google published MapReduce (2004), then FlumeJava and MillWheel, combined into Cloud Dataflow, whose model became Apache Beam: one API for batch and streaming with explicit event time, windows, watermarks and triggers.
  • Apache Spark replaced Hadoop MapReduce as the default batch engine and serves both batch and micro-batch streaming from the same DataFrame API, used widely through Databricks and cloud services such as EMR and Dataproc.
  • Apache Flink is the most widely used true stream processor for large stateful jobs; Alibaba, Uber and Netflix are among the companies that have described large Flink deployments.
  • Kafka Streams and ksqlDB keep stream processing inside the Kafka ecosystem, with state stores backed by changelog topics and exactly-once via Kafka transactions.
  • Lakehouse table formats (Iceberg, Delta Lake, Hudi) let streaming jobs write into the same tables that batch jobs read, which is how many teams run Lambda-style designs without two separate storage systems.
Interview angle

When to bring it up

Whenever the design includes analytics, counters, leaderboards, trending lists or anything computed over many events: clicks in the URL shortener, trending queries in autocomplete, view counts in the video platform. Say which outputs need streaming and which can be batch, and why. Mentioning event time and late data unprompted is a strong signal.

Follow-ups to expect

  • Event time or processing time? What happens when the job restarts after 10 minutes down?
  • How do you handle events that arrive late? (Watermark delay, allowed lateness, side output, batch correction.)
  • How do you get exactly-once counts? (Checkpoints with source rewind, plus idempotent upserts or transactional sinks.)
  • You found a bug in the aggregation. How do you fix last month's numbers? (Rerun the batch job, or replay the log into a new table in Kappa.)
  • Lambda or Kappa, and what does each cost to operate?

Red flags

  • Windowing by processing time for business metrics, without acknowledging the distortion.
  • Assuming events arrive in order, or that all events for a minute have arrived when the wall clock passes the minute.
  • Proposing a streaming pipeline for a report that someone reads once a month.
  • Claiming end-to-end exactly-once without saying how the sink handles replays.
