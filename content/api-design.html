Why it matters

An API is the one part of a system you cannot quietly change. Once a mobile app version, a partner's batch job or another team's service depends on a response shape, that shape is a promise. Internal code can be refactored on a Tuesday afternoon; a published API carries its mistakes for years, because some client still running a 2023 build will break the day you fix them.

API design is two jobs: choosing a style (REST, gRPC or GraphQL) that fits who calls you, and getting the cross-cutting contracts right from day one: paging, errors, safe retries, slow work, and growth without breakage.

REST: resources and a uniform interface

REST (Representational State Transfer) models the API as a set of resources, each with a URL, manipulated through the small fixed set of HTTP methods. The URL names a thing; the method says what to do with it.

GET    /v1/users/42                 read one user
GET    /v1/users/42/posts?limit=20  list a user's posts
POST   /v1/users/42/posts           create a post (server assigns the id)
PUT    /v1/posts/9817               replace post 9817 entirely
PATCH  /v1/posts/9817               change some fields of post 9817
DELETE /v1/posts/9817               delete it

Resource names are plural nouns, ids are opaque strings, and nesting stops at one level (/users/42/posts, not /users/42/posts/9817/comments/3/likes). Actions that do not map onto a noun, such as "cancel this order", become either a state change (PATCH /orders/7 {"status": "cancelled"}) or a sub-resource (POST /orders/7/cancellation). Google's guidelines also allow a custom verb, POST /orders/7:cancel.

Safe and idempotent methods

HTTP defines two properties per method that clients, proxies and retry libraries rely on. A safe method does not change server state, so crawlers and prefetchers may call it freely. An idempotent method has the same effect whether it is applied once or ten times, so a client that timed out can simply send it again.

MethodSafeIdempotentWhy
GET, HEADYesYesReads only
PUTNoYes"Set post 9817 to this": the second identical PUT changes nothing
DELETENoYesThe post stays deleted; a repeat may return 404, but the state is the same
POSTNoNo"Create a post": two calls create two posts
PATCHNoDepends{"title": "x"} is idempotent; {"op": "increment"} is not

This table is why payment and order creation, which are POSTs, need idempotency keys: they are exactly the calls you most want to retry and least want to duplicate.

Status codes that carry meaning

Clients branch on the status code before they read the body, so pick codes that tell them what to do next. The classes are the important part: 2xx done, 4xx the client must change something before retrying, 5xx the server failed and a retry may work.

CodeUse it forClient should

201 CreatedPOST created a resource; include LocationStore the new id
202 AcceptedWork queued, not done (see long-running operations)Poll or wait for a callback

The classic mistake is returning 200 {"success": false}. Every load balancer, retry library, dashboard and alert keys off the status code, and all of them now think the call worked.

gRPC: typed RPC over HTTP/2

gRPC drops the resource model and exposes methods. You describe services and messages in a .proto file, and a compiler generates client stubs and server interfaces in each language. Calling a remote service looks like calling a local function, with types checked at compile time on both sides.

syntax = "proto3";

service UserService {
  rpc GetUser(GetUserRequest) returns (User);                       // unary
  rpc WatchPosts(WatchPostsRequest) returns (stream Post);          // server streaming
  rpc UploadEvents(stream ClickEvent) returns (UploadSummary);      // client streaming
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);        // bidirectional
}

message User {
  int64  id        = 1;
  string name      = 2;
  string email     = 3;
  int64  followers = 4;
  reserved 5;            // was "phone"; the number is never reused
}

Protobuf on the wire

Protocol Buffers encode each field as a field number plus a value, not as a field name. Small integers become one or two bytes (varints) and strings are length-prefixed. Encoding {id: 42, name: "Ada Lovelace", email: "ada@example.com", followers: 18422} by hand gives 37 bytes of protobuf against 75 bytes of compact JSON, and parsing binary fields is far cheaper than parsing text. The field numbers are the contract: renaming a field is free, but changing or reusing a number silently corrupts data for old clients, which is why removed fields are marked reserved.

HTTP/2 and the four call types

gRPC runs on HTTP/2, where every call is a stream multiplexed over one long-lived TCP connection. That makes streaming a first-class feature: the proto above shows all four shapes. Unary is ordinary request/response. Server streaming suits feeds and watch APIs, client streaming suits uploads of many small events, and bidirectional streaming suits chat or live collaboration.

The long-lived connection has a cost that bites in production. A layer-4 load balancer balances connections, so once a client has opened its one connection, every request goes to the same backend, and new backends get no traffic. gRPC needs request-level balancing: an L7 proxy such as Envoy, or client-side balancing over a list from service discovery. See Load Balancing.

Deadlines

Every gRPC call should carry a deadline: an absolute time by which the caller stops caring. It travels in the grpc-timeout header, and a well-behaved server passes the remaining time on to the calls it makes downstream. If the user-facing request has 300 ms left and the first hop used 120 ms, the second hop gets 180 ms, not a fresh timeout of its own. When time runs out every service in the chain stops work for that request and returns DEADLINE_EXCEEDED. Most gRPC libraries set no deadline by default, which means a stuck backend holds the caller's resources forever. Always set one. Timeouts, Retries & Circuit Breakers covers the budgeting.

Browsers cannot speak raw gRPC (page JavaScript cannot read HTTP/2 trailers), so browser clients need gRPC-Web and a translating proxy. In practice gRPC dominates service-to-service traffic.

GraphQL: the client chooses the shape

GraphQL exposes one endpoint and a typed schema of the whole data graph. The client sends a query naming exactly the fields it wants, nested as deeply as the schema allows, and gets back JSON in the same shape. Facebook built it in 2012 for its mobile apps, where one screen needed data from many resources and every round trip on a phone network was expensive.

type User { id: ID!  name: String!  email: String  posts(first: Int, after: String): PostConnection! }
type Post { id: ID!  title: String!  author: User! }
type Query { user(id: ID!): User }

# the client's query
query ProfileCard {
  user(id: "42") {
    name
    posts(first: 3) { edges { node { title } } }
  }
}

Resolvers and the N+1 problem

The server executes a query by calling a resolver function per field. user has a resolver that loads a user; posts has a resolver that loads the posts of whichever user it is given. This composes nicely and hides a trap. A query for 10 users with their posts runs the users resolver once and then the posts resolver once per user: 11 database queries. A list of 100 users with posts and each post's comments can fan out into thousands.

The standard fix is DataLoader, a small batching and per-request caching layer. Resolvers call loader.load(userId) instead of querying directly. The loader waits until the current tick of execution finishes, sends one batched query for every id requested, and resolves each promise with its own rows. Query count drops from 1 + N to 1 + 1 per level of nesting.

Caching, cost and persisted queries

Letting clients write arbitrary queries creates problems REST does not have:

  • HTTP caching is lost. Queries are usually POSTs to /graphql, so CDNs and browser caches see nothing cacheable. Caching moves into the client (normalized caches like Apollo's) and the server's data loaders.
  • Cost is unbounded. One deeply nested query can do more work than a thousand REST calls. Servers enforce depth limits and compute a query cost from the shape before running it; GitHub and Shopify rate-limit their GraphQL APIs by points derived from that cost rather than by request count.
  • Persisted queries address both. With trusted (persisted) documents, the client registers its queries at build time and at runtime sends only an id or hash. Apollo's automatic persisted queries (a SHA-256 of the query text, registered at runtime on first use) give the same bandwidth and caching benefit but no allowlist, because any query can register itself. Requests become small, can go over GET and hit a CDN, and the server can refuse any query not on its allowlist, which shuts the door on expensive ad-hoc queries from attackers.

Note that a GraphQL response is often 200 OK with partial data plus an errors array, so monitoring that watches only status codes misses failures.

Pagination

Any endpoint that returns a list must be paged from the first release, with a default and a maximum page size (say 20 and 100). Adding paging later is a breaking change, and an unpaged list is a denial-of-service waiting for the table to grow.

Offset pagination and why it degrades

-- GET /posts?limit=20&offset=100000
SELECT id, created_at, title
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;

Offset is easy to build and lets the UI jump to page 5,000. It has two problems. First, the database cannot skip rows it has not read. Even with an index on the sort columns, it walks 100,020 index entries and throws 100,000 away, so page 5,001 costs about 5,000 times as much as page 1. Second, pages shift under concurrent writes. If a new post arrives between the client fetching page 1 and page 2, every row moves down one place, and the last row of page 1 shows up again at the top of page 2. A deletion does the opposite and a row is silently skipped.

Keyset (cursor) pagination

Keyset pagination, also called seek pagination, remembers where the previous page ended instead of how many rows came before. The next query asks for rows strictly after that point in sort order:

-- index: CREATE INDEX posts_feed ON posts (created_at, id);
-- GET /posts?limit=20&cursor=eyJjIjoxNzAxMDAwMDAxLCJpIjo5ODgxfQ
SELECT id, created_at, title
FROM posts
WHERE (created_at, id) < (1701000001, 9881)   -- last row of the previous page
ORDER BY created_at DESC, id DESC
LIMIT 20;

The database seeks straight to the cursor position in the B-tree and reads 20 entries, whatever the page number. The id tiebreaker matters: created_at alone is not unique, and two posts in the same second would be skipped or repeated at a page boundary. The sort key must be unique, and every column in it must be in the index in the same order.

The script below measures both on a one-million-row SQLite table with the right index, and then reproduces the duplicate-row bug.

import sqlite3
import time

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE posts (id INTEGER PRIMARY KEY, created_at INTEGER, title TEXT)")
db.executemany("INSERT INTO posts VALUES (?, ?, ?)",
               ((i, 1_700_000_000 + i, f"post {i}") for i in range(1, 1_000_001)))
db.execute("CREATE INDEX posts_feed ON posts (created_at, id)")

OFFSET = "SELECT created_at, id FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET ?"
KEYSET = ("SELECT created_at, id FROM posts WHERE (created_at, id) < (?, ?) "
          "ORDER BY created_at DESC, id DESC LIMIT 20")


def best_us(sql, args):
    times = []
    for _ in range(5):
        t = time.perf_counter()
        rows = db.execute(sql, args).fetchall()
        times.append(time.perf_counter() - t)
    return min(times) * 1e6, rows


for skip in (20, 10_000, 100_000, 900_000):
    cursor = db.execute(OFFSET.replace("20 OFFSET", "1 OFFSET"), (skip - 1,)).fetchone()
    off_us, rows = best_us(OFFSET, (skip,))
    key_us, same = best_us(KEYSET, cursor)   # cursor = last row of the previous page
    assert rows == same
    print(f"skip {skip:>7,}: OFFSET {off_us:8.0f} us   keyset {key_us:4.0f} us")

# Offset pages shift when a row is inserted between two requests
page1 = db.execute(OFFSET, (0,)).fetchall()
db.execute("INSERT INTO posts VALUES (1000001, 1701000001, 'new post')")
page2 = db.execute(OFFSET, (20,)).fetchall()
print("duplicate across pages:", set(page1) & set(page2))
page2_keyset = db.execute(KEYSET, page1[-1]).fetchall()
print("keyset duplicates:", set(page1) & set(page2_keyset))

# One run on a laptop:
# skip      20: OFFSET        3 us   keyset    3 us
# skip  10,000: OFFSET       31 us   keyset    3 us
# skip 100,000: OFFSET      275 us   keyset    3 us
# skip 900,000: OFFSET     2605 us   keyset    3 us
# duplicate across pages: {(1700999981, 999981)}
# keyset duplicates: set()

Offset cost grows linearly with depth, nearly 900 times slower at row 900,000 than at the start, while keyset stays flat. This is a small table held entirely in memory; on a real database where the skipped entries come off disk and compete with other queries, deep offsets turn into multi-second queries that a scraper can trigger on purpose.

Designing the cursor

  • Make it opaque. Encode the sort values as base64 JSON ({"c":1701000001,"i":9881}) and return it as next_cursor. Clients must not parse it, which leaves you free to change what is inside. Sign or encrypt it if it would reveal anything sensitive.
  • Bind it to the query. A cursor issued for sort=-created_at&status=open is meaningless for another sort. Include them in it, or reject mismatches with 400.
  • Signal the end with a missing or null next_cursor, not with a short page. Skip total_count unless the product needs it: an exact COUNT(*) over a large filtered set costs more than the page itself.
  • Accept the trade. Keyset cannot jump to page 5,000. That suits feeds, infinite scroll and exports; admin tables with numbered pages can keep offset with a capped depth.

Filtering and sorting

Keep the grammar flat and boring: one query parameter per filter, explicit ranges and a single sort parameter with a minus sign for descending.

GET /v1/orders?status=open&created_after=2026-10-01T00:00:00Z&sort=-created_at&limit=50

The important rule is server-side: only allow filters and sorts that an index supports. Each allowed combination is a query plan you have committed to keep fast forever. When users genuinely need free-form search, give them a separate search endpoint backed by a search engine; see Search & Inverted Indexes.

Versioning

Most API changes should not need a new version at all (see evolution rules). Versions exist for the rare change that cannot be made additive. The strategies differ in where the version lives and how often it changes.

StrategyExampleStrengthWeakness
URL path/v1/orders, /v2/ordersVisible, easy to route and to cacheCoarse: a whole new surface for one breaking change
Header / media typeAccept: application/vnd.shop.v2+jsonClean URLs; versions per representationInvisible in logs and links; easy to forget
Date-pinnedStripe-Version: 2024-06-20Small, frequent changes; each account stays on its version until it upgradesServer must translate between every supported version
None (evolve only)GraphQL with @deprecatedOne schema; usage data shows when a field can goNeeds discipline and field-level usage tracking

Stripe's model is worth knowing: every account is pinned to the API version current when it made its first call, and the latest code internally runs a chain of small "version change" transformations to produce each older shape. GitHub's REST API uses a dated header too (X-GitHub-Api-Version: 2022-11-28). In an interview, URL major versions plus strictly additive evolution is the simple, safe answer.

Whatever the scheme, retire old versions deliberately: announce a date, return Deprecation (RFC 9745) and Sunset (RFC 8594) headers on old calls, and contact the callers still using them.

Error contract: problem details

Every error from every endpoint should have the same shape, so clients write one error handler. RFC 9457 (which replaced RFC 7807) standardizes one, served as application/problem+json:

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.shop.example/problems/insufficient-stock",
  "title": "Not enough stock",
  "status": 422,
  "detail": "Only 2 units of SKU TS-0042 are available; 5 were requested.",
  "instance": "/v1/orders/ord_7Qx2/lines/1",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "available": 2
}
  • type is the stable, machine-readable identifier clients branch on. It is a URI that can point to documentation. title is a short human summary for that type, and detail explains this occurrence.
  • Extension members such as available carry data the client can act on, for example to offer "buy 2 instead". Validation errors usually add a list of field-level problems.
  • Include a request or trace id, so a support ticket can be matched to logs. Never include stack traces, SQL or internal host names.

gRPC's equivalent is a status code (INVALID_ARGUMENT, UNAVAILABLE, ...) plus structured details in the trailers; map between the two consistently at the edge.

Idempotency keys for unsafe retries

A client sends POST /v1/payments, the server charges the card, and the response is lost to a network blip. The client cannot tell "never arrived" from "succeeded but the reply was lost". Retrying risks a double charge; not retrying risks a lost order.

The fix is an idempotency key: the client generates a unique value (a UUID) per logical operation and sends it as Idempotency-Key: 5d1f6a0e-.... The server records the key with the outcome, and a retry with the same key returns the stored response instead of charging again. Stripe popularized the pattern and an IETF draft standardizes the header. Storage, concurrent duplicates, request fingerprints and expiry are covered in Idempotency & Delivery Semantics. For API design the rule is simple: every non-idempotent endpoint that moves money or creates something users care about accepts an idempotency key.

Long-running operations

Some requests take longer than any sane HTTP timeout: exporting a year of orders, transcoding a video, provisioning a database. Holding a connection open for minutes breaks on proxy timeouts and network switches and leaves the client unsure whether the work happened. Instead, accept the work, return at once, and give the client a resource to watch.

  • The operation is a resource with a status (PENDING, RUNNING, SUCCEEDED, FAILED, CANCELLED), optional progress, creation time, and a result link or error. Google's API design guide (AIP-151) defines exactly this as an Operation with a done flag and either a response or an error.
  • Make submission idempotent. A client that loses the 202 and retries should get the same operation back, not start a second export. An idempotency key on the POST does it.
  • Allow cancellation (POST /v1/operations/op_7Qx:cancel) and expire finished operation records after a retention period, such as seven days.
  • Bound the polling. Retry-After tells well-behaved clients how long to wait; rate limits handle the rest.

Webhooks

A webhook is an HTTP callback: when an event happens, your system POSTs it to a URL the customer registered. It is how Stripe tells merchants a payment succeeded and GitHub tells CI a branch was pushed. Design for receivers that are slow, down or malicious.

  • Deliver at least once. Send from a queue, retry failures with exponential backoff over hours or days, and disable endpoints that keep failing. Because retries happen, the same event can arrive twice: include a unique event id so receivers can deduplicate.
  • Do not promise order. Retries reorder events. Either include a version or timestamp so the receiver can drop stale updates, or send thin events ("invoice in_4410 changed") and let the receiver fetch the current state from the API.
  • Receivers acknowledge fast. Return 2xx as soon as the event is stored, then process it asynchronously. Slow handlers cause timeouts and therefore duplicate deliveries.
  • Sign every delivery. The receiver's URL is public, so anyone can POST to it. Sign the body plus a timestamp with a per-endpoint secret, and have receivers reject bad signatures and old timestamps.
import hashlib
import hmac
import time

SECRET = b"whsec_5f1c9a7e2b"     # shared once, when the customer registers the endpoint
TOLERANCE = 300                  # seconds; rejects replays of old deliveries


def sign(body: bytes, ts: int) -> str:
    mac = hmac.new(SECRET, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    return f"t={ts},v1={mac}"


def verify(body: bytes, header: str, now: float) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    ts = int(parts["t"])
    if abs(now - ts) > TOLERANCE:
        return False
    expected = sign(body, ts).split("v1=")[1]
    return hmac.compare_digest(expected, parts["v1"])   # constant-time compare


body = b'{"id":"evt_81F","type":"invoice.paid","data":{"invoice":"in_4410"}}'
header = sign(body, int(time.time()))
print(verify(body, header, time.time()))                         # True
print(verify(body.replace(b"4410", b"9999"), header, time.time()))  # False: body tampered
print(verify(body, header, time.time() + 3600))                  # False: replayed an hour later

The timestamp is inside the signed bytes, so an attacker who captured one delivery cannot replay it later with a fresh timestamp. Receivers must verify the raw request bytes, not re-serialized JSON. Stripe's Stripe-Signature header uses this same t=...,v1=... layout.

Evolving an API without breaking clients

Clients are deployed on their own schedules, and some are never updated. The working rule is: only make additive changes, and make clients tolerant readers that ignore fields they do not recognize.

ChangeSafe?Why
Add a new endpoint or methodSafeNobody calls it yet
Add an optional request field or query parameterSafeOld clients do not send it; the default preserves old behaviour
Add a field to a responseSafeTolerant readers ignore it (strict schema validators on the client do not)
Add a value to an enum in a responseRiskyClients with an exhaustive switch crash on the unknown value; document that enums may grow
Make an optional request field requiredBreakingOld clients do not send it and now get 400
Remove or rename a fieldBreakingClients reading it get nothing
Change a field's type or meaningBreaking"amount": 1000 going from cents to dollars corrupts data silently
Change defaults, error codes, or validation strictnessBreakingClients depend on observed behaviour, not just the documented schema

Renaming is done by expansion and contraction: add the new field, write both, migrate clients, watch usage of the old field fall to zero, then remove it in the next major version. The same discipline appears in protobuf (never reuse a field number), in GraphQL (@deprecated(reason: "...") plus per-field usage metrics) and in database migrations; see Data Modeling.

In the real world

  • Stripe: resource-oriented REST with date-pinned versions, idempotency keys on POSTs, cursor pagination via starting_after (an object id) and signed webhooks.
  • GitHub: a REST API with dated versions alongside a public GraphQL API, rate-limited by a points budget computed from each query's cost rather than by request count.
  • Google: gRPC (2015) is the open-source successor to its internal Stubby RPC. Its API Improvement Proposals codify custom methods (:cancel), page_token pagination and long-running operations.
  • Facebook and Netflix: Facebook open-sourced GraphQL in 2015. Netflix runs a federated GraphQL gateway in which each domain service owns part of the schema.
  • Slack: Web API list methods use cursor pagination, returning response_metadata.next_cursor.
Interview angle

When to bring it up

Every design question has an API step after requirements. Write three to five endpoints with methods, key parameters and response codes, and say which style you chose and why ("REST for the public API, gRPC between internal services"). Mention pagination and write idempotency without being asked. In the URL shortener case, the 301 vs 302 choice is an API decision with product consequences.

Follow-ups to expect

  • Why is page 10,000 slow, and how do you fix it? Offset walks and discards rows; keyset seeks to the cursor.
  • The client timed out on a payment POST. Can it retry safely? Only with an idempotency key.
  • REST, gRPC or GraphQL for this system? Tie the answer to the callers: browsers, mobile, internal services, third parties.
  • How do you handle a 10-minute report? 202 Accepted, an operation resource, polling with Retry-After or a webhook.
  • How do you change a response field without breaking old mobile apps? Additive change, deprecation, usage tracking, then removal.
  • GraphQL is slow on lists. Why? N+1 resolvers; batch with DataLoader and cap query cost.

Red flags

  • Verbs in REST paths (/getUser, /createOrder) and 200 responses that contain errors.
  • List endpoints with no pagination, or offset pagination on an infinite feed.
  • Retrying non-idempotent POSTs blindly, or no retry story at all.
  • Holding an HTTP request open for minutes of work.
  • Renaming fields in place and calling it a minor release.
