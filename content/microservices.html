Why it matters

An online shop starts as one codebase with one database. Two years later it has 120 engineers, a 40-minute test suite, and a deploy train that leaves twice a week. A bug in the recommendations code blocks a checkout fix from shipping. Black Friday traffic hits search hard while checkout sits idle, but the only way to scale either is to run more copies of everything.

Splitting the system into separately deployed services fixes some of these problems and creates new ones: every function call that becomes a network call can now be slow, fail halfway, or arrive twice, and data that used to live in one transaction is now spread across several databases. The architecture question in an interview is rarely "monolith or microservices?" in the abstract. It is "where exactly would you cut this system, and what does each cut cost you?"

Three ways to structure a system

Monolith

One codebase, built and deployed as one unit, usually with one database. Modules call each other in-process. Nothing stops any code from touching any table.

Modular monolith

Still one deployable and usually one database, but split into modules with explicit public interfaces and private internals. Each module owns its tables. Boundaries are enforced by tooling, not by the network.

Microservices

Many small services, each deployed independently, each owning its data, talking over the network through APIs and events. Each service is owned by one team.

These are points on a spectrum, not three boxes. Plenty of healthy systems are a large modular monolith plus a handful of services split out for a specific reason: a search service on different hardware, a video transcoder that needs GPUs, a payments service under stricter compliance rules.

What splitting buys you

Every real benefit of microservices comes from independence. If a split does not make something independent, it only adds network hops.

  • Independent deploys. The checkout team ships a fix at 14:05 without waiting for the search team's release, and a bad deploy rolls back one service, not the whole product. This is the benefit that matters most in practice, because deploy coordination is what slows large teams down first.
  • Independent scaling. Search needs 60 CPU-heavy instances during a sale; account settings needs 3. In a monolith you scale the whole binary, including the code that is idle. Separate services also let you pick different hardware (GPUs, memory-heavy nodes) per workload. See Scalability.
  • Fault isolation. A memory leak in the recommendations service kills recommendation pods, not checkout. This only holds if callers treat the failing service as optional, with timeouts and fallbacks (see below).
  • Team autonomy. A team owns a service end to end: code, schema, on-call, release schedule and, within limits, language and libraries. Fewer people need to agree before anything ships.
  • Smaller blast radius for change. A service with 20,000 lines of code is easier to understand, test and rewrite than a 2-million-line application.

Conway's law

Conway's law (Melvin Conway, 1968) says that a system's design ends up mirroring the communication structure of the organisation that builds it. Four teams building a compiler produce a four-pass compiler. The practical reading for microservices runs in both directions:

  • Service boundaries that cut across team boundaries cause constant cross-team coordination, which is exactly what services were meant to remove.
  • The inverse Conway manoeuvre: design the team structure you want first (for example one team per business capability), and the architecture tends to follow.

This is why microservices are as much an organisational choice as a technical one. With eight engineers, there is no coordination problem to solve, and the costs below arrive with none of the benefits.

What distribution costs you

A function call inside a process takes nanoseconds, never gets lost, and either returns or throws. A network call takes milliseconds, can time out with no way to tell whether the other side acted, and can be retried into a duplicate. Moving to microservices turns thousands of the first kind into the second kind.

Network calls

Each hop adds serialization, a network round trip and often TLS, typically 0.5 to 5 ms inside a data centre. A page that makes 30 internal calls pays that 30 times unless the calls run in parallel.

Partial failure

Some services are up, some are down, some are slow. A slow dependency is worse than a dead one, because it ties up threads and connections in every caller. You need timeouts, retries with backoff and circuit breakers everywhere (Timeouts, Retries & Circuit Breakers).

Distributed data

Placing an order, charging a card and reserving stock used to be one ACID transaction. Now it spans three databases, so you need sagas, outboxes and idempotent handlers (Distributed Transactions), and you live with eventual consistency.

Observability

One user request touches ten services, each with its own logs. Without distributed tracing and a shared correlation id, "why was this checkout slow?" has no answer (Observability).

Operational load

Hundreds of deploy pipelines, dashboards, alert rules, dependency upgrades and on-call rotations. You need a platform: container orchestration, service discovery, config, secrets and a gateway.

Contract management

An in-process refactor is one commit. Changing an API used by six other services means versioning, backward compatibility and coordinated rollout (API Design).

The math of a call chain

When a request needs every service in a chain to succeed, availabilities multiply. Five services that are each up 99.9% of the time give a chain that is up 0.9995 ≈ 99.5% of the time. That looks close, but it is five times the downtime.

One service 0.999 ≈ 99.90% → 43 min down per 30 days Chain of 5 0.999^5 ≈ 99.50% → 216 min down per 30 days Chain of 10 0.999^10 ≈ 99.00% → 430 min down per 30 days Chain of 50 0.999^50 ≈ 95.12% → 35 hours down per 30 days Fan-out to 100 1 - 0.99^100 ≈ 63% of requests wait on at least one 1-in-100 slow call

Latency compounds in two ways. In series, latencies add, and so do the chances of hitting a slow call. In parallel fan-out, the request waits for the slowest of its calls, so a 1-in-100 stall in each backend becomes a stall for most requests once you fan out widely. Google's "The Tail at Scale" paper made this point famous. A quick simulation shows both effects:

import random
import statistics

random.seed(7)


def call() -> float:
    """One service call in ms: usually 8-12 ms, but 1% of calls hit a 200 ms stall (GC, retry, cold cache)."""
    return random.uniform(8, 12) + (200 if random.random() < 0.01 else 0)


def p(samples, q):
    return statistics.quantiles(samples, n=1000)[int(q * 1000) - 1]


N = 200_000
single = [call() for _ in range(N)]
chain5 = [sum(call() for _ in range(5)) for _ in range(N)]     # A calls B calls C ... in series
fanout10 = [max(call() for _ in range(10)) for _ in range(N)]  # one request waits for 10 parallel calls

for name, s in [("1 call", single), ("5 in series", chain5), ("10 in parallel", fanout10)]:
    print(f"{name:15} p50={p(s, .50):6.1f} ms  p99={p(s, .99):6.1f} ms")

# 1 call          p50=  10.0 ms  p99=  12.0 ms
# 5 in series     p50=  50.2 ms  p99= 252.3 ms
# 10 in parallel  p50=  11.8 ms  p99= 211.6 ms

Each service on its own has a p99 of 12 ms, and nothing in its dashboards looks wrong. The request that chains five of them has a p99 of 252 ms, twenty times worse. Three design rules follow:

  • Keep synchronous chains shallow. Two or three hops on the critical path, not seven. If service A always needs data from B, consider whether they are really one service, or whether A should keep a local copy of the data it needs.
  • Fan out in parallel, not in series, and set a deadline for the whole request that each hop shrinks as time passes.
  • Make non-essential calls optional. If recommendations time out after 50 ms, render the page without them. A dependency you can do without does not count against your availability.

Drawing service boundaries

The hardest part of microservices is not the infrastructure. It is choosing the cuts. Bad boundaries make every feature touch four services and every request make ten calls. Good boundaries let most changes stay inside one service.

Bounded contexts

Domain-Driven Design (DDD) gives the most useful tool. A bounded context is a part of the business inside which a term has one precise meaning and one model. The same word often means different things in different contexts, and that difference is a strong hint about where a boundary belongs.

Heuristics for finding good cuts:

  • Cut along business capabilities (catalog, pricing, checkout, fulfilment), not technical layers. A "database service" or a "validation service" is a layer, and every feature will need to change it.
  • Things that change together stay together. If the last 20 pull requests to pricing also touched promotions, they are one context for now.
  • One owner per piece of data. For every table, exactly one service may write it. If two services both need to write order status, the boundary is wrong.
  • Check the call graph. A proposed split where A calls B on nearly every request, in both directions, is one service drawn as two.
  • Start coarse. Merging two services later is painful; splitting a well-modularised one is routine. Martin Fowler's "monolith first" advice comes from this asymmetry: you rarely know the right boundaries until the system has been in use for a while.

The database-per-service rule

Each service owns its data, and no other service reads or writes its tables directly. Others go through its API or consume its events. This is the rule that makes independence real: the orders team can rename a column, split a table or move from PostgreSQL to DynamoDB without telling anyone, because nobody else depends on the schema.

It does not have to mean a separate database server per service. Separate schemas or separate logical databases on a shared cluster, with credentials that only allow each service into its own schema, give the same decoupling at much lower cost. What matters is that the schema is private.

The price is that queries which used to be one JOIN now span services. Three standard answers:

  • API composition. A caller fetches from several services and joins in memory. Fine for small result sets.
  • Local read copies. A service subscribes to another's events and keeps the few fields it needs, for example orders keeping a copy of the customer's name and shipping address. This is CQRS in miniature.
  • A reporting store. All services stream changes into a warehouse for analytics and cross-cutting queries, which never hit the operational databases.

Migrating: the strangler fig

A big-bang rewrite of a working monolith is one of the most reliable ways to fail a software project: the old system keeps changing while the new one is built, and nothing ships for a year. The strangler fig pattern, named by Martin Fowler after a vine that grows around a tree until it replaces it, migrates piece by piece while the system stays live.

  1. Put a routing layer in front. A reverse proxy or API gateway that, at first, forwards everything to the monolith. Nothing changes for users.
  2. Pick the first piece carefully. Something with a clear boundary, few inbound dependencies, and a real reason to move (it scales differently, changes often, or needs a different team). Notifications and search are classic first candidates. The core order model is a bad first candidate. The figure below extracts Payments because it has a sharp boundary and a compliance reason to move; in practice teams often start with something lower-risk.
  3. Build the new service and shift traffic gradually. Route 1% of /payments requests to the new service, compare results (some teams run both and diff the responses, called a shadow or dark launch), then ramp to 100%.
  4. Move the data last. Usually the new service first reads through the monolith's API, then gets its own store kept in sync by change data capture, and finally becomes the owner while the monolith reads from it. Data migration is where most of the effort and risk sits.
  5. Delete the old code. A migration that never removes code from the monolith has doubled the system instead of splitting it.

Inside the monolith, branch by abstraction helps: introduce an interface in front of the module being extracted, make all callers use it, then switch the implementation behind it from in-process code to a client for the new service.

Anti-patterns

Distributed monolith

Services that must be deployed together, in a specific order, because they share libraries with business logic, share schemas, or make lockstep API changes. You pay every cost of distribution and get none of the independence. Test: can one team deploy its service on a Tuesday afternoon without telling anyone?

Shared database

Five services reading and writing the same tables. Any schema change needs all five teams, a slow query from one degrades all, and nobody knows which service owns a column. It is the most common way to end up with a distributed monolith.

Chatty services

Fine-grained calls in loops: fetch an order, then call the product service once per line item, then pricing once per item. A 40-item order becomes 80 network calls. Use batch endpoints, local copies of reference data, or merge the services.

Nano-services

Services so small that the operational overhead (pipeline, dashboards, on-call, network hop) outweighs the logic inside. A service per database table or per function is a sign. A team of five owning thirty services is another.

Common mistake

Splitting by noun into "entity services" (a UserService, an OrderService, a ProductService that are thin CRUD wrappers over tables) and putting the business logic in an orchestrator above them. Every feature then changes the orchestrator and two entity services. Services should own behaviour and the data it needs, not just rows.

A reasonable default for a new product is a modular monolith with strict module boundaries and private schemas. Extract a service when a specific pressure appears: a team that needs its own release cadence, a component with very different scaling or hardware needs, a security or compliance boundary, or a part that needs a different runtime. Each extraction should name the pressure it relieves.

In the real world

  • Amazon: in the early 2000s Amazon broke up its monolithic retail application and required teams to expose functionality only through service interfaces. Teams were kept to two-pizza size (small enough to feed with two pizzas) and own their services end to end, which is Conway's law applied on purpose. The same internal platform work led to AWS.
  • Netflix: after a database corruption in 2008 stopped DVD shipments for three days, Netflix spent about seven years moving from a monolith in its own data centres to hundreds of microservices on AWS, and open-sourced much of the tooling it needed (Eureka, Hystrix, Zuul).
  • Segment: split each of its 140+ data destinations into its own service and queue, then found that shared-library drift, per-service autoscaling tuning and operational overhead were slowing the small team down. They later merged the destinations back into a single service and repository, and described the result in a 2018 post and reported faster development and fewer incidents.
  • Shopify: kept its large Ruby on Rails application as a modular monolith, reorganised into components with explicit boundaries, and built Packwerk, an open-source tool that fails the build when code reaches into another component's private internals.
  • Amazon Prime Video: in 2023 its video-quality monitoring team moved a pipeline from distributed serverless components (Step Functions and Lambda) into a single process and reported cutting infrastructure cost by over 90%, mostly by removing per-second Step Functions state transitions and the S3 hand-off of video frames between components.
Interview angle

When to bring it up

In almost every design you will draw several services. Say why each boundary exists ("the redirect path scales 100× more than link creation, so they are separate services sharing a store") instead of drawing ten boxes by habit. If the interviewer asks about architecture for a new product or a small team, propose a modular monolith and name the triggers that would justify splitting.

Follow-ups to expect

  • How do you decide boundaries? Business capabilities, bounded contexts, data ownership, change coupling, team ownership.
  • How do you handle a transaction across services? Sagas with compensations, the transactional outbox, idempotent consumers.
  • What happens when a downstream service is slow? Timeouts, circuit breakers, fallbacks, bulkheads; keep it off the critical path if possible.
  • How do you query across services? API composition, local read models built from events, a reporting store.
  • How would you migrate this monolith? Strangler fig behind a routing facade, data moved last.

Red flags

  • Several services sharing one database schema.
  • Deep synchronous call chains on the user's critical path with no timeouts or fallbacks.
  • Choosing microservices for a three-person team "for scalability", when the scaling problem could be solved by running more copies of one stateless application.
  • Ignoring the organisational side: services with no clear owning team.
