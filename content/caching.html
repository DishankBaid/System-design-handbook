Why it matters

A product page needs data that takes 10 ms to compute from the database. It is requested 100,000 times per second and changes a few times a day. Computing it 100,000 times a second is wasted work; computing it once and keeping the answer in memory, where it can be read in half a millisecond, is caching. Almost every system that serves real traffic depends on it, and many outages start with a cache that stopped doing its job.

A cache is a fast, smaller store holding copies of data whose source of truth lives elsewhere. Caches work because access is skewed: a small fraction of keys gets most of the traffic. They are hard because a copy can disagree with its source. The chapter covers where caches sit, how reads and writes flow through them, what to evict, how to keep copies correct, and how to stop a cache miss from taking down the database.

The arithmetic of hit ratio

The hit ratio h is the fraction of requests answered by the cache. Two formulas carry most cache reasoning:

average latency = t_cache + (1 - h) × t_db database load = (1 - h) × request rate with t_cache = 0.5 ms, t_db = 10 ms, 100,000 requests/s: h = 80% latency 2.5 ms database 20,000 queries/s h = 90% latency 1.5 ms database 10,000 queries/s h = 95% latency 1.0 ms database 5,000 queries/s h = 99% latency 0.6 ms database 1,000 queries/s h = 99.9% latency 0.51 ms database 100 queries/s

Look at the database column. Going from 90% to 99% is a tenfold drop in database load, from a change that looks like nine points. It cuts the other way too: a database sized for a 99% hit ratio is undersized by ten times if the ratio falls to 90%, for example after a cache restart or a deploy that changed key names. The cache has quietly become a load-bearing part of the system, and its failure modes must be designed for.

Read and write patterns

Five patterns describe who talks to the cache and when the database is updated. Step through them:

PatternFreshnessWrite latencyRiskGood fit
Cache-aside + delete on writeStale only in races and TTL windowsDatabase onlyRace shown below; first read after write is a missGeneral web reads
Read-throughSame as cache-asiden/aCache layer must know how to loadLibraries and managed caches (DAX)
Write-throughFresh for written keysCache + databaseCaches data nobody reads; partial failure leaves them disagreeingRead-after-write heavy data
Write-backCache is the latestCache onlyData loss if the cache dies before flushingCounters, metrics, write bursts that tolerate loss
Write-aroundMiss after each writeDatabase onlyWrite-heavy keys never stay cachedData written once, read later (or never)

Why delete rather than update on write? Two concurrent writers that each update the cache after the database can interleave so the cache ends up with the older value, forever. A delete is idempotent and order-independent: whatever the interleaving, the next read reloads from the database. Updating the cache also wastes work on keys nobody will read.

Eviction

A cache is smaller than the data, so it must choose what to drop. Eviction policies bet on which keys will be needed again.

LRU

Least recently used goes first. Captures recency, and is the default almost everywhere. Weakness: one big scan of cold keys flushes the hot set.

LFU

Least frequently used goes first. Keeps stable favourites through scans, but needs counters that decay, or yesterday's viral key lives forever.

FIFO and random

Cheap and surprisingly close to LRU on many real workloads. Twitter's study of its cache clusters found FIFO performing similarly to LRU for most of them.

TTL

Not an eviction policy but an expiry: each key carries a lifetime. It bounds staleness and reclaims memory from dead keys. Use it on almost every key.

Production caches approximate these. Redis does not keep a global LRU list; it samples a few keys (5 by default, maxmemory-samples) and evicts the best candidate among them. Its LFU mode uses an 8-bit logarithmic counter per key that decays over time. Memcached keeps a segmented LRU per slab size class. Caffeine (Java) uses W-TinyLFU, which admits a new key only if it is likely to be more popular than the one it would evict. Note that Redis's default policy is noeviction: when memory is full, writes fail. Set allkeys-lru or allkeys-lfu for a pure cache.

An exact LRU is short in Python because OrderedDict keeps keys in order and moves one to the end in O(1):

from collections import OrderedDict


class LRUCache:
    """O(1) get and put: OrderedDict keeps keys in recency order."""

    def __init__(self, capacity):
        self.capacity = capacity
        self.data = OrderedDict()
        self.hits = self.misses = 0

    def get(self, key):
        if key not in self.data:
            self.misses += 1
            return None
        self.hits += 1
        self.data.move_to_end(key)            # now the most recently used
        return self.data[key]

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)     # evict the least recently used


cache = LRUCache(capacity=3)
for key in ["home", "cart", "home", "p:91", "p:17", "home", "cart"]:
    if cache.get(key) is None:
        cache.put(key, f"<html for {key}>")
print(list(cache.data), f"hits={cache.hits} misses={cache.misses}")
# ['p:17', 'home', 'cart'] hits=2 misses=5

Invalidation

Every cached value is a copy that may be out of date. The strategies trade freshness against effort:

  1. TTL only. Accept staleness up to the TTL. Simple and robust; fine for data where minutes of staleness are invisible (a product description, a follower count).
  2. Delete on write. The service that writes the database deletes the key. Fresh within milliseconds, if every write path remembers to do it.
  3. Change data capture. A separate process tails the database's replication log and deletes keys for every changed row. No write path can forget. Facebook's McSqueal daemons read the MySQL commit log and broadcast deletes to every frontend memcache cluster in that region.
  4. Versioned keys. Put a version in the key (product:91:v17) and bump the version on change. Old entries are never read again and age out. Ideal for client and CDN caches you cannot reach.

Keep a TTL even with active invalidation. It is the backstop that bounds the damage when an invalidation is lost, and invalidations do get lost: a network blip, a crashed consumer, a bug in one write path.

The race in cache-aside

Delete-on-write has a well-known hole. It needs a slow reader and a writer to interleave in a specific way, which at high request rates happens every day.

Fixes, from strongest to cheapest:

  • Leases. From Facebook's memcache paper: a miss returns a lease token, a delete invalidates outstanding tokens, and a SET is accepted only with a valid token. The same mechanism limits stampedes, because memcache hands out a token for a key at most once every 10 seconds; other clients are told to wait briefly and retry. Facebook reported this cut peak database queries for affected keys from 17,000 to 1,300 per second.
  • Versioned sets. Store the row's version (or updated_at) with the cached value, and set only if the new version is higher, using memcached's cas or a small Redis Lua script. A stale reader cannot overwrite a newer value. This fixes stale-overwrite races; it cannot help if the stale reader is the first to fill an empty key, which is why it pairs with delete-on-write plus a short TTL.
  • Delayed second delete. Delete the key on write, then delete it again a second or so later, after any in-flight stale reader has finished. Cheap and effective in practice, but a timing guess.
  • Short TTL. Bounds the window. It does not fix anything, it only limits how long the wrong value lives.

Stampedes and thundering herds

A popular key expires. In the time it takes one request to recompute it, every other request for that key also misses and goes to the database. At 2,000 requests per second and a 200 ms recompute, that is about 400 identical queries in a burst, for one key. If the recompute is an expensive aggregate, the database falls over, the recompute times out, the key never gets filled, and the herd keeps coming. This is a cache stampede (or dog-pile). The same thing happens on a much larger scale when a cache node restarts empty.

  • Request coalescing (single-flight). Within one process, the first miss for a key starts the load; concurrent misses for the same key wait on that load instead of starting their own. Go's singleflight package and Caffeine's loading cache do this. It reduces the herd to one query per process, not one per cluster.
  • A distributed lock or lease. The first miss takes a short lock in the cache (SET lock:key NX PX 2000); others wait briefly and retry, or serve a stale copy. One query per cluster. Remember lock expiry, so a crashed holder does not block the key.
  • Serve stale while revalidating. Keep the old value past its soft expiry and refresh in the background. Users see slightly stale data instead of a slow page. HTTP has this built in as stale-while-revalidate.
  • Probabilistic early expiration (XFetch). Each request recomputes early with a probability that rises as expiry approaches: recompute if now - delta × beta × ln(rand()) ≥ expiry, where delta is how long the last recompute took, rand() is uniform in (0, 1], and beta (default 1) tunes eagerness. Since ln(rand()) is negative, the left side is now plus a random amount with mean delta × beta. Expensive keys start refreshing earlier. No coordination needed.
  • Jittered TTLs. Keys written together (a cache warm-up, a batch job) expire together. Add a random 10 to 20% to each TTL so their expiries spread out.

XFetch is three lines of logic. This simulation runs one hot key for ten minutes at 2,000 requests per second with a 60-second TTL and a 200 ms recompute:

import math
import random


def should_recompute(now, expiry, delta, beta=1.0, rng=random):
    """XFetch (Vattani et al., VLDB 2015): recompute early with a probability that rises
    as expiry approaches. delta = how long the last recompute took."""
    r = 1.0 - rng.random()                       # uniform in (0, 1], so log(r) is defined
    return now - delta * beta * math.log(r) >= expiry


def simulate(policy, rate=2_000, ttl=60.0, delta=0.2, seconds=600, seed=1):
    """Count database queries for one hot key under a steady request rate."""
    rng = random.Random(seed)
    now, expiry, db_queries, refill_at = 0.0, ttl, 0, None
    while now < seconds:
        now += rng.expovariate(rate)                  # next request
        if refill_at is not None and now >= refill_at:
            expiry, refill_at = refill_at + ttl, None  # recompute finished: fresh value
        if policy == "naive" and now >= expiry:
            db_queries += 1                            # every miss goes to the database
            if refill_at is None:
                refill_at = now + delta
        elif policy == "xfetch" and should_recompute(now, expiry, delta, rng=rng):
            db_queries += 1                            # early recompute; the old value is still served
            if refill_at is None:                      # (no coordination between requests)
                refill_at = now + delta
    return db_queries


print("naive :", simulate("naive"), "DB queries in 10 minutes")
print("xfetch:", simulate("xfetch"), "DB queries in 10 minutes")
# naive : 3533 DB queries in 10 minutes
# xfetch: 18 DB queries in 10 minutes

Without protection, each expiry costs about 400 database queries. With XFetch it costs about two, and because the refresh happens before expiry, no request ever waits for the database.

Hot keys

A distributed cache spreads keys across nodes with consistent hashing or hash slots, which balances keys, not traffic. A single key at 200,000 reads per second exceeds what one Redis node comfortably serves, and every request for it goes to the same node. Responses:

  • Local cache in front. A few seconds of in-process caching for the hottest keys removes most of their traffic from the network. Staleness is bounded by that short TTL.
  • Replicate the hot key. Store copies under key#0 to key#7 on different nodes and read a random one. Writes must update or delete all copies.
  • Read replicas. Redis replicas can serve reads for a hot shard, with replication lag as the price.
  • Detect, do not guess. Hot keys change minute to minute (the trending product, the live match). Sample access counts in the client or proxy and promote keys to local caching automatically.

For a new system, Redis (or a compatible fork such as Valkey) is the usual default because it covers caching and several adjacent jobs. Memcached remains excellent at exactly one thing and runs some of the largest caches in the world.

Worked example: caching a product page

A store serves 50,000 product page requests per second at peak. Each page needs the product record (5 ms query), price and stock (3 ms), and review summary (40 ms aggregate). The database is sized for 5,000 queries per second.

DataChangesCache decisionExpected hit ratio
Product recordA few times a dayCache-aside in Redis, TTL 1 h with jitter, delete via CDC on update~99%
Price and stockEvery purchaseShort TTL (5 s) for display; checkout always reads the database~90%
Review summarySlowly, tolerates hoursTTL 6 h, XFetch so the 40 ms aggregate never stampedes~99.9%
Top 500 productsSame as aboveAlso in-process for 2 s in every app serverRemoves their Redis traffic
Database queries/s = 50,000 × [(1 - 0.99) + (1 - 0.90) + (1 - 0.999)] = 50,000 × (0.01 + 0.10 + 0.001) ≈ 5,550/s over the 5,000 budget Raise stock TTL hit ratio to 95% (TTL 10 s): = 50,000 × (0.01 + 0.05 + 0.001) ≈ 3,050/s fits

The weakest-cached item dominates the database load, so that is where tuning pays. The product decision hiding in the arithmetic: showing stock up to 10 seconds old on the product page is acceptable because checkout re-reads it transactionally. Caching is often a product question disguised as an infrastructure one.

In the real world

  • Facebook ran memcache as a look-aside cache at billions of requests per second: leases against stale sets and stampedes, McSqueal for invalidation from the MySQL log, mcrouter for routing, a "gutter" pool to absorb a failed server's keys, and warming new clusters from existing ones.
  • Twitter runs hundreds of cache clusters (Twemcache, then Pelikan). Its 2020 OSDI study of those clusters found heavy TTL use, many write-heavy workloads, and that simple FIFO performed comparably to LRU for most of them.
  • Netflix EVCache wraps Memcached with replication across availability zones, so a zone failure does not cold-start the cache.
  • Amazon DynamoDB Accelerator (DAX) is a managed read-through and write-through cache in front of DynamoDB.
Interview angle

When to bring it up

Whenever reads dominate writes. State the pattern, the TTL, the invalidation path and the expected hit ratio in one breath, then show what the hit ratio does to database load. Mention stampede protection for any hot or expensive key without being asked.

Follow-ups to expect

  • What happens to the database when the cache restarts? (Hit ratio collapses; warm-up, gradual traffic shift, coalescing.)
  • How do you keep the cache consistent with the database? (Delete on write or CDC, TTL backstop, the stale-set race and leases.)
  • Why delete instead of update on write?
  • One key gets 500k reads per second. Now what?
  • Write-back looks fast. Why is it rarely used for business data?

Red flags

  • A cache with no TTL and no invalidation story.
  • Treating the cache as the source of truth for data you cannot lose.
  • Sizing the database for the cached load with no plan for a cold cache.
  • Caching per-user data at the CDN.
