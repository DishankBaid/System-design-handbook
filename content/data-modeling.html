Why it matters

Two teams build the same order history page. One models entities first, normalizes them nicely, and discovers the page needs five joins across 400 million rows. The other starts from the page: "show a user's 20 most recent orders with their totals", and stores exactly that shape under exactly that key. Both schemas are "correct". Only one serves the page in 5 ms. Data modeling is deciding how data is shaped, keyed and duplicated so the operations that matter are cheap, the invariants that matter are easy to keep, and the model can still change next year.

In an interview, the data model is where design meets reality. A good one makes the rest of the design obvious; a bad one forces scatter-gather queries, distributed transactions and caches to paper over it. This chapter covers the working method (access patterns first), normalization and when to break it, relationships in each kind of store, DynamoDB's single-table design, time-series models, primary keys, and changing a schema without downtime.

Start from access patterns

Before drawing tables, list what the system must do, with rough rates. For the online store used throughout this chapter:

#Access patternRateShape of the answer
1Get a user's profile and addresses2,000/sOne user, a few addresses
2List a user's recent orders, newest first4,000/s20 order summaries
3Get one order with its line items6,000/sOne order, 1 to 50 items
4Place an order, decrement stock350/s peakAtomic multi-row write
5Find pending orders older than an hour1/minA few hundred rows
6Revenue by category per weekDailyAggregate over everything

This list does most of the modeling work. Patterns 1 to 3 are key lookups that must be fast. Pattern 4 needs a transaction. Pattern 5 needs an index that only covers a small subset. Pattern 6 is analytics and belongs in a warehouse, not in the serving model at all. A relational database can serve all of this from a normalized schema plus the right indexes; a key-value store needs the data pre-arranged per pattern. Either way you design from the list.

Normalization in practice

Normalization organises tables so each fact is stored once. The textbook defines a series of normal forms; in practice the first three cover nearly every real mistake.

1NF: atomic values

Each column holds one value, no repeating groups. Violation: tags = 'red,blue,xl' in one column. You cannot index or join on a tag, and updating one means string surgery. Fix: a product_tags table (or a native array type, if the database can index it).

2NF: whole-key dependency

In a table with a composite key, every column depends on the whole key. Violation: order_items(order_id, line_no, order_date, ...), where order_date depends only on order_id. It repeats on every line and can disagree between lines.

3NF: nothing but the key

No column depends on another non-key column. Violation: orders(id, user_id, user_email): the email depends on user_id. When Asha changes her email, every order row must change, or some will show the old one.

The three failure modes normalization prevents are the update anomaly (one fact changed in some copies but not others), the insert anomaly (cannot record a product until someone orders it) and the delete anomaly (deleting the last order deletes the only record of a customer's address).

A copy is not always a duplicate

order_items.unit_price looks like a copy of products.price. It is not: it records the price paid at the time of purchase, a different fact that must never change when the catalog price does. The same goes for the shipping address on an order. Ask "if the source changes, should this change too?" If the answer is no, it is its own fact and belongs in the normalized model.

Denormalization, deliberately

Denormalization stores data redundantly to make reads cheaper: copying the author's name onto every post, keeping orders_count on the user row, materialising a "user's recent orders" list. It is the right call when a read is far more frequent than the write that would invalidate it, or when the join it replaces would cross shards.

Every denormalized copy needs an owner and a sync mechanism, chosen explicitly:

  • Same transaction. Update the counter in the transaction that inserts the order. Always consistent; only works when both live in one database (or one partition).
  • Materialized view or trigger. The database maintains it. Convenient; refresh cost and locking need watching.
  • Change data capture. A consumer of the change stream updates the copies asynchronously. Scales across systems; copies lag by seconds. See CQRS.

Rule of thumb: normalize the system of record, denormalize the read paths, and be able to rebuild every denormalized copy from the source.

Relationships across data models

The same three relationship shapes appear everywhere, but each data model handles them differently.

RelationshipRelationalDocumentWide-column / key-value
1:1 (user, settings)Same table, or a second table sharing the primary keyEmbedSame item or same partition
1:few (user, addresses)Foreign key on the childEmbed an arrayRows in the parent's partition
1:many, unbounded (user, orders)Foreign key plus an index on itSeparate collection with a parent id; embedding grows without limitParent key as partition key, child sorted by clustering key
N:M (products, categories)Join tableArray of ids on one side; query the other side by indexTwo tables or item sets, one per direction, kept in sync

The deciding questions for embed versus reference: Is the child read with the parent almost every time? Is it owned by exactly one parent? Is the number of children bounded and small? Three yeses mean embed. A child shared between parents, or one that grows without bound (comments on a viral post, events from a device), gets its own collection or partition.

Single-table design in DynamoDB

DynamoDB has no joins and charges per request, so the goal is to answer each access pattern with one request. Every item has a partition key (PK), hashed to choose its partition, and an optional sort key (SK) that orders items within the partition. All items sharing a PK form an item collection, which a single Query can read in sort order, filtered by a sort key condition such as begins_with or a range.

Single-table design exploits that: put different entity types that are read together into the same item collection by giving them the same PK, and use typed, prefixed sort keys to tell them apart. The keys are generic strings (PK, SK) overloaded per entity.

#Access patternRequest
1Profile and addressesQuery PK = USER#42, SK < "ORDER#" (#PROFILE and ADDR# sort before ORDER#)
2Recent ordersQuery PK = USER#42, begins_with(SK, "ORDER#"), ScanIndexForward = false, Limit = 20
3Order with itemsQuery PK = ORDER#9001
4Place orderTransactWriteItems: order META, items, user's summary item, conditional stock decrements
5Old pending ordersQuery GSI1 PK = STATUS#PENDING, GSI1SK < now - 1 h; remove the GSI attributes when the order ships
6Revenue by categoryNot here: export the table to S3 and query it in a warehouse

The details that make it work, and the ones that bite:

  • Sort key design is query design. ORDER#2026-10-07#9002 sorts by date, so a reverse query returns newest first. Put the date before the id, and use ISO 8601 so string order equals time order.
  • Sparse indexes. A global secondary index (GSI) only contains items that have its key attributes. Setting GSI1PK only on pending orders gives an index of the few hundred pending orders, not all of them.
  • Hot partitions. STATUS#PENDING is a single partition key. At high write rates, shard it: STATUS#PENDING#0 to #9, and query all ten. Each partition supports up to 3,000 read capacity units and 1,000 write capacity units per second (roughly 3,000 strongly consistent 4 KB reads or 1,000 1 KB writes).
  • Item limits. Items cap at 400 KB, and an item collection in a table with a local secondary index caps at 10 GB, so unbounded children belong in their own partitions.
  • Cost of flexibility. A new access pattern may need a new GSI or a backfill that rewrites items. Single-table design pays off when access patterns are known and stable, which is why many teams use one table per bounded context or service rather than one per company.

Time-series and append-only models

Some data is never updated, only appended: sensor readings, clicks, messages, ledger entries. Modeling it as immutable rows keyed by entity and time makes writes trivially conflict-free and reads sequential. The trap is the partition that grows forever. A sensor reporting once per second produces 86,400 rows a day; keyed by sensor_id alone, one partition grows without bound and becomes both huge and hot. Bucketing adds a time component to the partition key:

PRIMARY KEY ((sensor_id, day), ts) rows per partition 86,400 readings/day × ~50 B ≈ 4.3 MB per partition, bounded read last hour one partition, one sequential slice read last 30 days 30 partitions, fetched in parallel retention drop or TTL whole days, never row-by-row deletes

Pick the bucket so a partition stays comfortably small (Cassandra guidance is to stay well under 100 MB) and common queries touch few buckets. Discord uses the same idea for messages: partition by channel and a ten-day time bucket.

A ledger is the append-only model applied to money: never update a balance in place, append a signed entry (+64.50 order 9001, -64.50 refund 77) and derive the balance by summing, with periodic snapshots so reads do not sum years of history. Every past state can be reconstructed, auditors can see every change, and concurrent writers never overwrite each other. This is the core of event sourcing.

Choosing primary keys

Natural or surrogate

A natural key comes from the domain: an email, an ISBN, a country code. A surrogate key is generated and means nothing: an integer or a UUID. Prefer surrogate keys for entities. Natural keys change (people change emails), turn out not to be unique (two products share a barcode after a supplier error), or leak personal data into URLs and logs. Keep the natural key as a separate column with a unique constraint. Natural keys are fine for immutable codes from a standard (currency = 'EUR') and for join tables, whose key is naturally the pair of foreign keys.

Random UUIDs, sequential ids and B-tree locality

Auto-increment integers are compact (8 bytes) and always insert at the right edge of the index. But they need a central counter, reveal how many orders you take a day to anyone who places two, and cannot be generated by clients or across shards without coordination. Random UUIDv4 fixes all three, at a cost that only shows up at scale: inserts land at random places in every B-tree index on the key.

import bisect
import itertools
import random

PAGE = 100                                    # keys per leaf page


def load(keys):
    """Insert keys into B-tree-like leaf pages; report page count, fill and recent footprint."""
    firsts, pages, ids = [], [], []           # first key, contents and a stable id per page
    new_id = itertools.count()
    touched = []                              # page id that received each insert
    for k in keys:
        if not pages:
            firsts, pages, ids = [k], [[k]], [next(new_id)]
            touched.append(ids[0])
            continue
        i = max(bisect.bisect_right(firsts, k) - 1, 0)
        page = pages[i]
        bisect.insort(page, k)
        firsts[i] = page[0]
        touched.append(ids[i])
        if len(page) > PAGE:
            # appending at the far right: keep the old page 90% full (as PostgreSQL does);
            # anywhere else: split in half
            rightmost = i == len(pages) - 1 and page[-1] == k
            cut = int(PAGE * 0.9) if rightmost else len(page) // 2
            pages[i:i + 1] = [page[:cut], page[cut:]]
            firsts[i:i + 1] = [page[0], page[cut]]
            ids[i + 1:i + 1] = [next(new_id)]
    fill = sum(map(len, pages)) / (len(pages) * PAGE)
    return len(pages), fill, len(set(touched[-10_000:]))


n = 300_000
rng = random.Random(3)
for name, keys in [("sequential ids", range(n)), ("random UUIDv4", [rng.getrandbits(122) for _ in range(n)])]:
    pages, fill, recent = load(keys)
    print(f"{name:15} {pages:5} leaf pages, {fill:.0%} full, last 10,000 inserts touched {recent:5} pages")
# sequential ids   3334 leaf pages, 90% full, last 10,000 inserts touched   112 pages
# random UUIDv4    4286 leaf pages, 70% full, last 10,000 inserts touched  3794 pages

Random keys make the index about 30% bigger (pages split in half and settle around 70% full) and, more importantly, spread recent inserts across nearly every leaf page. Sequential keys keep the hot set to about a hundred pages. Once the index is larger than memory, every random insert risks a disk read, and the write-ahead log fills with full-page images. Time-ordered ids get the best of both: globally unique without coordination, yet roughly increasing. UUIDv7 (RFC 9562, 2024) puts a 48-bit millisecond timestamp first, ULIDs do the same in a different encoding, and Snowflake-style 64-bit ids pack time, a machine id and a sequence. Use them for new tables. They still reveal creation time, which matters if that is sensitive. See Distributed ID Generation.

Schema evolution without downtime

A schema change and a code deploy cannot happen at the same instant, and during a rolling deploy old and new code run side by side for minutes. So every change must be compatible with the code before it and after it. The standard technique is expand and contract (also called parallel change): first add the new shape alongside the old, migrate, and only remove the old shape once nothing uses it.

  • Know which DDL is cheap. PostgreSQL 11+ adds a column with a constant default without rewriting the table; MySQL 8.0 has ALGORITHM=INSTANT for many column additions. Changing a column's type usually rewrites the table. Build indexes with CREATE INDEX CONCURRENTLY (PostgreSQL) or online DDL so writes are not blocked.
  • Use online schema change tools for big rewrites. GitHub's gh-ost and Percona's pt-online-schema-change build a shadow copy of the table, keep it in sync, and swap it in with a brief lock.
  • Set lock timeouts on migrations. An ALTER waiting behind a long transaction blocks every query queued behind it. A short lock_timeout and a retry are safer than an outage.
  • Document stores move the problem into code: store a schema_version in each document, have readers handle every version still on disk, and migrate lazily on write or with a background job.
  • Event and message schemas live forever in logs and queues. With Avro or Protobuf, only add optional fields, never reuse a field number, and enforce compatibility in a schema registry.

Soft deletes

A soft delete marks a row as deleted (deleted_at = now()) instead of removing it, so it can be restored, audited or referenced by old orders. It is popular and has sharp edges:

  • Every query must filter it. One forgotten WHERE deleted_at IS NULL shows deleted data to users. Put the filter in a view or the ORM's default scope, and add partial indexes on the live rows.
  • Uniqueness breaks. A deleted user still holds their email, so they cannot sign up again. Use a partial unique index: CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL.
  • Privacy law wins. GDPR erasure requests require really removing personal data. Soft-deleted rows must eventually be purged or anonymised.
  • Tables bloat with dead rows that every scan still reads.

Alternatives: move deleted rows to an archive table in the same transaction, or rely on an audit log or event history for recovery, and hard-delete from the live table.

In the real world

  • Amazon teams popularised single-table DynamoDB design, and AWS's own guidance is to identify access patterns before designing tables, with as few tables as possible.
  • Discord stores messages partitioned by channel and time bucket, with Snowflake ids that sort by time, so "messages before this one" is a range scan.
  • GitHub built gh-ost to run schema migrations on large MySQL tables without triggers, using the binary log to keep the shadow table in sync.
  • Stripe and most payment systems model balances as append-only ledgers with derived balances, never as a mutable balance column alone.
  • PostgreSQL's JSONB lets relational schemas embed document-like attributes (a product's varying specs) while keeping core fields normalized, a common middle ground. See SQL vs NoSQL.
Interview angle

When to bring it up

Right after requirements and estimation. Write the access patterns with rates first, then the tables or items with their keys, then name the index that serves each pattern. Point out which data is denormalized and how it stays in sync. Interviewers notice when the key design visibly follows from the queries.

Follow-ups to expect

  • Why did you embed this and reference that?
  • Show the query for "a user's last 20 orders". Which index serves it?
  • Your NoSQL design needs a new query next quarter. What changes? (New GSI or table, backfill.)
  • Auto-increment, UUIDv4 or something else for the primary key, and why?
  • How would you rename a column on a 1-billion-row table with zero downtime?

Red flags

  • Designing entities with no access patterns in mind, or access patterns with no rates.
  • Denormalized copies with no owner and no sync path.
  • Unbounded arrays inside documents or unbounded partitions in wide-column stores.
  • A one-step ALTER that breaks the code still running during a deploy.
