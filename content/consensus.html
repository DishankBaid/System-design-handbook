Why it matters

A primary database fails at 03:12. Two replicas each decide they should take over, both accept writes, and for the next four minutes the same customer balance is updated in two places with no way to merge the results. That outcome is called split brain, and preventing it is the job of consensus.

Consensus is a way for a group of machines to agree on a value, and to keep agreeing on a growing sequence of values, even when some of them crash and the network drops or delays messages. Once agreed, a value never changes. Almost every distributed system needs this somewhere, usually in one of four shapes:

Leader election

Exactly one node is allowed to act as primary at a time: the database primary, the Kafka controller, the active scheduler.

Configuration and membership

Which nodes are in the cluster, which shard lives where, which feature flags are on. Every node must see the same answer.

Locks and leases

Only one worker may run the nightly billing job or own a partition, even if two of them think they should.

Replicated state machines

Several servers apply the same commands in the same order, so they hold identical state and any of them can take over.

The last shape is the general one: the other three are all small replicated state machines. If every replica starts in the same state and applies the same deterministic commands in the same order, every replica ends in the same state. Consensus is used to agree on that order, one log entry at a time.

What makes this hard is not agreement when everything works. It is agreement when a node crashes halfway through, when a message arrives 30 seconds late, and when a node that was cut off comes back convinced it is still in charge. A correct protocol must guarantee three properties:

  • Agreement (safety). No two nodes ever decide different values for the same slot.
  • Validity. A decided value was actually proposed by someone, so a trivial "always decide 0" protocol does not count.
  • Termination (liveness). Every node that does not crash eventually decides.

FLP: why no protocol can promise everything

In 1985 Fischer, Lynch and Paterson proved a result now called FLP impossibility: in a fully asynchronous network, where messages can be delayed for any finite time and there is no clock to measure the delay, no deterministic protocol can guarantee all three properties if even one process may crash.

The intuition fits in two sentences. A node that has not heard from a peer cannot tell whether the peer crashed or is merely slow. If it waits, it may wait forever for a dead node; if it moves on, the slow node may come back with a vote that changes the outcome. The proof shows that an adversarial scheduler can always keep the system on that knife edge.

FLP does not make consensus useless. It tells you which property to bend. Every practical protocol, Paxos and Raft included, makes the same choice:

  • Safety always. No matter how messages are delayed, reordered or lost, two nodes never commit conflicting values.
  • Liveness when the network behaves. Progress needs a period where messages arrive within a bounded time, a model called partial synchrony. Timeouts and randomization get the system out of bad states quickly in practice, but a sufficiently unlucky network can stall it. A stalled cluster is unavailable, not wrong.

This is the CAP trade-off made concrete: a consensus group sides with consistency, and the minority side of a partition stops accepting writes.

Raft in depth

Raft was published in 2014 with a stated goal: be as efficient as Multi-Paxos but easy enough to understand that engineers implement it correctly. It splits the problem into three parts, leader election, log replication and safety, and it is the protocol behind etcd, Consul, CockroachDB, TiKV and Kafka's KRaft mode.

Terms and roles

Every server is in one of three roles. A follower is passive: it answers requests and never starts any. A candidate is trying to become leader. A leader handles every client write and replicates it. In normal operation there is exactly one leader and every other server is a follower.

Time is divided into terms, numbered with consecutive integers. Each term starts with an election and has at most one leader. Terms act as a logical clock:

  • Every message carries the sender's current term.
  • A server that sees a higher term than its own adopts it immediately, and if it was a leader or candidate it steps down to follower.
  • A server rejects any request carrying a lower term. This is how stale leaders are detected and ignored.

Each server keeps a small amount of state, and the split between persistent and volatile state is what makes crash recovery safe:

currentTermAll, on diskLatest term the server has seen

Raft's core needs only two RPCs: RequestVote, sent by candidates, and AppendEntries, sent by leaders both to replicate entries and, with no entries, as a heartbeat. A third, InstallSnapshot, ships a snapshot to a follower that has fallen too far behind.

Leader election

A leader sends heartbeats regularly. A follower that hears nothing for an election timeout assumes the leader is gone and starts an election: it increments its term, becomes a candidate, votes for itself and sends RequestVote to every other server. Three things can then happen.

  1. It wins. Votes from a majority of the full cluster for the same term make it leader. Each server grants at most one vote per term, first come first served, so at most one candidate can win a given term.
  2. Someone else wins. If it receives AppendEntries from a leader whose term is at least its own, it accepts that leader and returns to follower.
  3. Nobody wins. If several candidates split the votes, each one times out again, increments its term and starts a new election.

Why the timeouts are randomized

If every follower used the same timeout, they would all become candidates at the same instant, each vote for itself, and every election would split. Raft breaks the symmetry by drawing each timeout at random from a range, 150 to 300 ms in the paper. Usually one server fires well before the others and wins before anyone else wakes up. The simulation below measures how much the spread matters for a five-node cluster with 1 to 5 ms network delays.

import random

N, MAJORITY = 5, 3
MIN_TIMEOUT = 150   # ms; each server waits MIN_TIMEOUT + uniform(0, spread)


def election_round(spread, rng):
    """Simulate one round after the leader dies. Returns (someone_won, ms_until_first_timeout)."""
    timeout = [MIN_TIMEOUT + rng.uniform(0, spread) for _ in range(N)]
    delay = lambda: rng.uniform(1, 5)   # one-way network delay, ms
    # a server becomes a candidate if its own timer fires before any RequestVote reaches it
    first_request = [min(timeout[c] + delay() for c in range(N) if c != j) for j in range(N)]
    candidates = [c for c in range(N) if timeout[c] <= first_request[c]]
    votes = {c: 1 for c in candidates}  # every candidate votes for itself
    for j in range(N):
        if j not in votes:              # a follower grants its one vote to the first request to arrive
            arrivals = sorted((timeout[c] + delay(), c) for c in candidates)
            votes[arrivals[0][1]] += 1
    return max(votes.values()) >= MAJORITY, min(timeout)


def time_to_leader(spread, rng, max_rounds=50):
    elapsed = 0.0
    for rounds in range(1, max_rounds + 1):
        won, waited = election_round(spread, rng)
        elapsed += waited               # a split vote costs another full timeout
        if won:
            return True, rounds, elapsed
    return False, max_rounds, elapsed   # livelock: nobody ever wins


rng = random.Random(7)
for spread in (0, 5, 25, 150):
    runs = [time_to_leader(spread, rng) for _ in range(10_000)]
    wins = [ms for won, _, ms in runs if won]
    split = 1 - len(wins) / sum(rounds for _, rounds, _ in runs)
    mean = f"{sum(wins) / len(wins):.0f} ms" if wins else "never"
    print(f"spread {spread:3} ms: {split:6.1%} of rounds split, mean time to leader {mean}")
# spread   0 ms: 100.0% of rounds split, mean time to leader never
# spread   5 ms:  68.1% of rounds split, mean time to leader 473 ms
# spread  25 ms:   5.2% of rounds split, mean time to leader 163 ms
# spread 150 ms:   0.2% of rounds split, mean time to leader 175 ms

With no randomization the cluster never elects a leader. With a 5 ms spread, two out of three rounds still split because the spread is about the same as the network delay. A spread several times the network delay makes split votes rare. Making it much wider buys almost nothing and adds waiting time.

The paper states the timing rule as broadcastTime ≪ electionTimeout ≪ MTBF: the timeout must be long compared with a heartbeat round trip, so healthy leaders are not deposed by jitter, and short compared with how often servers fail, so the cluster is rarely leaderless. etcd defaults to a 100 ms heartbeat and a 1,000 ms election timeout, which leaves room for slow disks and cross-zone latency.

Log replication and the commit index

Once elected, the leader is the only server that accepts writes. For each client command it appends an entry to its own log, then sends AppendEntries to every follower with four key fields: the new entries, the prevLogIndex and prevLogTerm of the entry just before them, and leaderCommit, its own commit index.

An entry is committed once the leader has stored it on a majority of servers. Committed entries are durable: Raft guarantees that every future leader will have them. Only then does the leader apply the entry to its state machine and reply to the client. Followers learn the new commit index from leaderCommit in the next message and apply up to it.

The prevLogIndex/prevLogTerm pair is the consistency check. A follower accepts new entries only if its own log has an entry at prevLogIndex with term prevLogTerm. If not, it rejects, and the leader decrements that follower's nextIndex and tries again one entry earlier, until the logs match. The follower then deletes any conflicting entries after the match point and appends the leader's. Step 5 shows S5 discarding y←9, an uncommitted entry from an old term, exactly this way.

By induction this check gives the Log Matching Property: if two logs contain an entry with the same index and term, the logs are identical in every entry up to that index. The leader never deletes or overwrites its own entries; it only makes followers look like itself.

Two practical details make this fast. The leader writes to its own disk in parallel with sending to followers, since only a majority of copies matters. And it batches and pipelines: many commands share one AppendEntries and one disk sync, and the next batch is sent before the previous one is acknowledged.

Safety: the election restriction

Replication alone is not enough. Suppose a follower that missed the last few committed entries becomes leader: it would force everyone else to match its shorter log, deleting committed data. Raft prevents this at election time with the election restriction: a server refuses its vote if the candidate's log is less up to date than its own.

"Up to date" compares the last entry of each log. The log whose last entry has the higher term wins. If the last terms are equal, the longer log wins. That is why RequestVote carries lastLogIndex and lastLogTerm.

The argument that this is enough is short. A committed entry is stored on a majority. A winning candidate collected votes from a majority. Any two majorities of the same cluster share at least one server, and that server would only vote for a candidate whose log is at least as up to date as its own, which includes the committed entry. So every new leader already holds every committed entry. Raft calls this the Leader Completeness Property.

The subtle rule that implementations get wrong

A leader may only count replicas to commit entries from its own current term. An entry from an earlier term that happens to sit on a majority can still be overwritten by a later leader (figure 8 of the Raft paper walks through the exact sequence). Older entries become committed indirectly, when an entry from the current term after them commits. This is why a new leader immediately appends a no-op entry: committing it also commits everything before it, and tells the leader where the commit index really is.

The partitioned old leader

The scenario interviewers like most is a network partition that isolates the current leader with a minority. The old leader does not know it has been replaced. Raft stays correct anyway, because a leader without a majority cannot commit anything.

Three consequences are worth stating in an interview:

  • Clients of the old leader time out. Client A never got an acknowledgement, so it retries against the new leader. If the first attempt did reach a majority before the partition, the retry would apply it twice, so clients attach a unique id per command and the state machine skips duplicates. See Idempotency.
  • Reads are the trap. If S1 served reads from its local state during the partition, it would return stale data while believing it was leader. A linearizable read must confirm leadership first. With ReadIndex, the leader records its commit index, exchanges one heartbeat round with a majority to prove it is still leader, waits until it has applied up to that index, then answers. Lease reads skip the round trip by assuming no other leader can be elected within a lease shorter than the election timeout, which is only safe if clock drift is bounded.
  • Disruptive rejoins. A server cut off from everyone keeps timing out and incrementing its term. When it returns, its huge term forces the healthy leader to step down. The PreVote extension makes a server first ask whether it could win before incrementing its term, and CheckQuorum makes a leader step down on its own when it has not heard from a majority for an election timeout. etcd implements both.

Membership changes and snapshots

Two operational pieces complete the protocol. Changing the set of servers is itself a log entry, and switching directly from an old configuration to a new one could briefly allow two disjoint majorities. Raft either uses joint consensus, where decisions need majorities of both the old and new configuration during the transition, or restricts changes to one server at a time, since any majority of N and any majority of N+1 always overlap. Separately, logs cannot grow forever: each server periodically writes a snapshot of its state machine and discards the log before it, and a leader sends the snapshot to a follower that has fallen too far behind.

Quorum size and fault tolerance

Raft and Paxos need a majority, floor(N/2) + 1 servers, for every election and every commit. To survive f crashed servers you therefore need N = 2f + 1.

Servers NMajorityFailures toleratedComment
110No fault tolerance; fine for development
220Worse than 1: either failure stops progress
321Common default; survives one node or zone
431Same tolerance as 3, one more server to wait for
532Survives a failure during planned maintenance
642Same tolerance as 5
743Rare; each write waits for 3 followers

Even sizes add cost without adding tolerance, so clusters are almost always 3 or 5. Larger groups make every write wait for more acknowledgements and the leader's fan-out grows. To scale reads instead, add non-voting members: ZooKeeper observers and etcd learners receive the log but do not count toward the majority.

Placement matters as much as count. Five servers in one rack survive two disk failures but not one power failure. Spread three servers over three availability zones and the cluster survives the loss of any one zone; a zone failure with only two zones in play takes out a majority half the time.

What a consensus write costs

A committed write needs the leader plus enough followers to form a majority to store the entry durably. The leader sends to all followers in parallel, so the latency is set by the round trip to the fastest followers that complete the majority, plus disk syncs.

Single region, 3 servers in 3 zones (typical numbers) client → leader ~0.5 ms leader fsync, in parallel with sending ~1 ms leader ↔ fastest follower: RTT + fsync ~1 ms + ~1 ms apply and reply ~0.5 ms ≈ 3 ms per write, latency hidden by batching for throughput Three regions (us-east, us-west, eu-west), leader in us-east leader ↔ nearest other region RTT ~65 ms ≈ 65-80 ms per write, before the client's own trip to the leader

Two lessons follow. Within a region, consensus is cheap enough for metadata and even for transactional data, and fsync latency matters as much as the network, so etcd's documentation stresses fast disks. Across regions, every write pays an inter-region round trip, which is why globally replicated databases put the leader of each data range near the users who write to it. A linearizable read through ReadIndex pays one more round trip to a majority, so read-heavy systems use lease reads or accept stale reads from followers where they can.

Paxos and Multi-Paxos

Paxos, described by Leslie Lamport in 1989 and published in 1998, is the original practical consensus protocol. Basic Paxos decides a single value. Roles are proposers, acceptors and learners, and one server usually plays all three.

  1. Prepare. A proposer picks a proposal number n higher than any it has used and sends prepare(n) to the acceptors.
  2. Promise. An acceptor that has not promised a higher number promises to ignore proposals below n, and reports the highest-numbered proposal it has already accepted, if any.
  3. Accept. With promises from a majority, the proposer sends accept(n, v). It may choose v freely only if no acceptor reported an accepted value; otherwise it must use the value of the highest-numbered accepted proposal it heard about.
  4. Chosen. An acceptor accepts unless it has since promised a higher number. A value is chosen once a majority accept the same proposal.

Step 3 is the safety trick: once a value might have been chosen, every later proposer is forced to propose that same value. Two proposers can still livelock by repeatedly pre-empting each other with higher numbers, which is FLP again, so real systems elect a distinguished proposer.

Multi-Paxos runs one Paxos instance per log slot. A stable leader runs the prepare phase once for all future slots, after which each new slot needs only the accept phase: one round trip to a majority, the same cost as a Raft append. Raft is best understood as a Multi-Paxos variant with stronger rules. Log entries flow only from leader to followers, and the election restriction guarantees the new leader already has every committed entry, while a Multi-Paxos leader may have to learn missing slots from others after election. Those rules give up some flexibility to get a protocol that fits in one paper with a complete specification.

Where consensus lives in real systems

  • etcd runs Raft and stores all Kubernetes cluster state. Kubernetes controllers elect their own leaders with Lease objects stored in etcd, so only one scheduler or controller manager acts at a time.
  • ZooKeeper uses ZAB (ZooKeeper Atomic Broadcast), where each transaction id (zxid) combines an epoch, playing the role of Raft's term, with a counter. Writes go through the leader; reads are served locally by any server and can be stale unless the client calls sync first.
  • Consul servers form a Raft group (3 or 5 recommended) for the catalog and key-value store, while client agents use a separate gossip protocol for membership and failure detection. See Service Discovery.
  • Kafka KRaft replaced ZooKeeper with a Raft-based quorum of controllers that stores cluster metadata in an internal log. KRaft became production ready in Kafka 3.3, and Kafka 4.0 removed ZooKeeper support entirely. Message data still uses Kafka's own in-sync replica protocol, not the controller quorum.
  • Google Spanner splits data into ranges and replicates each through its own Paxos group with a long-lived leader, plus TrueTime for globally ordered transactions. CockroachDB and TiKV do the same with one Raft group per range, an approach called Multi-Raft.

Use consensus for small metadata, not bulk data

A single consensus group sends every write through one leader and one log. That makes it a superb source of truth for small, critical, slowly changing data, and a poor database for bulk data. etcd rejects requests above 1.5 MiB by default and ships with a 2 GB storage quota; ZooKeeper limits a znode to about 1 MB. The standard pattern is to use consensus for the control plane, which leader owns which shard and which config version is live, and let the data plane replicate bulk data with cheaper mechanisms. When the data itself needs consensus, shard it into many independent groups, as Spanner and CockroachDB do, so no single leader carries everything.

Distributed locks: leases and fencing tokens

A lock service built on consensus (etcd, ZooKeeper, Consul, Google's Chubby) lets one client at a time hold a named lock. Because a client can crash while holding it, the lock is always a lease: it expires after a time-to-live unless the holder keeps renewing it. Leases solve the dead-holder problem and create a new one. The holder can be paused, by a garbage collector, a VM migration or a swapped-out page, for longer than the lease, while being completely unaware that time has passed.

The fix is a fencing token: a number that the lock service increases every time it grants the lock. The client sends the token with every write, and the storage remembers the highest token it has seen and rejects anything lower. etcd provides this naturally as the revision of the lock key, ZooKeeper as the zxid or sequential node number, and Chubby called it a sequencer. The storage check is a conditional write:

UPDATE invoices SET status = 'sent', fence = 34
WHERE id = 'inv_8812' AND fence <= 34;   -- 0 rows updated means a newer holder exists
  • Leases need fencing for correctness. Without it, a lock is only an efficiency hint: it stops duplicate work most of the time. That is fine for "avoid sending the same report twice", not for "never double-charge".
  • Timing-based locks are not enough. Algorithms such as Redis Redlock acquire a lock on a majority of independent Redis nodes and rely on bounded pauses and clock drift. Martin Kleppmann's critique points out that they provide no fencing token, so a pause breaks them exactly as in the figure.
  • Leader election is the same problem. A deposed leader that has not noticed yet is a paused lock holder. Raft fences it with the term number; any external resource the leader writes to needs the same treatment, for example by including the term or lease revision in every write.

Interview angle

When to bring it up

Whenever your design has a single primary, a coordinator, a scheduler that must run once, or shared configuration. Say "I'll keep this in etcd or ZooKeeper, which use consensus, and elect the leader with a lease" rather than designing a protocol on the whiteboard. Go deep only when asked, and then explain terms, majorities and the election restriction. It is also the core of the key-value store discussion if you choose strong consistency over Dynamo-style quorums.

Follow-ups to expect

  • Why 3 or 5 nodes and not 4? Majority arithmetic: 4 tolerates the same single failure as 3.
  • What happens to the old leader in a partition? It cannot commit, steps down when it sees the higher term, and its uncommitted entries are overwritten.
  • How can a new leader be missing committed data? It cannot: the election restriction plus overlapping majorities.
  • How do you make reads linearizable? ReadIndex or leases; local follower reads can be stale.
  • Your lock holder pauses for 20 seconds. What breaks and how do you fix it? Fencing tokens checked by the storage.
  • Why not put all user data in etcd? One leader per group and small size limits; use consensus for metadata, or shard into many groups.

Red flags

  • "The node with the lowest id becomes leader" or a heartbeat-only failover with no quorum, which produces split brain under partition.
  • Believing a 2-node cluster is fault tolerant.
  • Treating a lease or Redis lock as a correctness guarantee without fencing.
  • Claiming consensus is "available" during a partition on the minority side.
