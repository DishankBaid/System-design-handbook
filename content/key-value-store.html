A distributed key-value store answers two calls, get(key) and put(key, value), across dozens or hundreds of machines that fail independently. Amazon's Dynamo paper set the template: spread keys with consistent hashing, keep N copies, let callers choose how many replicas must answer, track concurrent versions with vector clocks, keep accepting writes when nodes are down, and repair divergence in the background. Cassandra, Riak and Voldemort all follow it. This case study builds that design piece by piece.

How to use this case study

Partitioning is covered in depth in Consistent Hashing and is only summarised here. Other chapters used: Replication (quorums), Consistency Models, CAP & PACELC, Indexing: B-Trees & LSM Trees, Bloom filters.

1. Requirements

Functional

put(key, value) and get(key) for opaque values up to 1 MB. Delete. Optional TTL. No range scans, secondary indexes or multi-key transactions.

Non-functional

Always writable: a shopping cart write must succeed even when some replicas are down or partitioned. p99 latency under 10 ms within a region. Tunable consistency per request. Incremental scaling by adding nodes, with no downtime. No single point of failure and no special nodes.

Out of scope

Cross-region replication details, authentication, and a query language. Mention multi-region as asynchronous replication of the same design.

The key observation: the requirement is availability over consistency, the AP side of CAP. Dynamo was built so that "add to cart" never fails. Accepting writes during failures means replicas can disagree, so the design must detect conflicting versions and repair stale replicas, instead of preventing divergence up front. If the interviewer instead wants strong consistency, the answer is a different design: a store with consensus per shard (one Raft or Paxos group per range), such as TiKV, CockroachDB or Spanner.

2. Estimation

Assume 2 billion keys with 5 KB values on average, 300,000 reads and 100,000 writes per second at peak, N = 3 replicas, and quorums of R = 2 and W = 2.

Per-node load is comfortable for an SSD-backed LSM engine, so the challenges are not raw throughput. They are what happens when one of those 24 nodes is slow, dead or partitioned, and how replicas that missed writes catch up without comparing 651,000 keys one by one.

3. API

get(key)              → [ (value, context), ... ]    // usually one; several if versions conflict
put(key, context, value)                             // context = the version(s) this write replaces
delete(key, context)                                 // a put of a tombstone

Per request:  R (replicas that must answer a read), W (replicas that must ack a write)

GET  /kv/cart:u_481?r=2
→ 200 { "values": [ { "value": "...", "context": "g2AAAAJ..." } ] }
→ 300 Multiple Choices  { "values": [ {...lamp...}, {...mug...} ] }    // siblings
PUT  /kv/cart:u_481?w=2   X-Context: g2AAAAJ...
→ 204

The unusual part is the context: an opaque blob holding the version (vector clock) the client read. Passing it back on put tells the store "this value replaces those versions". A get can return several values, called siblings, when concurrent writes conflicted; the client merges them and writes the result back with a context covering both. Most stores also offer a simpler mode, last-write-wins, which hides siblings at the price of silently dropping some writes.

4. Data model

FieldPurpose
keyUp to a few hundred bytes. Hashed (MD5 or Murmur3) to a position on the ring
valueOpaque bytes; the store never interprets it
clockVector clock: one counter per coordinating node, e.g. {Sx: 3, Sy: 1}
tombstoneMarks a delete, kept long enough (e.g. 10 days) for every replica to learn of it
expires_atOptional TTL, enforced on read and dropped during compaction

Deletes are writes. If a delete simply removed the key from one replica, a replica that missed the delete would later "repair" the others with the old value and resurrect it. The tombstone carries a clock that supersedes the old value, and is only purged after a grace period longer than any repair cycle.

5. High-level design

  1. Route. The client library knows the ring (it gossips or fetches it) and sends the request straight to a node in the key's preference list. A simpler client sends to any node through a load balancer, which forwards it, at the cost of one extra hop.
  2. Coordinate. The receiving replica acts as coordinator. For a write it increments its entry in the vector clock, writes locally, and sends the new version to the other N - 1 replicas. For a read it asks replicas for their versions.
  3. Quorum. The coordinator replies once W replicas acknowledged the write, or R replicas answered the read. Slower replicas still receive the write; the client just does not wait for them.
  4. Repair. Stale replicas are fixed on the read path (read repair), by hinted handoff after short outages, and by periodic Merkle-tree comparison for everything else.

6. Deep dive: partitioning, replication and quorums

Keys are placed with consistent hashing and virtual nodes: hash the key onto the ring, and its preference list is the next N distinct physical nodes clockwise, skipping tokens of nodes already chosen and, in production, nodes in the same rack or availability zone. Adding a node takes small slices from many others; removing one hands its ranges to many successors. That chapter covers the mechanics; here the interesting part is what happens across those N replicas.

N, R, WBehaviourGood for
3, 2, 2R + W > N: reads overlap the last write quorum; tolerates one slow or failed replica for bothThe usual default
3, 1, 3Fast reads; a write fails if any replica is downRead-mostly data that rarely changes
3, 3, 1Writes always fast and available; reads need every replicaWrite-heavy logging, rarely read
3, 1, 1Fastest, but reads may miss recent writesCaches, metrics, data where staleness is fine

Even R + W > N is not linearizability. Sloppy quorums (below) can place a write outside the normal replicas, and two concurrent writes can both "succeed". Quorums give a high probability of reading recent data, not a guarantee; say so explicitly in an interview. See Replication for the general treatment.

7. Deep dive: versioning and conflict resolution

Because any replica can accept a write, two clients can update the same key through different coordinators while the network is split. The store needs to know whether one version replaced the other or whether they are concurrent. Wall-clock timestamps cannot answer that: clocks drift, and "later" does not mean "saw the earlier one". A vector clock can. Each version carries a map from node to counter; the coordinating node increments its own counter on each write. Version a descends from b if every counter in a is at least the one in b. If neither descends from the other, they are concurrent.

def descends(a, b):
    """True if clock a has seen everything clock b has."""
    return all(a.get(node, 0) >= n for node, n in b.items())


def compare(a, b):
    if a == b:
        return "equal"
    if descends(a, b):
        return "a is newer"
    if descends(b, a):
        return "b is newer"
    return "concurrent"                     # siblings: keep both, let the reader merge


def bump(clock, node):
    """The coordinating node increments its own entry on every write."""
    return {**clock, node: clock.get(node, 0) + 1}


def merge(a, b):
    return {node: max(a.get(node, 0), b.get(node, 0)) for node in a.keys() | b.keys()}


d1 = bump({}, "Sx")                          # cart = {book}
d2 = bump(d1, "Sx")                          # cart = {book, pen}
d3 = bump(d2, "Sy")                          # one client adds lamp via Sy
d4 = bump(d2, "Sz")                          # another adds mug via Sz, at the same time
print(d2, compare(d2, d1))
# {'Sx': 2} a is newer
print(d3, d4, compare(d3, d4))
# {'Sx': 2, 'Sy': 1} {'Sx': 2, 'Sz': 1} concurrent
d5 = bump(merge(d3, d4), "Sx")               # a reader sees both, unions the carts, writes back
print(dict(sorted(d5.items())), compare(d5, d3), compare(d5, d4))
# {'Sx': 3, 'Sy': 1, 'Sz': 1} a is newer a is newer
  • Clock size. Clocks grow by one entry per coordinating node. Because writes for a key are usually coordinated by its first few preference-list nodes, they stay small; Dynamo also truncated the oldest entry beyond a threshold (around 10), accepting rare false conflicts.
  • Union merges resurrect deletes. If one sibling removed "pen" and the other added "lamp", a plain union brings "pen" back. Amazon accepted that for carts. Data types designed for merging (CRDTs, such as an observed-remove set) fix it, and Riak ships them.
  • Last-write-wins is what Cassandra does instead: each cell carries a timestamp and the highest one wins. No siblings, no client merge logic, and concurrent updates are silently lost. It is the right choice when values are overwritten wholesale and losing a concurrent write is acceptable.

8. Deep dive: failures, repair and membership

Sloppy quorum and hinted handoff

A strict quorum fails writes when two of the three preference-list replicas are unreachable. To stay writable, Dynamo uses a sloppy quorum: the write goes to the first N healthy nodes walking the ring, and a node standing in for a down replica stores the write with a hint naming the intended owner.

Hinted handoff covers outages of minutes to hours. Hints are capped (Cassandra stops collecting them after 3 hours by default), because a node that is gone for days should be rebuilt, not trickle-fed millions of hints.

Anti-entropy with Merkle trees

Replicas still drift: a hint is lost when the hinting node dies, a replica misses writes while hints were capped, a disk silently corrupts a file. Background anti-entropy compares replicas and copies what differs. Comparing 651,000 keys per range key by key would move gigabytes. A Merkle tree makes it cheap: each leaf hashes a slice of the key range, each parent hashes its children, and two replicas walk down from the root only where hashes differ.

The catch is maintenance. Trees cover key ranges, so ownership changes (a node joining) invalidate them, and keeping them current under heavy writes costs CPU. Cassandra builds them on demand during a repair run rather than continuously. Operators schedule full repairs within the tombstone grace period, so no replica can outlive a delete it never saw.

Gossip membership and failure detection

  • Gossip. Every second, each node picks a random peer and exchanges its view of the cluster: each node's status, token ownership and a heartbeat counter that only its owner increments. Information spreads like an epidemic, reaching all 24 nodes in about eight rounds, with no central registry to fail.
  • Failure detection. A node that has not seen a peer's heartbeat increase is not instantly "dead". The phi accrual detector, used by Cassandra and Akka, learns the normal distribution of heartbeat gaps for each peer and outputs a suspicion level that rises continuously with silence; a threshold turns it into "down". A peer on a briefly congested link is not declared dead as quickly as one that went silent on a usually punctual link.
  • Local view only. "Down" is each node's own opinion and only changes where it sends requests and hints. Permanently removing a node from the ring is an explicit operator action, so a network blip never triggers mass data movement.

9. Deep dive: the storage engine

Each node stores its ranges in a log-structured merge tree, the engine behind Cassandra, ScyllaDB, RocksDB and LevelDB. It turns random writes into sequential ones, which suits a store that takes 12,500 replica writes per second per node. Indexing: B-Trees & LSM Trees covers the engine in depth; this is how it serves the KV store.

  • Write path. Append to the commit log (fsync in batches every few milliseconds, or per write for the strictest durability), insert into the memtable, acknowledge. When the memtable reaches its size limit (tens to hundreds of MB) it is written out as an immutable sorted file, an SSTable, and the log segment is discarded.
  • Read path. Check the memtable, then SSTables newest to oldest. Each SSTable has a Bloom filter that rules most files out without disk I/O, and a sparse index that points to the right block. A hot read path is backed by a block cache in RAM.
  • Compaction. Background merges combine SSTables, keep the newest version of each key, and purge tombstones older than the grace period. Size-tiered compaction favours write throughput; leveled compaction keeps reads to about one file per level at the cost of more rewriting. This is why nodes are kept half full: compaction needs room to write the merged output before deleting its inputs.

11. Key trade-offs to state

  • Availability over consistency: always writable under failures and partitions, in exchange for conflicts that someone must resolve.
  • Vector clocks and siblings vs last-write-wins: no lost updates but merge logic in the client, versus simplicity with silent loss of concurrent writes.
  • Tunable R and W: per-request choice between latency and freshness, in exchange for a system whose guarantees depend on configuration.
  • Leaderless, symmetric nodes: no failover and no single bottleneck, in exchange for gossip, repair and conflict machinery that a leader-based design would not need.
  • LSM storage: cheap writes, in exchange for compaction work and multi-file reads.
Interview angle

What the interviewer is checking

Whether you can assemble the standard building blocks into a coherent whole and explain why each exists: partitioning for scale, replication for durability, quorums for tunable consistency, versioning for conflicts, hinted handoff and Merkle trees for repair, gossip for membership, LSM for write throughput.

Follow-ups to expect

  • With N = 3, which R and W would you choose, and what does R + W > N actually guarantee?
  • Two clients write the same key during a partition. What does the next reader see?
  • A replica was down for 20 minutes. How does it catch up? And for 5 days?
  • How do you find which keys differ between two replicas without comparing all of them?
  • How does a node learn that another node died, and what stops a network blip from causing chaos?
  • Why do deletes need tombstones?

Red flags

  • Resolving conflicts with wall-clock timestamps while claiming no writes are lost.
  • Claiming R + W > N gives strong consistency.
  • Deleting keys outright on one replica.
  • A master node that holds the ring or routes every request.
  • Repair by full key-by-key comparison.
