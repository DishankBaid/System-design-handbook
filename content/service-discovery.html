Why it matters

The checkout service needs to call the payments service. Yesterday payments ran on three machines at 10.0.1.17, 10.0.2.31 and 10.0.3.8. This morning the autoscaler added two more, a deploy replaced all of them, and one host died at 04:12. Nobody edited a config file, yet checkout must keep finding a healthy payments instance on every request.

In a data center of fixed servers, addresses lived in config files and changed a few times a year. In the cloud and on Kubernetes, instances are cattle: they get a fresh IP every time they start, they live for hours or minutes, and the number of them follows the traffic curve. A hard-coded address list is wrong within a day.

Service discovery is the mechanism that maps a logical service name (payments) to the current set of healthy network locations (ip:port pairs) and keeps that mapping fresh as instances come and go. Every system with more than a handful of services has one, whether it is a dedicated registry, DNS, or a platform feature such as Kubernetes Services. It is the plumbing under load balancing and a prerequisite for microservices.

A discovery system has to do four jobs:

  1. Register. Record that a new instance of payments exists at 10.0.4.22:8443.
  2. Track health. Notice when an instance crashes, hangs or is being shut down, and stop handing it out.
  3. Answer lookups. Return the healthy instances for a name, fast, at the rate of every outgoing call (or every connection).
  4. Propagate changes. Get updates to every caller quickly, because a caller with a stale list keeps sending traffic to a dead box.

Client-side vs server-side discovery

There are two places to put the lookup, and the choice shapes everything else.

In client-side discovery, the caller asks the registry for the instance list, caches it, picks one instance itself (round robin, least requests, zone-aware) and connects directly. In server-side discovery, the caller sends the request to a stable address, a load balancer or proxy, and that component consults the registry and forwards the request.

A service mesh blends the two: the lookup is client-side in the sense that it happens next to the caller, but it lives in a sidecar proxy, so the application code stays as simple as in the server-side model.

The service registry

A service registry is a small, highly available database of service instances. Each entry holds the service name, address, port, metadata (version, zone, weight) and a health status. The interesting design questions are how entries get in, how dead entries get out, and how callers hear about changes.

Registration: who writes the entry

Self-registration

The instance calls the registry on startup and deregisters on shutdown. The Eureka client inside a Spring Boot app works this way. Simple, but every service in every language must embed the logic and get it right.

Third-party registration

Something else watches the platform and writes entries: the Kubernetes endpoints controller, a Consul agent reading a service definition, AWS Cloud Map with ECS. The application knows nothing about discovery.

Graceful shutdown should always deregister explicitly. Most instance removals are planned (deploys, scale-in), and an explicit deregistration takes effect in milliseconds. The timeout machinery below exists for the unplanned cases: crashes, kernel panics, network cuts and hung processes.

Heartbeats, TTLs and health checks

The registry cannot see a crash directly. It learns about it from silence, using one of two models:

  • Leases with heartbeats (push). The instance holds a lease with a time to live (TTL) and renews it by sending a heartbeat every few seconds. If renewals stop, the lease expires and the entry is removed. etcd leases, ZooKeeper sessions (whose ephemeral znodes vanish when the session expires), Consul TTL checks and Eureka renewals all work this way.
  • Active health checks (pull). Something probes the instance, for example GET /healthz every 10 seconds, and marks it unhealthy after a few failures. Consul agents run HTTP, TCP and gRPC checks locally on each node; the Kubernetes kubelet runs readiness probes.

A heartbeat proves the process can send packets. A probe of a real endpoint proves it can serve requests, which catches a deadlocked worker pool that still has a live heartbeat thread. Both are bounded by the same trade-off: detection time is roughly interval × allowed misses, and shortening it raises the rate of false removals during GC pauses and network blips.

Getting changes to callers: poll or watch

Removing the entry from the registry is half the job. Callers cache the instance list, because asking the registry on every request would make it the busiest service in the company. The question is how fast the cache learns about changes.

  • Polling. The client re-fetches the list every N seconds. Simple and robust, but adds up to N seconds of staleness to every change. Eureka clients poll every 30 seconds by default.
  • Watches. The client holds a long-lived request and the registry answers when something changes: etcd watches on a key prefix, ZooKeeper watches (classically one-shot and re-armed after each event; persistent watches since 3.6), Consul blocking queries, the Kubernetes watch API. Changes arrive in milliseconds.

The simulation below makes the difference concrete. Three payments instances heartbeat every 10 seconds with a 30 second TTL, a caller sends 300 requests per second round robin, and 10.0.1.17 hangs at t = 100 s.

INSTANCES = ["10.0.1.17", "10.0.2.31", "10.0.3.8"]
DEAD = "10.0.1.17"


def simulate(heartbeat, ttl, client_refresh, crash_at=100, rps=300, end=400):
    """One-second ticks. DEAD stops heartbeating at crash_at.
    Returns (removed_from_registry_at, client_stopped_at, failed_requests)."""
    last_beat, registry, view = {}, set(), []
    removed_at = stopped_at = None
    failed = 0
    for t in range(end):
        for ip in INSTANCES:
            if t % heartbeat == 0 and not (ip == DEAD and t >= crash_at):
                last_beat[ip] = t
                registry.add(ip)
        for ip in list(registry):
            if t - last_beat[ip] > ttl:          # lease expired
                registry.discard(ip)
                removed_at = t
        if t % client_refresh == 0:              # client re-reads the registry
            view = sorted(registry)
        if t >= crash_at and DEAD in view:
            failed += rps // len(view)           # round-robin share sent to the dead box
        elif t >= crash_at and stopped_at is None:
            stopped_at = t
    return removed_at, stopped_at, failed


for name, hb, ttl, refresh in [
    ("poll every 30 s, TTL 30 s", 10, 30, 30),
    ("watch (push),   TTL 30 s", 10, 30, 1),
    ("watch (push),   TTL 15 s", 5, 15, 1),
]:
    removed, stopped, failed = simulate(hb, ttl, refresh)
    print(f"{name}: removed t={removed}s, client stops t={stopped}s, failed requests={failed:,}")

# poll every 30 s, TTL 30 s: removed t=121s, client stops t=150s, failed requests=5,000
# watch (push),   TTL 30 s: removed t=121s, client stops t=121s, failed requests=2,100
# watch (push),   TTL 15 s: removed t=111s, client stops t=111s, failed requests=1,100

Polling more than doubles the damage here, because the client only re-read the list 29 seconds after the registry already knew. Shrinking the TTL halves it again. In practice the failed requests are not all user-visible: a caller with retries and outlier detection re-sends a failed call to another instance and ejects a host after a few consecutive errors, which shrinks the window from seconds to a handful of requests. Discovery and client-side resilience work together; neither is enough alone.

Worked example: how stale can a caller be?

Every cache layer between the registry and the caller adds delay. Netflix's Eureka stack is the classic illustration because it has several layers, each with a sensible-looking default. Worst case for a caller to stop using a crashed instance:

Lease expiry 90 s lease, doubled by renew() bug = 180 s Eviction task runs every 60 s, just missed + 60 s Server response cache read-only cache refresh + 30 s Client registry fetch poll every 30 s + 30 s Ribbon server list load balancer refresh every 30 s + 30 s ------ Worst case ≈ 330 s, 5.5 minutes

The lease line surprises people: the documented lease is 90 seconds, but Lease.java itself notes that renew() sets the timestamp one duration ahead, so real expiry is 2 × 90 s. The bug is deliberately left unfixed. Many write-ups quote 240 seconds because they miss it.

Five and a half minutes of a third of the traffic hitting a dead instance is why Eureka users lean so hard on client retries, and why newer systems prefer push. The equivalent path in Kubernetes is much shorter:

Readiness probe periodSeconds 10 × failureThreshold 3 ≈ 30 s EndpointSlice update controller writes, watchers notified ≈ 1 s kube-proxy reprograms iptables / IPVS on each node ≈ 1 s ------ Worst case ≈ 30 to 35 s

Tuning either stack is a trade between detection speed and false positives. A 1 second heartbeat with a 3 second TTL detects crashes fast, and also removes every instance that hits a 4 second garbage collection pause.

DNS-based discovery

The oldest registry in the world is DNS, and every language already has a client for it. A name such as payments.service.consul or payments.shop.svc.cluster.local resolves to the A records of current instances. SRV records (RFC 2782) carry port, priority and weight as well, so instances need not share a port.

DNS works well as the interface and badly as the whole system:

  • Caching ignores your TTL. Stub resolvers, sidecar caches and language runtimes cache answers on their own terms. The JVM caches successful lookups for 30 seconds by default, and forever when a security manager is installed, unless networkaddress.cache.ttl is set.
  • Connection pools resolve once. Many HTTP and database clients look up the name when they open a connection and reuse it for hours. A perfect DNS answer does nothing for a connection that already exists.
  • No health or load information. Plain DNS cannot say which instance is overloaded. Clients usually take the first address, so ordering matters, and a response is capped in size, so you cannot return hundreds of instances.

Registries that offer a DNS interface (Consul, CoreDNS in Kubernetes) fix the health part by answering only with instances whose checks pass, and by setting a low TTL. The caching problems stay on the client side, which is why the data-plane approaches below exist.

Kubernetes Services

Kubernetes builds discovery into the platform, so most teams on it never run a separate registry. Pods get new IPs on every restart; a Service gives a set of pods (selected by labels such as app=payments) one stable name and one stable virtual IP.

  • Endpoints. The control plane watches pods matching the selector and writes their IPs into EndpointSlice objects (up to 100 endpoints each by default). A pod is listed as ready only while its readiness probe passes, so the kubelet's probe is the health check.
  • ClusterIP. The default Service type gets a virtual IP, for example 10.96.12.7. No process listens on it. kube-proxy on every node watches EndpointSlices and programs kernel rules (iptables, IPVS, or nftables in recent versions) that rewrite packets for 10.96.12.7:80 to a randomly chosen ready pod.
  • DNS. CoreDNS serves payments.shop.svc.cluster.local as an A record pointing at the ClusterIP. Because the IP never changes, client-side DNS caching stops being a problem.
  • Headless Services. With clusterIP: None there is no virtual IP; DNS returns the IPs of every ready pod. Use it when the client must pick pods itself: databases with a primary, StatefulSets with stable per-pod names like kafka-0.kafka.data.svc.cluster.local, or gRPC clients doing their own balancing.
Common mistake: gRPC behind a ClusterIP

kube-proxy balances connections, not requests. HTTP/2 and gRPC clients open one long-lived connection and multiplex every request over it, so all traffic from a checkout pod lands on one payments pod while the others sit idle, and new pods added by the autoscaler get nothing. Fix it with a headless Service plus client-side balancing (gRPC's DNS resolver with round_robin), a periodic maximum connection age on the server, or an L7 proxy or mesh that balances per request.

A second Kubernetes-specific trap is shutdown. When a pod is deleted, the kubelet sends SIGTERM and the endpoint removal propagates to every node in parallel. For a second or two, other nodes still route new connections to a pod that is already exiting. The standard fix is a preStop hook that sleeps a few seconds before the app starts shutting down, so it keeps serving until every node has dropped it.

Service mesh: discovery in the data plane

A service mesh moves discovery, load balancing, retries, timeouts and mutual TLS out of application libraries and into a proxy that runs next to every instance, usually as a sidecar container in the same pod. The application calls http://payments on localhost; the sidecar knows the real endpoints.

A mesh has two halves, and the split is the key idea:

Data plane

The proxies that carry every request, typically Envoy. Each holds the full endpoint list for the services it calls and balances per request using live latency and error data. Fast path, no central hop.

Control plane

The component that watches the platform (Kubernetes API, Consul catalog) and pushes configuration to every proxy. In Istio this is istiod. It is off the request path: if it goes down, proxies keep routing with their last configuration.

The control plane talks to Envoy over xDS, a family of gRPC streaming APIs: LDS for listeners, RDS for HTTP routes, CDS for upstream clusters, EDS for the endpoints in each cluster, and SDS for certificates. Discovery proper is EDS: when a payments pod becomes ready, istiod pushes an updated endpoint list to every proxy that calls payments, typically within a second.

The mesh costs a proxy per pod (memory, CPU, and a fraction of a millisecond per hop) and a complex control plane to operate. Two newer variants reduce that: Istio's ambient mode replaces sidecars with a per-node proxy for L4 and optional per-service proxies for L7, and proxyless gRPC lets gRPC clients speak xDS directly, getting mesh discovery with no proxy at all.

CP or AP: how consistent must the registry be?

A registry is a replicated database, so the CAP question applies: during a network partition, does it refuse to answer (CP) or answer with possibly stale data (AP)?

  • CP registries. ZooKeeper (ZAB), etcd (Raft) and Consul's servers (Raft) replicate writes through a consensus quorum. A minority partition cannot register instances, and linearizable reads fail there too. This is exactly what you want for leader election and locks.
  • AP registries. Eureka servers replicate to each other asynchronously and each answers from its own copy. During a partition both sides keep accepting registrations and serving reads, and they reconcile afterwards.

For discovery, the AP argument is strong. The data is already stale by the time it reaches a caller, and callers can survive a wrong entry (a failed call gets retried elsewhere). What callers cannot survive is no answer: a service that cannot find payments at all is down. So even CP registries are used in an AP way. Consul offers stale reads that any server can answer, and every good discovery client caches its last known list and keeps using it when the registry is unreachable.

Eureka's self-preservation mode

Eureka adds one more guard. If a server receives fewer heartbeat renewals in the last minute than 85% of what it expects, it assumes the problem is the network between it and the instances, not mass death, and stops expiring leases. The reasoning: twenty instances failing at once is far less likely than one switch failing, and wrongly deleting healthy instances is worse than keeping some dead ones, because callers can retry past a dead one but cannot call an instance they do not know about. The cost is that during a real mass failure, the registry keeps advertising dead instances until renewals recover.

The practical rule: on Kubernetes, use Services and add a mesh only when you need per-request balancing, mTLS or traffic shifting. Across VMs, several clusters or several platforms, Consul is the common choice. Use ZooKeeper or etcd directly when you already run them for coordination and want discovery from the same system.

In the real world

  • Netflix built Eureka for AWS, where instances churn constantly and partitions between availability zones happen. Paired with the Ribbon client-side balancer, it was the reference for client-side discovery and became the default in Spring Cloud.
  • Airbnb SmartStack (2013) ran two small daemons per host: Nerve health-checked local services and registered them in ZooKeeper, and Synapse watched ZooKeeper and rewrote a local HAProxy config. Applications called localhost, an early form of the sidecar pattern.
  • Lyft built Envoy to replace a similar setup. Its first discovery service was a simple eventually consistent REST endpoint, because Lyft argued that discovery data does not need strong consistency, and xDS grew out of that API.
  • Kubernetes made discovery a platform primitive: every Service gets a DNS name and a stable virtual IP, with readiness probes as the health check.
  • Twitter's Finagle used ZooKeeper serversets: each instance creates an ephemeral znode, and clients watch the parent node and balance across children.
Interview angle

When to bring it up

As soon as you draw two services talking to each other and say they autoscale. One sentence usually suffices: "Instances register in the platform's registry (Kubernetes Services, or Consul elsewhere); callers resolve by name and balance client-side or through the mesh." Go deeper if the interviewer asks how failures are detected or what happens when the registry is down.

Follow-ups to expect

  • Client-side or server-side discovery? Give the hop count, the polyglot cost, and where a mesh fits.
  • How fast is a dead instance removed? Interval times misses, plus propagation; mention push vs poll and client retries.
  • What happens if the registry goes down? Cached lists keep traffic flowing; only changes stop.
  • Should the registry be CP or AP? Discovery tolerates stale data far better than no data.
  • Why does gRPC traffic not balance on Kubernetes? Connection-level balancing; use headless Services or an L7 proxy.

Red flags

  • Hard-coding instance IPs or relying on DNS with a long TTL for autoscaled services.
  • Putting a registry query on the path of every request with no client cache.
  • Health checks that call the database, so one dependency failure delists the whole fleet.
  • Treating the registry as the source of truth for correctness (for example leader election) while running it in an AP mode.
