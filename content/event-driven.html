Why it matters

When an order is placed, six things must happen: charge the card, reserve stock, create a shipment, email the customer, update the analytics warehouse and award loyalty points. If the order service calls each of those services directly, it must know all six, wait for all six, and fail when any one of them is down. Every new feature that cares about orders means another change to the order service.

In an event-driven architecture, the order service instead announces a fact, OrderPlaced, and stops there. Each interested service subscribes and reacts on its own schedule. Adding a seventh reaction means deploying a new subscriber, without touching the order service. The coupling moves from "who do I call" to "what does this event look like", which is a smaller and more stable contract.

The price is that the system's behaviour is no longer visible in any one place. A request becomes a chain of asynchronous reactions across services and topics, consistency becomes eventual, and failures surface minutes later in a different service. This chapter covers the patterns, and the engineering needed to keep them understandable. The transport underneath is usually a log like Kafka (Pub/Sub & Event Streaming) or a broker with fan-out (Message Queues).

Events, commands and queries

Three kinds of message look similar on the wire but mean very different things. Getting the distinction right is most of the design.

Event

A fact that already happened, named in the past tense: OrderPlaced, PaymentCaptured. The sender does not know or care who listens. Zero, one or many consumers. Cannot be rejected, only reacted to.

Command

A request for a specific receiver to do something, in the imperative: ChargeCard, ReserveStock. Exactly one handler. Can fail or be refused, so the sender usually needs a reply.

Query

A request for information that changes nothing: GetOrderStatus. Usually synchronous (HTTP, gRPC), because the caller is waiting for the answer.

A common smell is a command dressed up as an event: SendWelcomeEmail published to a topic. It has one intended receiver and the sender depends on it happening, so the decoupling is fake. Either publish the fact (UserRegistered) and let the email service decide, or send a command to the email service's queue and admit the dependency.

Three ways to use events

Martin Fowler's taxonomy (which also lists CQRS, covered in its own chapter) separates patterns that are often lumped together as "event-driven":

Event notification

The event is thin: it says what happened and carries an identifier. {"type": "OrderPlaced", "order_id": 81723}. Consumers that need details call back to the source. The event is small and the source stays the only owner of the data, but every consumer adds read load to the source and depends on it being up when the event is processed.

Event-carried state transfer

The event is fat: it carries the data consumers need, so they never call back. CustomerAddressChanged includes the full new address, and the shipping service keeps its own local copy of customer addresses. Consumers are fully decoupled at runtime and reads are local and fast. In exchange, data is duplicated across services, each copy is eventually consistent, and the event schema becomes a much larger contract.

Event sourcing

The third pattern goes further: the events are the source of truth, and current state is derived by replaying them. That changes how a service stores data, not just how it communicates, and it has its own chapter: CQRS & Event Sourcing. Events used for integration between services and events used for storage inside one service should usually be different events, because internal storage events change with the implementation while integration events are a public contract.

Choreography vs orchestration

A business process that spans services, such as placing an order, needs something to drive it forward and to undo completed steps when a later one fails. There are two ways to arrange that.

Choreography

In choreography, there is no coordinator. Each service listens for events and emits its own; the process emerges from the chain of reactions.

Orchestration

In orchestration, one component, the orchestrator, owns the process. It sends commands to services, waits for replies, persists its progress, and decides what to do next, including compensating actions when a step fails. This is the saga pattern from Distributed Transactions, implemented as an explicit state machine.

ChoreographyOrchestration
Where the flow livesImplicit, spread across subscribersExplicit, in one state machine
CouplingServices only know event schemasOrchestrator knows every participant's commands
Adding a reactionDeploy a new subscriber, nothing else changesChange the orchestrator
Failure handling and compensationEach service must know which events mean "undo"Central, testable, with timeouts per step
Answering "where is order 81723 stuck?"Correlate logs across servicesLook at the saga's state
Single point of failureNone beyond the busThe orchestrator, so it must be persistent and replicated

A practical rule: use choreography for loosely related reactions to a fact (send an email, update search, award points), where adding a listener should not require anyone's permission. Use orchestration for a process with ordered steps, a business outcome and compensations, such as order fulfilment, loan approval or account onboarding. Most real systems mix them: an orchestrated saga for fulfilment that publishes OrderConfirmed, which a dozen services consume by choreography. Workflow engines such as Temporal, AWS Step Functions and Camunda exist to make orchestrators durable without hand-writing the state persistence.

Event schema design and evolution

An event published to a shared topic is a public API with consumers you may not know about. Once it is published, it is also permanent: events retained in a log or an event store will be read years later by code that did not exist when they were written.

The envelope

Every event should carry the same metadata, whatever its payload. The CNCF CloudEvents specification standardises most of it.

{
  "id": "9b2f6c1e-4d0a-4c4e-9a63-2f1d8c0e7b51",   // unique per event: the deduplication key
  "type": "com.shop.order.OrderPlaced",
  "specversion": "1.0",
  "source": "/services/order",
  "time": "2026-10-09T14:03:27.512Z",             // when it happened, not when it was sent
  "subject": "order/81723",                        // the entity: also the partition key
  "dataschema": "registry://orders/OrderPlaced/3",
  "correlationid": "c-5f1a9e",                     // extension: same for the whole business flow
  "causationid": "evt-77e2...",                    // extension: the event that caused this one
  "data": { "order_id": 81723, "customer_id": 4411, "total_cents": 4200, "currency": "USD",
            "lines": [ { "sku": "MUG-RED-12OZ", "qty": 2, "unit_cents": 2100 } ] }
}

Design rules that save pain later: name events for business facts, not database changes (OrderCancelled, not OrderRowUpdated); include the entity id and a timestamp of the business occurrence; use explicit units and currencies (total_cents plus currency, never a bare float); and include enough state that common consumers do not need to call back.

Compatibility and a schema registry

Producers and consumers deploy independently, so for some period an old consumer reads new events and a new consumer reads old ones. A schema registry (Confluent Schema Registry, AWS Glue Schema Registry, Apicurio) stores every version of each event schema and rejects a new version that breaks the configured compatibility rule. Producers embed a schema id in each message, so consumers can always find the exact schema it was written with.

ModeGuaranteeWho upgrades firstTypical allowed change
BackwardNew consumers can read data written with the previous schemaConsumersDelete a field; add a field with a default
ForwardOld consumers can read data written with the new schemaProducersAdd a field; delete a field that had a default
FullBoth directionsEither, in any orderAdd or remove only fields that have defaults
*_TransitiveSame, checked against every earlier version, not just the lastAs aboveRequired when consumers replay old data from a long-retention log

Format choice shapes what is possible. Avro resolves the writer's schema against the reader's schema by field name, using defaults for missing fields; it is compact and the registry's original home. Protobuf identifies fields by number, so renaming is free but a field number must never be reused (mark removed ones reserved). JSON Schema is the most readable and the loosest; it is easy to publish JSON that no schema checks at all. When a change cannot be made compatibly (a field changes meaning), publish a new event type or version (OrderPlaced.v2) and run both until old consumers migrate.

Eventual consistency and the user experience

In an event-driven flow, the moment the user clicks "Place order" is not the moment the order is confirmed. Payment may take a second, stock reservation another 50 ms, and the search index or "my orders" page might reflect the order a few seconds later. If the UI pretends otherwise, users see confusing states: an order missing from their order list right after they placed it, or a confirmation that is later revoked.

  • Design the intermediate state. Return 202 Accepted with an order id and show "Order received, confirming payment". Push the final status over a WebSocket or SSE connection, or poll a status endpoint (Polling, SSE & WebSockets).
  • Read your own writes. Serve "my orders" for the user who just ordered from the order service's own database, not from a read model fed by events, or merge the just-created order into the response on the client.
  • Optimistic UI only for safe actions. Showing a "like" immediately is fine. Showing "payment successful" before payment succeeded is not.
  • Make the lag measurable. Track the time from event creation to each consumer's processing, and set an SLO for it ("search reflects new products within 30 seconds at p99"). See Consistency Models for the vocabulary.

Debugging and tracing async flows

With synchronous calls, a stack trace or a single trace shows what happened. With events, the "call stack" is spread across topics, services and time. Three pieces of metadata make it recoverable:

  • Correlation id. Generated once at the edge (the HTTP request that placed the order) and copied onto every event and command in the flow. Searching logs for correlationid=c-5f1a9e returns the whole story of order 81723.
  • Causation id. The id of the event that directly caused this one. Correlation tells you which flow; causation rebuilds the tree within it, which matters when one event fans out into several.
  • Trace context in message headers. OpenTelemetry propagates the W3C traceparent header through Kafka or AMQP message headers, so a distributed trace continues across the asynchronous hop and shows queueing time as a gap between spans. See Observability.

Beyond tracing: keep an event catalogue (who produces and who consumes each event type, generated from code or documented with AsyncAPI), make DLQs visible per consumer, and build a way to replay a single event to a single consumer. The first production incident without these tools usually pays for them.

Publishing reliably: the outbox and CDC

The order service must do two things when an order is placed: write the order to its database and publish OrderPlaced. These are two different systems, and no local transaction spans both. This is the dual-write problem:

  • Write the database, then publish: a crash between the two leaves an order that no other service will ever hear about.
  • Publish, then write: a crash between the two announces an order that does not exist.
  • Publish inside the database transaction: the publish cannot be rolled back if the commit fails, and a slow broker now holds database locks.

The transactional outbox removes the second system from the transaction. The service writes the event as a row in an outbox table in the same local transaction as the business change. A separate relay reads the outbox and publishes to the broker, retrying until it succeeds. Either both the order and its event exist, or neither does; publishing is then at-least-once, so consumers deduplicate by event id.

There are two ways to run the relay:

  • Polling publisher. A loop selects unpublished rows in order, publishes them, marks them published. Simple, works on any database, adds query load and some latency (the poll interval).
  • Change data capture (CDC). A connector such as Debezium reads the database's replication log (PostgreSQL logical decoding, the MySQL binlog) and turns committed changes into Kafka records, typically within milliseconds and without polling. Debezium's outbox event router maps outbox rows to topics and keys. CDC can also publish changes to ordinary tables directly, but that leaks your internal schema as a public contract; the outbox table lets you publish deliberate events instead.

The code below shows the outbox end to end with SQLite: the order and its event commit atomically, the relay crashes after publishing but before marking the row, and the consumer's deduplication absorbs the resulting duplicate.

import json
import sqlite3
import uuid

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE orders (id INTEGER PRIMARY KEY, customer TEXT, total_cents INTEGER, status TEXT);
CREATE TABLE outbox (seq INTEGER PRIMARY KEY AUTOINCREMENT, event_id TEXT, topic TEXT,
                     payload TEXT, published INTEGER DEFAULT 0);
""")


def place_order(order_id, customer, total_cents):
    """The order row and its event commit together, or not at all. No dual write."""
    event = {"event_id": str(uuid.uuid4()), "type": "OrderPlaced", "version": 2,
             "order_id": order_id, "customer": customer, "total_cents": total_cents}
    with db:  # one local ACID transaction
        db.execute("INSERT INTO orders VALUES (?, ?, ?, 'PLACED')", (order_id, customer, total_cents))
        db.execute("INSERT INTO outbox (event_id, topic, payload) VALUES (?, 'orders', ?)",
                   (event["event_id"], json.dumps(event)))


def relay(publish, crash_after_publish=False):
    """Poll the outbox in order and publish. Debezium does this by tailing the WAL instead."""
    rows = db.execute("SELECT seq, topic, payload FROM outbox WHERE published = 0 ORDER BY seq").fetchall()
    for seq, topic, payload in rows:
        publish(topic, json.loads(payload))
        if crash_after_publish:
            print("relay crashed after publishing, before marking the row")
            return
        with db:
            db.execute("UPDATE outbox SET published = 1 WHERE seq = ?", (seq,))


processed = set()  # in production: a table written in the same transaction as the side effect


def email_service(topic, event):
    if event["event_id"] in processed:
        print(f"  duplicate {event['type']} for order {event['order_id']} ignored")
        return
    processed.add(event["event_id"])
    print(f"  emailing {event['customer']}: order {event['order_id']} "
          f"for ${event['total_cents'] / 100:.2f} received")


place_order(81723, "ana@example.com", 4200)
place_order(81724, "raj@example.com", 1750)
relay(email_service, crash_after_publish=True)   # publishes 81723, dies before marking it
print("relay restarted")
relay(email_service)                             # republishes 81723 (at-least-once), then 81724
print("unpublished rows left:", db.execute("SELECT COUNT(*) FROM outbox WHERE published = 0").fetchone()[0])

Output:

  emailing ana@example.com: order 81723 for $42.00 received
relay crashed after publishing, before marking the row
relay restarted
  duplicate OrderPlaced for order 81723 ignored
  emailing raj@example.com: order 81724 for $17.50 received
unpublished rows left: 0

The outbox makes publishing reliable, not exactly-once. That is why the event id in the envelope matters: it is the key every consumer uses to discard the duplicate. The Idempotency chapter covers storing that key atomically with the side effect.

Pitfalls

Event storms

A consumer reacts to an event by emitting events that other consumers react to, sometimes in a cycle. A bulk import of 2 million products fires 2 million ProductUpdated events, each triggering search reindexing, cache invalidation and recommendation recomputation. Guard with batch events for bulk operations, rate limits on consumers, and loop detection via causation chains.

Hidden coupling

Services look decoupled but rely on unstated facts: that PaymentCaptured always follows OrderPlaced within a minute, or that a field is never null. The coupling is still there, just invisible to the compiler. Document contracts, test them with consumer-driven contract tests, and keep a catalogue of who consumes what.

Ordering

Events about one entity can arrive out of order across partitions, after retries, or from different producers. Key events by entity id so they share a partition, carry a per-entity version number, and make consumers ignore stale versions.

Duplicates

Every hop is at-least-once: the outbox relay, the broker, the consumer's offset commit. Every consumer needs an idempotency strategy, usually a processed-event table keyed by event id or a natural idempotent write.

Lost failures

A consumer that fails puts the event in a DLQ, and the user's order stays "confirming payment" forever. Every saga step needs a timeout, and stuck flows need an alert and a dashboard.

Distributed monolith

If every feature still needs coordinated changes to five services and their events, the system has the costs of distribution and the coupling of a monolith. See Monolith vs Microservices.

Worked example: the order-placed flow

An online retailer takes 3 million orders per day, with flash sales peaking at 10 times the average rate. The flow: the order service accepts the order (outbox), an orchestrated saga charges payment and reserves stock, and on confirmation an OrderConfirmed event fans out by choreography to email, search, analytics and loyalty. Each order produces about 8 events over its lifetime (placed, payment authorised, stock reserved, confirmed, shipment created, shipped, delivered, plus one notification event), averaging 1 KB.

Orders 3,000,000 / 86,400 s ≈ 35/s average, ~350/s peak Events 3M × 8 = 24M/day ≈ 280/s average, ~2,800/s peak Bandwidth 2,800/s × 1 KB ≈ 2.8 MB/s peak: small for any broker Inventory 50 reservations/s per consumer (20 ms DB write each) 350 / 50 = 7 consumers → 12 partitions on order.events for headroom Retention 24 GB/day × 7 days × 3 replicas ≈ 504 GB Outbox rows ~3 per order × 3M = 9M rows/day, deleted after 24 h Latency budget for "order confirmed" (p99) outbox → Kafka via CDC ~ 50 ms saga: ChargeCard → reply ~ 800 ms (payment provider dominates) saga: ReserveStock → reply ~ 60 ms OrderConfirmed → push to browser ~ 100 ms total ≈ ~1 s, so the UI shows "confirming" briefly, then flips

The numbers show where the design effort belongs. Throughput is trivial; a three-broker cluster is mostly idle. What matters is the correctness machinery: the outbox, idempotent consumers keyed by event id, per-step timeouts in the saga (if payment has not replied in 30 seconds, query the provider, then compensate), and a clear UX for the second during which the order is neither confirmed nor failed. During a flash sale the risk is not the broker but the inventory consumer's database contention on hot SKUs, which keying the ReserveStock commands by SKU (one command per order line) keeps serialised per SKU.

In the real world

  • Debezium is the standard open-source CDC engine on Kafka Connect, with connectors for PostgreSQL, MySQL, SQL Server, MongoDB and others, and a built-in outbox event router.
  • Confluent Schema Registry popularised registry-enforced compatibility for Avro, later adding Protobuf and JSON Schema. AWS Glue Schema Registry and Apicurio fill the same role.
  • Amazon EventBridge is a managed event bus with content-based routing rules, a schema registry that can infer schemas from traffic, and archive and replay.
  • Temporal (from the creators of Uber's Cadence), AWS Step Functions and Netflix Conductor are orchestration engines: they persist workflow state after every step so a saga survives process crashes and can wait for days.
  • CloudEvents, a CNCF specification, standardises the event envelope so that events can move between brokers, clouds and serverless platforms with the same metadata.
Interview angle

When to bring it up

When one action triggers several independent follow-ups (order placed, user signed up, video uploaded), or when a multi-service process needs to survive partial failures. State the pattern precisely: "The order service writes the order and an OrderPlaced outbox row in one transaction; Debezium publishes it; fulfilment is an orchestrated saga with compensations; notifications and analytics subscribe by choreography." It fits the notification system, ride-sharing and video platform cases.

Follow-ups to expect

  • How do you update the database and publish the event atomically? (Transactional outbox, polling or CDC.)
  • Choreography or orchestration for this flow, and why?
  • Payment succeeded but stock is gone. What happens? (Compensating refund, triggered by the saga.)
  • How do you change an event's schema without breaking consumers? (Registry, compatibility mode, additive changes with defaults, new event version for breaking changes.)
  • A user says their order is stuck. How do you find out where? (Correlation id, trace, saga state, DLQs.)

Red flags

  • Writing to the database and then publishing to Kafka in the request handler, with no answer for a crash in between.
  • Assuming events arrive exactly once and in order.
  • Choreographing a long, failure-prone business process with no owner, no timeouts and no compensation plan.
  • Publishing raw database change events as the public contract between teams.
