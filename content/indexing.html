Why it matters

A users table holds one billion rows of about 200 bytes each. Without an index, SELECT * FROM users WHERE id = 4217 reads all 200 GB to find one row. With a B-tree index the same query reads five pages (four index levels plus the row), 40 KB in total, and usually finds three of them already in memory.

Full scan 1,000,000,000 rows × 200 B = 200 GB at 2 GB/s sequential read (fast NVMe) ≈ 100 s, and the whole cache is evicted Index 5 page reads × 8 KB = 40 KB top 3 levels cached, 1 to 2 SSD reads at ~100 µs ≈ 0.1 to 0.2 ms

That is a factor of roughly half a million. An index is a separate data structure, kept in sync with the table on every write, that maps column values to row locations so the database can jump to matching rows instead of scanning. Every index makes some reads dramatically cheaper and every write somewhat more expensive. The two engine families in this chapter, B-trees and LSM trees, sit at different points on that trade-off, and choosing between them is choosing a database.

B-trees

The B-tree (Bayer and McCreight, 1972) is the default index in PostgreSQL, MySQL, Oracle, SQL Server and SQLite, and the storage structure of MongoDB's WiredTiger engine. Databases actually use the B+tree variant: all entries live in the leaves, inner pages hold only separator keys and child pointers, and leaves are linked to their neighbours so range scans can walk sideways.

Pages and fanout

Everything is organised in fixed-size pages, the unit the database reads and writes: 8 KB in PostgreSQL, 16 KB in InnoDB. An inner page holds hundreds of separator keys, each with a pointer to the child page covering the range between it and the next key. The number of children per page is the fanout. Because fanout is in the hundreds, the tree is extremely shallow: each extra level multiplies capacity by a few hundred.

How tall is the tree for a billion rows?

Assume each index entry costs about 24 bytes for a bigint key (key, pointer and per-entry overhead) and pages are 90% full. This snippet computes the height for different key types:

import math


def btree_levels(rows, page_bytes=8192, key_bytes=8, ptr_bytes=8, overhead=8, fill=0.9):
    """Levels of a B+tree: leaves hold one entry per row, inner pages one per child."""
    per_page = int(page_bytes * fill // (key_bytes + ptr_bytes + overhead))
    pages, levels = math.ceil(rows / per_page), 1          # leaf level
    sizes = [pages]
    while pages > 1:
        pages = math.ceil(pages / per_page)
        sizes.append(pages)
        levels += 1
    return per_page, levels, sizes[::-1]                   # root first


for key, label in [(8, "bigint"), (16, "uuid"), (40, "email ~40 B")]:
    fanout, levels, sizes = btree_levels(1_000_000_000, key_bytes=key)
    print(f"{label:12} fanout {fanout:3}  levels {levels}  pages per level {sizes}")

# bigint       fanout 307  levels 4  pages per level [1, 35, 10611, 3257329]
# uuid         fanout 230  levels 4  pages per level [1, 83, 18904, 4347827]
# email ~40 B  fanout 131  levels 5  pages per level [1, 4, 445, 58272, 7633588]

Two things follow. First, a billion rows is four levels; even ten billion would add only one more. Second, all the inner pages for the bigint index together are 1 + 35 + 10,611 pages, about 87 MB, which stays in the buffer cache. In practice a lookup costs one disk read for the leaf and one for the row. Wider keys lower the fanout, which is one reason to keep primary keys compact.

Writes: in-place updates and page splits

A B-tree updates pages in place. Inserting a key means descending to the right leaf, writing the entry into it, and logging the change to the write-ahead log first (see durability). When the leaf is full it splits: half its entries move to a new page and a separator is added to the parent, which can split in turn. The root splitting is the only way the tree grows taller, which is why it stays balanced.

Where inserts land matters. Sequential keys (an auto-increment id, a timestamp) always go to the rightmost leaf, which stays hot in cache and fills completely. Random keys such as UUIDv4 land on a random leaf each time: every insert may read a cold page, splits happen all over the tree, and pages end up around 70% full on average. On large tables that difference shows up as several times more I/O per insert. Data Modeling covers time-ordered ids that avoid it.

Clustered and secondary indexes

Where does the row itself live? Engines answer this in two ways, and the answer changes the cost of every secondary index.

  • A clustered index stores the full rows in its leaves, sorted by the index key. InnoDB always clusters on the primary key; SQL Server lets you choose one clustered index per table. Range scans on the primary key read rows that are physically adjacent, which is excellent for queries like "orders for customer 42" when the primary key is (customer_id, order_id). Every secondary index stores the primary key as its pointer, so a lookup by email does two tree descents. A long primary key bloats every secondary index.
  • In a heap-organised table (PostgreSQL, also Oracle by default) rows sit wherever there was space, and every index, including the primary key, stores the row's physical address (ctid). One descent and one heap read. The cost moves to updates: a new row version at a new address must be added to every index, unless PostgreSQL can do a HOT update (no indexed column changed and the new version fits on the same page).

Composite indexes and the leftmost prefix

A composite index on several columns sorts entries by the first column, then by the second within equal first values, and so on, exactly like a phone book sorted by last name, then first name. That ordering determines which queries it can serve. An index on (user_id, status, created_at):

Query predicateUses the index?Why
user_id = 42YesLeftmost column: one contiguous range of entries
user_id = 42 AND status = 'shipped'YesLeftmost two columns: a narrower contiguous range
user_id = 42 AND status = 'shipped' AND created_at > '2026-09-01'Yes, fullyEqualities first, one range last: still one contiguous range
user_id = 42 ORDER BY status, created_atYes, no sort stepEntries are already in that order
user_id = 42 AND created_at > '2026-09-01'PartlyFinds user 42's range, then must filter created_at across every status

created_at > '2026-09-01'Usually notThird column alone, same problem

This is the leftmost prefix rule. Some optimisers can skip scan an index whose first column has few distinct values (Oracle, MySQL 8.0, PostgreSQL 18), but do not design around it. The practical recipe for ordering columns: equality predicates first, then the column you sort by or filter with a range, last. Selectivity matters less than that rule; a range in the middle stops the following columns from narrowing the search.

Covering indexes

If an index contains every column a query needs, the database answers from the index alone and never touches the table: an index-only scan, and the index is covering for that query. CREATE INDEX ON orders (user_id, created_at) INCLUDE (total, status) (PostgreSQL 11+, SQL Server) stores total and status in the leaves without making them part of the sort key. A query listing a user's recent orders with their totals then reads a handful of adjacent leaf entries instead of one random table page per order. PostgreSQL also needs the page to be marked all-visible in its visibility map to skip the heap check, which a recent VACUUM provides.

What every index costs

  • Writes. Every insert, and every update of an indexed column, modifies every index on the table. A table with eight indexes does roughly nine B-tree modifications per insert.
  • Space and memory. Indexes compete with data for the buffer cache. An unused index is pure cost; PostgreSQL's pg_stat_user_indexes shows indexes with zero scans.
  • Low selectivity. An index on a boolean column that is true for 40% of rows is rarely used: fetching 40% of rows via random lookups is slower than one sequential scan, and the planner knows it. A partial index (WHERE status = 'pending') indexes only the rare, interesting rows.

LSM trees

A B-tree writes wherever the key belongs. With random keys and a table much larger than memory, that means random I/O and rewriting a whole 8 KB page to change 100 bytes. The log-structured merge tree (O'Neil et al., 1996), used by RocksDB, LevelDB, Cassandra, ScyllaDB, HBase and Bigtable, never modifies anything on disk. It buffers writes in memory and writes sorted, immutable files sequentially, then merges them in the background.

  1. Write. Append the change to the write-ahead log for durability, then insert it into the memtable, a sorted in-memory structure (usually a skip list). An update is just a newer entry for the same key; a delete writes a marker called a tombstone.
  2. Flush. When the memtable reaches its size limit (64 MB by default in RocksDB), it becomes immutable and is written out in key order as an SSTable (sorted string table): data blocks, a sparse index of the first key in each block, and a bloom filter of all its keys.
  3. Read. Look in the memtable, then in SSTables from newest to oldest; the first version found wins. For each file, the bloom filter answers "definitely not here" or "maybe here" from memory. Only on "maybe" does the engine read the sparse index and one data block.
  4. Compact. Background threads merge SSTables, keeping only the newest version of each key and discarding overwritten values. Tombstones can only be dropped when the merge reaches the oldest data, otherwise an older value would reappear.

Bloom filters make LSM reads affordable

Without filters, reading a key that does not exist would open every SSTable. A bloom filter per file costs about 10 bits per key and gives roughly a 1% false-positive rate: with 10 bits per key and 7 hash functions the rate is (1 - e-7/10)7 ≈ 0.82%. So a point lookup typically does one real disk read for the file that has the key, and a lookup for a missing key usually does none. Range scans get no help from bloom filters and must merge iterators over every level, which is the weakest spot of LSM engines.

Compaction strategies

How files are merged decides the engine's character.

Leveled (LevelDB, RocksDB default)

Each level is about 10 times larger than the one above, and within a level (from L1 down) files have non-overlapping key ranges. A read checks every L0 file, then at most one file per level below. Each byte gets rewritten roughly 10 times per level it passes through, so write amplification is high, but space overhead stays near 10%.

Size-tiered (Cassandra default)

When several files of similar size accumulate (4 by default), merge them into one bigger file. Each byte is rewritten only a few times, so writes are cheap. But a key may live in many overlapping files, so reads check more of them, and a big merge temporarily needs as much free disk as its inputs.

Time-window

For time-series data with TTLs, group files by time window and never merge across windows. Expired windows are dropped as whole files. Cassandra's TWCS is the standard example.

A tiny LSM tree

The whole idea fits in a few dozen lines. This version leaves out the WAL, bloom filters and levels, but shows memtable flushes, newest-first reads, tombstones and compaction:

import bisect

TOMBSTONE = object()


class TinyLSM:
    """Memtable + immutable sorted runs (SSTables) + full compaction. No WAL, no bloom filters."""

    def __init__(self, memtable_limit=4):
        self.memtable = {}            # real engines use a skip list; we sort at flush time
        self.sstables = []            # newest first; each is a sorted list of (key, value)
        self.limit = memtable_limit

    def put(self, key, value):
        self.memtable[key] = value
        if len(self.memtable) >= self.limit:
            self.flush()

    def delete(self, key):
        self.put(key, TOMBSTONE)      # deletes are writes too

    def flush(self):
        self.sstables.insert(0, sorted(self.memtable.items()))
        self.memtable = {}

    def get(self, key):
        if key in self.memtable:
            value = self.memtable[key]
            return None if value is TOMBSTONE else value
        for run in self.sstables:     # newest first: the first hit wins
            i = bisect.bisect_left(run, (key,))
            if i < len(run) and run[i][0] == key:
                return None if run[i][1] is TOMBSTONE else run[i][1]
        return None

    def compact(self):
        # merging everything into one bottom run is the only time tombstones can be dropped
        merged = {}
        for run in reversed(self.sstables):   # oldest first, newer values overwrite
            merged.update(run)
        live = sorted((k, v) for k, v in merged.items() if v is not TOMBSTONE)
        self.sstables = [live]


db = TinyLSM()
for i, user in enumerate(["asha", "ben", "kiran", "mei", "omar", "zoe", "asha", "ben"]):
    db.put(user, f"v{i}")
db.delete("kiran")
db.put("lena", "v9")
print(len(db.sstables), "sstables", db.get("asha"), db.get("kiran"), db.get("mei"))
db.flush()
rows = sum(len(r) for r in db.sstables)
db.compact()
print(rows, "rows on disk before compaction,", len(db.sstables[0]), "after")
# 2 sstables v6 None v3
# 10 rows on disk before compaction, 6 after

Ten rows were on disk because asha and ben were written twice and kiran has both a value and a tombstone. Compaction leaves six live keys. That gap between data written and data live is the space amplification a real engine keeps in check.

Read, write and space amplification

Three ratios describe any storage engine. Write amplification: bytes written to disk per byte the application wrote. Read amplification: disk reads per query. Space amplification: bytes on disk per byte of live data. The RUM conjecture states that you can optimise for two at the expense of the third, and the engines bear that out.

B-treeLSM, leveledLSM, size-tiered

Facebook's MyRocks (MySQL on RocksDB) is the clearest real comparison: for its user database it used about half the storage of compressed InnoDB and wrote far less to flash, while InnoDB kept the edge on read-heavy range queries. Neither family wins outright; pick from the workload.

Other index types

Hash indexes

A hash table from key to location: O(1) equality lookups, no ranges, no ordering, no prefix matching. Bitcask (Riak) keeps a hash of every key in memory pointing into append-only files. PostgreSQL has hash indexes, but a B-tree is almost always the better default.

Inverted indexes

Map each word to the list of documents containing it. They power full-text search and PostgreSQL's GIN indexes on arrays and JSONB. Covered in depth in Search & Inverted Indexes.

Geospatial indexes

Two-dimensional data does not sort well in one dimension. R-trees (PostGIS via GiST) group nearby rectangles; geohashes and S2 or H3 cells turn a location into a sortable id so an ordinary B-tree can answer "nearby" queries. See the ride-sharing case study.

Bitmap and columnar

Analytical stores keep one bitmap per value of low-cardinality columns and combine them with fast bitwise AND/OR, or store each column separately with min/max statistics per block so whole blocks can be skipped.

Worked example: indexing an orders table

An orders table has 500 million rows. The three hot queries are listed below with the index each one needs.

QueryRateIndexPages read
Order by id: WHERE id = ?8,000/sPrimary key~4, two uncached
A user's 20 latest orders with totals: WHERE user_id = ? ORDER BY created_at DESC LIMIT 203,000/s(user_id, created_at) INCLUDE (total, status)~4 to 5, index only
Pending orders older than 1 hour: WHERE status = 'pending' AND created_at < now() - interval '1 hour'1/minPartial: (created_at) WHERE status = 'pending'A few, index is tiny

Without the second index, each user-history request would find the user's orders some other way or sort them: a user with 300 orders means 300 random row fetches and a sort, 3,000 times a second. With it, the 20 entries sit next to each other in one or two leaf pages and carry everything the page shows. The partial index contains only the few thousand pending orders instead of 500 million entries, so it costs almost nothing to maintain. What we deliberately did not add: an index on status alone (low selectivity) and one on created_at alone (no hot query needs it). Each would slow every insert for no benefit.

In the real world

  • PostgreSQL defaults to B-tree, deduplicates repeated keys in B-tree leaves since version 13, and offers GIN, GiST, BRIN (block range summaries for huge, naturally ordered tables) and hash indexes.
  • MySQL InnoDB clusters every table on its primary key; if you do not define one, it picks a unique non-null index or invents a hidden 6-byte row id.
  • RocksDB is the embedded LSM engine behind MyRocks, CockroachDB (until its Go rewrite, Pebble, which keeps the same design), TiKV, Kafka Streams state stores and many more.
  • Cassandra and ScyllaDB let you choose compaction per table: size-tiered, leveled or time-window, which is the most direct way to tune an LSM for its workload.
  • MongoDB's WiredTiger uses B-trees with prefix and block compression, showing that the line between the families is blurring in both directions.
Interview angle

When to bring it up

In the data model step, after listing queries: name the index each hot query needs ("a composite index on (user_id, created_at) makes the timeline query a single range scan"). Bring up LSM vs B-tree when the workload is extremely write-heavy (logs, events, messages, metrics), as the reason a Cassandra-style store fits.

Follow-ups to expect

  • How many disk reads does a lookup in a billion-row table take? (Four levels, top ones cached, so one or two.)
  • Will this composite index serve that query? (Leftmost prefix, equality first, range last.)
  • Why are LSM writes faster, and what do reads pay for it? (Sequential writes; multiple files, bloom filters, compaction.)
  • Why might adding an index make the system slower? (Write cost, cache pressure, a bad plan choice.)
  • Why do random UUID primary keys hurt insert performance?

Red flags

  • "Index every column." Every index taxes every write.
  • Expecting an index on (a, b) to serve WHERE b = ?.
  • Claiming LSM trees are simply faster: they trade read and space cost for write throughput.
  • Forgetting that a B-tree index lookup still costs a table read unless the index covers the query.
